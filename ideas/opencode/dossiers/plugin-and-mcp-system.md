# Feature: Plugin & MCP System

## Purpose

OpenCode is extensible in two complementary ways that both end up presenting extra capability to the running agent as if it were native:

1. **Plugin API** — a JavaScript/TypeScript module (local file or npm package) that the host process loads at startup and that can register lifecycle hooks (intercepting chat, tool execution, permission prompts, session compaction, etc.), contribute custom tools, register an OAuth/API-key auth provider for a model provider, or install a workspace adapter. Plugins run in-process, share the host's network/filesystem access, and are the mechanism OpenCode itself uses to ship several built-in auth integrations (GitHub Copilot, OpenAI Codex, Azure, Cloudflare, xAI, Cerebras, Modal, GitLab, DigitalOcean, Snowflake Cortex, Poe).
2. **MCP (Model Context Protocol) client** — a way to connect to external, out-of-process servers (local subprocess over stdio, or a remote HTTP/SSE endpoint) that expose tools, prompts, and resources following the MCP specification. OpenCode discovers what each server offers, converts its tools into the same tool shape used internally, and adds them to the set of tools available to the agent, namespaced by server name.

Both mechanisms let a user or organization extend what the agent can do without modifying OpenCode's own source: plugins extend *host behavior* (hooks into the running program), MCP extends *tool inventory* (external processes/services offering callable capabilities).

## Behavior

### Plugin loading and lifecycle

- On startup, for each project instance, the host builds an ordered list of plugin factories:
  1. **Built-in plugins** — a fixed, hard-coded list of auth-provider plugins compiled into the binary (Copilot, Codex/OpenAI, Modal, GitLab, Poe, Cloudflare Workers AI, Cloudflare AI Gateway, Azure, DigitalOcean, Snowflake Cortex, xAI, Cerebras). These always run first and can be disabled wholesale by a runtime flag.
  2. **Configured plugins** — entries from the merged config's `plugin` array, each either a bare specifier string or a `[specifier, options]` tuple. A specifier is either an npm package identifier (any form `npm-package-arg` can parse: name, name@version, scoped, git URL, `npm:` alias) or a local path/`file://` URL.
  3. **Auto-discovered file plugins** — any `.ts`/`.js` file found directly under a `plugin/` or `plugins/` directory in the project is implicitly added to the plugin list (no config entry required).
- Every entry, factory function `(input, options) => Promise<Hooks>`, is invoked exactly once at boot, in the fixed order above (built-ins, then external plugins in config order). Sequential (not parallel) execution is deliberate so that hook registration/side effects have a deterministic order across runs.
- Each configured/npm plugin goes through a **resolve → entry-detect → compatibility-check → import** pipeline:
  - *Resolve*: npm specifiers are installed on demand (into a managed cache) if not already present; local specifiers are turned into a `file://` target (a directory needs a `package.json` or an `index.{ts,tsx,js,mjs,cjs}`; if neither exists, resolution fails).
  - *Entry-detect*: the resolved package/file is inspected for a "server" entrypoint — via a `package.json` `exports["./server"]` map entry, a `main` field, or (for local plugins) an index file. If it exposes no server entrypoint, the plugin is skipped (not an error) — this lets one npm package own both a server extension and, separately, a TUI-only extension or theme with no shared entrypoint.
  - *Compatibility*: npm plugins may declare `engines.opencode` (a semver range) in `package.json`; if the running version doesn't satisfy it, loading fails before import. File/local plugins skip this check (treated as local dev code). The check itself is skipped entirely when the running version isn't a valid/","major-0" semver (dev builds).
  - *Import*: the entrypoint module is dynamically imported. A failed import is permanent for the process (the runtime caches failed dynamic imports), except that file-plugin resolution failures that look like "missing package.json or index file" get one retry after the host finishes installing/waiting on dependencies.
- **Shape detection on the loaded module**: the default export may be either (a) an object `{ id?, server?, tui? }` where `server` is the plugin factory function ("v1 typed" shape) — exactly one of `server`/`tui` must be present, not both — or (b) a legacy shape where *any* exported value that is itself a function is treated as a factory (multiple named exports are all invoked; duplicate values are de-duplicated by reference). If the default export is present but exposes neither `id`, `server`, nor `tui`, the loader falls through to legacy-export detection.
- **Plugin identity**: a file/local plugin *must* export an `id` string (non-empty after trim), or loading fails with a type error. An npm plugin may omit `id`; the package's `package.json` `name` field is used instead (and must be present).
- Each plugin factory is invoked with a fixed `PluginInput`: an SDK client bound to the running server, the current `Project`, `directory`, `worktree`, a `serverUrl` getter, a `$` shell object (Bun's shell primitive, unavailable outside Bun), and an `experimental_workspace.register(type, adapter)` function that lets a plugin add a new workspace backend (interface only — workspace/control-plane behavior is documented elsewhere). Plugin-specific config (`options` element of the config tuple) is passed as the factory's second argument.
- The factory returns a `Hooks` object (may be `{}`). All returned `Hooks` objects across all loaded plugins are accumulated into one ordered list held for the life of the instance.
- Immediately after all plugins load, every hook's optional `config(cfg)` callback is invoked once with the resolved config; each call is individually try/caught and logged — one plugin's `config` hook throwing does not stop others from receiving the notification (verified: "config hooks are individually error-isolated").
- **Event hook**: every plugin's `event({ event })` callback (if present) is invoked, fire-and-forget, for every internal event published for that project directory (filtered by directory so a plugin only sees events for its own project instance).
- **Dispose**: when the instance's scope closes, every hook's `dispose()` is invoked (best-effort, errors logged and ignored); this runs in addition to and separately from the per-hook event unsubscribe.

### Hook invocation ("trigger")

- Hooks that follow the `(input, output) => Promise<void>` shape (the bulk of the API — `chat.message`, `chat.params`, `chat.headers`, `permission.ask`, `command.execute.before`, `tool.execute.before`, `tool.execute.after`, `tool.definition`, `shell.env`, `experimental.*`) are invoked through one generic "trigger" primitive: for a named hook, every loaded plugin's implementation of that hook name (if any) is called *in plugin load order*, each one awaited (synchronous or async implementations both work), and each hook receives the **same mutable `output` object**, so a later plugin observes mutations an earlier plugin already made to `output` — plugins compose by chaining mutation of shared state, not by returning replacement values.
- Hooks are triggered from many call sites across chat/session/tool/compaction code (not itself part of this feature's boundary): before/after tool execution, before running a slash command, when building system prompt text, when transforming outbound chat messages, when computing LLM request parameters/headers, when a permission prompt is about to be shown, when resolving the environment for a shell/PTY, and when computing a tool's LLM-facing description/parameters.
- A plugin's `tool` map (`Hooks.tool`) contributes custom tools directly into the tool registry alongside built-in tools and MCP-derived tools (see Interfaces).
- A plugin's `auth` (`AuthHook`) registers an OAuth or API-key method for a named model provider; a later-loaded plugin's `auth` for the **same** provider id overrides an earlier one (verified: a user plugin loaded after the built-ins replaces the built-in GitHub Copilot auth method entirely for that provider). Detail of how auth methods are consumed by login flows and credential storage belongs to the Auth/Credentials feature — only the registration contract is in scope here.
- A plugin's `provider` (`ProviderHook`) can supply/override the model list for one provider id, given a resolved `Auth` (again, only the registration contract is documented here; credential resolution is the Auth feature's concern).

### Plugin installation & config-file mutation (CLI-facing)

- A separate "install" workflow (used by an `opencode plugin add`/`install`-style command) resolves a plugin spec, inspects its manifest for which entrypoints it exposes (`server`, `tui`, or theme-only via a `oc-themes` package field), and idempotently patches the appropriate JSONC config file(s) (`opencode.json` for server plugins, a `tui` config file for TUI plugins) by inserting the plugin into the `plugin` array — preserving existing comments/formatting, deduping by package name (ignoring version) unless `force` is passed, and choosing global vs. project-local config location. Concurrent installs across processes are serialized with a file lock. This module is CLI/config tooling around the loader and is not itself part of the runtime hook system.
- A separate, on-disk "plugin metadata" store (`plugin-meta.json` under app state) tracks, per plugin id, load timestamps/count and a fingerprint (file mtime for local plugins; resolved npm version for npm plugins) so tooling can report "first seen / updated / unchanged" and cache theme file locations. This is bookkeeping, not behavior that affects hook execution.

### MCP client

- MCP servers are declared in config as a map from server name to a discriminated config object with `type: "local"` (spawn a subprocess: `command` argv, optional `cwd` resolved relative to the project directory, `environment` overrides merged over the host's own environment, optional `enabled`, optional `timeout`) or `type: "remote"` (a `url`, optional `headers`, optional `oauth` config or `oauth: false` to force it off, optional `enabled`, optional `timeout`).
- **Connecting local servers**: spawns the given command as a child process and speaks MCP over its stdio using a JSON-RPC-over-stdio transport. `stderr` is piped (not silently dropped). If the command is literally `opencode` (self-invocation, e.g. an MCP server implemented as another OpenCode instance), a `BUN_BE_BUN=1` env var is forced so it runs under the real Bun binary rather than opencode's own bundled runtime shim.
- **Connecting remote servers**: two transports are attempted **in order** — Streamable HTTP first, then legacy HTTP+SSE — using the same OAuth provider instance and headers for both; the first to connect successfully wins. If the first attempt fails with an auth-related error, the second transport is *still tried* unless the failure was itself an auth failure (`needs_auth`/`needs_client_registration`), in which case remaining transports are skipped and the auth status is surfaced immediately rather than retried.
- **Tool discovery**: after connecting, if the server's capabilities advertise `tools`, the client lists tools with cursor-based pagination (each page requested with the per-server timeout; a repeated cursor value or more than 1000 pages is treated as a protocol error and aborts discovery — the whole server is marked `failed`, its transport is closed). A server whose `tools/list` results fail strict schema validation specifically due to an unresolvable/duplicate `$ref` in an `outputSchema` (detected by matching known SDK error text) is retried once via a tolerant schema that ignores `outputSchema`, so unusual but otherwise-valid tool catalogs still load; any *other* `tools/list` failure (e.g., a transport error) fails the whole connection instead of falling back.
- **Prompts / resources / resource templates**: discovered the same paginated way, but only if the corresponding server capability is advertised; failures here are logged and treated as "no items" rather than failing the connection (unlike tool-list failures).
- **Tool exposure to the agent**: each discovered MCP tool is exposed under the id `sanitize(serverName) + "_" + sanitize(toolName)`, where `sanitize` replaces every character outside `[A-Za-z0-9_-]` with `_` (so `.` in either name becomes `_`, meaning two similarly-named tools/servers can collide after sanitization — first one registered wins, since results are merged into a plain object keyed by the sanitized id). Calling the tool proxies to `client.callTool`, using the JSON schema from the MCP tool definition, with `additionalProperties: false` forced onto the input schema; the call resets the timeout on protocol progress notifications. If the MCP result is marked `isError`, the concatenated text content becomes a thrown error (or a generic "MCP tool returned an error" if there's no text). If the result has no `content` array but *does* have `structuredContent`, the structured content is JSON-stringified into a synthetic text content block so downstream consumers always see text.
- Prompts and resources are exposed keyed as `serverName:promptName` / `serverName:resourceUri` respectively (using a lighter escaping — only `%` and `:` in the *server name* are percent-escaped — deliberately different from the tool-id sanitizer, since resource URIs must stay intact).
- **Live tool-list updates**: if a server supports `tools.listChanged`, incoming `notifications/tools/list_changed` triggers a fresh tool list fetch and republishes the client's cached definitions; until that notification arrives, the previously cached tool list is served (verified: tools() reuses cached definitions until a protocol notification arrives).
- **Server-initiated close**: if the underlying transport reports `onclose`, the server's clients/defs/instructions are dropped and its status flips to `failed` with `"Connection closed"`, and a `mcp.tools.changed` event is published for that server so subscribers (e.g. the TUI status sidebar) can refresh.
- **Server log forwarding**: MCP `notifications/message` (logging) notifications are mapped to the host's own log levels (`debug`→debug, `info`/`notice`→info, `warning`→warning, `error`/`critical`/`alert`/`emergency`→error) and logged with server name, logger, level, and data.
- **`roots` capability**: the client advertises the `roots` capability and responds to `roots/list` with a single root pointing at the current project directory (as a `file://` URL) — this lets a server discover which directory it's operating against without being told explicitly. `sampling`, `elicitation`, and `tasks` capabilities are explicitly not yet advertised (commented out with tracking issue links), i.e. those MCP features are not currently supported.
- **Disabled servers**: an entry with `enabled: false` is recorded in status as `disabled` and never opens a connection or subprocess at all (no probing, no process spawned).
- **Disconnect/reconnect**: disconnecting closes the live client, drops cached tools/instructions, and sets status to `disabled`; connecting again re-runs the full connect pipeline from the persisted config and can succeed even after the previous session was torn down (a fresh MCP session is established — not resumed).
- **Session recovery (remote/local, JSON-RPC transport-level behavior)**: if a session-bound POST request returns 404 (the remote server expired/lost that session), the transport reinitializes a session and retries the request once before giving up.
- **Process cleanup**: on instance shutdown, for every local (stdio) client with a live child process, its process tree (walked via `pgrep -P`, recursively, POSIX only) is sent `SIGTERM` before the MCP client itself is closed, to avoid orphaned grandchild processes (e.g., npx-spawned actual server binaries).
- **Aggregated status**: `status()` returns one of `connected | disabled | failed(error) | needs_auth | needs_client_registration(error)` per configured server name, always including every server currently in config even if it never successfully connected.

### MCP OAuth

- For `type: "remote"` servers with OAuth not explicitly disabled, an `OAuthClientProvider` implementation backs the MCP SDK's OAuth flow, persisting per-server token/client-registration state to a dedicated `mcp-auth.json` file (mode 0600) under the app's data directory, guarded by a cross-process file lock. Stored entries are validated against the server's URL before being reused (`getForUrl`) so that pointing an existing server name at a different URL doesn't leak credentials meant for the old URL.
- If no static `clientId` is configured, RFC 7591 Dynamic Client Registration is attempted automatically; the resulting client id/secret (and secret expiry) are persisted. If the authorization server rejects dynamic registration, the server is marked `needs_client_registration` with guidance to configure `clientId` manually.
- **Two-phase auth start**: `startAuth` first tries connecting with a *pending* (in-memory only) OAuth provider; if that unexpectedly succeeds without needing user interaction (e.g., already-valid stored... — actually a fresh provider — succeeds via some non-interactive grant), the resulting tokens are committed immediately and the server is connected with no browser step. If the SDK instead throws `UnauthorizedError` and captured a redirect URL, that URL becomes the `authorizationUrl` returned to the caller and the half-open transport is cached (keyed by server name) awaiting `finishAuth`.
- **Interactive `authenticate()`**: starts the local OAuth callback HTTP server (bound to `127.0.0.1`, default port 19876, path `/mcp/oauth/callback`, both overridable per-server via `redirectUri` or the `callbackPort` shorthand), generates a random 32-byte hex `state`, opens the system browser to the authorization URL, and awaits the callback. The callback handler validates the `state` parameter is present and matches a pending request (rejecting with a CSRF-flavored error otherwise), extracts the `code`, and resolves the waiting promise; the OAuth callback page is rendered as a small HTML success/error page. A 5-minute timeout auto-rejects an abandoned flow. The callback server auto-stops once no auths are pending, and is reused/restarted if a different port/path is requested mid-run.
- `finishAuth(name, code)` completes the pending transport's `finishAuth`, commits the pending provider's tokens/client info into the persistent store, clears the code verifier, and only then runs the normal connect pipeline (tool discovery, watch registration) using the newly authorized transport.
- `removeAuth` deletes the stored entry and cancels any in-flight callback wait for that server name.
- `getAuthStatus` reports `not_authenticated | expired | authenticated` by comparing a stored token's `expiresAt` against the current time; it does not itself refresh tokens (refresh, when needed, happens through the SDK's own token/refresh plumbing driven by `tokens()`/`saveTokens()` on the provider).

## Business rules & edge cases

- Built-in plugins load before external/configured ones, and file/npm plugins load in the config's own order; a later plugin's `auth` for the same provider id **wins** (last-registered replaces earlier registrations for that provider — demonstrated for auth, and true generally of anything keyed by an id in a "later wins" merge).
- A plugin package that was previously shipped separately (`opencode-openai-codex-auth`, `opencode-copilot-auth`) and has since been absorbed into the built-in set is silently skipped if still referenced in config — treated as neither an error nor a load.
- A plugin resolving to a package/file with **no** matching entrypoint for the requested kind (`server` vs `tui`) is *not* an error; it's reported as "missing" so callers (e.g., install tooling) can still read package metadata such as theme declarations.
- A plugin whose default export tries to declare **both** `server` and `tui` is rejected outright (type error) — a module must pick one.
- npm package resolution is sandboxed: a resolved entry path must stay inside the resolved plugin package directory; an entry pointing outside it throws rather than being followed (path-escape protection).
- `oc-themes` package metadata entries must be relative paths (not absolute, not `file://`) and must resolve inside the plugin directory; violations throw.
- Compatibility gating via `engines.opencode` is skipped for pre-1.0/invalid running versions (dev builds) and for local/file plugins (assumed to always be compatible, since it's project-local code).
- MCP tool/prompt/resource pagination hard-caps at 1000 pages and rejects a cursor value repeated across pages — both are treated as a protocol/server bug, not a soft warning; tools specifically fail the whole connection, prompts/resources/templates just yield nothing for that call.
- MCP tool discovery output-schema fallback is deliberately narrow: only errors whose message matches reference/schema-resolution wording trigger the tolerant retry; a generic transport or server error is not retried and fails the connection.
- MCP OAuth token/client-info reuse is scoped to an exact stored `serverUrl` match — changing a server's URL under the same config name invalidates cached credentials rather than silently reusing them against the new endpoint.
- MCP OAuth callback state validation is mandatory: a callback with no `state`, an unrecognized `state`, or a mismatched `state` against what was persisted for that server is rejected as a possible CSRF attempt (separately checked both in the local callback HTTP handler and again in `authenticate()` after the promise resolves, comparing the stored `oauthState`).
- Disabled MCP servers (`enabled: false`) never spawn a process or open a socket at all — cost of a disabled entry is zero beyond bookkeeping.
- One MCP server failing to connect, timing out, or failing tool discovery never prevents other configured servers from connecting; each server's status/tools are independent (verified explicitly).
- Local MCP server connection timeouts (default 30s, configurable per-server) actually terminate the spawned process (and its descendant process tree) rather than merely abandoning the read.
- Remote MCP connection timeouts abort *both* transport attempts' in-flight HTTP requests, not just the promise wrapper around them.
- Sanitized tool ids can collide across different raw names/servers (e.g., `my.special-server` + `tool.b` sanitizes the same as a different raw combination); the implementation does not detect or warn about such collisions — later entries in iteration order simply overwrite earlier ones in the returned map.

## Workflows & states

**Plugin load (per project instance, once at boot):**
1. Gather built-in plugin factories (unless disabled by flag) → gather configured `plugin` specs (unless a "pure"/no-external-plugins flag is set) → wait for any pending dependency install if there are external plugins to load.
2. For each configured spec, resolve target → detect entrypoint → check compatibility → dynamically import (with one retry only for a specific "file plugin setup not ready yet" failure class).
3. Invoke each successfully loaded factory sequentially, in the built-in-then-config order; collect returned `Hooks` objects into one ordered list.
4. Invoke `config(cfg)` on every hook once, independently error-isolated.
5. Subscribe once to the internal event bus; forward every event (for this project directory) to every hook's `event()` callback.
6. On instance teardown: unsubscribe from events, then call every hook's `dispose()` (best-effort).

**MCP server connection states** (`Status` union): `connected` (client live, tools cached) → can transition to `failed(error)` (spontaneous disconnect, timeout, discovery error) or back to `disabled` (explicit `disconnect()`); `disabled` (never connected, or disconnected) → `connected` via `connect()`/`add()`; a remote server needing auth first surfaces as `needs_auth` (or `needs_client_registration` if dynamic registration isn't supported) before any `authenticate()`/`finishAuth()` call can move it to `connected`.

**MCP OAuth flow:** `startAuth` (try silent/non-interactive connect; on `UnauthorizedError`, capture the authorization URL and cache the half-open transport) → `authenticate` (start local callback server, open system browser, await redirected `code` guarded by `state`) → `finishAuth` (complete the SDK's token exchange, persist tokens/client info, run the normal connect+discovery pipeline) → server reaches `connected`. `removeAuth` can be called at any point to wipe stored credentials and cancel a pending callback wait.

## Data

- **Plugin config** (`opencode.json` `plugin` field): array of `string | [string, Record<string, unknown>]`. Origins (which file declared each entry, and whether it's "global" or project-"local" scope) are tracked separately from the plain spec list so config-writing tools know where to patch and duplicate specs (same npm package name, or identical file URL) can be deduplicated with "last one wins" semantics while preserving relative order otherwise.
- **Plugin runtime metadata** (`plugin-meta.json`, app state dir): keyed by plugin id → `{ source: file|npm, spec, target, requested?, version?, modified?, first_time, last_time, time_changed, load_count, fingerprint, themes? }`. Not consumed by hook execution; used for install/status tooling.
- **MCP server config** (`opencode.json` `mcp` field): map of server name → `{ type: "local", command: string[], cwd?, environment?, enabled?, timeout? }` or `{ type: "remote", url, enabled?, headers?, oauth?: {clientId?, clientSecret?, scope?, callbackPort?, redirectUri?} | false, timeout? }`. A global `experimental.mcp_timeout` config value is the fallback per-request timeout when a server doesn't set its own.
- **MCP OAuth store** (`mcp-auth.json`, app data dir, file mode 0600): map of server name → `{ tokens?: {accessToken, refreshToken?, expiresAt?, scope?}, clientInfo?: {clientId, clientSecret?, clientIdIssuedAt?, clientSecretExpiresAt?}, codeVerifier?, oauthState?, serverUrl? }`.
- **MCP resource shape**: `{ name, uri, description?, mimeType?, client }` (client = owning server name).
- **Events published**: `mcp.tools.changed { server }` (tool list changed or server disconnected — subscribers should re-fetch), `mcp.browser.open.failed { mcpName, url }` (system browser couldn't be launched for an OAuth authorization URL), `plugin.added { id }` (an internal/v2-style plugin registration — see Open Questions on scope).

## Interfaces

- **Tool System** (documented elsewhere): the tool registry merges built-in tools, plugin-contributed tools (`Hooks.tool`, each converted from a Zod-like schema shape into the JSON Schema the LLM API expects), and MCP-discovered tools (converted via a dedicated adapter that also handles the MCP call/response translation) into one flat, permission-filtered tool list per request. Only the contract at that merge boundary is in scope here.
- **Permission System** (documented elsewhere): `Hooks["permission.ask"]` and `Hooks["tool.execute.before"]`/`"tool.execute.after"` are invocation points a plugin can use to intervene in permission prompts and tool calls; how those results actually gate execution is the Permission System's concern.
- **Auth/Credentials/Accounts** (documented elsewhere): `Hooks.auth` (`AuthHook`, OAuth/API-key method registration per provider id) and `Hooks.provider` (`ProviderHook`, per-provider model list override) are the plugin-facing registration surface; credential storage, refresh, and how a registered auth method is actually invoked during login live in that feature. The built-in provider auth plugins (GitHub Copilot, OpenAI Codex, Azure, Cloudflare, xAI, Cerebras, Modal, GitLab, DigitalOcean, Snowflake Cortex, Poe) are themselves implemented using this same plugin mechanism but their internal OAuth/device-code/token-refresh logic belongs to that feature.
- **Config & Data Contracts** (documented elsewhere): both the `plugin` array and the `mcp` map are config schema fields; this dossier covers how they're consumed/loaded, not the general config file merge/resolution rules.
- **Codemode** (documented elsewhere): a `code-mode` tool describes the merged tool catalog (including sanitized MCP server names) to support a "write code that calls tools" execution mode; only the fact that MCP/plugin tools appear in that catalog is in scope here.
- **Workspace/control-plane** (not otherwise covered by this task): `PluginInput.experimental_workspace.register(type, adapter)` lets a plugin add a new workspace backend (`configure`/`create`/`remove`/`target` lifecycle); the workspace subsystem that consumes registered adapters is out of scope, only the registration call is documented here.
- **TUI plugin API** (`packages/plugin/src/tui.ts`, `packages/opencode/src/plugin/tui/*`): a parallel, separately-loaded plugin kind (`tui` entrypoint instead of `server`) that extends the terminal UI (routes, dialogs, slots, keymaps, themes, sound packs). It shares the loader/resolve/entrypoint machinery described above (a package can expose `server`, `tui`, both as separate entrypoints, or theme-only) but its hook surface and runtime are UI-specific and not detailed further here since the task scope is the server-side hook/tool/auth/MCP surface.

## Error handling

- Plugin factory throwing during load: caught, logged with the plugin's spec/path, and that plugin simply contributes no hooks — other plugins still load. Built-in plugin failures are similarly isolated (logged, that one built-in contributes nothing).
- Plugin `config()` hook throwing: caught and logged per-hook; does not stop notifying remaining hooks.
- Plugin `event()` / `dispose()` hook throwing: caught and logged; does not stop remaining hooks' event/dispose calls.
- Install/compatibility/entry failures each surface a distinct, user-facing toast/event message (missing package, version incompatibility, entrypoint missing, import failure) rather than one generic "plugin failed" message.
- MCP connect failures produce a specific `Status` (`failed` with message, `needs_auth`, or `needs_client_registration`) rather than throwing out of the connect path; the caller (session/tool registry) always gets *some* status per configured server.
- MCP tool-list discovery failure (after the output-schema tolerant retry doesn't apply) fails the entire server connection (closes the just-opened client) rather than exposing a server with partial/no tools silently.
- MCP prompt/resource/resource-template discovery failures are logged as warnings and treated as empty results — non-fatal to the connection.
- MCP local-server or remote-server connect timeouts actively tear down the underlying process/HTTP requests, not just abandon the promise (avoids leaked child processes / hung sockets).
- MCP OAuth: missing/invalid/mismatched `state` on the callback is rejected with a CSRF-flavored error page and does not resolve any pending flow; a stalled flow times out after 5 minutes and rejects the waiting caller.
- MCP OAuth browser-launch failure publishes `mcp.browser.open.failed` (with the URL) rather than failing the whole auth attempt, so a caller can show the URL for the user to open manually.

## Non-functional observations

- Plugin execution is intentionally **sequential**, not parallel, both at load time and at hook-trigger time — the code comments call this out explicitly as required for deterministic hook ordering across runs, which is a meaningful constraint for a reimplementation (do not parallelize hook dispatch for a latency win).
- MCP server connections *are* established concurrently across servers ("unbounded" concurrency) — unlike plugin loading, one slow/misbehaving MCP server does not delay others from becoming available.
- MCP resource safety: a transport is only "owned" by the caller once `connect()` succeeds; on any failure during connect, the transport is explicitly closed to avoid leaking sockets/subprocesses.
- Descendant-process cleanup for local MCP servers only really applies on POSIX (`pgrep` is used); the code comments acknowledge this is a best-effort, platform-limited cleanup.
- The v1 plugin auth-file store (`mcp-auth.json`) and plugin metadata store (`plugin-meta.json`) both use file locks for cross-process safety, since multiple OpenCode processes (server + CLI invocations) may touch them concurrently.
- Plugin/MCP config resolution happens per "instance" (a project+directory pairing), so the same plugin/MCP config can be independently instantiated (separate connections, separate hook lists) for multiple concurrently open projects in one running host.

## Acceptance criteria — 5-8 Given/When/Then statements

1. **Given** a project config lists a plugin twice under different version specifiers pointing at the same npm package, **when** plugins load, **then** exactly one instance loads (the later config entry wins) and the earlier entry is dropped rather than both being loaded.
2. **Given** two plugins both register an `auth` hook for the same provider id, and the second is loaded after the first, **when** authentication methods for that provider are queried, **then** the methods from the second (later-loaded) plugin are what's returned — the first is fully replaced, not merged.
3. **Given** a `local` MCP server config with a `timeout` shorter than the server's actual startup time, **when** the client attempts to connect, **then** the server's status becomes `failed`, the spawned process (and any subprocess it spawned) is actually terminated, not merely abandoned.
4. **Given** a remote MCP server configured with OAuth not disabled and no stored credentials, **when** a connection is attempted, **then** the server's status becomes `needs_auth` (or `needs_client_registration` if the server doesn't support dynamic client registration) instead of `failed`, and a subsequent interactive authenticate flow can bring it to `connected`.
5. **Given** an MCP server advertises `tools.listChanged` and later sends a tool-list-changed notification, **when** the agent next asks for the current tool set, **then** it receives the refreshed tool list; before that notification, repeated queries return the same cached tool list even if the server's underlying tools have changed.
6. **Given** an OAuth callback arrives with a `state` value that doesn't match the one recorded for the in-flight authorization for that MCP server name, **when** the callback is processed, **then** the flow is rejected as a CSRF attempt and no tokens are persisted.
7. **Given** one of several configured MCP servers fails to connect or fails tool discovery, **when** the tool set for the agent is computed, **then** tools from the other, successfully connected servers are still available — the failure of one server produces only a `failed` status entry for that server, not a global error.
8. **Given** a plugin package's `package.json` declares an `engines.opencode` semver range that the running version does not satisfy, **when** that plugin is loaded from npm, **then** it is skipped with a compatibility error surfaced to the user, and no other configured plugin's loading is affected.

## Confidence & open questions

- **High confidence** on: the V1 plugin loader/resolver/entrypoint pipeline (`packages/opencode/src/plugin/{index,loader,shared,install,meta}.ts`), the public `Hooks`/`tool`/`AuthHook`/`ProviderHook`/`WorkspaceAdapter` contract (`packages/plugin/src/{index,tool}.ts`), and the MCP client end-to-end (`packages/opencode/src/mcp/*`) — all cross-checked against a large, behavior-specific test suite (`packages/opencode/test/mcp/*`, `packages/opencode/test/plugin/*`, `packages/opencode/test/server/httpapi-mcp*.test.ts`, `packages/opencode/test/cli/mcp-add.test.ts`).
- **Scope clarification needed**: `packages/core/src/plugin/*` (including `plugin/provider/*`, `host.ts`, `internal.ts`) and `packages/plugin/src/v2/*` are **not** the same subsystem as the user-facing plugin API documented above, despite sharing the word "plugin." They implement an in-progress, internal "PluginV2" composition/registration architecture (`ctx.catalog.transform`, `ctx.agent.transform`, `ctx.aisdk.sdk/language` runtime hooks, etc.) that OpenCode uses to wire its *own* built-in features — provider catalogs (one file per LLM provider under `core/src/plugin/provider/`), agent/command/skill config projection, and models.dev integration — as composable, orderable, disposable registrations. Its own design doc (`packages/plugin/src/v2/effect/PLAN.md`) explicitly states it is a target design, not current-state documentation, and that a public embedding API and Promise wrapper are still deferred. At the pinned commit it does not appear to be reachable by an external, config-loaded plugin author (no loader wires `plugin_origins` into `PluginV2.Service.add`); it is exercised only by internal callers (`packages/core/src/plugin/internal.ts`'s hard-coded boot list). **Recommendation for the reimplementing team**: build to the V1 contract described in this dossier as the actual current plugin API; treat V2 as a roadmap item to watch for in a future pinned commit, not something to reimplement now.
- **Open question**: the exact precedence/merge rule when a plugin `tool` id collides with a built-in tool id, or when an MCP-sanitized tool id collides with a plugin tool id, was not pinned down beyond "the tool registry is a flat map assembled in a fixed order" (built-ins, then plugin tools, then MCP tools, per `tool/registry.ts`) — later entries in that assembly order appear to win on id collision, but no test explicitly exercises a plugin-vs-MCP or plugin-vs-builtin id collision.
- **Open question**: the "5 seconds" default MCP request timeout documented in the config schema's field description (`core/src/v1/config/mcp.ts`: "Defaults to 5000 (5 seconds) if not specified") does not match the constant actually used for connection timeout in `packages/opencode/src/mcp/index.ts` (`DEFAULT_TIMEOUT = 30_000`, i.e. 30 seconds) — this looks like stale documentation in the schema rather than a real 5s default; a reimplementation should follow the 30s code behavior for connection timeout and treat the request-timeout default (`experimental.mcp_timeout`) as unset/undefined unless a server or that experimental config value sets one.
- **Not verified**: token refresh behavior for expired MCP OAuth tokens (whether/when a refresh_token grant is attempted automatically vs. requiring the user to re-run `authenticate`) — the code wires `tokens()`/`saveTokens()` into the underlying MCP SDK's own OAuth machinery, so the refresh trigger point lives in that third-party SDK rather than in OpenCode's own code, and was not traced further.
