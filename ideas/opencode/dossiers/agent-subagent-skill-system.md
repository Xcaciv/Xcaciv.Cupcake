# Feature: Agent, Subagent & Skill System

## Purpose

Lets the coding-agent product be reconfigured at three levels without changing the runtime: (1) **agents** — named personas that pair a system prompt, a default model, and a permission policy, selectable as the "main" persona driving a conversation or as a "subagent" persona dispatched to do a bounded piece of work; (2) **subagent dispatch** — a way for the currently active agent to hand off a self-contained task to a fresh, isolated conversation running under a different (usually more restricted) persona, and get a single text result back; (3) **skills** — reusable, on-demand instruction bundles (a short manifest plus free-form guidance and optional companion files) that any agent can pull into its own context mid-conversation when the task at hand matches the skill's stated purpose, without paying the context cost of every skill all the time.

## Behavior

### Agents
- An agent is a record of: display name, one-line description ("when to use"), a `mode` (`primary` — usable as the main driver of a conversation; `subagent` — only dispatchable as a sub-task; `all` — either), an optional pinned model (provider+model id) and variant, optional temperature/top_p, an optional system-prompt override, an optional max-iteration ("steps") cap, an optional UI color, a `hidden` flag (excluded from pickers), and a **permission ruleset** (see the Permission System dossier for evaluation semantics; this dossier only describes how each agent's ruleset is assembled).
- Seven built-in agents ship out of the box: `build` (primary, full access), `plan` (primary, read-mostly), `general` (subagent, general-purpose), `explore` (subagent, read-only search specialist), and three hidden internal-use primaries — `compaction`, `title`, `summary` — used by the conversation runtime for its own housekeeping (summarizing context, naming a session, writing a PR-style recap), not meant to be user-selected.
- Every built-in agent's ruleset is layered from three pieces, merged in order (later layers override earlier ones on conflicting rules): a shared baseline (allow everything by default; ask before touching files outside the project; deny the "doom loop" and interactive-question actions by default; read access to `*.env*` files asks first), the agent's own overrides, then the user's global permission config from settings. `build` additionally allows the interactive-question action and entering plan mode. `plan` additionally allows the question action and exiting plan mode, denies dispatching the `general` subagent, denies all edits except to a `.opencode/plans/*.md` path and a corresponding path under the app's data directory, and allows external-directory access under a `plans` data folder. `general` additionally denies the "write a todo list" action. `explore` denies everything by default and re-allows only search/read/fetch actions (grep, glob, list, bash, webfetch, websearch, read).
- Every agent's ruleset unconditionally allows external access to a small set of internal working directories (a temp scratch directory, and every discovered skill's own directory) regardless of user config, unless the user explicitly denies that exact path pattern.
- Custom agents are declared in project or global config, either inline (a config-file map keyed by agent name) or as a Markdown file with YAML frontmatter under an `agent/`, `agents/`, `mode/`, or `modes/` directory (searched in every configured config directory, including ancestor directories up to the project root). A file under `mode/`/`modes/` is forced to `mode: primary`; a file under `agent/`/`agents/` keeps whatever `mode` its frontmatter declares (default `all`). The Markdown body becomes the agent's system prompt.
- Declaring a custom agent with the same name as a built-in one *patches* the built-in (overriding only the fields it sets, merging its permission rules on top) rather than replacing it wholesale; declaring a new name creates a new agent defaulting to `mode: all` and the baseline-plus-user permission ruleset. Setting `disable: true` on any agent (built-in or custom) removes it entirely from the catalog for that run.
- A legacy `tools: { <toolname>: boolean }` map is still accepted on an agent definition for backward compatibility and is translated into `permission` rules at load time (`write`/`edit`/`patch` all collapse onto the single `edit` permission action); any unrecognized top-level key on an agent definition is preserved verbatim under an `options` bag rather than rejected, so provider- or tool-specific extensions don't break loading.
- The agent used to drive a given conversation turn is supplied per-turn (by the caller — CLI flag, TUI picker, or API request) as a plain agent-name string; if omitted, the session falls back to the previously-used agent for that conversation, and a brand-new conversation falls back to a configurable "default agent" (or the first non-hidden primary agent, conventionally `build`) if none is configured. Switching agents is simply supplying a different name on the next turn — there is no separate "mode" mutation, and the choice (plus whatever model went with it) is persisted onto the conversation so later turns (and internal steps like compaction) know which persona/model produced which message.
- Requesting a `default_agent` that doesn't exist, that is a subagent-only agent, or that is hidden is a hard configuration error at startup.
- A CLI-driven "generate an agent" flow exists: given a natural-language description (and optionally a specific model), an LLM call produces a suggested identifier, a "when to use" description, and a full system prompt; the operator then picks which permission categories to allow and whether the agent is primary/subagent/all, and the tool writes a new Markdown agent definition file (global or project-scoped) from the result.

### Subagent dispatch ("Task")
- Any agent whose permissions allow it can invoke a dispatch action that: takes a short task description, a free-form task prompt, and the name of the target agent to run as; optionally an existing prior dispatch's id to resume that same isolated conversation instead of starting fresh; and optionally a background flag (gated behind an experimental toggle) to run asynchronously and be notified on completion rather than blocking.
- Dispatch first checks a nesting-depth limit: it walks the calling conversation's parent chain, and if the count of ancestors already meets or exceeds a configurable limit (default: 1), the dispatch is rejected — meaning by default a subagent conversation cannot itself dispatch a further subagent; only a top-level ("no parent") conversation may. Raising the limit in config allows deeper nesting.
- Dispatch then asks for permission (permission action keyed by the target agent's name as the pattern) unless the call is internally marked as pre-approved, then resolves the named target agent — failing with an explicit "unknown agent type" error if it doesn't exist.
- A fresh child conversation is created (or an existing one reopened, if a resume-id was given) whose title embeds the task description and target agent name, and whose own permission ruleset is derived as: every deny rule and every external-directory rule inherited from the parent conversation's effective permission (acting as a hard ceiling the child cannot escape, regardless of the child agent's own more permissive rules), plus the child agent's own permission ruleset layered on top, plus a hard deny on "write a todo list" and on further dispatch unless the child agent's own ruleset explicitly allows those. Put differently: the parent's own *restrictions* constrain the child, but the parent's *allowances* do not leak into the child — the child's capability ceiling is its own agent definition, gated only by what the parent explicitly denied.
- The child conversation runs with the target agent's pinned model if it has one, otherwise inheriting the dispatching message's model; it starts with a fresh context unless resuming a prior dispatch id, in which case it continues that child conversation's own history.
- On completion, the single last text response from the child conversation is returned to the caller as the dispatch's result, wrapped with a small amount of state metadata (a task id reusable to resume the same child conversation later, running/completed/error status). If the child's final turn errored, or its last tool call errored, the dispatch itself reports failure with that error surfaced. The child conversation's full transcript (its own tool calls, intermediate reasoning) is never shown to the caller or the end user — only that one final message.
- In background mode, the dispatch call returns immediately with a "started" acknowledgment; when the child conversation finishes, its result is injected asynchronously into the parent conversation as a synthetic follow-up message rather than being returned from the original call.
- A user can also request a specific subagent directly by writing an `@agentname` token in their message; if the token resolves to a known agent (and not to an existing file path, which takes precedence), it is rendered as a distinct reference in the message and the currently-active agent is nudged with an appended instruction to formulate a task and invoke the dispatch action against that named agent — the mention does not bypass the active agent's own dispatch permission gate.

### Skills
- A skill is: a name, an optional one-line description, an optional flag marking it eligible for use as a slash-style command (forward-looking; not wired into the shipped skill-invocation tool), the filesystem location of its manifest, and its full instructional body text.
- Skills are discovered, at conversation start, from several sources, layered together into one catalog keyed by name (a later-discovered duplicate name logs a warning and is dropped, keeping the first): a single built-in "how to configure this product" skill (registered first, so any on-disk skill with the same name silently takes precedence); every project's own skill directories (`.opencode/skill/**/SKILL.md` and `.opencode/skills/**/SKILL.md`, searched in every configured config directory); external-tool-compatible directories (`~/.claude/skills/**/SKILL.md` and any `.claude/skills/**/SKILL.md` found walking up from the working directory to the project root, unless disabled), and an equivalent `.agents/skills/` convention (not user-disableable, always scanned alongside); any additional local directories or remote URLs listed explicitly in config (remote skill "packs" are described by a small JSON index of named skill bundles and their file lists, downloaded and cached locally, with version-tagged bundles refreshed via an atomic stage-then-swap so a failed download never corrupts the previous cached copy).
- Each manifest is a Markdown file with YAML frontmatter (`name`, `description`) whose body is the skill's instructional content; a manifest with no parseable frontmatter, or frontmatter missing a `name`, is silently skipped (not an error).
- A skill without a `description` is loaded (and its base directory is still trusted as an allowed external-access path) but is never advertised to the model — it's invisible in the catalog surfaced to the agent and doesn't appear in the "no skills available" vs. populated summary rendering.
- Per-turn, the set of skills advertised to the model is filtered by permission: a skill is hidden from the agent's system-prompt listing if that agent's ruleset would deny the "invoke a skill" action for that skill's specific name; if the agent denies the action outright for everything, no skill catalog section is added to the system prompt at all.
- The advertised catalog is rendered into the system prompt as a labeled list (name + description) instructing the model to invoke a dedicated "load skill" action by name when a task matches one of the descriptions.
- Invoking that action: re-checks permission for that specific skill name (asking the operator if required), then returns the skill's full instructional body as a formatted block, along with the skill's base directory path and a sampled listing (capped, e.g. at 10 entries) of the other files living alongside the manifest (scripts, reference docs, templates) so the model knows what it can additionally read from that directory — those companion files are not embedded automatically, only listed.

## Business rules & edge cases

- Custom-agent config that names a built-in agent **merges**, it never fully replaces; an unset field on the override keeps the built-in's existing value, but permission rules always accumulate (built-in defaults, then override, then user-global) rather than one replacing another wholesale.
- A whitelisted "truncated tool output" scratch-directory pattern is force-allowed for external-directory access on every agent unless the operator has *explicitly* denied that exact pattern (a wildcard deny on all external directories does not implicitly catch it) — this exists purely so agents can still read their own oversized tool output back from disk even under a locked-down external-access policy.
- Skill directories and configured project "reference" directories are likewise auto-whitelisted for external-directory access on every agent, again overridable only by an explicit deny of the exact whitelisted pattern.
- `plan` mode denies dispatching the `general` subagent by default but explicitly still allows dispatching any *other* subagent (including custom ones) — the deny is specific to the one built-in name, not a blanket "no subagents in plan mode" rule, and a user can re-allow `general` via their own permission config.
- **Discrepancy vs. product documentation**: product-facing docs describe `plan` mode as "asking permission before every bash command." At the agent-definition level this is not the case — `plan`'s ruleset does not touch the bash action at all, so bash inherits the shared baseline's "allow" just as it does for `build`. Both agents are defined and behave identically for bash gating at this layer (confirmed by both the shipped test suite, which asserts `build`'s bash permission is `allow` and never asserts anything different for `plan`, and by direct reading of `plan`'s permission overrides, which cover only edits, the question/plan-enter/exit actions, the `general` subagent, and a scoped external-directory allowance). This corroborates the same finding already reached independently by the Permission System dossier.
- A subagent's *own* permission ruleset is always the ceiling on what it itself can do — a parent's more permissive rules are never inherited by the child, only the parent's restrictions (deny rules, external-directory rules) are, and those act as an additional ceiling on top of the child's own ruleset, not a replacement for it. A subagent can therefore be granted a capability (e.g. edits) that its dispatching parent agent does not itself have.
- A subagent conversation is, by default, one level deep only: it cannot dispatch a further subagent unless the operator raises the configured nesting-depth limit above its default of 1.
- Background-mode dispatch is gated behind an experimental environment toggle and is refused outright if that toggle is off.
- The internal `compaction`, `title`, and `summary` agents deny *every* permission action by design (they exist purely to run one constrained, tool-free LLM call each and must never be able to call tools).
- Requesting a nonexistent agent name (as the driving agent for a turn, or as a dispatch target) fails with an explicit error that also lists the currently available agent names as a hint.
- A duplicate skill name discovered from two different sources is not an error: the first-registered one wins (the built-in "how to configure this product" skill is deliberately registered before disk discovery specifically so a user can override it by placing a same-named skill on disk), and later duplicates only produce a warning log.

## Workflows & states

1. **Startup catalog build (agents):** load built-in agent definitions → scan configured directories (and their ancestors, for project-scoped external conventions) for agent Markdown files → for each, decode either the current schema or a legacy schema-and-migrate path depending on which frontmatter keys are present → apply each as a patch (existing name) or new entry (new name) against the built-in catalog, in file order → drop any agent marked disabled → guarantee the scratch-directory allowance on every surviving agent.
2. **Per-turn agent resolution:** turn arrives with an optional agent-name → resolve to that named agent, or the conversation's last-used agent, or the configured/first-eligible default → fail fast if the resolved name doesn't exist, is hidden, or (for the conversation-default case specifically) is subagent-only → persist the resolved agent (and model) onto the conversation if it changed since the last turn.
3. **Subagent dispatch lifecycle:** caller turn requests dispatch → depth-limit check → permission ask → target-agent lookup → child conversation created or reused → child's ruleset derived (parent restrictions + child's own ruleset + hard denies unless self-permitted) → child conversation run to completion (or backgrounded) → last text message (or error) extracted and returned as the dispatch's sole output → (background path only) result later injected into the parent conversation as a synthetic message once the child finishes.
4. **Skill catalog build (per conversation-turn context):** built-in skill registered → local project directories scanned → external-tool-compatible directories scanned (unless disabled) → explicit extra local paths scanned → explicit remote URLs pulled (index fetched, bundles downloaded/cached, refreshed only on a version bump) → all matches parsed and merged into one name-keyed catalog, duplicates dropped.
5. **Skill invocation:** model sees the permission-filtered, described-only catalog in its system prompt → model calls the "load skill" action with a name from that catalog → permission re-check for that specific name → skill body plus companion-file listing returned into the conversation as tool output → model proceeds using that guidance (and may separately read any listed companion file).

## Data

- **Agent record**: name, description, mode (`primary`/`subagent`/`all`), native/built-in flag, hidden flag, color, temperature, top_p, model reference (provider id + model id) and variant, system-prompt override, max-steps cap, a free-form `options` bag for unrecognized custom fields, and a permission ruleset (ordered list of `{action, resource-pattern, effect}`-shaped rules; see the Permission System dossier for how a ruleset is evaluated against a concrete action+resource).
- **Agent config source (Markdown)**: YAML frontmatter with keys `model`, `variant`, `temperature`, `top_p`, `prompt` (or the file body itself, if using the directory-convention form), `tools` (deprecated boolean map), `disable`, `description`, `mode`, `hidden`, `options`, `color`, `steps` (or deprecated `maxSteps`), `permission`; any other key is preserved verbatim as a custom option.
- **Dispatch call parameters**: short description, task prompt, target agent name, optional resume-id, optional background flag; **dispatch result**: task id, running/completed/error state, and the child's final text (or error text).
- **Skill record**: name, optional description, optional slash-command-eligibility flag, absolute manifest location, full instructional body text.
- **Skill config surface**: a list of extra local directory paths to scan, and a list of remote index URLs to pull bundles from.
- **Remote skill index** (fetched per configured URL): a list of named bundles, each with its version tag and the list of files making up that bundle (must include the manifest file itself or the bundle is skipped with a warning).

## Interfaces

- **Permission System** (documented elsewhere): every agent's capability set and every skill/dispatch invocation is gated by evaluating a permission ruleset against an action name and a resource pattern; this dossier only describes how each agent's ruleset is assembled and merged, not how a ruleset is evaluated or how the interactive "ask" flow works.
- **Tool System** (documented elsewhere): dispatch and skill-invocation are both exposed to the model as ordinary callable tools; an agent's permission ruleset also determines which of the product's other tools that agent may call at all (e.g. the read-only search agent has every action denied except a specific allowlist).
- **Session & Conversation Runtime** (documented elsewhere): owns the actual conversation/turn loop, message history, model-streaming, and the "which agent produced this turn" bookkeeping this dossier describes only at the level of "a turn carries an agent name and that name resolves to an Agent record."
- **Config & Data Contracts** (documented elsewhere): supplies the on-disk/config-file schema, directory discovery, and Markdown-with-frontmatter parsing primitives that both the agent loader and the skill loader are built on.
- **Plugin & MCP System** (documented elsewhere): plugins can register additional agents at startup (observed and covered by an internal regression test), and MCP server-provided instructions are surfaced into an agent's system prompt through the same "system prompt assembly" step that adds the skills catalog — the two are composed together, not competing.
- **Command System** (documented elsewhere): a companion CLI subcommand exists to list all currently resolved agents and to interactively (or non-interactively) generate and write a brand-new custom agent definition file from a natural-language description, including a permission-category picker.

## Error handling

- Unknown dispatch target agent: hard failure with an explicit "unknown agent type" message.
- Dispatch depth-limit exceeded: hard failure naming the configured limit and how to raise it.
- Background dispatch requested without the experimental toggle enabled: hard failure naming the required toggle.
- Child conversation's final turn erroring, or its last tool call erroring: the dispatch itself fails, surfacing the child's error message (and the child's conversation id, for follow-up/resume) rather than silently returning partial output.
- Requesting a nonexistent driving-agent name, or a `default_agent` config value that names a nonexistent, hidden, or subagent-only agent: hard configuration/runtime error, with the list of currently valid agent names included as a hint where applicable; a `default_agent` pointing nowhere usable (e.g. every primary agent disabled) fails with an explicit "no primary visible agent found" error.
- Skill manifest with unparseable frontmatter, or frontmatter missing a required `name`: silently skipped — logged as an error event, not surfaced to the model, and not fatal to loading the rest of the catalog.
- Skill invocation naming an unknown skill: fails with a typed "not found" error listing every currently available skill name.
- Remote skill-index fetch failure, or an individual bundle file download failure: logged and the affected bundle/file is skipped rather than aborting discovery of every other configured skill source; a versioned bundle refresh that fails partway is rolled back atomically so the previously-cached bundle is left intact.

## Non-functional observations

- Skill sources are cached per conversation-context lifetime (loaded once, reused across the rest of that run) rather than re-scanned on every turn; the on-disk implementation leaves open, as an explicit unresolved question in its own comments, whether local skill sources should invalidate on filesystem-change notifications.
- Skill discovery deliberately supports being a drop-in replacement for at least one external competing product's on-disk skill convention (`.claude/skills/`), plus a vendor-neutral convention (`.agents/skills/`), alongside the product's own native convention — a deliberate compatibility/interop design choice, independently disableable per convention.
- Remote skill-bundle refresh uses a stage-to-temp-directory-then-atomic-rename strategy specifically to avoid ever leaving a half-downloaded bundle in the live cache location.

## Duplicate-implementation note (packages/core vs packages/opencode)

Per the repo-wide pattern of `packages/core/src/<domain>` and `packages/opencode/src/<domain>` sometimes holding two independent implementations of the same feature, this feature has exactly that split, and the two are **not equally live**:

- `packages/opencode/src/agent/agent.ts` + `packages/opencode/src/skill/*` is the implementation actually wired into the running product: it is what the shipped subagent-dispatch tool, the shipped skill-invocation tool, the shipped system-prompt assembly, and the shipped CLI `agent create`/`list` commands all call. Everything described above as current behavior comes from this implementation and its colocated tests.
- `packages/core/src/agent.ts` (an "AgentV2" catalog keyed by a distinct branded id type, populated via a mutable-draft/transform pattern rather than a static merge) plus `packages/core/src/plugin/agent.ts` (registers the same seven built-in personas, same prompts, same permission shapes, translated into the newer rule shape) and `packages/core/src/config/plugin/agent.ts` (the config/Markdown loader for it) is a parallel, functionally-equivalent rewrite. Likewise `packages/core/src/skill.ts` + `packages/core/src/skill/guidance.ts` re-implement skill discovery and system-prompt advertisement against a reactive "system context" mechanism (which can push incremental "the skill list changed" updates into an already-built system prompt, and a "this skill is no longer available" retraction) that has no counterpart in the live implementation. Nothing in the product's actual dispatch tool, CLI, or system-prompt assembly path references this newer catalog — no core-side dispatch ("Task") tool exists at all — so it appears to be an in-progress rewrite not yet wired to run, rather than a second live code path.
- Where the two disagree only in incidental shape (id branding, rule-list encoding, draft/transform vs. static-merge population), this dossier describes the live (`packages/opencode`) behavior as authoritative and flags the `packages/core` version only as a forward-looking parallel implementation to watch, not as a second behavior to reconcile.

## Acceptance criteria — 5-8 Given/When/Then statements

1. **Given** no custom agent configuration at all, **when** the agent catalog is built, **then** it contains at least the seven built-in agents (`build`, `plan`, `general`, `explore`, `compaction`, `title`, `summary`), with `build` and `plan` as visible primary agents, `general` and `explore` as subagents, and `compaction`/`title`/`summary` as hidden primaries.
2. **Given** the `plan` agent's assembled permission ruleset, **when** evaluating the edit action against an arbitrary file path versus a path under `.opencode/plans/`, **then** the arbitrary path is denied and the plans-scoped path is allowed; **and** evaluating the dispatch action against the `general` subagent name is denied by default while dispatching `explore` or a custom subagent name is allowed; **and** evaluating the bash action is allowed by default (not "ask"), matching `build`'s bash evaluation, contradicting the "plan asks before bash" documentation claim.
3. **Given** a custom agent config entry naming an existing built-in agent (e.g. `build`) with only a subset of fields set (say, a new model and description), **when** the catalog is built, **then** the resulting agent keeps its built-in `mode` and `native` flag, adopts the new model and description, and its permission ruleset is the built-in's ruleset with the override's rules layered on top (not replaced).
4. **Given** an agent whose ruleset denies dispatch of the `general` subagent, **when** that agent's active conversation invokes dispatch against `general` without a pre-approval bypass, **then** the dispatch is rejected at the permission-ask step before a child conversation is ever created.
5. **Given** a top-level conversation (no parent) using an agent that is allowed to dispatch, **when** it dispatches a subagent and that subagent's conversation itself attempts to dispatch a further subagent, **then** the second dispatch is rejected with a nesting-depth-limit error, because the default configured nesting depth is 1.
6. **Given** a dispatching agent whose own ruleset denies file edits and a target subagent whose own ruleset explicitly allows file edits, **when** the subagent is dispatched with no additional parent-session deny rules in effect, **then** the child conversation's effective ruleset allows edits (the subagent's own grant is not suppressed by the parent's restriction, only by rules the parent explicitly denies).
7. **Given** two skill manifests with the same declared name discovered from different directories, **when** the skill catalog is built, **then** the one discovered first is kept, the later one is dropped with only a warning logged, and no error is raised.
8. **Given** a skill manifest with a `name` but no `description`, **when** the per-turn skill catalog is filtered for advertisement to the model, **then** the skill's directory remains an allowed external-access path but the skill itself does not appear in the advertised catalog text.

## Confidence & open questions

Confidence: high for the live (`packages/opencode`) agent catalog assembly, permission-layering rules, custom-agent config/Markdown loading, and skill discovery/advertisement/invocation mechanics — all directly backed by reading the implementation plus a large, explicit colocated test suite (`packages/opencode/test/agent/agent.test.ts`, `plan-mode-subagent-bypass.test.ts`, `plugin-agent-regression.test.ts`, `packages/opencode/test/skill/*.test.ts`) whose assertions were mined directly into the business rules and acceptance criteria above. Medium confidence on exactly how a client (TUI/API) surfaces the agent picker and the `@mention` UX end-to-end, since that spans the adjacent Session & Command System dossiers and was only traced as far as the prompt-building interface boundary.

Open questions:
- Whether `packages/core`'s AgentV2/SkillV2/SkillGuidance stack (draft/transform population, branded ids, reactive "system context" reconciliation) is an in-progress replacement intended to eventually take over from `packages/opencode`'s implementation, a design experiment, or dead code — no dispatch ("Task") tool exists on the core side to invoke it, so it could not be confirmed live from the code alone.
- The `slash` boolean field on the core-side skill schema (marking a skill eligible for slash-command-style invocation) has no corresponding behavior anywhere in the live implementation's skill-invocation tool or command system; whether this is a planned feature or an already-abandoned one is unresolved.
- The core skill loader's own source comment flags an explicit unresolved design question about whether local skill sources should invalidate on filesystem-watch events — noted here rather than resolved, since it is an open question in the source itself, not something this pass could adjudicate.
- The exact end-user surface for choosing/switching an agent per turn (TUI keybinding, slash command, or API field) was traced only to the point where a turn's request already carries a resolved agent name; the picker/affordance itself lives in the Session Runtime / Command System territory this dossier was asked not to cover.
