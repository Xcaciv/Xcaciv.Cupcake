# Feature: Control Plane & Cloud Sync

## Purpose
Beyond the login handshake itself (Auth's territory) and beyond mirroring a session to a public share link (Storage/Sync/Share's territory), OpenCode's connection to its own hosted service ("opencode.ai", or a self-hosted equivalent reachable at the same base URL) does two more things once a user/org account is active:
1. **Delivers organization-scoped policy** — pulls a remote provider/model catalog document from the account's server (scoped by an `x-org-id` header) and merges it into the running configuration and the in-memory model catalog, so an org admin can centrally control which LLM providers/models members can use, at what price, and with what request shaping — without the user maintaining that config locally.
2. **Provides a "workspace" abstraction and cross-instance session sync** — an experimental, pluggable notion of an alternate place a project's work can run (a local git worktree, or a remote OpenCode instance reachable over HTTP — e.g. a cloud-provisioned sandbox), plus the mechanics to keep a session's conversation history consistent when it is created, synced live, or explicitly relocated ("warped") between the local instance and one of these workspaces.

Both mechanisms are additive/optional: without an active org-linked account, no remote config is fetched; without the experimental-workspaces flag, no workspace ever syncs.

## Behavior

### Organization-scoped remote configuration
- When there is an active account with an active organization, the CLI (during config load) fetches `GET {account.url}/api/config` with a bearer token (the account's access token) and an `x-org-id` header, decodes the response as `{ config }`, and — if present — merges that JSON document into the configuration stack as a "global" source (alongside file-based config sources), tagging every provider id it defines as "console-managed" for later reference. Absence of a remote config (HTTP 404) is treated as "no remote config," not an error.
- Fetching the account's current access token is done in the same pass and, if present, is also exported as an environment variable (`OPENCODE_CONSOLE_TOKEN`) and persisted to the instance's env store, so plugins/tools running in-process can use it.
- Any failure of this remote fetch (network error, non-2xx status, decode failure) is caught, logged at debug level, and the rest of config loading proceeds as if no remote config existed — a control-plane outage never blocks the CLI from starting.
- A second, parallel implementation of the same idea exists as a pluggable "opencode" cloud connector built on a newer, generic integration/credential framework (see Interfaces): it registers itself as a connectable integration with two methods — an OAuth device-code flow ("OpenCode Console account") and a plain API key ("API key (service account)"). Once connected (OAuth or key), it fetches the same kind of remote document (`GET {server}/api/config`, bearer + optional `x-org-id`) and instead of merging it into text config, projects it directly into the in-memory model/provider **catalog**: provider request shape (native HTTP or an AI-SDK adapter package), per-model capabilities (tool-calling, input/output modalities), cost tiers (including a higher-cost tier once context exceeds 200k tokens), release dates, context/limit numbers, and an enabled/disabled + status (active/deprecated) flag per model. It re-fetches and reprojects automatically whenever the underlying connection changes (connect, disconnect, credential refresh).
- Without any credential for this connector, the "opencode" provider is still usable in a degraded/free mode: a placeholder API key value (`"public"`) is installed, and every model in that provider's catalog that has any positive input cost is disabled — so only zero-cost models remain selectable until the user actually connects an account or key.
- The device-code flow used by this connector is self-contained (its own client id, its own `/auth/device/code` and `/auth/device/token` calls against the default server `https://opencode.ai/console`), independent of the CLI's separate `opencode auth login`/`console login` account flow described in Auth; on success it also fetches `/api/user` and `/api/orgs`, and — when more than one org exists — deterministically picks the alphabetically-first org (by name, then id) as the one whose id is sent as `x-org-id` on later catalog fetches, and stores that org's name as the credential's display label.
- Refreshing this connector's OAuth credential posts `grant_type=refresh_token` to `/auth/device/token` on the server recorded in the credential's own metadata (so a credential obtained against a non-default/self-hosted server keeps refreshing against that same server).

### Workspaces (experimental)
- A **workspace** represents an alternate execution location for a project: an id, a type (a string key resolved to a pluggable adapter — built-in `worktree`, or any adapter a plugin registers, scoped either to one project or globally), a display name, an optional branch, an optional local directory, opaque adapter-specific `extra` data, the owning project id, and a last-used timestamp. The entire subsystem is inert unless an experimental-workspaces flag is enabled; with it off, listing returns empty and no syncing starts.
- **Adapter contract**: an adapter can `configure` (fill in/normalize a workspace's fields before it's persisted), `create` (actually provision it — e.g. create a git worktree, or start/attach a remote sandbox — receiving an environment-variable bag to hand to whatever process backs the workspace), optionally `list` (discover pre-existing workspaces the adapter itself knows about, keyed by name for de-duplication against ones already recorded), `remove` (tear down provisioned resources), and `target` (resolve the workspace to either a `{type:"local", directory}` or a `{type:"remote", url, headers?}` destination). The built-in `worktree` adapter always resolves to a local target (a git worktree directory); a remote-provisioning adapter (cloud sandbox, dev-server, etc.) is expected to resolve to a `remote` target backed by an HTTP(S) URL for another OpenCode instance.
- **Creating** a workspace: resolve the adapter → `configure` (may throw; on failure nothing is persisted) → insert the workspace row → `create` (may throw; if it does, the row is **kept** — a half-provisioned workspace is left visible rather than silently discarded) → pass the current provider-credential set (`OPENCODE_AUTH_CONTENT`), the new workspace id, an experimental-workspaces flag, and the process's OpenTelemetry exporter env vars into the adapter's `create` env bag → concurrently wait for the workspace to reach a terminal connection status ("connected" or "error", capped at a 5-second timeout) while starting its sync loop.
- **Discovering** externally-known workspaces (`syncList`): calls every registered adapter's `list()` concurrently, and for each item not already present (matched by name within the project) inserts a new workspace row and starts syncing it; adapters without a `list` method are skipped without error.
- **Connection status** per workspace is one of `connecting` / `connected` / `disconnected` / `error`, held in memory (not persisted) and broadcast on the global event bus only when it actually changes (repeated identical statuses are suppressed, not re-emitted).
- **Local workspace sync** is just a directory-existence check: connected if the target directory exists, error otherwise; no ongoing loop.
- **Remote workspace sync** is a persistent loop per workspace, one at a time (a duplicate start request for an already-connected workspace is a no-op; a start on a workspace last seen "error" is retried): connect an SSE stream to the target's `/global/event`, on success first pull `/sync/history` (see below) then mark the workspace "connected" and forward every subsequent server-sent event onto the local global event bus (annotated with the workspace id) — except a `server.heartbeat` event, which is swallowed. A special `sync`-typed event carrying an embedded event-log entry (`syncEvent`) is first replayed into the local durable event log (see Interfaces) before being forwarded; a replay failure for one such event is logged and that one event is dropped without tearing down the stream. If the connection ever fails or the stream ends, status becomes `error`/`disconnected` and the loop reconnects with exponential backoff (starting at 1s, doubling, capped at 2 minutes) — it never gives up permanently on its own.
- **History sync**: on (re)connecting to a remote workspace, the local instance computes, for every local session already assigned to that workspace, the highest durable-event sequence number it has locally, and POSTs that whole `{sessionID: seq}` map to the remote's `/sync/history`; the remote replies with the ordered list of events the caller is missing, which are replayed into the local event log (each tagged with the workspace id as the "owner" claiming those aggregates) and thereby re-project session/message/part state.
- **Session warp** relocates one session between workspaces (including to/from "no workspace," i.e. back to the local project):
  1. If the session currently belongs to a workspace, do a final history-sync push against that workspace's own remote (best-effort — failure is logged, not fatal) so nothing is lost, or, if that workspace is local, simply cancel any in-flight prompt for the session; then claim the session's event-log ownership for the destination (workspace id, or the local project id when detaching) so late-arriving events from the old workspace stop mutating it.
  2. If `copyChanges` was requested and the session had a workspace, capture a raw diff/patch from the *source* workspace's target (local `vcs diffRaw`, or a `GET /vcs/diff/raw` call to a remote target) before touching anything else.
  3. If a patch was captured, apply it to the *destination* target first (local `vcs apply`, or `POST /vcs/apply` to a remote target) — deliberately before moving the session, so a failed apply never leaves the session warped with lost changes.
  4. Detaching (`workspaceID: null`) simply clears the session's workspace assignment and returns.
  5. Attaching to a local-target workspace simply sets the session's workspace assignment.
  6. Attaching to a remote-target workspace instead replays the session's entire local durable-event history to the destination's `/sync/replay` (in batches of 10 events, in original sequence order), then calls the destination's `/sync/steal` to have it claim ownership of the session id, and only then updates the local session's workspace assignment.
- **`waitForSync`** lets a caller block (with an optional timeout and abort signal) until a given map of `{aggregateID: minimum sequence}` is satisfied locally — checked immediately, then re-checked every time *any* global event tagged with a workspace fires or a `sync`-typed event fires anywhere, so it wakes promptly on relevant activity without polling tightly.
- **Removing** a workspace: reassigns/deletes its sessions (any session that is not itself the parent of another still-attached session is removed outright), stops its sync loop and clears its in-memory status, invokes the adapter's `remove` (a failure here is logged but does not block deletion), then deletes the workspace row. Removing a workspace that doesn't exist is a no-op returning nothing.
- A small local HTTP surface (`/sync/history`, `/sync/replay`, `/sync/steal`, `/global/event`) is what one instance exposes so another instance's Workspace service can treat it as a remote target — this is the wire contract a from-scratch client/server pair must implement to interoperate, but the durable-event replay/claim semantics it rides on belong to Storage/Sync/Share, not here.
- A related, simpler local mechanic — **moving a session's working directory** within the *same* project (e.g. after a worktree rename) — captures a git changeset at the old directory, applies it at the new one, publishes a "session moved" event, then resets the old directory back to a clean state; it requires the destination to resolve to the same project as the session's current one (a cross-project destination is rejected) and is exposed as its own `/experimental/control-plane/move-session` endpoint. This is a local directory relocation, not a cross-workspace warp, though it lives in the same code area.

## Business rules & edge cases
- Remote org config is only ever fetched when an account exists **and** it has an active org id; an account with no org selected never triggers a fetch.
- A 404 from `/api/config` is a deliberate "no remote config for this org" signal and is treated identically to there being no account at all — it is not surfaced as an error.
- The generic "opencode" cloud connector and the CLI's own account/config-merge path are two independently-implemented routes to the same `/api/config` endpoint and the same org-header convention; nothing observed reconciles or deduplicates the two (see Open Questions).
- With no credential attached to the "opencode" connector, priced models are proactively disabled rather than left selectable-but-failing; a bare positive input cost is what defines "priced" (a model with zero input cost stays enabled even without a key).
- Workspace `create` is transactional in one direction only: a `configure` failure leaves nothing persisted, but a `create` (provisioning) failure leaves the already-inserted row in place — a caller sees a workspace row whose backing resource may not exist, and must call `remove` (or retry) explicitly.
- `syncList` de-duplicates purely by workspace **name** within a project; an adapter reporting a workspace whose name already exists locally (even under a different type/branch/directory) is silently skipped, not merged or updated.
- Only one sync loop runs per workspace at a time; requesting a start while one is already connected/connecting is a no-op, but a workspace last seen in `error` is allowed to restart.
- History-sync and session-warp-replay strictly reuse the same durable-event contiguous-sequence and ownership rules documented in Storage/Sync/Share — a workspace claiming a session's events via `/sync/steal` is exactly that feature's ownership-claim primitive, applied across a network boundary.
- Applying a copied-changes patch to the destination happens **before** the session's workspace assignment is updated or its history is replayed, specifically so that a failed patch application aborts the warp without leaving the session pointed at a workspace that never got the file changes.
- A session-warp's `copyChanges` diff/apply step is skipped entirely if the source and destination resolve to the exact same local directory (nothing to copy).
- Device-code polling for the "opencode" cloud connector follows the same RFC-8628-style retry/backoff convention documented in Auth (retryable `authorization_pending`, `slow_down` extends the wait by 5s) — implemented a third time here, independently of the CLI account flow and any provider plugin.
- Removing a workspace's sessions only deletes a session if it is not the parent of some other session still attached to that same workspace, avoiding orphaning a sub-session mid-removal pass.

## Workflows & states
**Remote org config (per config load):** account active with org? → no → skip. → yes → fetch `/api/config` (bearer + org header) → 404 or error → skip (logged) → success → merge into config as a global source and tag its provider ids as console-managed; independently export the account's current access token as `OPENCODE_CONSOLE_TOKEN`.

**Cloud connector catalog (event-driven):** connector registered at startup → on any `integration.connection.updated` event for "opencode" (connect, disconnect, credential refresh) → re-resolve active connection → if credentialed, fetch `/api/config`; if not, clear cached providers → reproject the entire provider/model catalog from whatever was fetched (or clear org-provided fields when nothing was fetched) → disable priced models when uncredentialed.

**Workspace lifecycle:** *(none)* → `create` → configure → insert row → provision (`create`) → wait for first terminal status while starting sync → *connected* / *error*. From *connected*: remote loop keeps reconnecting with backoff on drops; explicit `remove` tears down provisioning, deletes the row, and returns to *(none)*.

**Session-warp lifecycle for one session:** attached to workspace A (or unattached) → optional final sync-push from A → claim ownership for destination → optional capture-patch-from-A → optional apply-patch-to-destination (abort warp on failure) → destination local? set assignment, done. destination remote? replay full history in batches → steal ownership at destination → set assignment, done. destination null? clear assignment, done.

## Data
- **`workspace` table** (SQLite): `id` (`wrk_`-prefixed, sortable), `type`, `name` (defaulted empty string), `branch` (nullable), `directory` (nullable), `extra` (nullable JSON), `project_id` (FK to `project`, cascades on delete), `time_used` (epoch ms, defaults to creation time). One row per workspace; no direct link to any cloud account/org row — a workspace's "remoteness" is entirely determined by what its adapter's `target()` resolves to at runtime, not by a stored field.
- **In-memory-only**: per-workspace connection status (`connected`/`connecting`/`disconnected`/`error`), and the map of running sync fibers — neither survives a process restart; on restart, `startWorkspaceSyncing(projectID)` must be invoked again to resume syncing every stored workspace for a project.
- **Remote config document** (`RemoteConfig` / catalog-projection shape): `{ config: { provider: { [providerID]: { name?, npm?, api?, options?, models: { [modelID]: { name?, family?, id?, provider?, tool_call?, modalities?, headers?, options?, variants?, release_date?, cost?, status?, limit? } } } } } }` — an org-scoped superset of the normal local provider/model config shape (full schema owned by Config & Data Contracts; only the delivery mechanics are documented here).
- **Cloud-connector credential metadata** (stored via the generic Credential store, see Interfaces): for the "opencode" OAuth method, `{server, accountID, email, orgID, orgName}` alongside the standard access/refresh/expires fields — the `server` field is what makes refresh target the correct (possibly self-hosted) instance.
- **`project.sandboxes` column**: an array of absolute paths on the `project` table; present in the schema and populated (empty by default) but not read or written by anything in the Workspace/Integration code inspected here — see Open Questions.

## Interfaces
- **Auth, Credentials & Accounts** (documented elsewhere): owns the actual login/device-code/org-switch UX for the CLI's own cloud account (`opencode auth login` / `console login|switch|orgs`) and the account/org SQLite tables this feature reads (`active_org_id`, access token) to decide whether to fetch org config; also owns the generic OAuth/Key/Env "Integration" + "Credential" plugin framework this feature's cloud connector and catalog sync are built on (attempt lifecycle, credential storage/refresh-dedup) — this dossier only covers how the specific "opencode" integration uses that framework to deliver org policy.
- **Storage, Sync & Share** (documented elsewhere): owns the durable per-aggregate event log, its sequencing/replay/ownership-claim rules, and the local `/sync/*` HTTP handlers this feature's workspace history-sync and session-warp ride on; also owns the unrelated public/anonymous "share a session to a link" feature, which does not involve workspaces or accounts at all.
- **Config & Data Contracts** (out of scope): defines the full provider/model config schema this feature's remote fetch merges into, the config-source precedence rules (local file vs. `OPENCODE_CONFIG_CONTENT` vs. remote org config vs. system-managed/MDM config), and the managed/MDM config-delivery mechanism (`/etc/opencode` or platform equivalent, macOS `.mobileconfig`/Managed Preferences) — that MDM path is a purely local, IT-department-deployed file/plist read with no network call to opencode.ai and is not part of this feature.
- **Server/HTTP API** (out of scope): hosts the actual route wiring (`/experimental/control-plane/move-session`, the `/sync/*` surface, workspace CRUD endpoints) that exposes this feature's services to the CLI/TUI/desktop client and to other instances.
- **Session & Conversation Runtime** (out of scope): owns session creation/prompt-cancellation and the `session.workspace_id` field this feature reads/writes when attaching, detaching, or warping a session.
- **Provider & LLM Integration / Catalog** (out of scope): owns the in-memory model/provider catalog this feature's cloud connector projects org-delivered models and pricing into.

## Error handling
- Remote org-config fetch failures (network, non-2xx, decode) are caught and logged at debug level; config loading proceeds without the remote source rather than failing startup.
- The cloud-connector's catalog fetch likewise catches its own failures (logged as a warning) and leaves the catalog's org-provided fields simply absent rather than erroring the whole plugin/catalog reload.
- Workspace-specific tagged errors: `WorkspaceSyncHttpError` (non-2xx from a remote workspace call), `WorkspaceNotFoundError` (warp/target against an unknown workspace id), `WorkspaceSessionEventsNotFoundError` (warping a session with no local event history to replay), `WorkspaceSessionWarpHttpError` (a replay/steal call to the destination failed), `WorkspaceSyncTimeoutError` (a `waitForSync` deadline elapsed — carries the still-unsatisfied fence in its message), `WorkspaceSyncAbortedError` (the caller's abort signal fired first).
- A workspace `configure` or `create` throwing propagates as a failed effect that surfaces to the caller; `create`'s failure additionally leaves the workspace row inserted (see Business rules).
- A remote sync loop's connection or history-fetch failure sets that workspace's status to `error` and logs a warning, then the loop itself backs off and retries — it does not terminate the fiber or require external intervention.
- A single malformed/unreplayable event arriving over a remote workspace's SSE stream is logged and dropped without disconnecting the stream or failing the whole sync loop.
- Removing a workspace whose adapter throws on `remove` still deletes the local row (logged as an error, not propagated) — local bookkeeping is never left stuck behind an unreachable/broken remote resource.
- `MoveSession`'s directory-move rejects with a typed error when the destination resolves to a different project than the session's current one, and distinguishes capture/apply/reset failures (`CaptureChangesError`, `ApplyChangesError`, `ResetSourceChangesError`) so a caller can tell which half of the two-repository patch operation failed.

## Non-functional observations
- The entire Workspace subsystem is gated behind a single experimental flag; a reimplementation could treat it as an optional module without affecting the rest of the control-plane behavior (remote org config delivery has no such gate and is always active once an org is selected).
- Two independent code paths fetch the same org-scoped `/api/config` document (the CLI's direct account-service call feeding text-config merge, and the generic-Integration-framework "opencode" connector feeding the model catalog) with separately-implemented HTTP calls, device-code polling, and org-selection logic — a consolidation opportunity, and a discrepancy risk if the two ever disagree about which org/account is "active."
- Remote workspace sync reconnects indefinitely with exponential backoff (capped at 2 minutes) and never gives up — a permanently unreachable workspace will poll forever at that ceiling rather than being marked permanently dead; only an explicit `remove` stops it.
- Session-warp's ordering (apply patch to destination before reassigning/replaying) is a deliberate correctness choice: it favors "warp aborts cleanly" over "warp partially completes with data in two places."
- Connection-status change events are deduplicated in-memory before being broadcast, which keeps the global event stream from being flooded by a fast-reconnecting or flapping remote workspace.

## Acceptance criteria — 5-8 Given/High-level Given/When/Then statements
1. **Given** an active account with an active organization, **when** configuration is loaded, **then** the CLI fetches that org's remote config with the account's bearer token and an org header, merges a successful (2xx) response into the effective configuration, and treats a 404 response the same as "no remote config" rather than an error.
2. **Given** the remote org-config fetch fails for any reason (network error, non-2xx, malformed response), **when** configuration loads, **then** the failure is logged and configuration loading completes successfully using only the other available sources.
3. **Given** the "opencode" cloud connector has no active credential, **when** its catalog is projected, **then** every model in that provider's catalog with a positive input cost is disabled while zero-cost models remain enabled, and a placeholder API key value is installed for the provider.
4. **Given** the experimental-workspaces flag is disabled, **when** workspace listing or workspace-syncing is invoked, **then** no workspaces are returned and no sync loop is started, regardless of what is stored in the database.
5. **Given** a workspace whose adapter's `create` step throws after the workspace row has been inserted, **when** the failure occurs, **then** the workspace row remains visible in a subsequent list/get call rather than being rolled back.
6. **Given** a session currently attached to a remote workspace, **when** it is warped to a different remote workspace with `copyChanges` requested, **then** the source's uncommitted diff is captured and successfully applied at the destination before the session's full event history is replayed and ownership is stolen at the destination — and if applying that diff at the destination fails, the session's workspace assignment is left unchanged.
7. **Given** a remote workspace's live SSE connection drops, **when** the sync loop notices, **then** the workspace's status becomes `error`/`disconnected` and the loop automatically retries the connection with an exponentially increasing delay capped at two minutes, without any external call to restart it.
8. **Given** a caller invokes `waitForSync` for a workspace/session sequence fence that is already satisfied in the local database, **when** the call is made, **then** it returns immediately without waiting for any event; **given** the fence is not yet satisfied and the caller supplies a timeout, **when** the timeout elapses first, **then** the call fails with an error whose message names the still-unsatisfied fence.

## Confidence & open questions
- High confidence on the mechanics actually exercised by tests: the `Workspace` service's create/list/syncList/remove/sessionWarp/status/waitForSync behavior and the remote sync loop's reconnect/backoff/dedup/history/steal behavior are all covered by an extensive integration test suite (`packages/opencode/test/control-plane/workspace.test.ts`) that this dossier's Behavior and Acceptance Criteria sections were mined from directly. The generic `Integration` service's attempt lifecycle (pending/complete/failed/expired, code-vs-auto modes, scoped cancellation) is likewise directly tested (`packages/core/test/integration.test.ts`).
- **Two unreconciled implementations of the same remote-config-delivery idea**: `packages/opencode/src/account/account.ts` (`Account.config`, feeding `packages/opencode/src/config/config.ts`'s merge step) and `packages/core/src/plugin/provider/opencode.ts` (the "opencode" Integration, feeding the model catalog) both call the same-shaped `/api/config` endpoint with the same org-header convention, using independently-implemented device-code login, org selection, and token refresh. It is not visible from the code alone whether one is meant to supersede the other, whether they are expected to ever disagree (e.g. different active accounts/orgs resolved by each), or whether this is transitional/in-progress migration work — this mirrors an identical open question already flagged in the Auth dossier about the legacy `auth.json`/account-SQLite system versus the newer generic Credential/Integration system, and should be confirmed with the team before a reimplementation commits to one path.
- **`project.sandboxes`** is a populated-but-unused schema column (array of absolute paths) discovered on the `project` table; nothing in the Workspace or Integration code paths inspected reads or writes it. Its intended relationship to the Workspace concept (e.g. tracking cloud-provisioned sandbox directories) is unclear and should be confirmed before assuming it is dead weight.
- The **`/experimental/control-plane/move-session`** local-directory-move endpoint lives under the same `control-plane` code area as Workspace but performs a same-project directory relocation with no network/cloud/account involvement at all; it is included here for completeness of "everything under `control-plane/`" but may belong more naturally with a project/worktree-management feature in a from-scratch design.
- The debug-only `debug-workspace-plugin.ts` / dev README describe a manual local-loopback way to simulate a remote workspace for development; it is not part of the shipping product behavior and is mentioned only because it usefully confirms the remote-target wire contract (`/global/event`, a workspace id + port handshake via a watched file).
- Multi-org selection for the cloud connector's device-code login is resolved automatically (alphabetically-first org by name) with no interactive choice, mirroring the same explicitly-flagged "TODO: let the user choose" provisional behavior already noted in the Auth dossier for the CLI's own account login — likely the same underlying gap surfacing in both code paths.
