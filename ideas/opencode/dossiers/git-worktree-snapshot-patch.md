# Feature: Git, Worktree, Snapshot & Patch

## Purpose

This feature gives the agent (and its host UI) a safe, git-backed way to see and undo its own edits, and a way to run sessions in isolated copies of the repository:

1. **Git inspection** — read the host repository's status, branch, default branch, and diffs (for a "source control" panel and for the agent's own situational awareness), and apply an arbitrary unified diff to the working tree on request.
2. **Worktrees** — create/list/remove/reset additional `git worktree` checkouts so a session (or subagent) can work in its own directory without disturbing the user's active checkout, with an auto-provisioning boot sequence (populate files, run the project's start command).
3. **Snapshots (checkpoints)** — before/after every agent turn (and on demand), silently capture the state of the project's tracked+untracked files into a hidden, private git object store keyed to that project, so any subset of files can later be diffed against an earlier capture or selectively restored — independent of, and without polluting, the user's own git history or index.
4. **Patch format** — parse and apply a custom, human/LLM-authored patch envelope (`*** Begin Patch ... *** End Patch`, with `Add File`/`Delete File`/`Update File` sections and `@@`-anchored hunks) that is not standard unified diff; this is the format the edit/apply-patch tool accepts from the model, and the revert flow renders unified diffs back out of the same primitives.

## Behavior

### Git primitives
- **Repository discovery**: walk upward from a directory looking for a `.git` entry, then shell out to git to resolve the working-tree root, the git-dir, and the "common dir" (shared object store root, relevant for worktrees). Returns nothing if the directory isn't inside a git repository.
- **Internal repository creation**: initialize a git repository whose git-dir lives outside the working tree (used to host the snapshot store), tuned with `core.autocrlf=false`, `core.longpaths=true`, `core.symlinks=true`, `core.fsmonitor=false`, `feature.manyFiles=true`, `index.version=4`, `index.threads=true`, `core.untrackedCache=true` — chosen for correctness across platforms and to keep the first big index operation fast on very large repositories. Optionally "seeded" from another (real) repository by writing an `objects/info/alternates` pointer so blob hashes are shared, and by best-effort copying that repository's index file so identical content doesn't need to be re-hashed.
- **Remote / branch / default-branch resolution**: current branch via a quiet symbolic-ref of `HEAD` (empty/undefined when detached). Default branch resolution prefers, in order: the chosen remote's own `HEAD` symref (remote preference: `origin`, else the sole remote, else `upstream`, else the first remote); then the configured `init.defaultBranch` value if it names an existing local branch; then a local `main` branch; then a local `master` branch.
- **Root commit(s)**: the repository's root commit hash(es) (`rev-list --max-parents=0`), sorted.
- **Status/diff surface** (used for a source-control view): status is `git status --porcelain` restricted to the project directory, classified into `added` (new/untracked), `deleted`, or `modified` (including merge-conflict codes, which fold into "modified"). Diffing against a ref returns a name-status list; per-file or whole-tree unified patches are generated with a caller-supplied context-line count and a byte-size cap — if a single file's patch or the whole batch would exceed its cap, that entry's patch text is returned empty with a "truncated" flag rather than a partial patch.
- **Untracked file diff**: computed via a "no-index" diff against `/dev/null`; both exit code 0 (no difference — degenerate case) and 1 (differences found, git's normal signal) are treated as success.
- **Working-tree patch application**: apply a unified diff to a directory via `git apply` fed on stdin; failure returns the tool's stderr/stdout as the error message. A dedicated "apply this raw patch to the workspace" HTTP action distinguishes "not a git project" from "patch failed to apply" as different error reasons.
- **Scoped index refresh** (used internally by snapshot capture): given one path scope, list changed tracked files and new untracked files under it, resolve which are ignored by consulting an external repository's ignore rules, drop oversized untracked files (configurable byte threshold) and now-ignored files from the index, and stage everything else — all via null-byte-delimited path lists so filenames with unusual characters are handled safely.

### Worktrees
- A worktree's directory lives under a per-project data directory (not inside the project itself), and its name is generated as a random slug; a caller-supplied name is slugified and, on collision (existing directory or an existing local branch already using the derived branch name), retried with a random suffix, up to a fixed attempt limit before failing outright.
- Creation: `git worktree add --no-checkout` either onto a brand-new branch named `opencode/<slug>` or, when a detached worktree is requested, directly onto `HEAD` with no branch. The new directory is registered with the project as a "sandbox" location. Provisioning then proceeds asynchronously: hard-reset the new worktree to populate its files, bootstrap the app's own per-directory state there, and only then emit a "ready" event (carrying the worktree's name and branch) — or, if any step fails, a "failed" event carrying the failure message instead of ever emitting "ready." After boot succeeds, the project's configured start command runs in the new worktree, followed by any additional per-call start command.
- Listing excludes the primary (original) worktree; if a linked worktree's directory happens to share a basename with the primary worktree, it is disambiguated by using its parent directory's name instead.
- Removal: any live in-process state cached for that directory is disposed first; the git-recorded worktree entry is force-removed; a filesystem watcher daemon running inside it is stopped; the directory is then physically deleted with a bounded retry loop (substantially more retries on Windows, to ride out delayed file-handle release); its dedicated branch is force-deleted. If `git worktree remove` itself fails but a fresh listing shows the worktree is now gone anyway, that's treated as success rather than an error. If the directory was never a registered worktree at all (already detached/deleted), any leftover directory on disk is still cleaned up and the call still reports success.
- Reset ("start over" for a worktree): resolve the project's default branch, fetch it if it's a remote branch, hard-reset the worktree to that ref, force-clean (untracked + ignored files); if `git clean` reports files it could not remove, those specific paths are deleted directly and clean is retried once. Submodules are then updated, hard-reset, and cleaned recursively. A final `git status` must come back completely empty or the whole operation fails, reporting the residual status text. On success, the start command(s) are re-run in the background. Resetting the primary worktree itself is explicitly refused.

### Snapshots (checkpoints)
- Each project gets one hidden, private git repository dedicated to snapshots, stored under the app's data directory and keyed by project ID + a hash of the real worktree path; its working tree points at the real project directory via `--git-dir`/`--work-tree` (or the `GIT_DIR`/`GIT_WORK_TREE` environment variables), so it never touches the user's own `.git`.
- Snapshotting is only active when the project is a git project and the user hasn't explicitly disabled it in config (`snapshot`/`snapshots: false`); when disabled, capture returns "no snapshot" (undefined) rather than erroring, and every downstream feature that depends on a snapshot degrades gracefully (no diff/preview/restore available).
- **Capture** (produces a content-addressed git tree ID): sync the snapshot repo's own ignore file from the real repo's exclude file plus any newly-discovered oversized paths; list changed tracked files and new untracked files within the requested scope; resolve which of those the *real* repository's `.gitignore` rules would hide (even though the snapshot repo has no ignore rules of its own beyond what was just synced) and drop those from the snapshot's index; filter out untracked files above a size ceiling (2 MB) — these are recorded into the synced ignore file instead of being staged, so they're skipped on future captures too; stage everything that remains; write the tree. All capture/restore/diff operations against one project's snapshot repo are serialized behind a mutex so concurrent tool calls can't corrupt the shared index.
- **Diff between two captured trees**: enumerate the paths that differ between the two trees (again filtered through the real repo's ignore rules), then for each path report add/delete/modify status, added/deleted line counts, and a unified diff text; a numstat result of "binary" markers on both sides is reported as a binary file with no patch text and zero counts.
- **Selective restore**: given a map of {path → tree ID to restore that path from}, each path is either checked out from its tree (if present there) or deleted from the working directory (if the tree has no entry for it) — every other file in the working tree is left untouched. Restores for many paths sharing the same source tree are batched into one git call when their paths can't logically interfere with each other (no shared directory prefix), falling back to one call per path if the batch fails or is inconsistent.
- **Preview restore** (no actual filesystem mutation): the same selective-restore logic is run against a disposable, temporary git index file layered on top of the "current" tree, producing a hypothetical resulting tree that is diffed the normal way — then the temporary index is always deleted, even if an error occurred while building it.
- **Full checkout**: replace every file the target tree has an entry for; anything not mentioned in the tree is left alone (not deleted) — callers are steered toward selective restore whenever only specific files should change.
- **Housekeeping**: a background loop runs a `git gc` with a 7-day prune horizon on the snapshot repository roughly once an hour (starting a minute after the service comes up), only while snapshots are enabled and the store already exists.

### Patch format ("apply_patch")
- The patch text is wrapped between literal `*** Begin Patch` and `*** End Patch` marker lines (a surrounding shell heredoc, e.g. `apply_patch <<'EOF' ... EOF`, is stripped first if present). Between the markers, one or more file operations appear in order:
  - **Add**: `*** Add File: <path>` followed by lines each prefixed with `+`, giving the new file's entire content.
  - **Delete**: `*** Delete File: <path>`, no body.
  - **Update**: `*** Update File: <path>`, optionally followed immediately by `*** Move to: <newPath>`, followed by one or more hunks. Each hunk starts with `@@` (optionally carrying a free-text "which function/section" label after it) and then lines prefixed ` ` (context, present in both old and new), `-` (removed), or `+` (added); a hunk may end with a literal `*** End of File` line meaning its context must match at the very end of the file.
- **Applying an update hunk**: the hunk's "old" line sequence is searched for in the file, starting the search just after wherever the previous hunk (or the hunk's own context label, if any) was found. If an exact match fails, three progressively looser passses are tried: trailing-whitespace-insensitive, fully-trimmed, and Unicode-punctuation-normalized (smart quotes, em/en dashes, ellipsis character, and non-breaking spaces are folded to their plain-ASCII equivalents) — in that order, first match wins. `*** End of File` biases the search to try anchoring at the file's last lines first. If the old-line sequence still isn't found and its final line is empty, one more attempt is made with that trailing blank line dropped from both the old and new sequences. Failing to locate a hunk's context or its old lines is a hard error naming the offending file and lines. A hunk with no old lines at all is a pure insertion at the current search position (end of file if there is no prior anchor). All of a file's computed replacements are applied from the bottom of the file upward so earlier edits never shift the line numbers used by later ones.
- **Byte-order mark**: a leading UTF-8 BOM on the original file is stripped before matching/diffing and reattached to the written output if either the original or the newly produced content carried one. Output content is always normalized to end with exactly one trailing newline.
- **Applying a whole patch to disk**: operations are applied strictly in the order given — write new content (add), remove the file (delete), or read-current → derive-new → write (update, optionally writing to a new path and removing the old one for a move). A patch containing no operations at all is a hard failure. Failure partway through one operation does not roll back operations already applied; the caller is expected to report which targets succeeded before the failure.

## Business rules & edge cases

- Snapshot and worktree functionality are both gated on the project actually being a git repository; a non-git project silently gets no snapshots (capture returns nothing) and worktree operations fail with an explicit "not a git project" error.
- A snapshot capture failure is deliberately non-fatal: it is logged as a warning and treated as "no snapshot for this turn," never as an error that blocks the agent's response — checkpoints are a best-effort safety net, not a hard dependency.
- Snapshot capture excludes anything the *user's real* `.gitignore` would exclude, even though the private snapshot repository has no such rules baked in on its own; ignore rules are re-evaluated fresh against the current candidate file list every time (not cached), and files that newly match an ignore rule are proactively dropped from a previous capture's staged state.
- Untracked files above a fixed size ceiling (2 MB) are never captured; they're recorded in the snapshot repo's own exclude file so repeated captures don't keep re-scanning them.
- Restoring a path absent from the target snapshot tree deletes it from the working directory outright — restore is not additive-only.
- Worktree name/branch generation retries on collision a bounded number of times (26 attempts) and then fails outright rather than looping forever.
- Removing a worktree that no longer exists as a registered git worktree (e.g., manually deleted) still succeeds, cleaning up any stray directory rather than erroring "not found."
- Resetting the primary/original worktree is explicitly disallowed — reset only ever applies to a linked (sandbox) worktree.
- A worktree reset that leaves any residual `git status` output (after clean + submodule reset) is treated as a failure and reports the residue, rather than silently leaving a dirty tree.
- `apply_patch` moves: the newer, authoritative tool implementation explicitly rejects any update hunk carrying a `Move to` directive ("moves are not supported yet"); the older/legacy tool implementation fully implements move (write to new path, delete old path) — see Confidence & open questions.
- `apply_patch`'s newer tool implementation applies changes sequentially and, on a mid-patch failure, reports exactly which earlier operations were already applied so the caller/model knows the on-disk state is a partial application, not an atomic all-or-nothing change; there is no rollback of already-applied hunks — confirmed at the tool level: a forced failure deleting the second of two files still leaves the first file's deletion committed, and once a mutation has started committing it is not interruptible mid-flight (an interrupt landing during the second file's removal still lets that removal finish).
- The newer tool validates the *entire* patch (every hunk resolves and every target's precondition holds) before mutating anything — a later hunk that targets a missing file aborts the whole patch and the earlier, otherwise-valid hunks are confirmed never applied. This differs from the "no rollback" note above only in effect, not in mechanism: validation failures block before any write; only a failure during the actual write phase leaves earlier writes standing.
- The newer tool explicitly refuses to add a file that already exists at the target path (treated as an error, target left untouched) and defers reading any target's current content until *after* every affected resource's edit permission has been approved (confirmed zero file reads occur before permission approval, including for out-of-project "external directory" targets) — and it re-checks for a raced-in file at the target path in the narrow window between permission approval and the actual write, failing rather than clobbering whichever content won the race.
- A raw patch text with well-formed markers but zero operations inside is rejected as an "empty patch" error, distinct from a malformed-markers parse error.
- Git status/diff byte-size caps intentionally return an empty patch with a "truncated" marker rather than a partial/corrupt diff — callers must check the truncation flag rather than trust a short diff at face value.
- Snapshot capture of a linked worktree is fully isolated from the primary worktree's snapshot state (separate hashed store keys under the same project ID); a diff computed from within a linked worktree's context reports only that worktree's own changes plus any shared-file edits, not primary-worktree-only edits, and a revert issued from within a linked worktree only ever touches files inside that worktree.
- A snapshot's selective `restore(to a hash)` and a full `revert(list of patches)` are not the same operation: restoring to an earlier hash brings tracked/deleted/modified files back to that point but leaves alone any file created *after* that hash (restore is non-destructive to newer additions); revert additionally deletes files that did not exist at the target point. When a file was deleted, re-tracked (so "deleted" is the baseline), then recreated later, reverting to that baseline removes the recreated file; but when a file existed at the target point, was deleted, and was recreated with different content, reverting restores the *original tracked content*, not just the file's existence.
- Reverting a list of multiple patches that all touch the same file uses the *earliest* patch in the list for that file's content, and patches are applied strictly in the order given in the list (not reordered by recency) — relevant when the same path alternates file/directory type across snapshots.
- Internal diff/revert batching (both `diffFull` and multi-file revert) processes files in fixed-size chunks (observed boundary: 100 files) and must preserve the original file ordering across chunk boundaries when stitching results back together.
- Session-level revert operates on messages' true chronological creation order, not on any lexical ordering of message IDs — message IDs are not guaranteed sortable as strings.
- A file's permission bits (chmod) with no net content change and no net final-mode change do not produce a snapshot diff entry — though this was only verified for a chmod sequence that ends back at the file's original mode, so it does not fully establish whether an actual net permission change (a different final mode than the file started with) is likewise excluded from diffs.
- `git worktree remove` can report a non-zero exit code (e.g., "Directory not empty") even though the removal fully succeeded on disk (observed with certain git behavior/flaky filesystems); the removal logic re-verifies actual on-disk/registered state afterward rather than trusting the exit code alone, so it still reports success when the worktree is confirmably gone.
- Re-initializing git on an already-git project (`project/git/init` called twice) is a no-op for reload purposes — the forced "instance reload" event only fires the first time VCS status actually transitions from non-git to git, not on every call.
- Legacy, on-disk session-level diff storage that predates the current per-message diff-storage model is now ignored entirely by the diff-reading endpoint (rather than being schema-validated and surfaced) — requesting a session's overall diff when only legacy storage exists returns an empty result, not an error; per-turn diffs (scoped to one message) are unaffected and come from the newer, message-scoped storage.

## Workflows & states

**Auto-checkpoint per agent turn/step:**
1. Before the model call for a step begins, capture a snapshot of current state ("start" snapshot).
2. The step runs (tool calls execute, editing files).
3. After the step settles, capture a snapshot again ("end"); if both captures succeeded, diff them to get the list of changed file paths, and attach the start snapshot ID + changed-file list to the step/assistant-message record.

**Revert flow (stage → commit/clear):**
1. **Stage**: given a target message to roll back to, capture the *current* state first if nothing is already staged (so the "before I touched anything" state is preserved); walk forward through the session's assistant messages after that point, collecting the earliest known snapshot + changed-file set for every file that was touched; restore each such file to its pre-target-message snapshot; re-capture current state and diff it against the very first "current" capture to produce a preview diff; persist this pending "revert" record on the session and broadcast a "revert staged" event.
2. **Commit**: finalize the staged revert — permanently delete the session's messages after the revert boundary and broadcast a "revert committed" event. The already-restored file contents are left as-is.
3. **Clear (undo the staging)**: restore every file touched by the staged revert back to the "current" snapshot captured at stage time (i.e., undo the preview), drop the pending revert record, and broadcast a "revert cleared" event — the session's messages are untouched.

**Worktree lifecycle:**
`create` (validate git project → generate unique name/branch → `git worktree add --no-checkout` → register as sandbox) → `boot` (hard-reset to populate files → bootstrap app state → emit ready/failed → run start command(s)) → in use → `reset` (return to default branch + clean state, optional) and/or `remove` (dispose state → force-remove worktree → delete branch → delete directory).

**VCS branch-change notification:** the git service watches for filesystem changes to a `HEAD`-named file inside the repository's git metadata; whenever it fires, the current branch is recomputed, and if it differs from the last known value, a branch-updated event is broadcast.

## Data

- **Repository** (core): `{ worktree, gitDirectory, commonDirectory }` — three absolute paths describing one git repository's checkout root, its own `.git` metadata location, and the shared object-store root (equal to `gitDirectory` for a normal repo, different for a linked worktree).
- **ChangeSet** (core): an opaque branded string holding raw unified-diff text (tracked-file diff + synthesized untracked-file diffs concatenated) captured for a specific path.
- **TreeID** / **Snapshot.ID**: an opaque branded string — a git tree object hash, used as the checkpoint identifier throughout capture/diff/restore/preview APIs.
- **Worktree info**: `{ name, branch?, directory }` — branch is absent for a detached worktree.
- **File.Diff / FileDiff schema**: `{ path/file, status: added|deleted|modified, additions, deletions, patch }` — the common shape used for snapshot diffs, VCS diffs, and apply-patch tool output (field name is `path` in the strict/newer schema, `file` — optional — in the looser legacy/VCS-facing schema).
- **Revert.State** (session-level, persisted): `{ messageID, partID?, snapshot?, diff?, files? }` — describes a pending or historical revert boundary: which message it targets, the snapshot ID the "current" state was captured into, a concatenated diff string, and the structured per-file diff list.
- **Snapshot.Patch** (legacy): `{ hash, files[] }` — a captured commit-ish hash plus the absolute paths it touched, used by the legacy revert-by-file-list flow.
- **Worktree/VCS events**: `worktree.ready {name, branch?}`, `worktree.failed {message}`, `vcs.branch.updated {branch?}`.
- **Storage locations** (under the app's per-user data directory): snapshot repositories at `<data>/snapshot/<projectID>/<hash-of-worktree-path>`; sandbox worktrees at `<data>/worktree/<projectID>/<name>`.

## Interfaces

- **Git service (tree/repository oriented)** — consumed by the snapshot and worktree-provisioning machinery: repository discovery/clone/create, remote lookup, HEAD/branch/default-branch/root-commit history queries, fetch/checkout/reset-hard sync operations, changeset capture/apply/discard for a path, worktree create/remove/list, scoped index refresh and ignore-checking, and tree capture/write/diff/preview/restore/checkout.
- **Git service (porcelain oriented)** — consumed by the source-control ("Vcs") surface: branch, default-branch, has-HEAD, merge-base, show-file-at-ref, status, diff (name-status), stats (numstat), per-file/whole-tree patch text (with byte caps and truncation), untracked-file patch/stat, and raw patch apply.
- **Vcs service and HTTP surface**: `GET /vcs` (branch + default branch info), `GET /vcs/status`, `GET /vcs/diff?mode=git|branch` (git = diff against HEAD/working status; branch = diff against the merge-base with the default branch), `GET /vcs/diff/raw`, `POST /vcs/apply` (apply a raw patch to the workspace; fails distinctly for "not a git project" vs "patch didn't apply").
- **Worktree service and HTTP surface** (under an "experimental" path prefix): `GET` list, `POST` create (optional name + optional extra start command), `DELETE` remove (by directory), `POST .../reset` (by directory).
- **Snapshot service**: capture (returns nothing if disabled/unsupported/best-effort-failed), files-changed-between-two-captures, structured diff, preview-restore, restore, full-checkout. A no-op implementation of the same interface exists for contexts where snapshots must be present but inert.
- **Session revert integration**: session-level stage/commit/clear/cleanup operations (see Workflows) exposed through session HTTP endpoints and consumed by the prompt/processor pipeline that runs each agent turn.
- **apply_patch tool**: model-facing tool taking one field (`patchText`); resolves every target path through the shared file-mutation/permission-approval layer *before* reading any file contents, requests a single batched "edit" permission covering every affected resource (plus any external-directory approvals needed), applies changes sequentially, and reports the applied operations plus per-file structured diffs. This is the primitive the Tool System's edit tooling documents separately; this dossier covers only the underlying patch-parsing/application/diffing engine it calls.
- **Adjacent-feature boundaries** (not documented here, only touched): the Tool System owns the tool-facing wrapper and permission UX around `apply_patch`/edit; Session & Conversation Runtime owns when/why a snapshot is taken per turn and how revert requests reach this layer; the Server/HTTP API owns request/response wire formats for the endpoints listed above.

## External technology

| Technology | Role |
|---|---|
| Git (external CLI, invoked as a subprocess) | All repository inspection, diffing, patch application, worktree management, and the snapshot store itself are implemented by shelling out to `git`. |
| `diff` (npm package, v8) | Generates unified diff text and line-level add/remove statistics for the legacy snapshot diff path and the apply-patch tool's reported diffs, independent of `git diff`. |
| Effect-TS | Structures every operation as an effect with typed tagged errors, mutex/semaphore-guarded critical sections, and scheduled background tasks (snapshot GC loop, worktree boot/reset as forked background fibers). |
| SQLite (via an ORM) | Persists session-level revert state and the per-message start/changed-files snapshot references. |
| Bun runtime | Executes the TypeScript service code and spawns the `git` subprocesses. |

## Error handling

- Git command failures are surfaced as typed, tagged errors carrying an operation name (e.g., `clone`, `checkout`, `diff`, `restore` for repository/tree operations; `create`, `remove`, `list` for worktree operations; `capture`, `apply`, `reset` for changeset operations), the affected directory, and a human-readable message drawn from the command's stderr (falling back to stdout, falling back to a generic "git \<op\> failed").
- Worktree-removal errors additionally carry a `forceRequired` flag, set by pattern-matching git's error text for phrases indicating the worktree has uncommitted/untracked content blocking a plain removal.
- Snapshot errors are tagged by operation (`capture`, `files`, `diff`, `preview`, `restore`) and, notably, a *capture* failure is delibrately swallowed (logged, not propagated) so it never fails an agent turn — every other snapshot operation (diff/preview/restore) does propagate its error to the caller, since those are explicit user-triggered actions rather than passive background bookkeeping.
- Patch parsing errors are plain descriptive exceptions ("Invalid patch format: missing Begin/End markers", "Failed to find expected lines in \<file\>: ...", "Failed to find context '...' in \<file\>") that name the offending file and, where relevant, echo the exact lines that could not be matched.
- The apply_patch tool wraps every failure into a single failure type whose message is built contextually: if no operations had yet succeeded, "Unable to apply patch at \<path\>"; if some had already succeeded, "Patch partially applied before failing at \<path\>. Applied: \<list\>" — so the model always learns the true on-disk state after a partial failure.
- The VCS "apply a raw patch" action distinguishes two failure reasons explicitly: the project isn't a git repository at all, versus the patch was rejected by `git apply` (working tree not clean/compatible) — modeled as a discriminated error rather than one generic failure.

## Non-functional observations

- All snapshot mutations (capture/restore/diff/preview) against one project are serialized behind a per-repository lock, avoiding concurrent-index corruption when multiple tool calls or turns overlap.
- Diff/patch generation enforces explicit byte-size ceilings (both per-file and for a whole batch) and reports truncation rather than silently returning partial or oversized payloads — protecting the model's context window and the HTTP transport from unbounded diff sizes.
- The snapshot store is deliberately tuned (`manyFiles`, index v4, threaded index, untracked-file cache, object-store sharing/seeding via alternates) specifically to keep the *first* capture on a very large repository fast — called out in-code as a response to real-world slow-repository cases.
- Physical directory removal (worktree teardown) retries with backoff, far more aggressively on Windows, acknowledging that antivirus/file-handle latency there routinely delays deletion.
- Windows path handling is canonicalized and case-folded specifically for worktree directory matching, since git and the filesystem can disagree on casing there.
- A background hourly `git gc` bounds the snapshot repository's on-disk growth without requiring any user action.
- Batched blob retrieval (`git cat-file --batch`) is used in the legacy diff path specifically to avoid one `git show` subprocess per changed file, with a documented fallback to the slower per-file path if the batch protocol response can't be parsed.

## Acceptance criteria — 5-8 Given/When/Then statements

1. **Given** a directory inside a valid git repository, **when** repository discovery runs, **then** it returns the working-tree root, git metadata directory, and shared object-store directory; **given** a directory not inside any git repository, **when** discovery runs, **then** it returns no repository rather than erroring.
2. **Given** snapshots are enabled for a git project, **when** an agent turn begins and ends, **then** a checkpoint is captured both before and after the turn, and the set of files that changed between those two checkpoints is computed and attached to that turn's record — **and** if capture fails for any reason, the turn still completes normally with no snapshot recorded.
3. **Given** a file matches the project's `.gitignore` or exceeds the untracked-file size ceiling, **when** a snapshot is captured, **then** that file's content is excluded from the snapshot (and, if untracked, remembered so future captures skip it too).
4. **Given** a session with prior turns that modified files, **when** a revert is staged targeting an earlier message, **then** every file touched since that message is restored to its state as of the earliest snapshot associated with that message, a preview diff of the restoration is produced and persisted on the session, and no session messages are deleted yet.
5. **Given** a staged revert, **when** it is committed, **then** all session messages after the revert boundary are permanently deleted and the already-restored file contents remain; **when** it is cleared instead, **then** the affected files are restored back to their pre-revert state and no messages are deleted.
6. **Given** a request to create a sandbox worktree in a git project, **when** creation runs, **then** a uniquely-named directory and branch are created via `git worktree add`, the worktree is populated and bootstrapped asynchronously, and a ready (or, on any failure, a failed) event is emitted — never both, and never neither.
7. **Given** a well-formed `apply_patch`-format patch with one Add, one Update, and one Delete operation, **when** it is applied, **then** the new file is created with the given content, the updated file's matched hunks are replaced in place (trying exact then progressively fuzzier line matching), the deleted file is removed, and the operations are applied in the order they appeared in the patch text.
8. **Given** an `apply_patch` whose second of three operations fails (e.g., its expected old lines can't be found), **when** the tool runs, **then** the first operation's change remains applied, the third operation is never attempted, and the reported error names the failing path and lists which operations already succeeded.
9. **Given** a git worktree removal where the underlying `git worktree remove` command reports a non-zero exit code but the directory and its git-registered worktree entry are actually gone afterward, **when** the removal completes, **then** the operation reports success (verified against actual state) rather than surfacing the misleading failure exit code.

## Confidence & open questions

- **Duplicated Git services.** Two independent Git service implementations exist: a tree/repository-oriented one (`packages/core/src/git.ts`) consumed by the snapshot and worktree-provisioning code, and a porcelain-oriented one (`packages/opencode/src/git/index.ts`) consumed by the source-control ("Vcs") HTTP surface. Per the stated convention, core is treated as authoritative for overlapping concepts (repository discovery, patch application), but the two are not simple duplicates — they cover different call shapes (tree IDs vs. working-tree porcelain) and both appear live in the current codebase. Not confirmed which, if either, is scheduled for removal.
- **Duplicated Snapshot services with different semantics.** `packages/core/src/snapshot.ts` (tree-ID keyed, map-based multi-file restore/diff/preview) and `packages/opencode/src/snapshot/index.ts` (single git-commit-hash keyed, `restore(oneHash)` / `revert(patches[])` / `patch(hash)` / `diffFull(from,to)`) both exist, are both fully wired into distinct session runtime code (`core/src/session/runner/llm.ts` + `core/src/session/revert.ts` vs. `opencode/src/session/processor.ts` + `opencode/src/session/revert.ts` + `opencode/src/session/summary.ts`), and are not simply old-vs-dead — it was not possible from static reading alone to confirm whether both run in the shipped app for different session types, or whether one is legacy/unreachable. Flagged rather than resolved.
- **`apply_patch` move support diverges (confirmed by tests on both sides).** The newer/authoritative tool (`packages/core/src/tool/apply-patch.ts`, backed by `packages/core/src/patch.ts`) explicitly rejects any patch containing a file move — its own test asserts the rejection happens before any hunk in the patch is applied and before any permission check runs. The older tool (`packages/opencode/src/tool/apply_patch.ts`, backed by `packages/opencode/src/patch/index.ts`) has a dedicated passing test proving move-with-update works, including overwriting an existing destination and reporting `type: "move"` metadata for the permission prompt. Since core is authoritative by convention, this reads as an intentional (possibly temporary) feature regression rather than a bug — but this dossier cannot confirm intent from statics alone.
- **"Add over an existing file" is a direct, tested contradiction, not just an inferred one.** Core's `tool-apply-patch.test.ts` has a test titled "rejects add hunks targeting an existing file without replacing it" — an Add whose target already exists fails and the existing content is left untouched. Opencode's `tool/apply_patch.test.ts` has a test titled "adds file overwriting existing file" — the same operation silently succeeds and overwrites. Both tools implement a tool literally named `apply_patch` with the same input shape; a reimplementation must pick one semantic deliberately rather than assume there is a single canonical answer in this codebase. Given the stated convention, core's stricter (reject-on-collision) behavior should be treated as authoritative, but the opencode behavior is exercised by its own passing test, not dead code.
- **Patch-parse error granularity differs between the two parsers.** Core's `Patch.parse` throws specific messages per malformed construct (missing `+` prefix on an add line, an update section with no `@@` chunk, an unrecognized line inside the envelope). Opencode's `Patch.parsePatch` collapses all such cases to one generic "Invalid patch format" message. Not a behavioral contradiction (both reject malformed input) but a fidelity difference worth deciding on for a reimplementation's own error messages.
- **A likely-stale bug comment on a race-condition regression test.** `packages/opencode/test/session/snapshot-tool-race.test.ts` documents, in its header comment, a real race where a near-instant (test-double) tool response can complete before the pre-tool-call snapshot is captured, making before/after snapshots identical and hiding a real file change from the turn's diff. The test body, however, only polls for up to ~5 seconds and asserts the diff *eventually* becomes non-empty — it does not assert the buggy (empty-diff) outcome. It is unclear from static reading whether this documents a fixed bug (stale comment) or a still-present, timing-dependent race that the poll loop merely tolerates in practice. A reimplementation should decide explicitly whether "snapshot capture must happen strictly before any tool executes" is a hard ordering guarantee or merely a best-effort one.
- **Selective `restore(to a hash)` vs. full `revert(patch list)` are intentionally different operations, not duplicate implementations of the same idea** — confirmed by dedicated tests: `restore` leaves alone anything created after the target point, `revert` removes it. This is a real API distinction to preserve, not an inconsistency to resolve.
- **Legacy hand-rolled diff generator.** `packages/opencode/src/patch/index.ts` contains a `generateUnifiedDiff` function that does a naive line-index comparison (not a real longest-common-subsequence diff) to produce an `unified_diff` metadata field on parsed update changes; it was not confirmed whether this value is actually consumed anywhere downstream or is dead output — if it is used for anything user-visible, its correctness on any but the simplest single-line edits is doubtful.
- **Duplicated Snapshot/session-revert code paths, now partially clarified by tests but not fully.** Tests confirm both `packages/core/src/session/revert.ts` (tree-ID/map based) and `packages/opencode/src/session/revert.ts` (single-hash/patch-list based, exercised end-to-end by `revert-compact.test.ts` including multi-turn stage/unstage round-tripping of real file content) are live, tested code — not one dead and one active. It remains unconfirmed which runtime/session type each path serves in the shipped app, or whether they are two full generations coexisting during a migration.
- **A few snapshot edge-case tests assert only "does not crash," not correctness** — circular symlinks and concurrent-write-during-capture cases assert a non-negative array length rather than a specific expected result. Treat "handles circular symlinks / concurrent writes gracefully" as a documented intent, not a verified specific behavior, when reimplementing.
- **VCS "branch" diff mode against a project with no remote/default branch.** `Vcs.diff("branch", …)` returns an empty diff whenever no default branch can be resolved or the current branch equals the default — this reads as "nothing to show" but could equally be read by a UI as "no changes," which may be worth disambiguating in a reimplementation.
- **`git worktree remove` reporting failure despite succeeding** is explicitly handled (not just theorized): the removal path re-verifies actual state on disk/in git's own worktree list rather than trusting the process exit code, and a dedicated test simulates a git binary that always reports this specific failure text after truly succeeding.
