# Feature: Terminal UI (TUI)

## Purpose

The TUI is OpenCode's primary interactive interface: a full-screen terminal application that renders the chat/conversation view, the prompt/input editor, tool-call and diff output, permission-approval prompts, session/agent/model pickers, theming, and a plugin-extensible layout — all driven by keyboard (and optionally mouse) input. It owns no domain logic: every session, message, permission, tool, agent, and model concept it displays is fetched and mutated through a generated client (SDK) against a server API, either over a real network socket or an in-process transport. Architecturally it is a standalone package (`@opencode-ai/tui`) consumed by two different CLI executables ("legacy" and "new") that each wire up their own process/config/auth/worker plumbing and hand the TUI a single resolved configuration plus a transport; the TUI itself is forbidden from importing anything from the CLI or core backend packages, only the SDK's generated client contract.

## Behavior

**Bootstrap & connection.** Starting the TUI acquires a full-screen renderer (fixed 60fps target, custom keyboard protocol enabled, mouse support configurable), installs the global keymap, and mounts roughly twenty nested reactive "provider" contexts (paths, terminal environment, clipboard, args, small key/value store, toasts, routing, resolved config, plugin runtime, SDK client, permissions, project/workspace info, a session/event sync layer, a second event-sourced "v2" data layer, theme, per-project local preferences, prompt stash/history/frecency, dialogs, editor integration, location) before rendering the actual app tree. The SDK client is created against a base URL plus either a custom `fetch`/event-source pair (used for an in-process worker transport) or a real HTTP/SSE connection (used for a spawned or externally reachable server, or a remote `attach`). A global event stream (Server-Sent Events, or an injected equivalent) is consumed continuously; the client's own reconnect logic uses exponential backoff (1s doubling to a 30s cap) on stream failure, while a `server.instance.disposed` event triggers a full application-level resync (re-fetch of session list, providers, agents, config, etc.) rather than a mere stream reopen. Incoming events are coalesced into 16ms batches before being applied to reactive state, so a burst of streamed tokens produces one UI update instead of many.

**Routing.** Navigation is a plain in-memory route value (not a URL), one of `home`, `session` (with a session id), or `plugin` (a plugin-registered screen by name). Switching the session id remounts that portion of the tree; unknown plugin routes render a "go home" fallback. CLI arguments (`--continue`, `--session`, `--fork`) resolve to an initial route once sync reaches the needed readiness level, and in-app actions (creating a session, session-list selection, quick-switch slots 1–9, a deleted-session redirect) route programmatically.

**Chat/conversation view.** The session screen renders messages in a bottom-anchored scrollable list. User messages appear in a bordered box colored by the active agent, with file/directory attachments shown as small badges and a "QUEUED" badge when a prompt is waiting behind an in-flight turn; assistant messages render their parts (text, reasoning, tool calls) in order, growing incrementally as streamed text/tool state arrives (no separate "typing" placeholder). A footer line on the last/finished assistant message shows agent, model, duration, and interrupted/error state. Reasoning ("Thought") blocks show a spinner while streaming and, once done, collapse to one line with a click-to-expand toggle (unless "show thinking" mode is on, which keeps them expanded); model-specific quirks (e.g. a bolded title line preceding the body, or fully redacted/encrypted reasoning) are normalized into a consistent title/body/duration display. Scrolling supports page/half-page/line granularity, jump to first/last/next/previous message, and an optional scrollbar. An active session-level "revert" (undo) replaces every message from the revert point onward with a single collapsible banner summarizing affected files (+/- counts) and an inline confirm-to-redo action. Three timeline-oriented dialogs sit on top of the transcript: a chronological message list with live scroll-to-selected preview (`/timeline`), a per-message action menu offering Revert/Copy/Fork (opened by selecting a timeline entry or clicking a rendered user message), and a fork picker that can branch a new session from any prior message or from the whole session, re-seeding the new session's prompt box with the original message's text and attachments.

**Prompt/input editor.** A multiline text editor with cursor tracking and virtual "extmark" spans used to render non-text content (file/agent mentions, pasted-text placeholders, shell-mode hints) inline without corrupting the underlying text buffer. Typing `@` opens a fuzzy picker blending server-side file search (frecency-biased), MCP resources, `@agent` mentions, and named references, including `path#line` / `path#start-end` range syntax; typing `/` as the first character opens a slash-command picker (built-in plus server-registered commands); typing `!` as the first character switches the whole composer into "shell" mode, routing submission to a raw shell-execution call instead of a prompt. Pasting a recognized image/PDF/SVG file path, or an image straight from the OS clipboard, attaches it as a file part with a placeholder marker; long plain-text pastes (3+ lines or >150 characters) collapse into a `[Pasted ~N lines]` placeholder instead of flooding the buffer. An external-editor command suspends the terminal renderer and hands the buffer to `$VISUAL`/`$EDITOR` on a temp file, resyncing virtual parts afterward. Two independent draft mechanisms exist beyond normal editing: an unlimited-scope, single-slot "last draft" auto-restored across component remounts, and an explicit multi-slot on-disk "stash" (push/pop/list, JSONL-persisted) for deliberately parking work. A separate on-disk prompt history (also JSONL, capped at 50 entries, dedup on identical resubmission) is recalled with Up/Down only when the cursor is already at the start/end of the buffer, so it never fights normal cursor movement. Submission is guarded against several states: an empty buffer, an open autocomplete popup, a pending workspace/session-move operation, or a second concurrent submit (see Business rules).

**Model/agent switching.** `Tab`/`Shift+Tab` from the prompt directly cycle the active agent forward/backward (no picker); dedicated commands cycle "recent" or "favorite" models via function keys. Full pickers exist separately: an agent list dialog, a model dialog (favorites/recent/by-provider sections, or fuzzy search when filtering, chaining into a "variant" picker if the chosen model exposes reasoning/inference variants), and a provider-connect flow (API key or OAuth device/code flow) reached from the model dialog when no compatible provider is connected.

**Tool-call and diff rendering.** Each tool name maps to a dedicated renderer (shell/bash, glob, read, grep, web fetch/search, write, edit, task/subagent delegation, apply-patch, todo list, question, skill, a generic "execute" wrapper, and a generic fallback for unknown/plugin tools). Calls render as a compact single-line row while pending/running (verb text plus a spinner) and switch to either an expanded single line or a bordered block once real output exists — write/edit show a syntax-highlighted unified or split diff, bash shows captured (ANSI-stripped) terminal output truncated to a line/character budget with click-to-expand, task shows a live sub-line tracking the delegated subagent's current tool and eventually its total tool-call count and duration. Failed calls turn error-colored and are click-to-expand; calls whose failure matches known "permission denied/rejected" phrasing render as struck-through "denied" rather than a hard error; a call currently blocked on an open permission request is highlighted in the warning color. A full-screen diff viewer (its own route, opened by command or `/diff`) adds a collapsible file-tree sidebar, per-file reviewed/dimmed marking, single-file vs. all-files patch display, split/unified toggle, and hunk/file navigation, sourcing its diff from the working tree, the main branch, or "since last turn."

**Permission-approval prompts.** A permission request (raised by the server for an operation an agent isn't pre-authorized to do) appears as a warning-colored panel docked at the bottom of the transcript, expandable to fullscreen, showing a type-specific summary (diff for edits, command for bash, pattern for glob/grep, URL for web fetch, etc.) and three choices — Allow once, Allow always, Reject — navigated with arrow keys/`h`/`l` and confirmed with Enter, or clicked; Escape (and the app-exit binding) rejects. "Allow always" interposes a confirmation screen naming the exact rule that will be persisted for the process's lifetime. Rejecting a request that belongs to a subagent session opens an extra free-text "tell it what to do differently" step before sending the rejection; rejecting a top-level session's request sends immediately. Only one pending request is shown at a time (oldest first); others queue silently. While auto-approve mode is active, requests are answered automatically with "once" and never surface. A structurally parallel but distinct "question" flow (multi-step, multiple-choice-or-custom-text answers with a tabbed review-then-confirm UI for multi-question sets) occupies the same footer real estate and takes priority display order alongside permissions, both disabling the normal prompt while pending.

**Session list, workspaces, and other dialogs.** A session browser groups sessions by day with a pinned section, inline pin/delete/rename actions, and quick-switch slot badges. "Workspace" dialogs manage isolated checkouts (e.g. git worktrees) a session can run against — selecting/creating one for the current session ("Warp"), listing all known workspaces, confirming discard/carry-over of uncommitted changes, and recovering when a referenced workspace has vanished. A related "move" flow relocates an *existing* session to a different project directory. Command palette, skill picker, MCP server list/toggle, and a read-only status dialog (MCP/LSP/formatters/plugins) round out the dialog set, all built on a shared searchable-list primitive with fuzzy filtering, grouping, and a bottom action bar.

**Theming.** A theme is a JSON document defining ~50 semantic color slots (brand, status, text, background, border, a full diff palette, a markdown palette, and a syntax-highlighting palette), with values as literal colors, references to other named colors, ANSI codes, or dark/light variant pairs; 33 themes ship built-in, plus an optional terminal-derived "system" theme and user/plugin-installed themes from well-known directories (project-local taking precedence over global). The theme picker live-previews every highlighted item as the cursor moves and only commits on Enter (Escape reverts). A separate lock toggle pins dark/light mode independent of the terminal's live-reported mode; when unlocked, an OS/terminal theme-change signal is heard and colors update live.

**Keybindings and commands.** All input is defined as named commands with default key bindings (roughly 150 slots — navigation, session management, model/agent/session switching, diff-viewer controls, prompt/text editing, dialog navigation), fully rebindable through configuration, resolved into a queryable lookup at startup. A configurable leader key (default `Ctrl+X`) with a timeout window (default 2000ms) drives leader-prefixed shortcuts. A small mode stack (base/question/autocomplete/modal/plugin-pushed modes) gates which command layers are reachable at a given moment. Commands can additionally register themselves in a fuzzy-searchable command palette. An optional (off-by-default) "which-key" panel shows currently reachable bindings grouped by category.

**Plugin/slot extensibility.** Independent from the general backend plugin system, the TUI defines its own presentation-only plugin contract: authors export a `tui(api, options, meta)` function that can register routes, keymap layers/commands (optionally palette-visible), UI slots (named regions such as the sidebar sections, home footer/tips, or prompt-right decorations), dialogs, themes, and an "attention" (notification/sound) request API, and receive live read-only state accessors (session list/messages/status/diff/todo, provider/LSP/MCP status). Built-in first-party features (home tips/footer, five sidebar panels, notifications, plugin manager, which-key, diff viewer) are implemented through this exact same mechanism, not privileged internal code. Plugin loading/activation/config discovery/npm installation remain the responsibility of the hosting CLI, not the TUI package itself.

**Clipboard.** Copy always emits a terminal-native OSC 52 escape sequence (works over SSH, tmux/screen-aware), redundantly backed by a platform-specific native command (AppleScript, Wayland/X11 tools, PowerShell, or a bundled fallback library) resolved once and cached. Paste/read supports both plain text and images (platform-specific image extraction), routed to either a text insertion or a file attachment depending on MIME type. Mouse-drag text selection auto-copies on release with a toast confirmation.

**Notifications ("attention").** An opt-in (disabled by default) subsystem can trigger an OS-level terminal notification and/or a themed sound for events such as a permission or question needing input, a session finishing, or a session erroring — each independently gated by terminal focus state (default: OS notifications only when the terminal is unfocused, sounds always), with message text sanitized (ANSI/control characters stripped, length-capped) before being handed to the terminal. Sounds are organized into swappable named packs with per-event overrides.

**Windows-specific handling.** A small native (`kernel32.dll`) shim disables the console's default Ctrl+C signal delivery so Ctrl+C flows through the app's own keymap instead of killing the process outright, with a persistent guard that re-applies the fix if the console mode gets reset mid-session, and flushes any buffered console input on exit so it doesn't leak into whatever runs next in the terminal.

## Business rules & edge cases

- **Agent cycling vs. picking are different affordances.** `Tab`/`Shift+Tab` always cycle through agents directly and never open a dialog; the only way to see a searchable agent list is the explicit agent-list command/slash command. The same duality exists for models (function-key cycling vs. `/models` dialog).
- **Concurrent-submit race is explicitly guarded.** A module-level "submitting" flag prevents a second near-simultaneous submit trigger (e.g., double-pressed Enter racing a keybinding-dispatched submit) from creating a second, empty-prompt session while the first submit's async session-creation is still in flight — a previously real bug (the second call would read the input *after* the first had already cleared it, sending an empty prompt into a brand-new orphaned session).
- **Permission requests bubble to the parent, never render inside a subagent's own view.** A subagent (child) session's permission/question requests are surfaced in the *parent* session's transcript, gated by a check that the currently open session has no `parentID`; only one pending request renders at a time, in arrival order, with the rest queued silently.
- **"Denied" is a distinct rendering state from "error."** A failed tool call is only shown as a struck-through "denied" row (rather than a hard failure box) when its error text matches a small set of known permission-rejection phrases; everything else is a generic error.
- **Long tool output and long pastes are budgeted, not unlimited.** Tool output is truncated by both a line count and a character budget (scaled to terminal width) with a two-stage fallback (line-truncate, then hard character-truncate); large text pastes are collapsed into a placeholder rather than inserted verbatim, both reversible/expandable by the user.
- **History, stash, and the ephemeral "last draft" are three separate persistence layers** with different scopes and lifetimes: history auto-records on submit/clear (deduped on exact repeat, capped at 50), stash is an explicit user action (multi-slot, capped at 50), and the last-draft cache is a single in-memory slot restored only when the *new* composer instance is otherwise empty.
- **Frecency decays with time but rewards repetition**, biasing the `@`-mention ranking of non-file results (files themselves are pre-ranked server-side); this is a client-local heuristic, not a server-tracked value.
- **Leader-key sequences expire.** A pending leader combination is cleared after a configurable timeout so an abandoned leader press doesn't linger and hijack a later unrelated keystroke.
- **Environment capability forces specific keybind behavior.** When the hosting environment reports that terminal-suspend (Ctrl+Z-to-background) isn't supported, the TUI both disables the suspend binding and — unless the user explicitly bound something else — repurposes `Ctrl+Z` for input-undo, so the key isn't simply dead.
- **Revert/redo is a display layer over a server-side operation.** Undo re-populates the prompt with the reverted message's text/attachments for editing and resubmission; redo (with a confirmation dialog) either steps forward to the next later user message or fully clears the revert state — the TUI never computes the actual file reversion itself, only summarizes the affected files from the diff the server returns.
- **Draft-blocking operations gate submission.** A prompt cannot be submitted while an in-progress workspace creation or session-move is pending, or while a mention/slash-command popup is open.
- **Config validation degrades gracefully, never crashes startup.** An invalid or unreadable config file/keybind override/plugin spec is logged and skipped (not merged), and the app continues with whatever configuration did parse.
- **Plugin failures are isolated.** A plugin that fails to activate has its partial registrations (commands/routes/slots/subscriptions) rolled back and the rest of the app keeps running; plugin cleanup has a fixed time budget and a timeout is logged rather than blocking shutdown.
- **Session listing can be directory-scoped or project-wide**, toggled by a persisted flag, changing the session-list query from "sessions under the current path" to "all sessions in the project."

## Workflows & states

1. **Startup:** acquire renderer → install keymap/plugins → mount provider tree → SDK client connects and opens the event stream → sync bootstrap runs a blocking phase (project/session-list-if-continuing/providers/agents/config in parallel) then a non-blocking phase (LSP/MCP/formatter/VCS/console status) → startup screen dismisses once the blocking phase completes (or immediately under a fast-boot flag) → initial route resolves (explicit override, `--continue`/`--session` args, or home).
2. **Live update:** server emits events over the stream → coalesced in ≤16ms batches → applied to reactive session/message/permission/question/catalog state → transcript, footers, and dialogs re-render incrementally without a full remount.
3. **Reconnection:** a dropped event stream is retried by the client itself with exponential backoff, transparent to the rest of the app; a reported server-instance restart instead triggers the app to discard and re-run its entire bootstrap sync.
4. **Prompt submission:** user types (with `@`/`/`/`!` mode detection) → Enter (guarded against races/blocking states) → dispatch as shell command, slash command, or normal prompt → session created on demand if none exists → composer cleared and appended to history → transcript scrolls to bottom.
5. **Tool-call lifecycle:** pending (verb text) → running (spinner, live partial output for streaming tools) → completed (final rendering, diff/output/summary) or error/denied (color + click-to-expand) — independent per tool call, several of which can be in flight/visible per assistant turn (e.g. a `task` delegation's own nested tool calls).
6. **Permission lifecycle:** request arrives → queued (or auto-answered in auto-approve mode) → shown if it's the oldest pending → user picks Allow once / Allow always (with a rule-confirmation step) / Reject (with a free-text step for subagent-originated requests) → reply sent to the server → request removed from the queue on the corresponding "replied" event.
7. **Revert/redo:** user invokes undo → in-flight run aborted if needed → server reverts to the prior user message → transcript collapses affected messages into a summary banner and refills the prompt for editing → redo (confirmed) either steps to a later revert point or fully restores.
8. **Theme change:** open theme picker → arrow through list (each entry live-applied for preview) → Enter commits and persists the choice, Escape reverts to the previously active theme.
9. **Provider/model connection:** open model dialog with no compatible provider connected → prompted to connect → provider list → auth method selection (OAuth device/code or API key, plus provider-specific extra fields) → success re-bootstraps the client and returns to the model dialog scoped to the newly connected provider.
10. **Plugin lifecycle:** internal plugins load first, then external ones (skippable via a "pure" flag) → each plugin's registrations (routes/commands/slots/subscriptions/dispose-hooks) are tracked → on failure, that plugin's registrations are rolled back; on shutdown, cleanup runs in reverse registration order under a fixed time budget.

## Data

- **Route value:** a tagged union — home (optional pending prompt info), session (session id, optional pending prompt info), or plugin (plugin-assigned name plus opaque params); held in a single reactive store, replaced wholesale on navigation.
- **Keybind definition:** name → `{ default binding string(s), human description }`; a binding string supports comma-separated alternatives, a `<leader>` token, and `false`/`"none"` to unbind; user overrides are validated against the known name set and merged over the compiled-in defaults, with two forced exceptions applied last (suspend-unsupported handling, described above).
- **Resolved TUI config:** theme name; per-command keybind overrides; plugin specs and per-plugin enabled flags; leader-key timeout; attention/notification settings (enabled flag, notifications-on/off, sound-on/off, volume 0–1, active sound pack, per-event sound file overrides); prompt sizing (max height/width); scroll speed/acceleration; diff display style (auto vs. always-stacked); cursor style/blink; mouse on/off.
- **Theme document:** an optional map of named color aliases plus a map of ~50 semantic slots (brand/status/text/background/border colors, a diff palette, a markdown palette, a syntax-highlight palette, and a "thinking" opacity value); each slot's value is a literal color, an alias reference, an ANSI index, or a `{dark, light}** pair.
- **Local persisted state** (small JSON/JSONL files under a per-user state directory, independent of any server): current/recent/favorite models and variants, pinned/quick-switch session slots, per-project MCP enable/disable, permission auto-approve mode, a generic small key-value store (used for theme selection, thinking-display mode, which-key layout, sound-pack selection, tips visibility, etc.), prompt history (capped 50 entries), prompt stash (capped 50 entries), and `@`-mention frecency records (capped 1000 entries, `frequency`/`lastOpen` per path).
- **Permission request (as surfaced to the TUI):** an id, the target permission kind (edit/read/list/glob/grep/bash/task/webfetch/websearch/external_directory/doom_loop/other) with kind-specific detail fields (path, pattern, command, url, diff, directory+patterns), an "always" rule description, and the owning session id — used to render the type-specific summary and the "allow always" confirmation text.
- **Question request:** one or more sub-questions, each with predefined options (single- or multi-select) and an optional custom free-text answer slot.
- **Tool part (as rendered):** tool name, input arguments, a status (pending/running/completed/error), an output payload (only meaningful once completed), and an optional structured "metadata" object specific to that tool (e.g. a diff, diagnostics, or nested child tool calls) — treated as loosely-typed/`unknown` at the rendering boundary so unrecognized or evolving tool shapes never crash the view.

## Interfaces

- **Consumes (not documented here):** the Client SDK / Embedded Client feature. The TUI's only allowed dependency on OpenCode's domain state and actions is the generated SDK client — it may not import server, core, or CLI internals directly. The SDK is created with a base URL plus an optional custom `fetch` and event-source pair, letting the exact same TUI code run against a real network server, a spawned local server, or a fully in-process (embedded) backend with no behavioral difference. See the Client SDKs & Embedded Client dossier for the call surface and streaming/error contract this relies on.
- **Consumes (not documented here):** Session & Conversation Runtime, Agent/Subagent/Skill System, Permission System, Tool System, and Command System — the TUI only *surfaces* their state (messages, permission/question requests, tool call parts, agent/model catalogs, command list) and *drives* their operations (prompt, revert/unrevert, fork, permission reply, question reply/reject, session/model/agent switching) through SDK calls; it implements none of their business logic and tolerates unknown/evolving wire shapes from them (generic fallback rendering for unrecognized tools, loosely-typed tool metadata).
- **Consumed by two CLI hosts** (outside this package): a "legacy" host that can launch the TUI against an in-process worker thread (RPC bridge exposing a synthetic `fetch` and event source, avoiding a real network hop), against a spawned/externally reachable local HTTP server, or attached to a remote server URL with basic-auth headers; and a "new" CLI host that launches the same package against its own authenticated daemon transport. Both hosts own: command-line argument parsing, process/worker/server lifecycle, authentication, config file discovery/precedence/migration across global/project/`.opencode` layers and an environment-variable override, plugin package discovery/installation, and Windows process-level signal policy — none of which lives inside the TUI package. The TUI package's own config module only performs schema validation, defaulting, and keybind compilation on the single pre-resolved object it's handed.
- **Adjacent, out-of-scope sibling surface:** a separate "mini"/direct interactive mode (`--mini`) implemented entirely inside the CLI host packages (not `packages/tui`) offers a lighter split-footer terminal experience (immutable scrollback plus a mutable footer for prompt/status/permission UI) for the same session/permission/question concepts, sharing the SDK boundary but none of the TUI package's rendering code.
- **Exposes a plugin authoring contract** (`@opencode-ai/plugin/tui`) distinct from the server-side plugin contract — a TUI plugin module can register routes, keymap layers/commands, UI slots, dialogs, themes, and attention/notification requests, and reads live but read-only session/provider/LSP/MCP state; it cannot alter tool-call rendering dispatch (that dispatch table is fixed) but can add adjacent UI (new routes, sidebar/footer content, palette commands).

## Error handling

- **A dedicated crash screen** (not the normal theme system, in case theming itself is what crashed) catches any otherwise-uncaught render error, showing the error message, a scrollable stack trace, and three recovery actions: copy a pre-filled bug-report (with a length-budgeted stack trace) to the clipboard, restart, or quit; Ctrl+C always quits immediately regardless of the screen's own state.
- **Startup bootstrap failures are fatal by default**: a failure in the blocking phase (project/session/provider/agent/config fetch) tears down the whole app and reports the error after cleanup completes, rather than partially rendering; a distinct non-fatal path exists for the reconnect-after-server-restart case.
- **Streaming reconnection is automatic and silent** at the transport layer (exponential backoff up to a capped delay) and does not reset application state; a detected full server-instance restart instead intentionally discards and rebuilds all synced state.
- **Config and plugin errors degrade rather than abort**: unreadable/invalid config files, unknown keybind names, and plugin activation failures are all logged and skipped, leaving the rest of the configuration/plugin set intact; a plugin's own cleanup work is time-boxed and a timeout is logged rather than blocking application shutdown.
- **Tool-call and per-message failures render locally**, in place, without affecting the rest of the transcript — a malformed or unexpected tool metadata shape falls back to generic rendering instead of crashing the message list.
- **Specific defensive fixes are covered by regression tests**, e.g., a session-messages fetch that returns without a `data` field (an observed server error condition) is defaulted to an empty list rather than throwing, and the concurrent-submit race described above is closed with an explicit in-flight guard.
- **Recoverable, actionable failures get a purpose-built dialog** rather than a toast or crash screen — for example, failing to delete a session because its workspace disappeared offers "delete the workspace" or "restore into a new workspace" as explicit next steps.

## Non-functional observations

- **Strict one-directional package boundary.** The TUI package may depend only on the SDK's generated client contract, never on the server, core business logic, or either CLI host package — enforced as an explicit architectural rule (not just convention) so the same TUI binary works unmodified against a local, embedded, or fully remote backend.
- **Render efficiency is a deliberate design point**: incoming server events are batched into small time windows before being applied to reactive state, and the renderer targets a fixed 60fps, keeping a terminal UI responsive even under a fast token stream.
- **Extremely broad but shallow-composed surface.** On the order of 150 named, individually rebindable commands, 33 bundled themes, and dozens of dialogs/routes/tool renderers, almost all built from a small number of shared primitives (one list-picker, one prompt dialog, one confirm dialog, one alert dialog, one slot registry) rather than bespoke code per feature — the size comes from breadth of coverage, not structural complexity.
- **Unknown/evolving backend data is treated as a first-class case, not an afterthought**: tool call input/output/metadata is handled as loosely-typed data with local guards and a generic fallback renderer specifically so that new or third-party tools, and future wire-format changes, never require the TUI to recognize them in advance.
- **TUI-local state is intentionally kept local.** Prompt history/stash/frecency, recent/favorite models, pinned sessions, theme selection, and similar per-user conveniences are persisted to local files rather than pushed to the server, unless a specific product reason promotes them to shared/server state.
- **The TUI's internal plugin/slot mechanism is used for its own first-party features**, not reserved for third parties — home tips, sidebar panels, notifications, and the diff viewer are all implemented as ordinary (built-in) plugins through the same API surface an external author would use, which keeps that extensibility contract exercised by the product's own UI.
- **Colocated tests double as a behavior specification** for this feature: keybinding precedence and mode-gating, config resolution/override edge cases, prompt-race and reconnect/resync scenarios, diff-viewer file-tree construction, and inline tool-rendering snapshots are all directly asserted in the package's own test suite rather than only described in documentation.

## Acceptance criteria — 6-8 Given/When/Then statements

1. **Given** the prompt composer is focused with no autocomplete popup open, **when** the user presses Tab (or Shift+Tab), **then** the active agent for the session immediately cycles to the next (or previous) available agent and the composer's header reflects the new agent — no picker dialog opens.
2. **Given** a user triggers prompt submission twice in rapid succession (e.g., a double Enter press) before the first submission's session-creation call has resolved, **when** both triggers are processed, **then** exactly one session receives the typed text and no second, empty-prompt session is created.
3. **Given** a permission request arrives for a top-level (non-subagent) session while auto-approve mode is off, **when** the user selects Reject, **then** a reply of kind "reject" is sent immediately with no further prompt; **given** the same request instead belongs to a subagent session, **when** the user selects Reject, **then** the user is first offered a free-text field and that text (or nothing) is included with the rejection.
4. **Given** a tool call's execution fails, **when** the failure message matches a known permission-rejection phrase, **then** the call renders as a struck-through "denied" row; **given** any other failure, **when** it renders, **then** it appears as a standard error row with click-to-expand detail — the two states are visually and semantically distinct.
5. **Given** the live event stream to the server is interrupted, **when** the interruption is a transient stream drop, **then** the client reconnects automatically with increasing backoff and existing session/message state is preserved; **given** instead the server reports its own instance was disposed/restarted, **when** that event is received, **then** the application discards and re-fetches its entire synced state (project, sessions, providers, agents, config) rather than only reopening the stream.
6. **Given** the theme picker is open, **when** the user moves the selection cursor across entries, **then** each highlighted theme is applied live for preview; **when** the user presses Escape without confirming, **then** the theme reverts to whatever was active before the dialog opened, and only an explicit Enter persists the new choice.
7. **Given** a file diff is being displayed (inline in a tool call, in a permission prompt, or in the full-screen diff viewer), **when** the available width is below the split-view threshold or the configured diff style forces a single-column layout, **then** the diff renders unified (stacked) instead of side-by-side, with line numbers and syntax highlighting in both modes.
8. **Given** the hosting environment does not support suspending the terminal (e.g., a platform/multiplexer limitation reported to the TUI), **when** the resolved configuration is built, **then** the terminal-suspend binding is disabled and, unless the user explicitly bound something else, `Ctrl+Z` is remapped to trigger input-undo instead of being left inert.

## Confidence & open questions

**High confidence** (directly read in source and/or asserted by colocated tests): the provider/context bootstrap order and SDK connection/reconnect behavior; the route model and session-to-route resolution rules; keybinding definitions, defaults, leader-key/timeout mechanics, mode-gating, and the terminal-suspend-unsupported override; the prompt editor's `@`/`/`/`!` mode detection, attachment/paste handling, history/stash/frecency persistence and their capacity/dedup rules; the prompt-submission race-condition guard (backed by a dedicated regression test); tool-call rendering dispatch, truncation budgets, and the denied-vs-error distinction; the permission-prompt workflow (choices, subagent-reject free-text step, queueing, auto-approve mode); the diff viewer's navigation and source-selection behavior; the theme document schema, built-in theme count, and live-preview-then-commit picker behavior; the clipboard read/write mechanism (OSC 52 plus native fallback); the attention/notification gating and sound-pack model; the TUI's own plugin/slot API surface (drawn from an in-repo technical reference document in addition to source); and the package-boundary rule restricting the TUI to the SDK only (drawn from an in-repo migration/architecture specification in addition to import-graph evidence).

**Medium confidence / inference:** the precise end-to-end shape of "workspace" as a product concept (it is explicitly flagged experimental behind a feature flag in the code and its full lifecycle spans server-side behavior not covered by this dossier); the exact set of trigger points that call into the notification subsystem beyond the ones directly observed (permission/question asked, session idle/errored) — a built-in "notifications" plugin owns this mapping and could grow additional triggers without changing the delivery mechanism described here; the "mini" interactive mode was confirmed to exist as a sibling surface but was intentionally not traced in depth since it lives outside `packages/tui`.

**Open questions for a reimplementing team:**
- Whether the "which-key" hint panel and the multi-workspace feature are meant to graduate from opt-in/experimental to default-on in the product's intended future state, versus remaining permanently optional — no explicit roadmap marker was found in this snapshot.
- The full session/permission/question wire schemas (exact field sets per permission kind, per tool's metadata shape) are treated deliberately loosely by the TUI (typed as `unknown` at the boundary with local guards); a reimplementation needs the authoritative schema from the Server/SDK contract rather than this dossier's per-tool behavioral summary.
- Whether the two coexisting event-sourced state layers observed in the codebase (an older per-session sync store and a newer "v2" event-reduced data store covering messages/permissions/questions/catalogs) are a permanent architectural split or a mid-migration duplication that a from-scratch implementation should collapse into one.
- The exact scope of what must be reproduced from the two CLI hosts' transport modes (in-process worker RPC, spawned local server, remote attach) versus treating "a base URL plus optional custom fetch/event source" as the only contract the reimplemented TUI needs to honor — this dossier treats the transport modes as adjacent/host-owned and out of scope for the TUI feature itself.
