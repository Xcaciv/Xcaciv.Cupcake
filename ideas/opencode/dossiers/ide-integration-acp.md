# Feature: IDE Integration & ACP

## Purpose

Two related capabilities let OpenCode work naturally inside a code editor rather than only in a bare terminal:

1. **IDE detection & editor-extension helper** — lightweight heuristics that let the CLI recognize it is running inside a supported editor's integrated terminal, plus a helper to install a companion editor extension, plus that extension's own logic (a VS Code extension) for opening an OpenCode terminal and pushing "current file / current selection" context into it.
2. **Agent Client Protocol (ACP) server** — a standards-based agent backend (`opencode acp`) that speaks a JSON-RPC protocol over stdio so *any* ACP-compatible editor/client (Zed, other ACP clients) can drive OpenCode as their agent: creating/loading/resuming/forking sessions, sending prompts with rich content, switching model/effort/mode, granting tool permissions, and receiving streamed responses, tool-call progress, and usage/cost telemetry — without needing OpenCode's native HTTP/TUI client.

Both let an outside editor treat OpenCode as an embeddable coding agent instead of a standalone CLI.

## Behavior

### IDE detection (heuristic, editor-terminal side)
- Detection only fires when the process's `TERM_PROGRAM` environment variable equals `vscode` (this is set by VS Code-family integrated terminals). It then inspects the `GIT_ASKPASS` environment variable (a path VS Code-family apps set to their bundled git-askpass helper) and returns the first known IDE display name whose name is a substring of that path: `Windsurf`, `Visual Studio Code - Insiders`, `Visual Studio Code`, `Cursor`, `VSCodium`. If `TERM_PROGRAM` isn't `vscode`, or none of the known names match, the result is `"unknown"`.
- A separate, independent check (`alreadyInstalled`) reports true only if `OPENCODE_CALLER` equals `vscode` or `vscode-insiders` — this env var is set by the companion editor extension when it spawns OpenCode's terminal, so this is really "was I launched by the extension," not "is the extension installed."
- An install routine can invoke the detected IDE's own CLI binary (`code`, `code-insiders`, `cursor`, `codium`, `windsurf`) with an `--install-extension <extension-id>` flag to install the companion extension, distinguishing "already installed" (extension CLI reports it) from a hard failure (non-zero exit, stderr captured).
- A retired wire event (`ide.installed`) exists in the shared event catalog for backward-compatible decoding of old event logs but is explicitly excluded from the current/"latest" public event set — new code must not emit it.
- **Caveat for the reimplementation team:** at the pinned snapshot, none of the detection/alreadyInstalled/install primitives are invoked anywhere else in the CLI, TUI, or server startup path — only unit tests exercise them. Treat the *primitives* (how to detect, how to install) as a solid spec, but the *trigger* (when/whether to auto-prompt install on startup) is not observable in this snapshot and must be decided by the reimplementation team or reconstructed from product intent.

### Editor-extension side (VS Code extension)
- Registers three editor commands:
  - **Open new terminal** / **Open terminal (or focus existing)**: creates (or focuses) an integrated terminal literally named `opencode`, on a random local TCP port (16384–65535), launches `opencode --port <port>` in it with environment variables identifying the caller (`OPENCODE_CALLER=vscode`) and exposing the chosen port to later commands. It then polls a local health endpoint on that port (up to 10 tries, 200 ms apart) to detect once OpenCode's server is ready.
  - Once ready, if the editor's active file is known, the extension composes a file reference string of the form `@<workspace-relative-path>` and, if there is a non-empty text selection, appends a line locator: `#L<line>` for a single-line selection or `#L<start>-<end>` for a multi-line one (both 1-based). This reference, prefixed with `In `, is delivered to the running OpenCode instance's prompt input over HTTP if the server became reachable in time, or typed directly into the terminal as a fallback.
  - **Add current file to terminal**: on demand, builds the same `@path[#Lstart-end]` reference (without the `In ` prefix) for the active editor and either posts it to the OpenCode instance running in the currently focused `opencode` terminal (using the port that terminal was created with) or, if the port can't be determined, types it directly into the terminal.
- This is the concrete mechanism by which "the IDE tells OpenCode what file/selection is open" — it is push-based (editor decides when to send) and happens by literally inserting an `@file#Lx-y` reference into the prompt text, not via a separate structured "context" channel.

### ACP server

- Started via a dedicated CLI subcommand (`opencode acp [--cwd <dir>] [network options]`). On startup it: (1) boots OpenCode's normal embedded HTTP server on an ephemeral/configured port, (2) creates an OpenCode client pointed at that server, (3) wires the process's stdin/stdout as a newline-delimited-JSON duplex stream, and (4) hands that stream to an ACP connection object bound to an "Agent" implementation. The process stays alive until stdin closes (clean exit) or errors.
- **initialize**: reports protocol version `1`; capabilities including session load, MCP support (both HTTP and SSE-transported MCP servers), prompt capabilities (embedded resource context, images), and session capabilities (`close`, `fork`, `list`, `resume` all advertised). Exactly one auth method is offered, `opencode-login` ("Run `opencode auth login` in the terminal"); if the connecting client declares it understands an out-of-band "terminal-auth" mechanism, the auth method is additionally annotated with a runnable command (`opencode auth login`) the client can execute on the user's behalf. Agent identity is reported as `OpenCode` with the running installation's version string.
- **authenticate**: accepts only the `opencode-login` method id; any other id is rejected as an invalid parameter (no method actually performs interactive login through this call — the real login happens out-of-band via the CLI).
- **newSession**: loads (and caches, per working directory) a "directory snapshot" — available model/provider list, available modes (non-hidden, non-subagent agent profiles), available slash commands (including skills exposed as commands, added only if their name doesn't already collide with a real command), and any explicitly configured default model. It creates a backing conversation on the embedded server, chooses a starting model (configured default → best model from the "opencode" built-in provider → best model across all providers, in that priority — deliberately does **not** look at prior session history, to keep first-session startup fast and deterministic), chooses a starting "effort" variant if the model supports variants (prefers one literally named `default`), and chooses a starting mode if any non-hidden top-level agent profiles exist. Any MCP servers the client passed at session-creation time are registered against the backing session. The client is asynchronously notified of the available slash-command list. The response returns the new session id plus the current values of the exposed config options (see Data section).
- **loadSession / resumeSession / forkSession**: all re-derive model/variant/mode by scanning recent message history for the most recent message that carries an explicit model selection (preferring the latest *user* message with a model over the latest *assistant* message), falling back to the same default-model logic as newSession if none is found. `resumeSession`/`forkSession` only look at the most recent slice of history (last 20 messages) for this purpose. **Only `loadSession` replays the full prior transcript** back to the client as a stream of message-chunk notifications (text, file, reasoning) plus reconstructed tool-call updates — this matches the semantics of "the client has no local copy of this session and needs it primed," whereas resume/fork assume the client already has (or doesn't need) the transcript and only need the config state restored.
- **listSessions**: merges sessions created via this ACP connection but not yet visible in the backend's own session list ("live" sessions) with the backend's list, de-duplicated by id, sorted by most-recently-updated first, and paginated (page size 100) using an opaque cursor derived from an updated-at timestamp. Can be scoped to one working directory or span all of them.
- **closeSession**: discards local ACP bookkeeping for the session and best-effort aborts its currently running backing turn (a failed abort is logged and swallowed, never surfaced to the caller). Closing an unknown/already-closed session id is a no-op success, not an error.
- **cancel**: aborts the backing turn but — unlike close — deliberately keeps the ACP session alive so the client can keep prompting the same session afterward.
- **setSessionConfigOption / setSessionMode / setSessionModel**: validate the requested model/effort/mode against the cached directory snapshot for that session's directory and reject unknown values with a specific invalid-parameter error naming which field was invalid. These mutate only the lightweight in-memory ACP session record — they never re-fetch providers, agent modes, commands, or skills, which keeps switching model/effort/mode fast (confirmed by tests asserting call counts stay flat across repeated switches within one warm session/cwd).
- **prompt**: converts ACP's rich content blocks — plain text (optionally flagged as assistant-only "synthetic" or user-only "ignored" via an audience annotation), inline images, embedded text/binary resources, and resource links (including `file://` and editor-specific `zed://` URIs) — into OpenCode's internal message-part format. If the textual content of the prompt starts with `/`, it's treated as a slash command: a name matching a known command/skill is routed to the command-execution API; the literal command `/compact` is special-cased to trigger conversation summarization; anything else falls through to a normal prompt turn. Every one of these calls only resolves once the corresponding backend turn is not just complete but the *last queued client notification for that turn has actually been delivered* — this prevents a race where the JSON-RPC response for `prompt` arrives at the client before the final content/tool-call update it describes. After every prompt/command/compact call, if the model's context-window size is known, a token-usage/cost notification is pushed to the client.
- **Turn outcome mapping**: a clean finish reports `end_turn`; an aborted turn reports `cancelled`; a turn that hit an output-length ceiling reports `max_tokens`; a turn blocked by a content filter reports `refusal`; a turn that failed because a provider needs (re-)authentication is surfaced as a protocol-level "authentication required" error (not a stop reason) naming the provider; any other backend failure is surfaced as a generic internal error carrying only a curated, safe message (provider-supplied message text if present, otherwise a generic fallback) — raw stack traces, secrets, or other sensitive failure detail are never forwarded to the client.
- **Live event → protocol notification translation**: the server subscribes once to OpenCode's internal event stream and keeps a background loop reconnecting (with a fixed short backoff) whenever the stream drops. It tracks enough per-message-part metadata (role, part type, whether the part is "ignored") to correctly classify streamed deltas as assistant text, assistant "thinking"/reasoning, or user text notifications, falling back to an explicit re-fetch of the message if a delta arrives before its part's metadata has been seen. Tool invocations are mirrored through a pending → running → completed/error tool-call lifecycle, with tool kind inferred from the tool's name (execute/fetch/edit/search/read/think/other), file/URL/working-directory "locations" extracted per tool type, diff content synthesized for edits, image attachments filtered out of arbitrary attachments, and duplicate "running" shell snapshots (same captured output as last time) suppressed so the client isn't spammed with no-op updates.
- **Permission bridging**: when the backend asks for a tool-use permission, it is translated into an ACP permission request offering exactly three choices — allow once, always allow, or reject — with a human-readable title/location/diff-preview built from the tool's name and input. Permission requests for the same session are processed strictly one at a time (serialized). If the connected client doesn't support permission requests at all, or the request itself errors, the permission is auto-rejected rather than left hanging. Approving an edit-type permission additionally best-effort pushes the resulting file content to the client (by applying the proposed diff to the file's current on-disk content) so editors that show live diffs stay in sync; a diff that fails to apply, or a client that can't accept file writes, silently skips this step without failing the permission grant itself.
- **MCP server passthrough**: MCP servers supplied by the client when creating/loading/resuming/forking a session are registered with the backend (as either a local command+args+environment server or a remote URL+headers server). Registering the same server name again with an unchanged configuration for a session that already has it is skipped; registering it again with a *different* configuration is not skipped (it's added again).
- **Diagnostics**: setting an environment variable enables verbose stderr timing lines for major internal operations (server startup, directory-snapshot load and each of its sub-fetches, session creation, MCP registration); this is off by default and has no effect on protocol behavior.

## Business rules & edge cases

- IDE name detection is a **heuristic string match** on an inherited environment variable, not a capability handshake — it can misfire if a user manually sets `TERM_PROGRAM`/`GIT_ASKPASS`, and returns `unknown` for any unrecognized or non-VS-Code-family editor.
- New-session default-model resolution deliberately avoids scanning session history (only load/resume/fork do), to keep first-turn startup latency predictable; reimplementations must preserve this asymmetry rather than "optimizing" newSession to also look at history.
- A failed directory-snapshot load (e.g., a provider-auth failure while listing providers) is **not cached** — the next attempt for that same directory retries from scratch — while a *successful* snapshot is cached for the life of the connection per working directory and shared across all sessions opened against that directory.
- `closeSession` and `cancel` are asymmetric: close tears down ACP-side state (subsequent operations on that id fail as "session not found"), cancel does not (subsequent operations on that id still succeed) — this distinction must be preserved exactly.
- Selecting an unknown model, an effort/variant not offered by the currently selected model, an unknown mode id, or an unknown config option id must each fail with a distinguishable "invalid parameter" error rather than a generic failure, so clients can react appropriately (e.g. re-render valid choices).
- The `/compact` slash command is hard-coded special behavior distinct from ordinary named commands — it triggers summarization instead of the generic command-invocation path, and, unlike a normal command or prompt, does not itself carry token usage data back beyond the base response shape.
- Auth-required failures must always be classified as a dedicated "authentication required" protocol error (never generic internal error), including when the underlying failure is nested inside a lower-level provider error, so clients can prompt for credentials instead of showing an opaque error.
- Error responses must never leak sensitive detail (API keys, tokens, raw stack traces) — this is explicitly enforced/tested, not incidental.
- Un-set the exposed "mode" config option is expected to be absent from the response when the working directory truly has no selectable modes (only a single/default agent) — presence is conditional, not always emitted.
- Skills are folded into the same "available commands" list as real slash commands, but only when they don't collide by name with an actual command.
- Editor-provided file/resource URIs are handled defensively: unparseable or unsupported URIs degrade gracefully to a plain text block rather than erroring the whole prompt.

## Workflows & states

**ACP connection lifecycle**: process start → embedded HTTP server boot → stdio stream wrapped as JSON-RPC → `initialize` (capability + auth-method exchange) → optional `authenticate` → one or more sessions, each independently walking `newSession | loadSession | resumeSession | forkSession` → zero or more `prompt` / `setSessionConfigOption` / `setSessionMode` / `setSessionModel` / `cancel` calls → `closeSession` (optional, explicit) → process exit on stdin EOF.

**Per-session config state** (in-memory, not persisted by the ACP layer itself — the backing conversation is the durable record): id, working directory, registered MCP servers, selected model, selected effort/variant, selected mode, and a map of "known" message-part metadata used to correctly classify streaming deltas.

**Per-turn "idle" gating**: prompt-triggered backend calls (prompt / command / compact) are wrapped so their completion is deferred until the live-event subscriber has drained every update queued for that session's turn — this couples the request/response cycle to the async notification stream to guarantee ordering from the client's point of view.

**Editor-extension terminal workflow**: command invoked → terminal created (or focused) with a random port → OpenCode process launched in it → extension polls a readiness endpoint (bounded retries) → once ready, active-file/selection reference delivered into the running instance's prompt.

## Data

- **IDE identity**: one of a fixed enum of known editor display names, or `unknown`; not a rich structured object.
- **Retired event** `ide.installed` — payload is simply an IDE name string; present only for legacy decode compatibility, excluded from the "current" event catalog.
- **ACP session record**: id, working directory, list of MCP server descriptors (name + local command/args/env or remote url/headers), creation time, selected model (provider id + model id), selected effort/variant string, selected mode id, and a lookup of per-message-part metadata (message id, part id, part type, role, "ignored" flag, associated tool-call id, arbitrary metadata) used only internally for delta routing.
- **Directory snapshot** (cached per working directory): the provider→model catalog, a flat list of selectable models, a map from `provider/model` to that model's available effort variants, the list of selectable modes plus which one is default, the sorted list of available slash commands (including skill-derived ones), and an optional configured default model.
- **Config options surfaced to the editor** (returned on every session create/load/resume/fork/config-change): a "model" select (grouped by provider, value format `provider/model`, optionally `provider/model/variant`), an "effort" select (present only if the current model has variants; values are the variant keys, human-readable names derived by title-casing hyphen/underscore-separated words), and a "mode" select (present only if modes exist; values are mode/agent ids and display names, with optional descriptions).
- **Usage/cost data**: per-turn token usage broken into input/output/thought(reasoning)/cached-read/cached-write/total counts, plus a running total conversation cost, plus the model's total context-window size (looked up once per directory+provider+model and cached).
- **Tool call representation**: an id, human title (tool-specific — e.g. the actual shell command for shell tools, a URL for fetch, a search pattern for grep/glob, a resolved file path/count for file tools), a coarse kind classification, a lifecycle status (pending/in-progress/completed/failed), zero or more "locations" (paths the tool touched or ran in), the tool's raw input (enriched with a resolved absolute working directory for shell tools), and on completion/failure, rendered content (text output, diffs for edits, extracted image attachments) plus raw output/error metadata.

## Interfaces

- **Consumes** (adjacent "Server/HTTP API & Event Bus" feature, not documented here): the ACP process boots and talks to OpenCode's own embedded HTTP server/SDK client exactly as any other client would — session create/get/list/messages/prompt/command/summarize/abort/fork, config/provider listing, agent/skill/command listing, MCP registration, and the global server-sent event stream. ACP behavior is entirely a translation layer over this surface; it introduces no new persistence of its own beyond in-memory session bookkeeping for the life of the ACP process.
- **Consumes** (adjacent "Session & Conversation Runtime" and "Tool System" features, not documented here): message/part shapes, tool-part lifecycle states, and permission-request events are read as already-defined wire shapes and re-projected into ACP's own vocabulary.
- **Exposed to editors**: a JSON-RPC 2.0 protocol (Agent Client Protocol) framed as newline-delimited JSON over the process's stdin/stdout, implementing the standard ACP agent-side method set (initialize, authenticate, session new/load/list/resume/close, an experimental fork, session prompt/cancel, and session config-option/mode/model setters) plus emitting `session/update` and permission-request notifications/calls back to the client.
- **Editor-extension → OpenCode process**: a small ad hoc HTTP surface on the port the extension itself chose when launching OpenCode (a readiness probe endpoint and an "append text to the active prompt" endpoint) — this is part of the adjacent HTTP API surface, only its two call sites are described here.
- **Editor-extension → editor host**: registers named commands the editor's command palette/keybindings can invoke; reads the editor's active document, workspace-relative path, and current text selection to build file references.

## Error handling

- All ACP-layer failures are represented as a small closed set of typed errors (session not found, invalid config option/model/effort/mode, auth required, unknown auth method, unsupported operation, generic service failure) and deterministically mapped to standard JSON-RPC error codes: invalid-parameter errors, a dedicated "authentication required" code, method-not-found, and a generic internal-error code.
- Internal/service failures always carry a curated "safe" message rather than the underlying exception text; the underlying error's stack, secrets, or other unvetted content is never serialized into a client-visible response — this is treated as a hard requirement, not a best-effort nicety.
- Best-effort operations (aborting a backing turn on close/cancel, pushing a proposed-edit file write, sending a usage update, replaying a message during load) all swallow their own failures rather than propagating them, so a secondary/cosmetic failure never fails the primary request.
- Auth-required conditions are detected both when raised directly and when buried inside a wrapped/opaque failure from a lower layer (walked recursively through nested `error`/`data` fields) so the client reliably gets prompted to re-authenticate instead of seeing a generic error.
- A directory snapshot load failure is not cached, guaranteeing the next attempt for that directory gets a fresh try rather than being permanently stuck on a stale failure.
- The editor extension's own HTTP calls (readiness probe, append-prompt) are best-effort with bounded retries and silent fallback to typing directly into the terminal — a slow-starting or unreachable OpenCode process degrades gracefully rather than blocking the editor.

## Non-functional observations

- Directory-snapshot caching (per working directory, shared across sessions) and the explicit "don't scan session history on new-session default-model resolution" rule are deliberate first-turn-latency optimizations, verified by tests that assert exact call counts to backend listing/history endpoints stay flat across repeated operations.
- The "wait for last queued notification before resolving the request" behavior trades a small amount of latency for a stronger ordering guarantee that matters more for correctness (avoiding client-side races) than for raw throughput.
- An optional environment-variable-gated profiling mode emits coarse stderr timing lines for major internal operations, useful for diagnosing startup/latency regressions without instrumenting a full tracing pipeline.
- This is flagged by the task brief as an actively-evolving area (high recent commit churn on the ACP implementation); the two "unstable_"-prefixed protocol methods (fork session, set session model) are an explicit signal from the upstream protocol itself that those specific operations' shapes may still change.
- The IDE-detection module appears to be a dormant/orphaned subsystem in this snapshot (well-tested in isolation, but with no current caller wiring it into a real CLI flow) — a reimplementation should confirm current intended behavior with the product owner rather than assuming the historical "auto-detect and prompt to install" flow is still desired as-is.

## Acceptance criteria — 5-8 Given/When/Then statements

1. **Given** the process's terminal-program indicator is `vscode` and its git-askpass path contains `"Cursor"`, **when** IDE detection runs, **then** it reports the editor as Cursor; **given** the terminal-program indicator is anything else, **then** it reports `unknown` regardless of the askpass path.
2. **Given** an ACP client sends `initialize`, **when** the agent responds, **then** the response advertises protocol version 1, session capabilities for close/fork/list/resume, prompt capabilities for embedded context and images, MCP capabilities for both HTTP and SSE transports, and exactly one auth method (`opencode-login`); requesting authentication with any other method id is rejected as an invalid parameter.
3. **Given** a new session is created in a working directory with a configured default model, **when** `newSession` is called, **then** the returned session uses that configured model (not the first/best available one) and the response's model config option reflects it, and this must not require scanning any prior session history.
4. **Given** an existing session's saved transcript's most recent user message specifies a model/variant/mode, **when** the session is loaded, **then** the session's effort and mode config options reflect that message's values, and the client receives the full prior transcript replayed as message-chunk notifications; **given** the same scenario via resume or fork instead of load, **then** the config values are restored identically but no transcript replay notifications are sent.
5. **Given** a client requests `session/set_config_option` with an effort value the currently selected model does not offer, **when** the request is processed, **then** it is rejected as an invalid parameter without altering the session's stored configuration, and no additional provider/agent/command listing calls are made to answer the request.
6. **Given** a running prompt turn emits streamed reasoning/text chunks to the client, **when** the backend turn actually completes, **then** the `session/prompt` response is not returned to the client until the last such streamed update for that turn has itself finished being delivered.
7. **Given** a tool-use permission is requested while the client does not implement permission requests (or the request itself fails), **when** the agent handles it, **then** the permission is automatically rejected rather than left pending; **given** the client approves an edit-type permission, **then** the agent best-effort pushes the resulting patched file content to the client and never fails the permission grant if that push cannot be applied.
8. **Given** a backend or provider failure occurs during any ACP operation, **when** the error is returned to the client, **then** it is one of the defined protocol error codes (invalid params, authentication required, method not found, or internal error) carrying only a curated safe message — never raw exception text, stack traces, or credential/token material.

## Confidence & open questions

- High confidence on the ACP request/response behavior, error mapping, streaming/notification translation, permission bridging, and config-option semantics — all directly backed by both implementation source and an extensive, behavior-oriented test suite (unit tests against a fake SDK plus subprocess-level tests spawning the real `opencode acp` CLI).
- Medium-low confidence on the **trigger conditions** for IDE auto-detection and extension auto-install: the detection/install primitives are fully specified and tested in isolation, but in this pinned snapshot nothing in the CLI/TUI/server startup path actually calls them — open question for the product/reimplementation owner: is there a still-intended onboarding flow (e.g., "detect VS Code on first run, offer to install the extension") that should be reconstructed, or is this dead code being phased out? The retired `ide.installed` event (explicitly excluded from the current event manifest but kept for legacy decode) supports the "being phased out" reading.
- The VS Code extension's HTTP calls (`/app` readiness probe, `/tui/append-prompt`) are part of the adjacent Server/HTTP API surface and were only read far enough to document the two call sites and their payload shape (`{ text }`) — their full endpoint contracts belong to that adjacent feature's dossier.
- Not investigated: any equivalent editor-context integration for Zed or JetBrains beyond their generic ACP client role (no Zed- or JetBrains-specific extension source was found in this repository at the pinned commit; Zed is referenced only as a URI scheme — `zed://…?path=` — recognized when decoding resource links sent through the ACP protocol).
- Directory-snapshot cache lifetime: confirmed cached for the life of the ACP connection process and invalidated only on load failure; no explicit TTL, size bound, or manual-refresh trigger was found reachable from the ACP surface itself (a `refresh` capability exists on the underlying service but no ACP method currently calls it) — worth confirming this is intentional (a long-lived ACP session's provider/model list would not pick up runtime config changes without a process restart).
