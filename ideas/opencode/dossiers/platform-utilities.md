# Feature: Platform Utilities

## Purpose

A cross-cutting foundation layer of low-level services that almost every other feature in the agent CLI depends on but none of them should have to reimplement: generating stable sortable identifiers, resolving and safely reading/writing files, watching a project directory for changes, spawning and supervising child processes/shell commands, normalizing pasted/attached images to fit model limits, running third-party source-code formatters, and detecting the surrounding runtime (OS, host IDE, executable lookup). It exists so that "get a unique ID", "read this file safely", "run this shell command with a timeout and capped output", and "shrink this image so it fits in a prompt" behave identically everywhere they're used, across Windows/macOS/Linux and inside restricted/sandboxed hosts.

## Behavior

**Identifier generation.** Every persisted entity (session, message, part, event, permission, job, tool call, workspace, pty, question) gets an opaque string ID of the form `<prefix>_<26 chars>`. The 26-character body encodes a 48-bit value (46-bit millisecond timestamp packed with a 12-bit per-millisecond monotonic counter) as 12 lowercase hex characters, followed by 14 random base62 characters. IDs can be generated "ascending" (sort order matches creation order) or "descending" (bitwise-inverted timestamp so newest sorts first — used for reverse-chronological listings). A helper extracts the original millisecond timestamp back out of an ascending ID (not defined/meaningful for descending IDs). A companion "validate-or-generate" call accepts an externally supplied ID and requires it to start with the entity's expected prefix, throwing otherwise; if no ID is supplied it generates one.

**Filesystem access.** All path resolution funnels through a small set of primitives: resolve-to-real-path (following symlinks, falling back to the lexically resolved path if the target doesn't exist yet), containment/overlap checks between two paths (used to prevent path traversal outside a project root), "find upward" (walk from a start directory to the filesystem root or a stop directory collecting every directory that contains a named file/pattern), directory-entry listing with file/directory/symlink/other typing, safe read (missing file or permission-denied both resolve to "no content" rather than raising), JSON read/write, and "write creating parent directories on demand". On Windows, every path is first normalized: forward-slash-with-drive-letter forms produced by Git-Bash, Cygwin, or WSL (`/c/...`, `/cygdrive/c/...`, `/mnt/c/...`) are rewritten to native `C:/...` form, and resolved paths are canonicalized to the filesystem's on-disk casing so two different textual paths that point at the same file compare equal (important for case-insensitive filesystems and for using resolved paths as cache keys).

A higher-level "project file system" service constrains all reads/lists to a project root: any resolved path that escapes the configured root directory (after symlink resolution) is treated as a fatal error, not a soft failure. It exposes read (rejects directories), list (rejects files, returns entries sorted directories-first then alphabetically, directory entries suffixed with a path separator), fuzzy "find" by name, glob, and content grep — the last three delegate to either a native high-performance file-indexer library or, as a fallback (or when a feature flag disables the indexer), an external ripgrep-based search backend.

**Ignore/protected-path policy.** A fixed built-in list of build/dependency/VCS directory names (node_modules, .git, dist, target, __pycache__, .venv-style caches, etc.) and file glob patterns (swap files, logs, OS metadata files, coverage output) is used to decide what to exclude from search, indexing, and file-watching. Matching walks path segments for exact folder-name hits and glob-matches the remaining file patterns; callers may add extra patterns or a whitelist of patterns that force a path to NOT be treated as ignored. Separately, an OS-specific "protected paths" list (the user's Pictures/Music/Movies/Library-internals on macOS, AppData/Documents/Desktop-style folders on Windows) marks directories that must never be watched or scanned even if not otherwise ignored — e.g. macOS Spotlight/Trash/TCC-privacy-database directories.

**File watching.** A background watcher subscribes to native OS filesystem-change notifications (inotify/FSEvents/ReadDirectoryChangesW, selected by platform) for the project root, but only when the project is under version control and only when both the watcher itself and an "experimental" watcher flag are enabled; it is otherwise inert. It also independently subscribes to the VCS metadata directory (e.g. `.git`) — ignoring the frequently-churning index file but propagating changes to files like `HEAD` (branch switches) — even when the project root itself isn't watched, unless that directory is already covered by an ignore rule. Watch subscriptions resolve symlinked VCS directories to their real path first. All subscriptions are torn down on shutdown/dispose. Every raw filesystem create/update/delete notification is translated into a generic "file updated" event (`add` / `change` / `unlink`) published on the shared in-process event bus for other features to consume. Subscribing has a hard timeout; a subscription that doesn't confirm within it is logged as failed and abandoned rather than hanging startup.

**Process execution.** A process-running service wraps raw process spawning with: combined or separate stdout/stderr capture with independent byte caps (excess bytes are silently dropped and a truncated flag is set per stream, rather than raising); an overall timeout that kills the process (as a normal failure) if exceeded; abort-signal support; feeding a string, byte buffer, or a live stream of bytes to stdin; and "run to completion" vs. "stream output line-by-line" modes. In the streaming mode, exit-code policy is caller-selectable — an explicit list of acceptable exit codes turns a mismatch into an error carrying the collected stderr, while omitting the list means any exit code is treated as success. Piped multi-stage commands (A | B | C) are supported and represented/described the same way single commands are. On process teardown: if the process already exited cleanly, nothing further happens; if it's still running, the whole process group is signaled (falls back to signaling just the one process if group-kill isn't available, and uses `taskkill /T /F` on Windows since POSIX process groups don't exist there), with an optional escalation from a graceful signal to a forced kill after a grace period elapses. A lower-level, simpler process-spawn/run/text/lines helper (used for one-off tool detection like "does `ruff` exist and what does its help output say") layers a nothrow mode, an abort signal, and a byte-buffered stdout/stderr capture on top of the same cross-platform child-process launcher, and exposes an explicit `stop()` that is a no-op if the process is already dead and otherwise sends a kill signal (via `taskkill` on Windows).

**Image normalization.** Base64 data-URL image attachments (e.g., pasted screenshots) are decoded and checked against configurable maximum width, height, and base64-encoded byte-size limits (defaults: 2000×2000 px, 5 MiB of base64 text, auto-resize on). If the image is within limits it passes through unchanged. If it exceeds limits and auto-resize is disabled, normalization fails with a typed size error carrying the offending and configured dimensions/byte counts. If auto-resize is enabled, the image is progressively downscaled (each step ~75% of the previous linear dimension, floored at 1×1, starting from the largest scale that fits within the box) and at each candidate size both PNG and a descending sequence of JPEG quality levels (80, 85, 70, 55, 40 — note 85 is tried after 80) are attempted; the first encoding that fits under the byte cap is returned, replacing the image's MIME type and data URL. If no size/quality combination in the search space fits, normalization fails with the same typed size error. The resizer library is loaded lazily and cached; if it cannot be loaded at all, normalization fails with a distinct "resizer unavailable" error rather than crashing the caller.

**Source-code formatting.** A pluggable registry of ~25 built-in language formatters (prettier, biome, oxfmt, gofmt, rustfmt, ruff/uv, mix, clang-format, ktlint, rubocop/standardrb, dart, ocamlformat, terraform, shfmt, nixfmt, zig, gleam, latexindent, cljfmt, dfmt, ormolu, htmlbeautifier, pint, air/R, ...), each declaring the file extensions it handles and an async "is this formatter usable here" probe. Probes typically check for an executable on PATH and/or evidence in the project (a config file found by walking up from the project directory to the worktree root, or the tool listed as a dependency in a manifest file such as package.json/composer.json/pyproject.toml). Two formatters that wrap the same underlying tool (ruff and uv for Python) are linked so that disabling either disables both. Configuration can disable the whole subsystem, disable individual formatters, or override a formatter's command/extensions entirely. Formatting a file evaluates every enabled formatter whose extension list matches that file's extension, runs their "is it usable" probes concurrently, then runs the matched, usable formatters' commands sequentially against the file (each formatter mutates the file in place before the next runs), with the `$FILE` placeholder in the configured command substituted with the real path; a formatter invocation that fails to spawn or exits non-zero is logged but does not abort formatting of the file by later formatters, and formatter state (which formatters are enabled) is resolved lazily and cached once per working directory/instance.

**Environment & runtime detection.** A per-instance mutable snapshot of process environment variables is exposed through get/set/remove/list-all operations, seeded from the real OS environment at startup and mutated in-memory thereafter (mutations do not write back to the OS process environment). Host-IDE detection is heuristic: only triggers when running inside a `vscode`-flavored integrated terminal (`TERM_PROGRAM=vscode`) and then inspects the Git-askpass helper path environment variable for a substring match against known IDE branding (VS Code, VS Code Insiders, Cursor, VSCodium, Windsurf), defaulting to "unknown" otherwise. A separate flag records whether the CLI was launched *by* one of those IDE integrations already (`OPENCODE_CALLER` set to `vscode`/`vscode-insiders`) so the "install IDE extension" flow can skip itself. Executable lookup (`which`) searches PATH (or an override) plus the app's own bin cache directory, respects `PATHEXT` on Windows, and only returns files that are actually executable on POSIX (a non-executable regular file on PATH is treated as not found).

**Clipboard / OS integration (image-adjacent).** Reading an image from the OS clipboard is platform-specific: macOS shells out to `osascript` to dump clipboard PNG data to a temp file (deleted afterward) and falls back to plain text; Windows and WSL invoke a PowerShell one-liner that base64-encodes any clipboard bitmap as PNG; Linux tries Wayland's `wl-paste` then X11's `xclip`, both requesting the `image/png` MIME type; if no image is found anywhere, a generic cross-platform clipboard-text fallback library is used. Writing text to the clipboard both emits an OSC 52 terminal escape sequence (wrapped for tmux/screen passthrough when detected) so terminal emulators that support it pick it up directly, and additionally shells out to the best available native copy command for the platform (osascript / wl-copy / xclip / xsel / PowerShell `Set-Clipboard`), falling back to the generic clipboard library if none of those exist.

**Standard OS-convention paths & temp/cache directories.** A single global paths object computes the application's per-user data, cache, config, state, and temp directories following the platform's base-directory convention (XDG on Linux, equivalents elsewhere) plus `<tmp>/opencode` under the OS temp root, and creates all of them (plus `bin`, `log`, `repos` subdirectories) synchronously at process startup before anything else runs. The config directory can be overridden by an environment flag; the "home" directory can be overridden by a test-only environment variable. This is the closest analog to "temp-file management" in the codebase — there is no separate dedicated temp-file lifecycle/cleanup module; short-lived files (e.g., the macOS clipboard PNG dump) are created directly under the OS temp directory by their owning feature and deleted immediately after use, best-effort.

## Business rules & edge cases

- ID generation is monotonic within a process: if two IDs are requested in the same millisecond, a counter (reset whenever the millisecond changes) is embedded so ordering is preserved; only 12 bits (4096 values) are available per millisecond before the counter itself would need to roll into the timestamp field (unaddressed — see open questions).
- Providing an explicit ID to the "ascending"/"descending" generator only validates the prefix; it does not validate the rest of the ID's shape.
- A project-scoped filesystem read/list operation that resolves to a path outside the project root is a hard failure (not a recoverable error) — this is a security boundary against path traversal, deliberately not exposed as a normal catchable error to plugin/tool callers.
- `ensureDir` treats "already exists" as success only if the existing path really is a directory (guards a known Bun-on-Windows bug where `mkdir` with `recursive: true` can throw `EEXIST` unexpectedly).
- Ignore-pattern matching checks folder-name membership per path segment (so "any ancestor segment named node_modules" matches) but glob-matches file patterns against the whole path; a caller-supplied whitelist pattern always overrides a match.
- The file watcher is opt-in twice over: version control must be detected for the project AND an experimental flag must be set, or watching silently never starts; a second, independent flag can force-disable the watcher outright regardless of VCS/experimental settings.
- VCS-metadata watching ignores the `HEAD`-adjacent `index` file specifically (to avoid noise on every git add/status) but does not ignore `HEAD` itself, and skips re-subscribing to the VCS directory if it's already covered by a broader ignore/config rule.
- Watch-subscribe has a fixed timeout (10s); failing to subscribe in time logs an error and does not retry.
- Process output truncation counts bytes against the configured cap per stream independently; the truncated flag becomes true once the *cumulative* byte count exceeds the cap, even though only the first N bytes are actually retained.
- Killing a process group is best-effort: if group-kill fails (e.g., no permission, or the platform doesn't support process groups), it falls back to killing only the tracked process ID.
- The `stdin` option is documented as incompatible with piped (multi-stage) commands — passing it with a piped command is a caller error, surfaced as a typed failure rather than silently ignored.
- A `forceKillAfter` duration on process kill/exit is what enables the graceful-then-forceful escalation; without it, only the initial signal is ever sent.
- Image resize search space is capped at 32 downscale steps; once width or height would floor to 1 px it stops shrinking that dimension further but keeps shrinking the other, and PNG is always tried before any JPEG quality at a given size (so a resize can end up as PNG even though the original was JPEG, changing the reported MIME type).
- Auto-resize defaults to on; disabling it makes any over-limit image a hard failure instead of attempting a downscale.
- A malformed/non-base64 data URL (missing the `data:` scheme or `;base64,` marker) is rejected before any decode attempt, as a distinct error from a genuinely undecodable image payload.
- Two formatters sharing one underlying binary (ruff/uv) are cross-linked for disabling only — enabling one does not automatically enable the other; each still runs its own applicability probe.
- Formatter "enabled" probes are cached per formatter name for the lifetime of the per-directory instance state — a probe is not re-run on every format request, so a formatter that becomes available mid-session (e.g., installed by a running task) will not be picked up until state is reset.
- IDE detection is fragile by construction: it depends on `TERM_PROGRAM=vscode` AND a specific environment variable (`GIT_ASKPASS`) containing a recognizable app-bundle name; running inside a VS Code terminal on a machine where that variable is unset or renamed reports "unknown".
- `which()` on POSIX rejects a matching PATH entry that isn't executable, continuing to search rather than returning it.

## Workflows & states

1. **Startup path bootstrap**: compute OS-convention data/cache/config/state/temp directories → create all of them synchronously (failure here is fatal to process startup) → other services (bin cache, formatter's `which`, global temp) depend on these existing.
2. **Filesystem watcher lifecycle**: service init → check flags/VCS → resolve OS watch backend (or log unsupported and stay inert) → subscribe to project root (only if VCS + experimental flag) and, independently, to the VCS metadata directory → on each native change batch, map to add/change/unlink and publish on the event bus → on scope teardown, unsubscribe everything.
3. **Process run**: build a description string of the command(s) for error messages → optionally wrap stdin as a byte stream → spawn → concurrently drain stdout/stderr (or merged output) up to configured caps → await exit code → apply timeout race and/or abort-signal race around the whole collection → on any failure path, normalize the error into one typed error carrying the command description.
4. **Process run (fire-and-forget teardown)**: on scope release, if the process already finished, do nothing (unless it exited non-zero, in which case best-effort cleanup of any leftover process-group members is attempted); if still running, send a signal to the group (or the single process as fallback), and if a force-kill grace period is configured and the first signal doesn't result in exit within it, escalate to SIGKILL.
5. **Image normalize**: parse data URL → decode bytes with the image codec (lazily loaded/cached) → decode failure ⇒ typed decode error → check current dimensions/byte size against limits → within limits ⇒ pass through unchanged → over limits + auto-resize off ⇒ typed size error → over limits + auto-resize on ⇒ iterate downscale steps × encodings until one fits ⇒ return replaced content, or typed size error if none fit.
6. **Formatter dispatch for a saved file**: look up formatters whose extensions include the file's extension → run each match's "enabled" probe concurrently (result cached) → filter to usable ones → run each usable formatter's command against the file sequentially (each sees the previous formatter's output) → log and continue past any single formatter's spawn/exit failure.
7. **IDE-extension install flow**: detect current IDE via env heuristics → if the CLI already believes it was launched by that IDE's own integration, skip install → otherwise shell out to the IDE's CLI with an "install extension" command → classify result as already-installed / failed (with captured stderr) / success from exit code and stdout text.

## Data

- **Identifier**: `<prefix>_<12 hex chars><14 base62 chars>`, 26-character body; prefixes are a fixed enum (job, evt, ses, msg, per, que, prt, pty, tool, wrk). No separate "kind" field is stored — the prefix *is* the type tag, checked by simple string-prefix comparison.
- **Directory entry**: name + type (`file` | `directory` | `symlink` | `other`); a higher-level "project entry" is a relative path (directories suffixed with the OS path separator) + a coarser type (`file` | `directory`).
- **Content**: `{ uri, name?, content, encoding: "utf8"|"base64", mime }` — the canonical shape for file bytes moved across the system (also what image normalization operates on and returns).
- **RunResult** (process service): `{ command (description string), exitCode, output?/stdout/stderr (byte buffers), outputTruncated?/stdoutTruncated/stderrTruncated (booleans) }`.
- **Formatter status**: `{ name, extensions[], enabled (boolean) }`, one per registered formatter, used to report tool/formatter availability to callers (e.g. a status/diagnostics command).
- **Image limits config**: `{ auto_resize: bool, max_width, max_height, max_base64_bytes }`, defaulting to `true / 2000 / 2000 / 5*1024*1024`; sourced from project configuration and threaded into both the tool-facing (core) and session-attachment (opencode) normalizers.
- **Global paths**: `{ home, data, cache, config, state, tmp, bin, log, repos }` — absolute directory paths, computed once at process start.
- **Protected-path OS lists**: hard-coded per-platform directory-name lists (macOS: Music/Pictures/Movies/Downloads/Desktop/Documents/Public/Applications/Library + Library-internal privacy paths + root-level Spotlight/Trash/fsevents paths; Windows: AppData/Downloads/Desktop/Documents/Pictures/Music/Videos/OneDrive); empty on other platforms.
- **Ignore pattern set**: a fixed list of ~28 folder basenames (node_modules, .git, dist, build, target, __pycache__, .idea, .gradle, ...) and ~11 glob file patterns (`**/*.swp`, `**/.DS_Store`, `**/logs/**`, `**/*.log`, `**/coverage/**`, ...), extensible per-call with `extra` patterns and overridable with a `whitelist`.

## Interfaces

- **Tool System**: uses the project-scoped filesystem service (read/list/find/glob/grep) as the backing implementation for file-reading and search tools; uses the process-running service to execute arbitrary shell commands (a first-class "run a shell command" tool) and to shell out for formatter/linter probing; uses image normalization to prepare tool-return image content and pasted-image attachments before sending them to a model; uses the identifier generator for tool-call IDs.
- **Git / Worktree / Snapshot / Patch**: uses the process-running service to invoke the `git` binary (status, diff, commit, worktree management) and to shell out for VCS discovery; the filesystem watcher independently watches the VCS metadata directory to detect branch/HEAD changes and feeds that into snapshot/session state; snapshot and patch tooling also use the general-purpose filesystem read/write/find-up helpers.
- **LSP Integration**: uses `which`-style executable resolution and the process service to launch language-server binaries and to establish their working directories via the filesystem path-resolution/containment helpers; uses temp/global paths for any server-local scratch files.
- **Session Runtime**: uses identifier generation for session/message/part IDs; uses image normalization for user-pasted/attached images before storing them on a message part; uses the environment service to read/mutate the effective process environment surfaced to tools and sub-processes; uses the formatter service after file-editing tools run, to auto-format touched files.
- **TUI**: uses IDE detection to decide whether to offer/auto-run the "install IDE extension" flow; uses the clipboard read/write helpers for image paste and text copy; uses `which`/environment detection for terminal-capability decisions (e.g., OSC 52 support, tmux/screen passthrough).
- **Config system** (adjacent, not documented here): supplies the image-limit overrides, formatter enable/disable/override map, and file-watcher extra-ignore patterns consumed by the services above.
- **Event bus** (adjacent): the filesystem watcher's sole external output is publishing generic file-changed events (`add`/`change`/`unlink`) that other features subscribe to; it does not call back into any other service directly.

## Error handling

- Filesystem errors distinguish "not found" and "permission denied" as recoverable/expected (turned into `undefined`/`false` results by the "safe" helpers) from everything else, which propagates as a typed filesystem error carrying the failing method name and underlying cause.
- Path-escape violations from the project-scoped filesystem service are raised as unrecoverable defects, not typed/catchable errors — by design, so a plugin/tool cannot "handle" its way past the sandbox boundary.
- Process failures are normalized into a single typed error carrying the (possibly multi-stage/piped) command description, the exit code when known, captured stderr when available, and the underlying cause otherwise; timeouts and externally-triggered aborts are folded into this same error type rather than being distinct exception classes visible to callers.
- Two "require a particular outcome" combinators are provided: fail unless exit code is exactly 0, or fail unless exit code is in an explicit allow-list — both are opt-in wrappers around the base run result, not automatic.
- Image normalization uses four distinct typed errors (resizer-unavailable, invalid-data-url, decode-failed, size-exceeded-after-resize-attempts) so callers can present different messages/recovery for "we can't process images at all right now" vs. "this specific image is corrupt" vs. "this image is simply too big even after our best effort."
- Formatter command failures (spawn error or non-zero exit) are logged with the offending command and file but do not raise — formatting is treated as best-effort tooling, not something that should fail an edit operation.
- The file watcher fails soft everywhere: unsupported platform, missing native binding, subscribe timeout, or any uncaught initialization error all result in a functioning-but-inert watcher plus a logged error, never a startup crash.
- `which()` and IDE detection never throw for "not found" — they return `null`/`"unknown"`, pushing the "what do we do without it" decision to the caller.

## Non-functional observations

- Heavy duplication exists between `packages/core` (a newer, schema/tool-oriented layer) and `packages/opencode` (the original CLI layer) for identifier generation and image normalization — the algorithms are near byte-for-byte identical, suggesting an in-progress migration rather than two independently-designed subsystems; core is authoritative per project convention.
- Windows support receives disproportionate special-casing throughout (path drive-letter rewriting for Git-Bash/Cygwin/WSL styles, canonical-casing resolution, `taskkill /T /F` instead of POSIX process-group signals, PATHEXT-aware `which`, PowerShell-based clipboard) — a reimplementation on a POSIX-only platform can drop all of it, but a cross-platform port must treat Windows as a first-class, heavily-divergent code path rather than an afterthought.
- The fast native file-indexer is an optional accelerator with a full-fidelity fallback (ripgrep-based), gated by both a feature flag and a runtime availability check — a reimplementation can start with just the ripgrep-equivalent path and treat the indexer as a pure performance optimization.
- There is no dedicated "temporary file manager" abstraction (no create-and-auto-cleanup-on-scope-exit helper); temp usage is ad hoc (OS temp dir + manual best-effort deletion) in the one or two places that need it (clipboard image dump). A reimplementation is free to introduce a proper scoped-temp-file helper without breaking any documented contract.
- Image downscaling always tries lossless PNG before any lossy JPEG quality at a given size, which can silently convert a JPEG input into a (larger, sharper) PNG output at the same pixel size if that already fits the byte budget — a possibly-unintended asymmetry worth deciding on deliberately in a reimplementation.
- Per-millisecond ID counters cap at 4096 values with no documented overflow behavior — a very high single-process ID-issuance rate (e.g., a tight loop) could theoretically wrap or collide; not observed to be guarded against.

## Acceptance criteria — 5-8 Given/When/Then statements

1. **Given** an entity type with a defined prefix, **when** an ID is generated without an explicit value, **then** the result is `<prefix>_` followed by a 26-character body (12 hex chars encoding timestamp+counter, 14 random base62 chars), and generating two IDs of the same type within the same millisecond yields two different, correctly-ordered values.
2. **Given** a project-relative path that resolves (after following symlinks) outside the configured project root, **when** a filesystem read or list is attempted through the project-scoped filesystem service, **then** the operation fails as an unrecoverable "path escapes the location" error rather than returning partial or substitute data.
3. **Given** a shell command run through the process service with a byte cap on stdout, **when** the command writes more bytes than the cap, **then** the returned result contains exactly the first N bytes of output and a truncated flag set to true, while stderr (uncapped or independently capped) is unaffected.
4. **Given** a running child process whose scope is released (normal completion or fiber interruption) while the process is still alive, **when** teardown runs, **then** the process (and its process group, where supported) receives a termination signal, with an optional escalation to a forced kill if it has not exited by the configured grace period.
5. **Given** a base64 data-URL image exceeding the configured maximum dimensions or byte size with auto-resize enabled, **when** normalization runs, **then** it returns image content re-encoded at a smaller size and/or lower JPEG quality that fits within the configured byte limit, or fails with a typed size error if no attempted size/quality combination fits within 32 downscale steps.
6. **Given** a project directory containing a config file recognized by a built-in formatter (e.g. `.clang-format`) and that formatter's executable present on PATH, **when** a file with a matching extension is formatted, **then** the formatter's command is invoked with the real file path substituted for its placeholder, and a non-zero exit or spawn failure is logged without preventing other matching formatters from also running against the same file.
7. **Given** the process is running inside a VS Code-flavored integrated terminal with a Git-askpass path naming a supported IDE brand, **when** IDE detection runs, **then** it reports that IDE's exact name; given any other terminal or an unrecognized askpass path, it reports "unknown".
8. **Given** a project under version control with the experimental file-watcher flag enabled, **when** a file inside the project (or a change to the VCS `HEAD` file, excluding the VCS index file) is created, modified, or deleted, **then** a generic file-changed event naming the absolute path and the change kind (add/change/unlink) is published for other features to observe, and no such events are published for a project that is not under version control or when the watcher/flags are disabled.

## Confidence & open questions

- **High confidence**: identifier format/algorithm (cross-checked against three near-identical implementations — `packages/schema/src/identifier.ts`, `packages/core/src/id/id.ts`, `packages/opencode/src/id/id.ts`), process-runner truncation/timeout/kill/stdin semantics (directly backed by `packages/core/test/process/process.test.ts`), image-normalization resize/quality search and error taxonomy (backed by `packages/opencode/test/image/image.test.ts` and mirrored core implementation), ignore-pattern and IDE-detection behavior (backed by dedicated unit tests), formatter dispatch/caching/linked-disable rules (backed by `packages/opencode/test/format/format.test.ts`).
