# Feature: CLI, Daemon & Self-Update

## Purpose

Everything a user touches before a coding-agent session starts: the `opencode` command-line entrypoint (subcommand dispatch, default-to-TUI behavior, headless server mode, one-shot prompt mode), the mechanics that let several invocations of the CLI share a single running server, and the install/self-update pipeline that keeps a locally-installed binary current. It also covers a second, separately-shipped command-line product ("lildax", a preview v2 CLI) that implements a true background-daemon model the main product does not have.

## Behavior

### Two distinct CLI products

1. **`opencode`** (main product, `packages/opencode`) — a single native/Bun executable with ~25 subcommands. Running it with no subcommand (or a bare directory argument) starts the full-screen terminal UI. Every other mode (headless server, one-shot prompt, attach-to-remote) is an explicit subcommand or flag.
2. **`lildax`** (preview v2 CLI, `packages/cli`, npm package `@opencode-ai/cli`) — a much smaller command set (`api`, `debug agents`, `migrate`, `service start/restart/status/stop/password`, `serve`) built around a genuine background-daemon: any command that needs the server auto-starts a detached, persistent server process if one isn't already running, and reuses it across invocations. It talks to the same v2 HTTP API described in the "Server/HTTP API & Event Bus" dossier — this dossier only covers how the CLI locates, starts, verifies, and stops that server.

### `opencode` command dispatch

The entrypoint parses argv with a conventional CLI-argument parser and a strict subcommand table (unknown flags/subcommands are rejected with help text). Global flags available on every invocation: `--print-logs`, `--log-level` (DEBUG/INFO/WARN/ERROR), `--pure` (disable external plugins), `--help/-h`, `--version/-v`. Before any subcommand runs, three environment markers are set for child processes/plugins to detect they're running under the agent (`AGENT=1`, `OPENCODE=1`, `OPENCODE_PID=<pid>`), and an internal analytics/heap-tracking hook is started.

Top-level subcommands (default handler is the bare/no-subcommand case):
- **(default) `opencode [project]`** — start the interactive terminal UI, optionally in a given project directory. Flags: `--model/-m`, `--continue/-c`, `--session/-s`, `--fork`, `--prompt`, `--agent`, `--auto`/`--yolo`/`--dangerously-skip-permissions` (auto-approve permissions), `--mini` (minimal split-footer interactive mode instead of the full TUI), replay-history flags, network flags (`--port`, `--hostname`, `--mdns`, `--mdns-domain`, `--cors`).
- **`run [message..]`** — one-shot / scripted mode: send a single message (or `--command`) to a session and stream the response, then exit. Supports `--format json` for machine-readable event streaming, `--attach <url>` to target a remote/already-running server instead of spinning up a local one, `--continue`/`--session`/`--fork` for session resumption, `--share`, `--file/-f` to attach files, `--interactive/-i` for a direct interactive split-footer mode without the full TUI.
- **`attach <url>`** — connect the terminal UI (or, with `--mini`, the minimal interface) to an already-running `opencode serve` instance instead of starting one locally.
- **`serve`** — start a headless HTTP API server and block forever (`Effect.never`); prints the listening address and a warning if no server password is configured.
- **`web`** — like `serve`, but also opens the address in the system's default web browser, and prints both localhost and LAN-IP access URLs when bound to `0.0.0.0`.
- **`acp`** — start an Agent Client Protocol server (stdio-based protocol server for other editors/tools to drive the agent).
- **`upgrade [target]`** — self-update to the latest or a specific version (see Self-update below).
- **`uninstall`** — interactively remove the installed binary, config, data, cache and state directories, and shell-PATH modifications.
- **`models [provider]`**, **`agent`** (create/list agent definitions), **`providers`**/alias **`auth`** (login/logout/list AI providers), **`mcp`** (add/list/auth/logout/debug MCP servers), **`session`** (list/delete sessions), **`stats`** (token usage/cost), **`export`**/**`import`** (session data as JSON), **`db`** (open a SQL shell against the local database or print its path), **`plugin <module>`** (install a plugin and update config), **`github`** (install/run the GitHub bot agent), **`pr <number>`** (checkout a GitHub PR and start a session against it), **`account`**/console commands (login/logout/switch org), **`debug ...`** (internal troubleshooting: paths, LSP, ripgrep, snapshots, config, file access — not part of the stable surface).

### Local server lifecycle in `opencode` (no cross-invocation sharing by default)

Unlike lildax, the main `opencode` binary does **not** automatically discover or share a running server between separate CLI invocations. Each mode manages its own server instance:
- The **TUI** (`opencode [project]`) spawns a background worker (a separate OS thread within the same process) that owns an in-process HTTP server; the foreground process talks to it over an internal RPC channel rather than real sockets, unless the user explicitly passes network flags (`--port`/`--hostname`/`--mdns`), in which case the worker exposes a real TCP listener and the foreground process is handed that URL.
- **`run`** (without `--attach`) creates its own private in-process server for the duration of the command and exits when done.
- **`serve`**/**`web`** start a real, long-lived TCP server and block until killed; other CLI invocations must be pointed at it explicitly via **`attach <url>`** or **`run --attach <url>`** — there is no auto-discovery file or registration mechanism for the main product.
- On worker startup, and once per TUI/mini-mode launch (after a 1-second delay, best-effort/non-blocking), the client asks the worker to check for and possibly apply an update (see Self-update).

### lildax's real daemon (shared-server) model

lildax implements the "single server shared by many CLI calls" pattern the prompt describes:
- A **registration file** at `<state-dir>/server.json` records `{ id, version, url, pid }` for the currently-registered server.
- A **shared password** is generated once and persisted at `<state-dir>/password` (0600 permissions) so that repeated invocations can authenticate to the daemon without ever exposing a password flag/env var to the user.
- **Starting** (`service start`, or implicitly whenever any command needs the API): check whether the registered server responds healthy (`GET /v2/health`) and reports the *same version* as the running CLI binary. If so, and the CLI is a compiled binary (not a `bun run` dev invocation), reuse it immediately. Otherwise, if a stale/incompatible server is registered, stop it first, then spawn a new detached, `stdio: "ignore"`, unref'd child process running `<binary> serve --register` and poll (every 50ms, up to 100 tries / 5s) until a healthy, version-matching server is registered.
- **Registering** (inside `serve --register`): write the registration file, and start a background loop (every 10s) that re-reads the file and self-terminates (SIGTERM) if another process has since overwritten the registration with a different id — i.e., last-registered-wins, and an old daemon quietly evicts itself. On shutdown (scope finalizer) the daemon removes its own registration entry if it still owns it.
- **Stopping** (`service stop` / on daemon replacement): re-verify the registered server is still healthy and matches the expected id/version/url/pid before signaling it (protects against signaling an unrelated process that has since reused the same PID). Send SIGTERM, poll for process death (50ms × up to 100 tries), escalate to SIGKILL if still alive, poll again, then delete the registration file.
- **`service status`** reports the registered server's URL if healthy and version-matched, `undefined`/"stopped" otherwise (and opportunistically deletes a stale registration file).
- **`service restart`** = stop then start.
- **`service password [value]`** reads/sets the persisted password; setting a new value also stops the current daemon (so it must restart to pick up the new credential).
- The bare `lildax` invocation (no subcommand) starts the daemon (if needed) and launches the terminal UI against it. `lildax api <operation|method path>` resolves an OpenAPI operation ID (or a raw `METHOD /path`) against the daemon's `/openapi.json`, then makes the HTTP request and prints the raw response body.

### Self-update ("upgrade")

- **Version/latest-check**: `Installation.latest(method?)` queries the appropriate source per install method — GitHub Releases API (default/curl/unknown), the npm registry (npm/bun/pnpm, using the resolved registry config), Homebrew (via `brew info`/formulae.brew.sh, handling both the official formula and a custom tap), Chocolatey's OData feed, or the Scoop bucket manifest on GitHub.
- **Method detection** (`Installation.method()`): inferred from the running executable's path (`.opencode/bin` or `.local/bin` → curl-installed) or by checking whether each package manager (npm/yarn/pnpm/bun/brew/scoop/choco) lists `opencode`/`opencode-ai` as globally installed, preferring whichever manager name appears in the executable's own path.
- **`opencode upgrade [target] [--method]`**: interactive command; detects/confirms the method, resolves the target version (latest if unspecified), skips if already current, and runs the method-specific upgrade command (`npm/pnpm/bun install -g opencode-ai@<version>`, `brew upgrade` with tap handling, `choco upgrade --version=<v> -y`, `scoop install opencode@<v>`, or — for curl/unknown installs — downloads and re-executes the install script with `VERSION=<target>` piped to `bash`, falling back to `sh` if `bash` is unavailable). Failures produce a generic, sanitized error message (raw command stdout/stderr is deliberately not surfaced, to avoid leaking secrets that might appear in installer output) except that choco failures get a specific "run as Administrator" hint.
- **Automatic background check** (invoked opportunistically by the TUI/worker shortly after startup, and gated by config): if `autoupdate` is `false` or the `OPENCODE_DISABLE_AUTOUPDATE` flag is set, do nothing. Otherwise fetch the latest version; if it equals the current version, do nothing. If the release is a minor/major bump, or config explicitly requests `"notify"` mode, only emit an "update available" event (surfaced by the UI) rather than auto-installing. Only for a same-major.minor **patch** bump, and only when `autoupdate` isn't `"notify"`/`false`, and only when the install method is known, does it silently run the upgrade and emit an "updated" event afterward. A debug-only flag (`OPENCODE_ALWAYS_NOTIFY_UPDATE`) forces the notify-only path unconditionally, for testing.
- **`opencode uninstall`**: detects install method, shows a removal plan (data/cache/config/state directory sizes, binary path, and shell-config PATH lines, `--keep-config`/`--keep-data` to preserve directories), asks for confirmation unless `--force`/`--dry-run`, then deletes the selected directories, strips the `# opencode` PATH block it recognizes from the shell rc file, and — for package-manager installs — shells out to the manager's own uninstall command (or, for curl installs, prints the manual `rm` command rather than removing the running binary itself).

### Install script (`install`, served at `https://opencode.ai/install`)

A POSIX shell script invoked via `curl -fsSL https://opencode.ai/install | bash`. Behavior:
- Options: `-v/--version <ver>` (pin a version), `-b/--binary <path>` (install from a local file, skipping all download logic), `--no-modify-path`.
- Detects OS (darwin/linux/windows-via-MINGW-or-Cygwin) and architecture (aarch64→arm64, x86_64→x64), with an Apple-Silicon-under-Rosetta detection that forces `arch=arm64` even when `uname -m` reports x64.
- Selects an asset variant: `.tar.gz` on Linux, `.zip` elsewhere; appends `-musl` when Alpine or a musl libc is detected; appends `-baseline` on x64 hosts lacking AVX2 (checked via `/proc/cpuinfo`, `sysctl`, or a PowerShell `IsProcessorFeaturePresent` probe on Windows).
- Downloads the resolved GitHub release asset (or the local `--binary` file) with a custom curl-trace-based progress bar (falls back to plain `curl -#` on Windows, non-TTY terminals, or if the fancy path fails), extracts it, and installs the `opencode` binary at `$HOME/.opencode/bin/opencode` with mode 755.
- Skips reinstalling if a same-version `opencode` is already on `PATH`.
- Unless `--no-modify-path`, appends a `# opencode` marker plus a `PATH` export (or `fish_add_path`) to the first existing shell rc file it finds for the user's `$SHELL` (fish/zsh/bash/ash/sh, each with an ordered candidate list); warns instead if no config file exists or it's not writable. Also appends the install dir to `$GITHUB_PATH` when running inside GitHub Actions.
- **Note**: the project's `README.md` documents a different, more flexible install-directory resolution order (`$OPENCODE_INSTALL_DIR` → `$XDG_BIN_DIR` → `$HOME/bin` → `$HOME/.opencode/bin`) than what the script in this repository actually implements (hardcoded to `$HOME/.opencode/bin`). This is flagged as an open question below — a reimplementation should decide which behavior is authoritative (the currently-served install.sh may differ from this snapshot).

### npm package self-installing native binary

The main `opencode-ai` npm package ships a Node `postinstall` script rather than the platform binary itself. At install time it: maps `os.platform()`/`os.arch()` to a package-name suffix (`opencode-<platform>-<arch>[-baseline][-musl]`), probes for AVX2 support and musl libc the same way the shell installer does, and tries each candidate optional-dependency package in preference order — first by resolving it as an already-installed npm dependency and hard-linking (falling back to copy) its bundled binary into the package's own `bin/` folder, then, if resolution fields, by spawning a scoped `npm install --ignore-scripts --no-save` into a temp directory as a fallback. After copying, it executes `<binary> --version` to verify the binary actually runs before declaring success; if every candidate fails it prints a manual-install hint and exits non-zero.

### `lildax` build/shipping status

`packages/cli` is a real, separately-versioned product (`@opencode-ai/cli`, currently 1.x) with its own cross-platform build matrix (12 OS/arch/libc/baseline target combinations compiled to standalone `lildax` binaries) and its own npm publish path — it is genuinely shipped, not internal-only tooling. Its command spec self-describes as "OpenCode 2.0 preview command line interface", and its command set is intentionally much smaller than the main `opencode` CLI (no TUI-only flags, no session/provider/agent management subcommands) — its `default` (no-subcommand) handler just launches the terminal UI against the daemon, and `api`/`debug agents`/`migrate`/`service *`/`serve` round out the rest.

## Business rules & edge cases

- `--mini` cannot combine with `--command`, `--format json`, or run as a bare subcommand fallback with the wrong positional (`opencode run --mini` must be invoked as `opencode mini`, i.e. `args._[0] === "mini"`); it also requires a TTY stdout.
- Network flags (`--port`, `--hostname`, `--mdns`) are incompatible with `--mini` on the default (TUI) command specifically, because mini mode there always runs against the in-process worker.
- `--fork` requires `--continue` or `--session` to be set; otherwise it's a hard user error.
- `--replay-limit` / `--no-replay` / `--demo` are gated to `--mini` only — using them without `--mini` is an error, and `--replay` (the plain flag, not `--no-replay`) is rejected outright with a message that replay is on by default.
- In `run --attach`, attaching a local **directory** is refused when it's a directory (no shared filesystem assumption), and attaching a local **file** larger than 10 MiB is refused; smaller files are read in full and embedded as data URIs, while files (in non-attach/local mode) are referenced by `file://` URL instead of read into memory.
- Non-interactive `run` denies `question`/`plan_enter`/`plan_exit` permissions by default (headless/scripted runs must not block waiting on interactive prompts); permission prompts, when they do arise (e.g. subagent-created sessions), are auto-approved if `--auto`/`--yolo`/`--dangerously-skip-permissions` is set, and otherwise auto-rejected with a warning printed to the user.
- Auto-share only occurs if the resolved config's `share` mode is `"auto"`, a runtime flag forces it, or `--share` was passed explicitly.
- lildax's `Daemon.start()` only reuses an existing registered server if its version *exactly* matches the running client's version **and** the running client is a compiled binary — a `bun run` dev invocation always spawns a fresh server rather than trusting a cached one, to avoid stale-dev-server confusion.
- lildax daemon health/compatibility checks are always re-verified immediately before signaling a process to stop, specifically to guard against PID reuse by an unrelated process after the original daemon has already exited.
- Self-update never runs the actual package/OS install command in "unknown" install-method situations for the automatic background path (it silently no-ops); the interactive `upgrade` command instead prompts the user to confirm anyway.
- Automatic upgrade only silently self-installs for a **patch** version bump; any minor/major bump only raises a notification event, requiring the user to run `opencode upgrade` explicitly.
- Upgrade/downgrade error messages are deliberately generic ("Upgrade failed for <method> (exit code N)."), never including raw process stdout/stderr, to avoid echoing secrets that might leak through installer output — except a special-cased Chocolatey "not running from an elevated shell" hint.
- `uninstall`'s curl-install path never deletes the running binary itself (can't safely rm a file that's currently executing on some platforms); it prints the exact `rm` command for the user to run manually instead.

## Workflows & states

**Default interactive session (opencode, no args):**
`opencode` parsed → global env markers set → resolve target directory (cwd or positional `[project]`, resolved against `$PWD`) → chdir → spawn worker thread → worker boots its own in-process server and RPC listener → foreground validates the requested session (if `--session` given) exists → foreground schedules a best-effort "check for upgrade" call ~1s later → foreground runs the TUI event loop against the worker's transport (in-process fetch + event stream, or a real HTTP endpoint if network flags were given) → on exit, foreground calls `shutdown` RPC (disposes instances, stops server) with a 5s timeout, then terminates the worker.

**One-shot run (`opencode run <message>`):** parse args → validate mutually-exclusive flag combinations → resolve/chdir directory → build or reuse an SDK client (in-process server, or remote via `--attach`) → resolve/create/fork the target session → optionally trigger auto-share → subscribe to the session's event stream → send the prompt or slash-command → stream `text`/`reasoning`/`tool`/`step`/`error` events to stdout (formatted or raw JSON) until a `session.status: idle` event → exit with non-zero code if an error event occurred.

**Headless server (`opencode serve` / `web`):** parse network options (config-file values as defaults, explicit CLI flags always win when present) → bind a port (or scan upward from 4096 on lildax's `serve` if none was requested) → print the listening URL (and, for `web`, open a browser tab and print LAN IPs when bound to all interfaces) → block until killed.

**lildax auto-daemon flow (any command needing the API):** check registration file → if healthy + version-matched + binary is compiled → reuse → else stop any stale registered server → spawn detached `serve --register` child, unref it → poll for a healthy, version-matched registration (50ms interval, 5s budget) → build an authenticated client against the discovered URL.

**Self-update check (background):** on worker/session start → load global config → short-circuit if disabled → fetch latest version for the detected install method → compare to running version → notify-only for minor/major or `"notify"` mode → silently upgrade + emit "updated" event for a same-major.minor patch bump when method is known.

**Install (curl pipe):** parse flags → resolve OS/arch/variant → (skip if same version already on PATH) → download+extract or copy local `--binary` → move into `$HOME/.opencode/bin` → chmod 755 → append PATH line to a detected shell rc file → print a short "how to start" banner.

## Data

- **lildax registration file**: `<state-dir>/server.json` — JSON `{ id: string (uuid), version: string, url: string, pid: number }`, mode 0600, written atomically via temp-file + rename.
- **lildax shared password file**: `<state-dir>/password` — random 32-byte base64url string, mode 0600, written atomically via temp-file + rename; persists across daemon restarts.
- **Global directories** (both products; per-platform via XDG base directories, or `OPENCODE_TEST_HOME`/`OPENCODE_CONFIG_DIR` overrides in tests): `data`, `cache`, `config`, `state`, `tmp`, plus derived `bin` (under cache), `log`/`repos` (under data). These are exactly the directories `uninstall` offers to delete.
- **Installed-version identity**: a compile-time-embedded version string and "channel" (e.g. `latest`/preview/`local`), used both for update-availability checks and for the `userAgent()` string sent on outbound HTTP requests (`opencode/<channel>/<version>/<client>`).
- **Auth for server access**: HTTP Basic auth, `username` defaulting to `"opencode"` and configurable via `OPENCODE_SERVER_USERNAME`/`--username`, `password` from `OPENCODE_SERVER_PASSWORD`/`--password`/(lildax) the persisted password file; absence of a password means the server is unauthenticated (with an explicit startup warning).
- **CLI-to-worker RPC protocol** (opencode TUI only): an internal, in-process message channel between the foreground process and its worker thread, carrying `fetch` (proxy an HTTP request/response), `server` (start/replace a real TCP listener), `checkUpgrade`, `reload` (invalidate config + dispose instances), `shutdown`, and `snapshot` (heap snapshots for both sides) calls, plus a `global.event` push channel forwarding server-side bus events to the foreground UI.

## Interfaces

- **Server/HTTP API & Event Bus** (separate dossier): both CLI products are HTTP clients of this API — `opencode`'s worker embeds the server in-process (or exposes it over real TCP when network flags are set); lildax's daemon *is* a standalone instance of the v2 API server, started via `serve --register`, and the CLI only manages its process lifecycle and discovery, not its route surface. This dossier does not re-document the API's endpoints, only how each CLI locates/starts/stops the process serving them.
- **Terminal UI** (separate dossier): the default `opencode` subcommand and `attach`/`--mini`/lildax's default command all ultimately hand off to the TUI's `run()` entrypoint, passing a `{ url, fetch, events, headers, config, pluginHost, directory, args }` transport bundle; this dossier only covers how that bundle gets constructed (in-process worker vs. real HTTP vs. lildax daemon), not the UI's own behavior.
- **Client SDKs** (separate dossier): `run`, `api` (lildax), and the daemon's health/compatibility checks all go through the generated OpenCode HTTP client rather than raw `fetch` (aside from the low-level plumbing inside the worker RPC bridge and lildax's raw `api` passthrough).
- **Config & Data Contracts** (separate dossier): `autoupdate` (`true`/`false`/`"notify"`), `server.port`/`hostname`/`mdns`/`mdnsDocument`/`cors` are read from the resolved project/global config and merged with CLI flags (explicit flags always win over config).
- **Session & Conversation Runtime** (separate dossier): `run`/`attach`/TUI all create, resume, or fork sessions through the SDK rather than touching session state directly; this dossier only covers the CLI-level flags that select which session behavior to invoke.

## Error handling

- The top-level CLI wraps the entire parse+dispatch in a try/catch; recognized domain errors are rendered via a formatter that special-cases: user-triggered `CliError` (message + optional exit code), MCP server failures, account-service errors, "model not found" (with suggestions and a hint to run `opencode models`), provider-init failures, several categories of config errors (invalid JSON/JSONC, directory-name typos, invalid frontmatter, remote-config auth failures with a login hint, schema validation issues with per-field messages), and silent handling of user-cancelled interactive prompts (empty message, no stack trace). Anything unrecognized falls through to a generic "Unexpected error" + raw error text on stderr, and the process always exits non-zero via `process.exitCode = 1` (never left hanging) with a `finally` block forcing `process.exit()` to avoid orphaned subprocesses (documented as necessary because some MCP servers, e.g. Docker-container-based ones, don't react to SIGTERM without `--init`).
- Upgrade failures are captured as a typed error carrying a sanitized (non-leaking) stderr summary rather than the raw process output; a Chocolatey-specific failure string is pattern-matched to add an "run as Administrator" hint.
- lildax's daemon start/stop paths use bounded polling with explicit retry budgets (50ms × 100 = 5s) rather than indefinite waits, failing with an explicit "Failed to start server" / "Server process <pid> is still running" error if the budget is exhausted; stop escalates from SIGTERM to SIGKILL only after the graceful-stop budget expires.
- File-attachment errors in `run --file` (missing file, oversized/non-regular file, directory attached remotely) are user-facing errors with a specific message and a non-zero exit, not stack traces.
- The install script treats an unreachable/`404` GitHub release (when `--version` is pinned) and unsupported OS/arch combinations as hard, immediate failures with colored error output and non-zero exit; missing `tar`/`unzip` similarly aborts early with a clear message.
- The npm postinstall script tries every viable binary-package candidate (in a platform/AVX2/musl-aware preference order) before failing, and always empirically verifies the copied binary via `<binary> --version` rather than trusting a successful copy alone.

## Non-functional observations

- The main `opencode` CLI deliberately avoids any implicit persistent background process — every session's server lifetime is scoped to that CLI invocation (or explicit `serve`) — trading "always-warm server" convenience for simplicity and to avoid orphaned daemons; lildax explicitly reintroduces the shared-daemon model as part of its v2 design, gated behind version-compatibility checks so an old daemon is never silently reused by a newer client.
- Update checks and update application both happen off the interactive-path critical timeline: the version check is scheduled ~1 second after the TUI is already up and running (`.unref()`'d so it never keeps the process alive on its own), and failures are swallowed (`.catch(() => {})`) so a flaky network never blocks or crashes a normal session.
- Cross-platform binary matrix is unusually granular: three axes (OS×arch, AVX2-baseline vs. modern, glibc vs. musl) are each independently detected at both install-script time and npm-postinstall time using near-identical heuristics (duplicated logic between `install` and `postinstall.mjs`), which is a maintenance/consistency risk worth preserving deliberately in a reimplementation (single shared detection routine recommended).
- The CLI help surface is protected by golden/snapshot tests (per-command `--help` text) explicitly framed as a safety net for a planned future migration to a different underlying CLI-parsing library — evidence that the exact flag/alias/ordering surface is treated as a stable contract worth reimplementing faithfully.

## Acceptance criteria — 6-8 Given/When/Then statements

1. **Given** the user runs the CLI with no subcommand and no flags, **when** it starts, **then** the full interactive terminal UI launches against a freshly-created, private server instance scoped to the current (or given) project directory.
2. **Given** the user runs the one-shot prompt command with a message and no `--attach`, **when** the session goes idle after streaming the response, **then** the process exits 0 with all response text/tool-activity printed to stdout, or exits non-zero and prints an error if any `session.error` event occurred.
3. **Given** `--fork` is passed without `--continue` or `--session`, **when** the command is parsed, **then** the CLI prints a specific error and exits non-zero without attempting any session operation.
4. **Given** a headless-server subcommand is started with no server password configured, **when** it binds its port, **then** it prints an explicit "unsecured" warning to the console before accepting requests, and the printed listening URL matches the actual bound host/port (scanning upward from a default port if the requested one is unavailable, where applicable).
5. **Given** the shared-daemon CLI product runs a command that needs the API and no server is currently registered (or the registered one reports a different version or fails a health check), **when** the command executes, **then** it spawns a new detached background server process, waits (bounded retry) for it to register as healthy and version-matched, and reuses that same process for subsequent invocations until its version no longer matches the running CLI.
6. **Given** the automatic background update check runs and the latest available version differs from the installed version only by a patch bump, **when** the install method is known and `autoupdate` is not disabled/`"notify"`, **then** the upgrade is applied silently and an "updated" event is emitted; **given** the version difference is a minor/major bump instead, **then** only an "update available" notification event is emitted and no files are changed.
