# Feature: Session & Conversation Runtime

## Purpose

This is the core agent loop of OpenCode: the subsystem that turns a stored conversation ("Session") and a user's prompt into one or more calls to a language-model provider, keeps the durable transcript ("Session History") consistent while that happens, and manages everything needed for the loop to behave like an autonomous coding agent rather than a single request/response chatbot. Concretely it owns: Session lifecycle (create, resume by id, list, delete, fork/branch, revert to an earlier point); assembling the model-visible "System Context" (base agent/provider instructions, environment facts, project/global instruction files, skill/MCP guidance) for each Provider Turn; running the turn-by-turn loop that streams a model response, dispatches any tool calls it requests, and decides whether another turn is needed; compacting the conversation when it grows too large for the model's context window; suspending a turn on a blocking pending question; and tracking process-local background work (subagent tasks, long-running tool jobs) so it can be cancelled together with its owning Session.

## Behavior

**Two coexisting implementations.** At the pinned commit, this feature exists twice: a shipping implementation under `packages/opencode/src/session/*` (`prompt.ts`, `processor.ts`, `compaction.ts`, `system.ts`, `instruction.ts`, `retry.ts`, `overflow.ts`, `reminders.ts`, `tools.ts`, `llm.ts`) that is the only one reachable from the TUI, CLI, and HTTP session routes; and a parallel, heavily-tested but **dormant** implementation under `packages/core/src/session/{runner,execution,run-coordinator,context-epoch,compaction,history,input,projector}.ts` and `packages/core/src/system-context/*` that implements CONTEXT.md's precise domain vocabulary (System Context Registry, Context Source, Context Epoch, Session Drain, Admitted Prompt, Prompt Promotion, Mid-Conversation System Message) almost literally, but is never invoked from any opencode CLI/TUI/HTTP code path. See **Confidence & open questions** for the evidence trail. The narrative below describes the shipping pipeline's actual behavior, using CONTEXT.md's terms where they describe a concept genuinely present in both, and calling out explicitly where the shipping pipeline diverges from or falls short of the CONTEXT.md/dormant-V2 model.

**Session lifecycle.** A Session is a durable record (id, project/workspace, optional parent id, slug, working directory, title, active agent/model selection, running cost/token totals, an optional revert marker, an optional permission override, timestamps). Creating a Session with no parent produces a top-level conversation; the "task" tool creates genuine child Sessions by supplying a parent id, used for subagent work with an independent message history. Deleting a Session recursively deletes its children and cancels any background jobs owned by it or its descendants. Forking copies a source Session's message/part stream (optionally only up to one message) into a brand-new Session id under new message/part identities; a forked Session is distinguished from its source only by a title convention ("Child session - …" / a fork-numbered title), not by the parent-id field used for true subagent children.

**Prompt submission and the turn loop (a Session Drain in CONTEXT.md's sense).** Submitting a prompt persists the user's message and its parts (text, files, agent/subtask references — inlining MCP resources and reading local files, optionally by line range, along the way), then enters an iterative loop that: reloads the projected Session History (applying any completed compaction as a read-time view transform, not a destructive rewrite); checks whether the loop should stop — it stops once the last assistant message has a terminal finish reason and no pending, non-provider-executed tool calls, ignoring tool calls already marked as orphaned-by-interruption; otherwise assembles a fresh System Context, resolves the active agent/model, applies step-limit and mode-switch reminder logic, creates a new assistant message, and runs one Provider Turn; then interprets that turn's outcome (stop / continue / needs-compaction) to decide whether to loop again. Only one turn runs per Session at a time: a second prompt call while a turn is active attaches to (joins) the running turn rather than starting an independent second execution; starting an interactive shell against a busy Session fails outright instead of queuing. There is no durable "queued prompt" or "steering prompt" concept in the shipping pipeline — that inbox/promotion model (Admitted Prompt, Prompt Promotion, steer vs. queue delivery) exists only in the dormant V2 pipeline (`packages/core/src/session/input.ts`).

**System Context assembly.** The shipping pipeline rebuilds the entire system prompt from scratch on every single Provider Turn — there is no Context Epoch, Baseline System Context, or Context Snapshot concept in it. Each turn's system prompt joins: a base prompt selected either from the active agent's own configured prompt or, failing that, by pattern-matching the model id/provider against one of ~9 built-in per-family prompt templates (Anthropic, a "beast" template for GPT-4/o1/o3-class models, a Codex template, Gemini, Kimi/Moonshot, a branded Meta template, plan-mode and build-switch variants, and a default fallback); an environment block (working directory, worktree, git-repo flag, platform, and the current date computed fresh on every call); discovered instruction files (global and upward-project `AGENTS.md`/`CLAUDE.md`/`CONTEXT.md`-style files plus any configured extra paths/URLs, plus instruction files discovered opportunistically near a file the agent just read mid-turn, deduplicated per assistant message); connected MCP server instructions; available-skill descriptions filtered by the active agent's permissions; and an optional per-message system override. The dormant V2 pipeline implements the CONTEXT.md model of this precisely instead: a stable, cached Baseline System Context established once per Context Epoch, with subsequent changes admitted only as discrete, durable Mid-Conversation System Messages at a Safe Provider-Turn Boundary.

**Provider Turn execution.** One turn streams events (reasoning start/delta/end, tool-input start/delta/end, tool-call, tool-result/error, text start/delta/end, step-start/step-finish) from the model, persisting every incremental delta as an individual event/DB write as it arrives rather than buffering; captures a filesystem snapshot before and after each step for later diffing/reverting; detects "doom loops" (three identical consecutive tool calls with the same input) and asks for explicit confirmation before repeating; and on step-finish evaluates the running token usage against the compaction budget, flagging that compaction is needed if it's exceeded so the streaming loop stops early. The whole per-attempt pipeline is wrapped in a retry policy (see Error handling).

**Compaction.** Triggered automatically when a finished turn's usage crosses a computed budget (the model's usable input-token limit minus a reserved buffer — by default the smaller of 20,000 tokens or the model's max-output tokens, unless overridden) or by an explicit provider context-overflow error. Messages are grouped into "turns" (one user message through the next); working backward, whole recent turns are kept until a preserve-budget would be exceeded (default 25% of the usable context, clamped to 2,000–15,000 tokens, or a configured fixed tail-turn count), splitting a partially-fitting turn at a message boundary if needed. Everything older is serialized to flat text (tool output truncated at 2,000 characters; already-compacted output shown as a placeholder) and summarized by running a real, tool-less assistant turn against a fixed Markdown-structured summary template (this template is shared verbatim with the dormant core compaction module via one exported `buildPrompt` helper — the only real code-sharing between the two implementations). The result is spliced back in as a virtual view over durable history (a compaction message pair standing in for the summarized head) rather than by deleting anything; a separate, unrelated "prune" step instead mutates old completed tool outputs in place to shrink context without a full re-summarization pass. Repeated compactions fold the previous summary into a new one (a rolling summary).

**Pending questions.** A tool or flow can raise a blocking question (a set of options) that suspends the enclosing turn until the client supplies an answer or rejects it; the pending question is tracked only in an in-memory map (id → deferred outcome) and is not durable — a process restart loses all pending questions, failing them as rejected. A rejection is treated the same as a declined permission: it interrupts and unwinds the turn rather than being fed back to the model as ordinary tool output.

**Background jobs.** A process-local, non-durable registry tracks long-running async work (subagent "task" tool executions, other extended tool jobs) with a status (running/completed/error/cancelled), optional output, and free-form metadata used to record owning/parent Session ids. Cancelling or deleting a Session walks this metadata chain to recursively cancel every background job belonging to it or any descendant Session.

## Business rules & edge cases

- The loop only stops when the last assistant message has a terminal finish reason **and** no pending tool calls that aren't provider-executed; a tool call left "running" when a turn is interrupted is marked as an aborted error so the next loop iteration recognizes it as orphaned and does not resurrect it as still-pending.
- Doom-loop detection triggers permission confirmation after exactly 3 identical consecutive tool calls (same tool, same input) in a turn.
- An agent's own configured system prompt, if present, always overrides the provider-family pattern-matched base prompt.
- Entering "plan" agent mode injects a plan-specific reminder into the user message; switching from "plan" back to "build" injects a build-switch reminder (noting an existing plan file if one exists) — gated behind an experimental flag.
- Reaching an agent's configured step limit injects a fixed "maximum steps reached" instruction as a synthetic assistant message and disables further tool calls for that turn.
- Context-overflow provider errors are never blindly retried — they force a compaction attempt instead; a second overflow occurring after one compaction-triggered recovery becomes a terminal failure rather than looping again.
- Compaction's manual/auto toggle and buffer/keep-tokens sizing are configurable; auto-compaction is skipped entirely when a model reports no context limit or the configured auto flag is off.
- Forking a Session does not set the new Session's parent-id field (parent/child linkage there is a title convention only); only Sessions created explicitly with a parent id (e.g., by the subagent "task" tool) have a true `children()` relationship used for recursive deletion/cancellation.
- Session mutation methods (title, agent/model selection, archive flag, metadata, permission override, revert marker, summary, workspace) are all implemented as one read-merge-publish "patch" pattern that emits a domain event rather than writing SQL directly; the actual row write happens downstream in a projector reacting to that event.
- A revert is staged (diff computed, marker stored) but not applied until the next turn begins (`cleanup()`), at which point later messages/parts are actually deleted and the marker cleared; staging can be undone (`unrevert`) before that point without deleting anything.

## Workflows & states

1. **Session creation** → **prompt submission** (persist user message) → **turn loop**: reload history → check stop condition → assemble System Context → resolve agent/model → run one Provider Turn → interpret result (stop / continue / needs-compaction) → repeat or exit → **post-loop maintenance** (async title generation, per-turn file-diff summary, background context pruning).
2. **Compaction sub-flow**: budget/overflow detected → select head (to summarize) and tail (to retain) → produce summary via a tool-less assistant turn → splice summary in as a virtual view → resume the original pending turn.
3. **Session status states** (in-memory, non-durable): idle → busy (running) → shell / shell-then-run (interactive shell, with a queued follow-up run) → retrying (with attempt/backoff countdown surfaced to the UI) → back to idle.
4. **Revert sub-flow**: stage (diff + snapshot captured, marker stored) → optional unrevert (marker cleared, nothing deleted) → commit (lazy, at next turn start: later messages/parts deleted, marker cleared).
5. **Fork sub-flow**: create new Session → replay source Session's message/part stream (optionally truncated at a message id) under new ids into the new Session.
6. **Background job lifecycle**: start → optionally extended by follow-on work → running → completed / error / cancelled; a parent Session's cancellation cascades through job metadata to every descendant Session's jobs.
7. **Pending question lifecycle**: asked (event published, caller blocks) → replied (answers delivered, caller unblocks) or rejected (caller's turn is interrupted); state is held only in memory and lost on process restart.

## Data

- **Session record**: id, project id, optional workspace id, optional parent id, slug, directory/subdirectory path, title, active agent name, active model (id/provider/variant), version, optional share URL, summary stats (file additions/deletions/count, optional diff patches), running cost and token totals (input/output/reasoning/cache-read/cache-write), optional revert marker (target message id, pre-revert snapshot id, diff text, affected files), optional permission-ruleset override, created/updated/compacting/archived timestamps.
- **Message**: role (`user`/`assistant`) plus an ordered list of typed parts — text, file, reasoning, tool (a `pending → running → completed | error` state machine keyed by provider call id), step-start, step-finish (carries a filesystem snapshot pair, cost, and token usage), patch (file diff for that step), compaction (summary text, retained recent transcript, tail marker), subtask, and agent; message-level metadata carries timing, an optional structured error, and — for assistant messages — the exact system prompt sent, model/provider id, cost, and token breakdown.
- **Todo**: a Session-scoped ordered list (content, status, priority) fully replaced on every update, backing a todo-list tool.
- **Background Job record**: id, type, optional title, status (running/completed/error/cancelled), start/completion timestamps, optional output/error text, free-form metadata (used to carry owning/parent Session ids for cascade cancellation).
- **Pending Question**: id, owning Session id, one or more question prompts with options, optional originating tool name — held only in an in-process map, never persisted.
- **(Dormant V2 only)** a Context Epoch record per Session (immutable baseline text, a per-Context-Source structured comparison snapshot, and the durable event sequence the baseline was struck at) plus a parallel event-sourced message/inbox table set (`session_message`, `session_input`) that mirrors the shipping pipeline's tables one-for-one but is populated only by the dormant runner's own unshipped `session.next.*` event family — confirmed empty in production because the shipping pipeline never emits those events.

## Interfaces

- **Provider & LLM Integration** (adjacent, not documented here): the session runtime resolves an agent/model, then invokes that feature's single "stream a turn" operation with the assembled system prompt, message history, tool set, and sampling parameters, consuming its normalized event vocabulary and its retryable/context-overflow error classification to drive this feature's own retry and compaction decisions.
- **Tool System** (adjacent): this feature materializes the active agent's permitted tool definitions for each turn and reacts to tool-call/result/error events to persist state, but does not implement tool execution, sandboxing, or schema validation itself.
- **Permission System** (adjacent): tool authorization and doom-loop confirmation are routed through that system; a decline interrupts the current turn.
- **Storage/Sync/Share** (adjacent): Session/message persistence is ultimately performed by that layer's SQL projector reacting to domain events this feature publishes; a `share` URL field is carried on the Session record but shared-session mechanics belong to that feature.
- **Agent/Subagent/Skill System** (adjacent): supplies the active agent's own prompt/model/step-limit/permission configuration, skill/MCP guidance text, and the "task" tool that creates genuine parent/child Sessions for subagent work.
- **Command System** (adjacent): a slash command can be dispatched either as an ordinary prompt or, for a "subagent"-mode agent, as a subtask handled through the same tool-call machinery as any other tool.
- **Server/HTTP API** (adjacent): a set of HTTP handlers exposes create/prompt/cancel/messages/fork/revert/etc. over this feature's service interface; this dossier documents the underlying behavior, not the wire contract.

## Error handling

- Context-window overflow is classified specially: it is never retried as a generic transient failure — it instead triggers (or is folded into) a compaction attempt; a second overflow after one such recovery, or an overflow occurring after durable assistant output has already started, becomes a terminal failure instead of looping again.
- Other transient provider failures (HTTP 429/5xx, recognized rate-limit/network-reset/timeout patterns) are retried with exponential backoff plus jitter, up to a bounded number of attempts, honoring a provider-supplied retry-after value when present and otherwise capping the delay; a distinct usage-limit error from the first-party managed provider is surfaced with upsell/countdown metadata instead of a generic retry message.
- Authentication and malformed-request failures are not retried; they are recorded as a terminal, typed error on the assistant message and the loop stops.
- A tool call still "running" when its turn is interrupted (client cancel, process interruption) is explicitly finalized as an aborted error rather than left ambiguous, so the next loop iteration can recognize and skip it instead of re-executing or re-surfacing it as pending.
- A declined permission or a rejected pending question interrupts and unwinds the current turn rather than being converted into ordinary tool-result content for the model.
- A background job's own failure is captured as a typed `error` status independent of the owning Session's turn-level error surface; failing to retain a job's output does not retroactively change whether the job's underlying operation succeeded.

## Non-functional observations

- Every incremental streamed unit (each text/reasoning delta, each tool-call sub-state transition) is persisted as its own event/DB write as it arrives rather than buffered and flushed at turn end — this favors live-tailing/resumability over write throughput, and the codebase's own design notes (`specs/v2/session.md`) flag this exact trade-off as an open concern for the dormant V2 runner too.
- The shipping pipeline rebuilds and resends the entire system prompt on every Provider Turn with no caching, diffing, or epoch concept; it relies entirely on the underlying model provider's own server-side prompt caching (if any) for efficiency. This is a deliberate, documented gap relative to the CONTEXT.md/dormant-V2 design, which is built specifically to avoid this by maintaining one immutable, provider-cache-friendly Baseline System Context per Context Epoch and only ever appending small, discrete Mid-Conversation System Messages afterward.
- Both per-Session run coordination and the background-job registry are explicitly process-local and non-durable; an in-flight turn's coordination state (and any pending question) is lost on process restart — the same property CONTEXT.md documents for its (differently-implemented) Session Drain concept.
- Two structurally different compaction implementations coexist (the shipping pipeline's turn/tool-output-aware version, which executes the summarization as a full assistant turn through the ordinary streaming/tool machinery, and the dormant core version, which issues one lean direct LLM call); they share only a summary prompt-template constant, which is a real, if narrow, maintenance-duplication risk if the two are ever meant to converge.

## Acceptance criteria — 6-8 Given/When/Then statements

1. **Given** a Session with no prior messages, **when** a user submits a prompt, **then** the user's message is durably persisted, the active agent/model is resolved, a system prompt combining the agent/provider base prompt with environment, instruction, skill, and MCP context is assembled, and one Provider Turn is started.
2. **Given** a Provider Turn ends with pending tool calls, **when** the loop evaluates whether to continue, **then** it executes and awaits those tool calls, persists their results, and starts another Provider Turn without requiring a new user prompt; the loop stops only once the last assistant turn has a terminal finish reason and no pending tool calls remain.
3. **Given** the conversation's estimated token usage for the next turn exceeds the active model's computed usable budget, **when** that turn would otherwise be prepared, **then** the runtime compacts older turns into one durable summary while preserving a recent-turns tail, without physically discarding the original messages, before proceeding.
4. **Given** a provider call fails with a transient error, **when** the failure is handled, **then** it is retried with exponential backoff up to a bounded attempt count (honoring any provider-supplied retry-after value); a context-overflow failure instead triggers compaction rather than a blind retry, and an authentication failure is surfaced immediately without retry.
5. **Given** a Session with running subagent/background work is deleted, **when** the deletion is processed, **then** all of its child Sessions and every background job owned by it or its descendants are recursively cancelled.
6. **Given** a Session already has an active turn running, **when** a second prompt request for the same Session is received, **then** it attaches to the existing turn instead of starting an independent concurrent execution; a request to start an interactive shell against a busy Session is rejected outright instead of being queued.
7. **Given** three consecutive identical tool calls (same tool, same input) occur within one turn, **when** the next identical call is about to execute, **then** the runtime pauses and requests explicit confirmation before proceeding.
8. **Given** a user forks a Session at a specific message, **when** the fork completes, **then** a new Session is created containing a replayed copy of the source conversation up to that point under new message/part identities, and subsequent activity on either Session does not affect the other.

## Confidence & open questions

**High confidence:**
- The pipeline actually reached by the CLI/TUI and by the HTTP session route (`packages/opencode/src/server/routes/instance/httpapi/handlers/session.ts`, which calls `SessionPrompt.Service` exclusively) is `packages/opencode/src/session/{prompt.ts,processor.ts,compaction.ts,system.ts,instruction.ts,retry.ts,overflow.ts,reminders.ts,tools.ts,llm.ts}`. This was independently confirmed by tracing the TUI's prompt submission through the HTTP handler to `SessionPrompt.Service.prompt`/`loop`, and directly by `packages/opencode/test/session/prompt.test.ts`, which asserts `seen.filter((type) => type.startsWith("session.next.")).toEqual([])` after driving a real prompt through this path — i.e. the shipping pipeline is tested to emit *none* of the dormant V2 event family.
- A second, fully-built, extensively tested (~80 named cases in `packages/core/test/session-runner.test.ts` alone, plus dedicated suites for run-coordination, context epochs, projector, and system-context) implementation exists in `packages/core/src/session/{runner,execution,run-coordinator,context-epoch,compaction,history,input,projector}.ts` and `packages/core/src/system-context/*` / `packages/core/src/instruction-context.ts`. It is registered in the server's dependency-injection graph (`server.ts`) but is not invoked by any opencode CLI/TUI/HTTP code path — confirmed by an absence of any call site for `SessionV2.Service`'s `.prompt`/`.resume`, `SessionRunner`, or `SessionRunCoordinator` anywhere under `packages/opencode/src`. The repo's own `specs/v2/session.md` corroborates this directly: it frames the core implementation as the target "V2" design with an explicit "V1 Runtime Context Parity" checklist marking several shipping behaviors (provider-family base-prompt selection, MCP/plugin/structured-output tool materialization, per-prompt overrides, plugin system-prompt transforms, mention/reference expansion, manual compaction) as `missing` or `partial` on the V2 side, and its own `session.ts` facade's `shell`/`skill`/`compact`/`wait` operations are literally stubbed to fail.
- The one physical storage schema (`SessionTable`, `MessageTable`, `PartTable` in `packages/core/src/session/sql.ts`) is genuinely shared: the shipping `packages/opencode/src/session/session.ts` reads it directly via SQL and writes to it only indirectly, by publishing legacy-shaped domain events that a core-side projector (`packages/core/src/session/projector.ts`) turns into the actual inserts/updates. A second set of tables defined in the same file (`session_message`, `session_input`, `session_context_epoch`) exists only to serve the dormant runner and is not populated by the shipping pipeline.

**Open questions (flagged, not silently resolved):**
- Is the dormant V2 pipeline an active, near-term replacement or a longer-horizon/paused rewrite? `specs/v2/session.md` reads as an actively maintained design document with an explicit parity checklist and dated follow-up items, suggesting ongoing migration work, but nothing in the code (a feature flag, a cutover date, a partial rollout percentage) indicates when or whether it will actually take over the live request path. A reimplementation must decide up front which behavior model to target; this dossier documents the shipping (V1) behavior as ground truth per the task's instruction to describe what is "wired into the shipping CLI/TUI," while using CONTEXT.md's vocabulary to describe the target design wherever the two coincide.
- CONTEXT.md itself flags one unresolved design gap directly relevant here: a legacy plugin hook (`experimental.chat.system.transform`) can arbitrarily rewrite the assembled system prompt in the shipping pipeline, and no equivalent hook exists yet in the Context-Source-based model — a reimplementation needs to decide whether to port this escape hatch, replace it with typed Context Sources, or narrow its semantics.
- The shipping pipeline's complete lack of a Context-Epoch/baseline-caching concept (it resends the full system prompt every turn) is a substantive behavioral gap versus CONTEXT.md's specification. Since CONTEXT.md is the assigned glossary/spec for "this exact feature," a reimplementer should be aware that faithfully cloning today's shipping behavior and faithfully implementing CONTEXT.md's model are two different, currently-divergent targets.
- `packages/opencode/src/session/message.ts` (a legacy Vercel-AI-SDK-v1-shaped message schema, distinct from the live `message-v2.ts`) appears to have no import sites anywhere under `packages/opencode/src` and may be dead code; it is flagged here rather than silently dropped in case some code path outside the files examined (e.g. an import/export CLI command) still reaches it.
- `packages/opencode/src/session/tools.ts` (materialization of tool definitions, permission checks, and doom-loop plumbing feeding the processor) and `packages/opencode/src/session/llm.ts` plus `llm/*.ts` (the direct Vercel AI SDK streaming driver) were surveyed only at summary depth via delegated research rather than read line-by-line for this dossier; fine-grained request-shaping detail there should be cross-checked against the adjacent Provider & LLM Integration dossier before an implementation is built against it.
