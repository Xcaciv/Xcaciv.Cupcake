# Feature: Tool System

## Purpose

The Tool System is the catalog of capabilities the coding-agent's language model can invoke during a conversation turn: running shell commands, reading/writing/editing files, searching a project, applying multi-file patches, spawning subagent "tasks," managing a todo list, asking the user clarifying questions, fetching web pages, running web search, loading a packaged skill, and querying a language server for code intelligence. It defines each tool's parameter schema (what the model must supply), its side effects, its human-readable result, and a uniform mechanism that keeps oversized results from flooding the model's context window by writing them to disk and handing back a preview. Every tool call is also required to pass through the permission system before it can act, so this system is the seam where model intent becomes an authorized, auditable, bounded-size effect on the user's machine.

## Behavior

At session start (per assistant turn) the agent builds a fresh tool set: it starts from a **built-in tool registry**, adds any repository-local custom tools discovered under `.opencode/tool` or `.opencode/tools` (JavaScript/TypeScript files exporting a tool definition, or definitions contributed by loaded plugins), then narrows the list based on: the current model/provider (e.g. only OpenAI "gpt-*" non-oss/non-gpt-4 models get the patch-application tool instead of discrete edit/write tools; web search is only offered to specific providers or when a search provider is explicitly enabled), the active agent's permission ruleset (subagent types the current agent isn't allowed to launch are omitted from the task tool's description; whole tools can be hidden by policy), and feature flags (an experimental "run confined script" tool, an experimental code-intelligence tool, and an experimental "exit plan mode" tool are all gated). Each tool exposes: a stable string ID, a natural-language description (used as the model-facing tool documentation, sometimes assembled dynamically, e.g. injecting the current year into the web-search prompt or appending the list of launchable subagents into the task tool's description), and a parameter schema that is converted to JSON Schema for the model's function-calling interface.

When the model calls a tool, the host: decodes/validates the raw arguments against the tool's schema (returning a structured "rewrite your input" error back to the model on failure, without executing anything); constructs a per-call context carrying the session/message identifiers, an abort signal, the calling agent's name, the running conversation's message history, a `metadata()` callback the tool can use to stream incremental status/progress into the tool-call record while it runs, and an `ask()` callback that raises a permission request (see Permission System) — the call blocks until the request is resolved and only proceeds if not denied; runs the tool's effect; and — unless the tool has already marked its own output as "truncated" — passes the tool's raw text output through the shared **output-truncation** step before handing the final `{ title, output, metadata, attachments? }` result back to the model. Tool executions are also wrapped with lifecycle hooks so external plugins can inspect or rewrite arguments before execution and results after execution.

### Output truncation and overflow-to-file

A single shared truncation policy (also usable independently by any tool that needs custom limits, e.g. a "read from tail" direction) enforces two ceilings on any tool's textual output: a maximum line count and a maximum byte count, both configurable via `tool_output.max_lines` / `tool_output.max_bytes` in configuration and otherwise defaulting to 2000 lines / 50 KiB. If output fits under both ceilings it passes through unchanged. If it exceeds either, the policy keeps a prefix (default) or suffix ("tail" direction) of the content up to whichever limit is hit first, appends a marker stating how many lines or bytes were cut, writes the **complete, untruncated** original text to a per-tool-call file inside a dedicated on-disk directory (a "tool-output" store under the application's data directory, one file per call, named with an ascending, sortable ID), and appends a hint instructing the model how to inspect the rest — via a subagent task delegated to search/read the file if the current agent is permitted to spawn subagents, or otherwise by directly re-invoking grep/read against the saved file with offset/limit. The tool's own reported metadata records whether truncation occurred and, if so, the saved file's path. Saved truncation files older than 7 days (by file modification time) are purged on an hourly background sweep that starts about a minute after the tool system initializes.

Several tools implement their own finer-grained size discipline on top of this shared ceiling: file reads cap individual overlong lines (truncating any single line past 2000 characters with a suffix marker) independent of the overall line/byte budget, and the shell/bash tool streams command output incrementally, keeping only a bounded rolling window of the most recent bytes in memory (spilling older output to the same on-disk truncation file as it accumulates) so a long-running, chatty command cannot grow memory unbounded before the run finishes.

## Business rules & edge cases

- **Path resolution & workspace containment.** File-touching tools (read, write, edit, glob, grep, LSP, apply-patch, and shell path arguments the parser can recognize) resolve relative paths against the current working directory, but before touching anything outside the project's own directory tree they raise a distinct "external directory" permission check (separate from the tool's normal permission) scoped to a glob over the parent directory of the external target; that check is skipped when explicitly bypassed (used for read operations following an already-approved edit) and is only relevant for a directory kind vs. file kind of target.
- **Read tool:** refuses to read binary files (detected via a fixed list of known-binary extensions or a >30% non-printable-byte / any-NUL-byte heuristic over a small sample), instead reading images/PDFs into inline attachments (base64 data URLs) rather than text; when a requested path is missing it looks for similarly-named files in the same directory and surfaces up to three suggestions; when reading a directory it lists entries (directories/symlinks-to-directories suffixed with `/`) with pagination via offset/limit; requesting an out-of-range offset on a file is an error; each read that has more content is annotated with continuation guidance ("Use offset=N to continue").
- **Edit tool:** the exact-match replacement falls back through nine progressively fuzzier matching strategies (exact, line-trimmed, block-anchor with Levenshtein similarity threshold, whitespace-normalized, indentation-flexible, escape-normalized, trimmed-boundary, context-aware, multi-occurrence) before failing; a successful non-exact match is rejected if the matched span is disproportionately larger than the requested search text (to avoid accidentally replacing far more than intended); an ambiguous match (more than one equally valid occurrence) is rejected unless `replaceAll` is requested; an empty `oldString` is only valid when creating a brand-new file, never to blank out an existing one; edits are serialized per absolute file path with an in-process lock so concurrent tool calls to the same file cannot race; original line-ending style (LF vs CRLF) and a byte-order-mark, if present, are detected and preserved on write.
- **Write tool:** always fully replaces file content (no merge), preserves an existing BOM, and creates parent directories as needed.
- **Apply-patch tool:** parses a single free-form multi-file patch document into per-file "add / update / delete / move(rename)" hunks; a well-formed but empty patch, or a patch producing zero hunks, is rejected; a rename ("move") can overwrite an existing file at the destination, and an "add" can overwrite an existing file at that path; failure during verification/parsing of any hunk aborts before any file is touched (no partial application); every touched path is diffed and surfaced together in one permission request; after applying, each touched file is registered with the language-server integration and any diagnostics are appended to the tool's output.
- **Shell/bash tool:** the model-facing tool ID is fixed as `bash` for backward compatibility even though the underlying shell may be PowerShell or `cmd.exe` on Windows; the command text is parsed with a real shell grammar (Bash or PowerShell) to enumerate sub-commands, and any sub-command recognized as filesystem-mutating (`rm`, `mv`, `cp`, `chmod`, PowerShell/cmd equivalents, `cd`/`pushd`/`Set-Location`, etc.) has its path-like arguments resolved and checked for being outside the workspace, triggering the external-directory permission; every distinct command line is separately subject to a shell-command permission check, with an "always allow" pattern derived from a normalized command prefix (e.g. so future invocations of the same base command with different arguments can be pre-approved); commands are killed after a configurable timeout (default 2 minutes) or on user abort, and either condition is reported back to the model as `<shell_metadata>`; negative timeouts are rejected as invalid input.
- **Task (subagent) tool:** enforces a configurable maximum subagent nesting depth (default 1) by walking up parent sessions; rejects targeting an unknown agent type; a spawned subagent's permission set is a filtered/derived view of the parent's, and — unless the target agent explicitly grants them — the subagent is explicitly denied the todo-list tool and the task tool itself (no recursive task-spawning by default), plus any tools an admin config marks as "primary-only"; supplying a prior task's ID resumes that same subagent session instead of creating a new one; an experimental "background" mode (env-flag gated) launches the subagent asynchronously, returns immediately with guidance not to poll it, and later injects a synthetic message into the parent conversation with the subagent's result when it finishes; foreground tasks propagate the calling turn's abort/cancel into the child session.
- **Todo-list tool:** replaces the session's entire todo list with the array supplied by the model on every call (not a diff/patch); the tool's own title reports the count of still-incomplete items.
- **Question tool:** only exposed to certain client surfaces (app/CLI/desktop) or when explicitly enabled; blocks until the user answers or the calling context resolves the pending questions.
- **Plan-exit tool:** only available in an experimental "plan mode" and only in the CLI client; asks the user a yes/no question about proceeding to implementation, and if declined raises a rejection rather than switching modes; on approval it synthesizes a new user turn that switches the active agent to the "build" agent.
- **Skill tool:** loads a named skill's packaged instructions and lists (a capped sample of) the files alongside it, resolved relative to the skill's own directory, explicitly excluding the skill's own manifest file from that listing.
- **Web-fetch tool:** only accepts `http(s)://` URLs; enforces a response-size ceiling (5 MB, checked against both the `Content-Length` header and the actual bytes read) and a request timeout (capped at 2 minutes regardless of what the caller asks for); content is content-negotiated by requested output format (markdown/text/html) via an `Accept` header, and HTML is converted to Markdown or plain text as requested; if a request is blocked by a bot-mitigation challenge it is retried once with a different User-Agent; image responses are returned as inline attachments instead of text.
- **Web-search tool:** provider (of two upstream search backends) is chosen by an environment override, feature flags, or otherwise deterministically per-session (hashed session ID) to split traffic between the two; results come back as a single pre-formatted text blob from the upstream service.
- **LSP tool:** gated behind an experimental flag; requires the target file to exist and to have at least one attached language-server client, otherwise it fails outright rather than returning an empty result; supports a fixed menu of operations (go to definition, find references, hover, document/workspace symbols, go to implementation, call hierarchy in/out).
- **Custom/plugin tools:** repository-local tool files must export values shaped like a plugin tool (description + executor, with optional argument schema); a customtool with no declared arguments falls back to accepting an empty object rather than crashing (a fix for tolerating `undefined` args); both Zod-schema and legacy bare-JSON-Schema argument shapes are supported and normalized to a single JSON Schema surface for the model; every custom tool's output goes through the same truncation step as built-ins.
- **Invalid-tool placeholder:** a non-functional tool literally named "invalid" (described to the model as "Do not use") exists purely so the UI/runtime has something well-formed to render/report against when a tool call could not be resolved or its arguments could not be validated.

## Workflows & states

1. **Registry build (once per host process / config change):** scan configured tool directories and loaded plugins for custom tools → merge with the fixed built-in list → the merged catalog is exposed by ID.
2. **Per-turn tool-set resolution:** given the active model, provider, agent, and permission ruleset, filter the catalog (model-family edit-vs-patch split, web-search eligibility, code-mode/LSP/plan-mode flags) → run a plugin hook allowing external code to rewrite any tool's advertised description/schema → attach dynamically composed descriptions (task tool gets the current agent-launch table appended; the confined-script tool gets a generated map of reachable MCP tools appended, and is dropped entirely if that map would be empty) → hand the resulting name→schema→executor map to the model-calling layer.
3. **Per-call execution:** model emits a tool call → arguments decoded against schema (failure ⇒ typed error, no execution) → tool-specific permission check(s) fire, potentially more than one per call (e.g. external-directory check, then the tool's own action check; the shell tool may fire one external-directory check plus one command check per distinct sub-command) → side effect executes → tool-specific result/metadata built → generic truncation applied unless the tool opted out by already flagging its own truncation → result recorded against the tool call and returned to the model.
4. **Truncation-file lifecycle:** any oversized output is written once at call time; the store is periodically swept (hourly, first pass after ~1 minute) to delete entries older than 7 days; nothing else reads or rewrites a truncation file except the model choosing to grep/read it back via other tools.
5. **Subagent task lifecycle (foreground):** create or resume a child session → run its own full prompt/tool loop to completion or failure → surface its final text (or error) wrapped in a `<task>`/`<task_result>` or `<task_error>` envelope → propagate parent cancellation into the child.
6. **Subagent task lifecycle (background, experimental):** start the child run untracked by the calling turn → immediately return a "started" placeholder to the model → on completion/error, asynchronously inject a synthetic user-turn message into the original session carrying the same envelope, without blocking the parent conversation.

## Data

- **Tool definition:** ID, description (string, sometimes computed lazily per agent/session), parameter schema (converted to JSON Schema for the wire format, with a small cache keyed by schema identity), an executor function, and an optional custom "format this validation error for the model" hook.
- **Execution context passed to every tool:** session ID, message ID, calling agent name, an abort signal, an optional tool-call ID, an `extra` bag (used e.g. to smuggle the current model info into web-search, or task-prompt callbacks into the task tool), the conversation's message history, a `metadata()` progress-reporting callback, and an `ask()` permission callback.
- **Execution result:** a title (short human-readable label), the metadata object (tool-specific structured fields plus the universal `truncated`/`outputPath` fields once truncation runs), the output text handed to the model, and an optional list of attachments (e.g. inline images/PDFs as data URLs).
- **Truncation record:** stored as a plain text file per oversized call, named with an ascending sortable identifier prefixed `tool_`, under a dedicated "tool-output" directory in the application's per-user data directory; no index/database — discovery is by directory listing and file mtime.
- **Custom tool source:** files under a project's `.opencode/tool` or `.opencode/tools` directory (singular or plural both supported), each export becoming one tool named after the file (default export) or `filename_exportName` (named exports); plugin-contributed tools are merged the same way.

## Interfaces

- **Permission System** (documented separately): every tool's `ask()` call and the external-directory check are permission requests; a denial aborts the tool before its side effect runs. The task tool's own invocation is itself gated by a `task` permission scoped to the requested subagent type, and MCP/plugin tools funnel through the same `ask()` seam.
- **LSP Integration** (documented separately): read/write/edit/apply-patch "warm" or notify the language-server layer after touching a file and fold its diagnostics into their output; the dedicated LSP tool is a thin wrapper over that same integration's query operations.
- **Git/Worktree/Snapshot/Patch** (documented separately): the apply-patch tool's parsing and hunk-application logic, and the edit/write tools' diff generation for permission previews and file-diff statistics, are provided by that subsystem; nothing here reimplements diffing.
- **Codemode** (documented separately): the experimental "confined script" tool is a thin adapter that exposes connected MCP tools to a sandboxed interpreter; this dossier only notes its gating and that its presence suppresses exposing MCP tools individually to the model.
- **Session & Conversation Runtime** (documented separately): the runtime resolves the tool set for each model turn, adapts each tool definition into the model-calling SDK's function-call shape, wires the `ask`/`metadata` callbacks to real session/permission services, and additionally synthesizes a handful of MCP-resource tools (list/list-templates/read) and a structured-output tool outside the registry described here.
- **Agent/Subagent/Skill System** (documented separately): agent permission rulesets determine which subagent types the task tool may launch and which tools are visible/deniable per agent; the skill tool is a loader over that system's skill catalog.

## Error handling

- Argument decoding failures never execute the tool; they produce a distinct, typed "invalid arguments" error whose message explicitly instructs the model to rewrite its input to satisfy the schema (each tool can also customize how a validation error is phrased).
- Most tool-body failures (missing file, bad patch, permission denial bubbling up, ambiguous edit match, etc.) surface as ordinary thrown errors that become the tool's error result shown to the model — the conversation continues rather than aborting.
- The apply-patch tool guarantees all-or-nothing application: any hunk that fails to parse or verify aborts before any file on disk is touched.
- The shell tool distinguishes three non-zero-exit-code outcomes for the model: normal exit code, timeout expiry (explicitly suggesting a retry with a larger timeout), and user-initiated abort — all folded into a `<shell_metadata>` block rather than being reported as tool failures.
- Truncation-store cleanup failures are logged and do not interrupt the periodic sweep's next run.
- A tool call whose declared tool ID cannot be resolved, or whose output cannot otherwise be rendered normally, degrades to the inert "invalid" placeholder tool rather than crashing the turn.
- Task-tool subagent failures (assistant-message error, or a failed tool call inside the subagent's own last turn) are converted into a single descriptive error identifying the failed task's session ID.

## Non-functional observations

- Tool execution is traced (each call wrapped in a span carrying tool name, session/message/call IDs) for observability; this is incidental instrumentation, not part of the tool contract.
- The parameter-decoder for each tool is compiled once at tool-set build time and reused for every call in that turn, rather than rebuilt per invocation, as a deliberate micro-optimization given how often tool calls happen inside a single conversation.
- Shell output capture keeps only a small rolling window of the most recent output bytes in memory (roughly twice the truncation byte ceiling) regardless of how much a command ultimately produces, spilling the rest straight to the on-disk truncation file as it arrives, so a very verbose or long-running command doesn't grow host memory unbounded before the tool call resolves.
- Truncation and its retention sweep are unconditionally initialized once and self-schedule; there is no manual/administrative trigger.

## Acceptance criteria — 6-8 Given/When/Then statements

1. **Given** a tool call whose text output is under both the configured line and byte ceilings, **when** the tool finishes, **then** the model receives the output unchanged and the result's `truncated` flag is false.
2. **Given** a tool call whose output exceeds either the line or byte ceiling, **when** the shared truncation step runs, **then** the model receives a bounded preview (head by default) plus a count of cut lines/bytes and a pointer to the complete output saved to disk, and the result's metadata records `truncated: true` and the saved path.
3. **Given** a saved oversized-output file older than 7 days by modification time, **when** the periodic cleanup sweep runs, **then** the file is deleted; a file newer than 7 days is left in place.
4. **Given** an edit tool call whose `oldString` cannot be located in the target file by any of the tool's fuzzy-matching strategies, **when** the tool executes, **then** the call fails with an error stating the text must match exactly, and the file is left unmodified.
5. **Given** an edit tool call whose `oldString` matches more than one location in the file and `replaceAll` is not set, **when** the tool executes, **then** the call fails asking for more surrounding context, and the file is left unmodified.
6. **Given** a shell/bash tool call whose command references a path outside the current project workspace, **when** the command is parsed, **then** an external-directory permission check is raised for that path's parent directory before the command runs, in addition to the command's own permission check.
7. **Given** an apply-patch call containing multiple file hunks where one hunk fails to parse or verify, **when** the tool processes the patch, **then** no file on disk is modified for any hunk in that patch.
8. **Given** a task-tool call naming a subagent type the calling agent's permission ruleset does not allow it to launch, **when** the call is evaluated, **then** the permission check denies the call before any subagent session is created.

## Confidence & open questions

**High confidence:** the enumerated built-in tools, their parameter contracts, the shared truncation/overflow-to-file mechanism and its numeric defaults (2000 lines / 50 KiB / 7-day retention), the model/provider-based edit-vs-apply_patch split, and the two-registry situation below are all confirmed directly from source and by colocated tests (`packages/opencode/test/tool/*.test.ts`).

**Confirmed dual-implementation, and which one ships:** `packages/opencode/src/tool/*` (survey basis for this dossier) is the implementation actually wired into the running CLI — traced end-to-end from `packages/opencode/src/session/prompt.ts` (the real per-turn conversation loop, used by the HTTP server routes and `opencode run`) through `packages/opencode/src/session/tools.ts` (`SessionTools.resolve`, which adapts `packages/opencode/src/tool/registry.ts`'s tool list into the model-calling SDK's tool format and wires `ask`/`metadata`). `packages/core/src/tool/*` is a separate, more architecturally strict rewrite (its own `AGENTS.md` describes a "canonical tool" / `Tools.Service` / `PermissionV2` / Location-scoped design with a distinct `ToolOutputStore`) reachable only through `packages/core/src/session/runner/llm.ts` and `packages/core/src/location-services.ts`; no code path from the shipping CLI's actual send-message flow (`SessionRunner.run`) was found to be invoked anywhere in `packages/opencode/src`. Treat `packages/core/src/tool/*` as an in-progress migration target, not shipping behavior, at this commit.
- **Genuine behavioral divergence found, as flagged by the task brief:** the shipping `apply_patch` tool (`packages/opencode/src/tool/apply_patch.ts`) supports file moves/renames, including overwriting an existing file at the destination, and supports "add" overwriting an existing file — both exercised by tests (`moves file to a new directory`, `moves file overwriting existing destination`, `adds file overwriting existing file`). The parallel core implementation (`packages/core/src/tool/apply-patch.ts`) explicitly rejects any patch containing a move ("apply_patch moves are not supported yet"). Since the opencode-side implementation is what ships, a reimplementation should follow its move/overwrite semantics; the core version's stricter behavior appears to be an intentionally incomplete migration state rather than an alternate deliberate policy, but this is inferred, not stated anywhere as a decision.
- **Open question:** whether `packages/core/src/tool/*` and its `ToolOutputStore` (which independently defines the same 2000-line/50 KiB/7-day constants) are intended to fully replace `packages/opencode/src/tool/*` in a future release, and whether any other behavioral deltas beyond the apply-patch move case exist between the two, was not exhaustively diffed tool-by-tool given this dossier's summary depth — only apply-patch was spot-checked for divergence.
- **Open question:** the exact call site that redirects an unresolvable/mis-named model tool call to the "invalid" placeholder tool was not located within this survey's scope (only its definition and its CLI-rendering consumer were found); behavior of the placeholder itself is fully confirmed.
- **Open question:** `packages/opencode/src/tool/plan-enter.txt` exists alongside `plan-exit.txt` but no code path referencing a "plan_enter" tool was found — it may be dead/reserved content rather than an active tool; not included above as a live built-in.
