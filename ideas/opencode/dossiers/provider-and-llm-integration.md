# Feature: Provider & LLM Integration

## Purpose

Lets the CLI talk to dozens of different large-language-model backends — first-party APIs (Anthropic, OpenAI, Google, Amazon Bedrock, Azure, GitHub Copilot, xAI), aggregator/gateway services (OpenRouter, a Cloudflare AI Gateway, a first-party managed gateway), and an open-ended set of "OpenAI-compatible" community/self-hosted endpoints — through one internal API. It is responsible for: discovering which providers and models exist and are usable (via a hosted catalog plus local configuration/credentials); picking a default or explicit model per session/agent/subtask; translating a single internal request shape into each vendor's wire format and translating each vendor's streamed response back into one common event vocabulary (text, "thinking"/reasoning, tool calls, token usage); retrying transient failures with backoff while distinguishing them from permanent ones (bad auth, exceeded context window, exhausted quota); and exposing enough metadata (context-window size, per-token cost, capability flags) that other features can do cost/context accounting without vendor-specific logic.

## Behavior

**Catalog acquisition.** A background service maintains a JSON catalog of provider/model metadata fetched from a hosted URL (default `https://models.opencode.ai`, overridable). The on-disk cached copy is treated as fresh for 5 minutes; a background loop re-checks/refreshes it every 60 minutes; a cross-process file lock prevents two concurrent CLI invocations from fetching/writing the same cache file at once; the network fetch itself retries transient HTTP failures twice with a short backoff and times out after 10 seconds. If the network is unreachable and no disk cache exists, an embedded build-time snapshot of the catalog is used instead; if catalog fetching is explicitly disabled, an empty catalog is used. Once loaded, the catalog is cached in memory indefinitely and only invalidated by an explicit refresh.

**Provider/model table construction.** Starting from the catalog, a provider/model table is built by layering, in order: plugin-injected models; the user's static configuration (explicit provider/model entries, including fully custom npm-based providers and model aliases); providers detected purely from environment variables being set; providers with a stored credential (API key or OAuth); provider options injected by plugin-supplied auth loaders; a table of built-in per-provider quirk handlers (header injection, base-URL/region resolution, credential-chain resolution, dynamic model discovery); then the user's configuration is reapplied so it always wins on naming/credentials. A final pass applies provider allow/deny lists, strips deprecated models unconditionally and "alpha" models unless an experimental-models setting is enabled, applies any per-model allow/deny list, computes named "variants" (e.g. reasoning-effort or thinking-budget presets) per model, and drops any provider left with no usable models.

**Model selection.** An explicit `provider/model` id (from config or a run-time override) always wins. Otherwise, a small per-user "recently used model" memory is consulted; failing that, a provider is chosen from what's configured and its models are ranked by a fixed family-preference order (favoring current flagship families and "-latest" ids) to pick a default. A separate "small model" selector — used for cheap background subtasks — ranks candidate models by a blend of cost and release recency, preferring models whose id/family/name matches a small-model naming pattern (e.g. "mini", "flash", "nano", "haiku", "lite"), with per-provider overrides and exclusions for providers whose available-model reporting is known to be unreliable.

**Turning a chosen model into a live client.** Each catalog model declares which client-library package should be used to talk to it. The chosen package is loaded dynamically (either one of roughly two dozen first-party per-vendor packages, or an arbitrary user-specified npm package/local path for fully custom providers) and instantiated with merged options (base URL, API key, headers, per-provider template variables). The resulting client's outbound HTTP calls are wrapped with three independent timeouts: one for waiting on response headers, one for stalls between streamed chunks, and one for the request as a whole.

**Per-turn request preparation.** Before every model call: the system prompt is assembled from the agent's own prompt, session-level system text, and user-level system text (with a plugin hook able to rewrite it); sampling parameters (temperature, top-p, top-k) get per-model-family defaults where the model doesn't accept arbitrary values; reasoning/"thinking" options are shaped into whatever form the specific vendor's API expects (effort levels, token budgets, toggle flags — the taxonomy differs sharply by vendor); tool definitions are schema-lowered into whatever JSON-Schema subset the vendor's tool-calling API accepts; the message history is repaired for vendor-specific constraints (stripping empty content blocks some vendors reject, sanitizing/truncating tool-call ids to vendor-specific formats, fixing message-ordering constraints some vendors enforce, replaying "thinking" content only where the vendor allows it); prompt-cache breakpoints are placed on the request for vendors whose wire format supports explicit cache hints; and per-request headers are attached (session/project identifiers, or a generic session-affinity header for third-party endpoints).

**Streaming execution and normalization.** The prepared request is executed by a bundled multi-vendor streaming request library that owns tool-call dispatch and per-attempt retries, and its streamed output is converted into one internal event vocabulary shared by the rest of the system regardless of the vendor: block-scoped start/delta/end events for plain text and for reasoning/"thinking" content, start/delta/end events for an in-progress tool-call's input plus a completed tool-call event, a tool-result (or tool-error) event once the tool runs, step-boundary and turn-finish events carrying token usage, and a distinct provider-error event. A second, feature-flagged execution path can instead route a request through a dedicated protocol/transport implementation (see External technology) for a narrow subset of vendors and auth modes, producing the same event vocabulary directly; when that path can't handle the current model/provider/auth combination it transparently falls back to the default path for that request.

**Tool-call round-trip.** A tool call surfaced by the model is dispatched into the session's tool-execution system (not part of this feature) using the same normalized event vocabulary in both directions: the tool's declared schema was already lowered per-vendor when the request was built, and its result or error is fed back as the corresponding result/error event, ready to be replayed into the next turn's message history.

**Retry and rate-limit handling.** Failures are classified before deciding whether to retry: an error is treated as a context-window overflow (never retried — the caller is expected to shrink/compact the conversation instead) if it matches a large bank of known "prompt/context too long" phrasings across vendors; genuinely transient errors (5xx responses, explicit rate-limit/overload wording, recognized transient network failures) are retried with exponential backoff and random jitter, honoring a vendor-supplied "retry after" value when present and otherwise capping the delay; authentication, quota, and malformed-request errors are not retried. A specific usage-limit response from the first-party managed provider is surfaced with a distinct upgrade call-to-action and a human-readable "resets in" countdown rather than a generic error.

**Cost/context accounting.** Catalog metadata for each model carries its context-window size, maximum output tokens, and per-token pricing (including separate cache-read/cache-write pricing and, for some models, a different price tier above a context-size threshold). Every completed turn reports token usage broken down into fields that are mutually exclusive by construction (fresh input tokens, cache-read input tokens, cache-write input tokens, reasoning tokens as a subset of output) alongside vendor-convention inclusive totals, so a consumer can compute spend or context pressure without needing to know how the source vendor natively reports usage.

## Business rules & edge cases

- Deprecated models are always excluded from selection and from "did you mean" suggestions; alpha-status models are excluded unless an experimental-models setting is explicitly enabled.
- A default output-token cap (32,000) applies unless a lower per-model output limit applies instead — the request never asks for more tokens than the smaller of the two.
- The first-party managed provider hides all non-free models from the catalog unless the user has configured a key or has a stored credential for it.
- Region/model-id prefixing for one cloud vendor's models (e.g., mapping a bare model id to a region- or cross-region-inference-qualified id) is a hardcoded per-family, per-region compatibility table, not a general rule — it only applies to specific model families in specific regions.
- "Small model" auto-selection explicitly excludes two provider variants whose available-deployment reporting is known to be unreliable (a documented, presumably temporary, workaround rather than a permanent design choice).
- Context-overflow detection is a best-effort text-pattern match over dozens of observed vendor error phrasings, deliberately excluding phrasings that look like rate-limiting so a 429 is never misclassified as an overflow; it is explicitly documented as incomplete for at least one vendor whose overflow errors can otherwise be silently accepted.
- Prompt caching is applied automatically only for vendors whose wire format supports explicit inline cache markers; vendors that cache implicitly on the server side receive no explicit hints. Where explicit markers are used, at most four cache breakpoints are placed per request (last tool definition, last system block, latest user message, by default), and a manually-placed cache marker is never overwritten by the automatic placement.
- Some vendor families require message-history repairs to remain valid: one family rejects a tool-result message immediately followed by a user message (a synthetic filler turn is inserted); several families require sanitized/length- or alphabet-constrained tool-call identifiers; one integration requires a non-empty tool list on any request replaying prior tool calls even when no tools are currently enabled (a dummy, never-invoked tool is injected purely to satisfy that constraint).
- Several vendor families always disable "strict" tool-schema validation to tolerate dynamically-sourced (e.g. externally-supplied) tool schemas that would otherwise fail stricter structured-output validation.
- The experimental alternate execution path only supports a narrow allow-list of vendors/packages and API-key-style auth (plus one vendor's OAuth mode via a caller-supplied network override); everything else automatically and silently uses the default execution path, per request.

## Workflows & states

1. **Startup / catalog refresh**: disk-cache check → (if stale/missing) cross-process-locked network fetch → embedded-snapshot or empty-catalog fallback on failure → in-memory cache held until the next explicit refresh or the 60-minute background tick.
2. **Provider table build** (once per catalog load): catalog → plugin model injection → config providers → env-detected providers → credential-detected providers → plugin auth-loader injection → built-in per-provider quirk loaders → config reapplied → dynamic-discovery loaders (where a vendor supports them) → allow/deny-list and status filtering → variant computation.
3. **Per-turn request/response lifecycle**: resolve model (explicit or default) → resolve/instantiate live client → prepare request (system prompt, sampling params, reasoning options, tool schemas, message repairs, cache hints, headers) → choose execution path (experimental native path if enabled and supported for this model/provider/auth, else the default path) → stream normalized events (turn start → interleaved text/reasoning/tool-call events → step-finish → finish, or a provider-error in place of finish) → assemble the final message and usage totals.
4. **Failure sub-state**: on a streamed or thrown error, classify it; if retryable, compute a backoff delay (vendor-supplied retry-after honored when present) and re-attempt up to a bounded retry count, otherwise surface a terminal, distinctly-typed failure (context-overflow, auth, quota, or generic) to the caller instead of retrying.
5. **Auth flow** (interface only — implemented in the adjacent Auth/Credentials feature): pending-OAuth-authorize → callback/code-exchange → stored credential; or direct API-key entry → stored credential. Either outcome changes a provider's "source" (environment / config / stored-credential / plugin-provided) surfaced back through this feature's provider listing.

## Data

- **Catalog model record** (from the hosted catalog): id, display name, family, release date, attachment/reasoning/temperature/tool-call capability flags, supported reasoning-option shapes (effort levels, on/off toggle, or a token-budget range), input/output modality lists (text/audio/image/video/pdf), a status (alpha/beta/deprecated — the catalog's own vocabulary omits an explicit "generally available" value), per-token cost (input, output, optional cache-read/cache-write, optional cost tiers keyed by a context-size threshold, and an optional distinct price above a 200k-token threshold), context/input/output token limits, and optional "experimental modes" — named alternate configurations of the same base model with their own cost and request-body/header overrides (surfaced to users as separate selectable model ids).
- **Normalized internal Provider/Model record** (this feature's own shape, derived from the catalog plus local config/credentials): provider id, display name, a "source" tag (environment/config/stored-credential/plugin-provided), declared environment-variable names, optional stored key, arbitrary provider-level options/headers, and a map of models; each model carries a client-library package reference, capability flags (now including per-direction modality booleans and an "interleaved reasoning" descriptor), the cost/limit fields inherited from the catalog, a normalized status (alpha/beta/deprecated/**active**), free-form options/headers, and a map of named "variants" (each variant itself an options overlay, used for reasoning-effort/thinking-budget presets).
- **Normalized streaming event** (shared internal vocabulary): a small closed set of tagged event types — turn/step start, text start/delta/end, reasoning start/delta/end, tool-input start/delta/end, tool-call, tool-result, tool-error, step-finish, finish, provider-error — each optionally carrying a vendor-specific metadata escape hatch keyed by vendor name for data that doesn't normalize.
- **Usage record**: inclusive input/output/total token counts (matching common industry convention) plus an independently-meaningful, non-overlapping breakdown — fresh (non-cached) input tokens, cache-read input tokens, cache-write input tokens, and reasoning tokens as a subset of output tokens — so no consumer ever has to subtract two numbers to get a third.

## Interfaces

- **Config & Data Contracts** (adjacent, not documented here): this feature reads provider/model selection fields, default/small-model overrides, and provider allow/deny lists from project/user configuration; it does not define or validate that configuration's schema.
- **Auth/Credentials/Accounts** (adjacent): this feature only *consumes* stored credentials (API key or OAuth token) and exposes an interface for listing a provider's available auth methods and driving an OAuth authorize/callback exchange or API-key capture; the credential store itself, token refresh, and OAuth transport belong to that adjacent feature.
- **Permission System** (adjacent): one specialized provider integration (a workflow-style model that executes tools on a remote service's behalf) routes tool-call approval through the permission system; this is a narrow integration point, not general behavior of this feature.
- **Session & Conversation Runtime** (adjacent): this feature exposes a single "stream a turn" operation taking a chosen model, message history, tool set, and sampling/agent parameters, and returning the normalized event stream described above; message persistence, conversation compaction, and turn-level retry-state display are owned by that adjacent feature and only consume this feature's error classification and event vocabulary.
- **Tool System** (adjacent): tool definitions and their execution handlers are passed into this feature as opaque, named entries; this feature only translates their input schema per vendor and round-trips call/result/error events — it does not implement tool execution, sandboxing, or permission checks.
- **HTTP/CLI surface**: provider and model listing, along with auth connect/callback endpoints, are exposed over both an HTTP API (for a web UI or SDK client) and CLI subcommands; a separate debug-only CLI command exposes the in-progress next-generation catalog implementation (see Confidence & open questions) for inspection.

## Error handling

- Two independent error taxonomies exist today, one per execution path. The default path recognizes essentially two buckets — "context overflow" (detected by matching known vendor phrasings, an HTTP 413, or a specific vendor error code) and a generic "API error" carrying an explicit retryable flag (with a documented special case: one vendor's HTTP 404 is treated as retryable because that vendor is known to return 404 for models that do in fact exist). The experimental path recognizes a wider, explicitly-typed set: invalid request, no matching route, authentication (further split into missing/invalid/expired/insufficient-permission), rate limit (carrying a retry-after value), quota exceeded, content-policy violation, provider-internal (5xx-class), transport/network failure, malformed provider output, and unknown-provider — each with its own fixed retryability.
- Retry/backoff differs by path: the default path retries up to 5 times with an exponential (base delay doubling each attempt) schedule plus jitter, capped near 30 seconds when no vendor retry-after hint is present, and honors an explicit vendor-supplied retry-after value (in seconds or milliseconds) when one is given. The experimental path retries up to 2 times with a shorter base delay, its own cap, and its own jitter percentage, and additionally scrubs credential-like values out of any request/response data it attaches to an error for diagnostics.
- Human-facing error messages are cleaned up before display: JSON error bodies are unwrapped to extract a vendor "message"/"error" field; an HTML error page (typical of a gateway or proxy rejecting the request before it reaches the vendor) is replaced with a specific hint (e.g., suggesting re-authentication for a 401, a permissions check for a 403) instead of dumping markup; a handful of vendor-specific error codes get bespoke, non-retryable messages (quota exceeded, plan-upgrade-required, invalid prompt) versus a generic retryable "server error" for anything unrecognized.
- A usage/quota-limit response from the first-party managed provider is treated as retryable but also carries a distinct, richer call-to-action (a human-readable "resets in" duration and an upgrade link) rather than being folded into the generic retryable-error message.
- Header-wait and mid-stream stall each have their own dedicated timeout error type, distinct from a vendor-returned API error, so a caller can tell "the vendor never responded" apart from "the vendor responded with an error."

## Non-functional observations

- The per-vendor request/response compatibility logic (sampling defaults, reasoning/thinking option shaping, message repairs, tool-schema lowering, cache placement) is large and finely differentiated by vendor and even by specific model family/version — a strong signal that this is an area with an ongoing, high-frequency maintenance burden as vendors ship new models and API quirks, and it carries a correspondingly large, dedicated regression-test suite.
- Three overlapping implementations of the same conceptual feature coexist in the codebase at once (see Confidence & open questions): a legacy/shipping implementation that is the only one actually exercised for live session traffic today, an in-progress next-generation catalog/provider-instantiation implementation (hook/plugin-based, with its own parallel per-vendor test suite) not yet wired into session traffic, and a separately-versioned protocol/transport package that is fully used for its shared type vocabulary but only conditionally used for actual request execution. This represents real architectural duplication (e.g., the same cloud-region resolution logic and the same gateway-routing logic are each implemented twice) rather than a single evolving module.
- The hosted-catalog design (disk cache, in-memory cache, embedded offline snapshot, explicit disable flag, cross-process lock) is built for a CLI that may run many short-lived, concurrent invocations and must still work fully offline — this is a deliberate resilience design, not an afterthought.
- Retry/backoff tuning constants are duplicated and diverge between the two execution paths, which — if the experimental path were ever promoted to default — would change observable retry timing/behavior even for previously-passing scenarios.

## Acceptance criteria — 5-8 Given/When/Then statements

1. **Given** no cached provider/model catalog and a reachable catalog source, **when** the CLI starts, **then** it fetches the catalog, persists it to a local cache, and reuses that cache for subsequent lookups without re-fetching for at least several minutes.
2. **Given** the catalog source is unreachable and no local cache exists, **when** the CLI starts, **then** it falls back to a bundled offline snapshot (or an empty catalog if fetching was explicitly disabled) rather than failing to start.
3. **Given** a provider is simultaneously detectable via an environment variable, a stored credential, and an explicit local configuration entry, **when** the provider/model table is built, **then** the explicit configuration's values win for naming and options, credential/environment presence only affects whether the provider is marked usable, and the provider appears exactly once with a single merged model set.
4. **Given** no explicit model is configured for a request, **when** a model must be chosen, **then** a previously-used still-valid model is preferred if one exists, otherwise a deterministic family-priority ranking picks one from an available provider, and a distinct "no providers configured" or "no models available" failure is raised if none qualify.
5. **Given** a streaming request to any supported vendor, **when** that vendor emits text, reasoning, and tool-call content in its own wire format, **then** the caller receives one normalized event sequence (block-scoped start/delta/end for text and reasoning, start/delta/end plus a completed call for each tool invocation, and a single terminal finish-or-error event) independent of which vendor produced it.
6. **Given** a request fails with a transient condition (rate limit, server error, or a recognized transient network failure), **when** the failure is retried, **then** it is retried a bounded number of times with increasing backoff (honoring any vendor-supplied retry-after value), whereas a failure indicating an exceeded context window, invalid authentication, or exhausted quota is classified as non-retryable and surfaced immediately instead.
7. **Given** a model whose declared capabilities exclude a requested feature (tool-calling, adjustable sampling temperature, or a given input modality), **when** a request is prepared for that model, **then** the unsupported feature is omitted or substituted rather than sent as-is, so the request is not rejected purely for a capability mismatch.
8. **Given** two different vendors report token usage in their own native shapes, **when** a turn completes against each, **then** the returned usage is expressed in the same normalized fields (total input, total output, cache-read, cache-write, reasoning-subset) so a consumer can compute cost/context-pressure identically regardless of vendor.

## Confidence & open questions

**High confidence:**
- The implementation actually exercised for live session traffic today is the legacy-style `packages/opencode/src/provider/*` module (provider table construction, per-vendor quirk handling, request/response transform) together with the hosted-catalog fetch/cache logic in `packages/core/src/models-dev.ts`, executing requests through the default (non-experimental) execution engine. This was independently confirmed by tracing imports from the CLI entrypoint through session code, by each provider file's own recent commit history (active bug-fix churn), and by every relevant test suite being built against this module.
- `packages/llm` (the dedicated protocol/transport package) is a real, exercised dependency of the shipping CLI in two distinct ways: unconditionally, as the source of the shared normalized event/usage/error-classification vocabulary used even by the default execution path; and conditionally, as a full alternate execution engine used only when an experimental, off-by-default setting is enabled, and only for a narrow allow-list of vendor/auth combinations, with automatic per-request fallback to the default path otherwise.
- A third, separately-named "v2" catalog/provider-instantiation implementation exists in `packages/core` (hook/plugin-based provider and model registration, its own extensive per-vendor test suite). Its model-instantiation half (turning a model into a live client) has **zero** production call sites — it is exercised only by that implementation's own tests and by an unused "v2 plugin host." Its catalog/listing half, however, *is* live in the running server: it backs the HTTP provider/model listing endpoints and, more significantly, a fully independent, fully mounted "v2" session/agent-loop implementation (also in `packages/core`) that resolves models through this v2 catalog and issues LLM requests directly through the dedicated protocol/transport package's route stack — bypassing the third-party library entirely. That v2 session pipeline is reachable at its own API route, distinct from the route the shipping CLI/TUI client actually calls by default, so it is live, shipped code rather than a debug-only stub, but it is not on the default chat-send path.

**Open questions (unresolved contradictions to flag, not silently resolved):**
- **Which implementation is the intended long-term one, and why does a second, fully-live session pipeline already exist?** Three parallel implementations of essentially the same responsibility (provider discovery/config merge, and turning a model into a live client) coexist — including, in at least one case (a major cloud vendor's region-resolution logic), the *same specific compatibility logic* written independently in two of the three places. More strikingly, a complete second session/agent-loop implementation is already mounted in the running server and reachable over the network, resolving models via the "v2" catalog and issuing requests via the dedicated protocol/transport package with no Vercel-AI-SDK involvement at all — yet the client library the shipping CLI and terminal UI actually use is wired to the *other*, legacy session route, so this second pipeline currently receives no traffic from the shipped product. The source alone does not show whether this is a soon-to-be-flipped default, an API surface kept live for external/experimental clients only, or an abandoned branch of development.
- **Is the experimental native execution path meant to become the default?** It currently supports only a narrow subset of vendors/auth modes and has different retry-count, backoff-timing, and error-taxonomy granularity than the default path. Whether that divergence is accepted as permanent (i.e., the native path stays a narrow fast-path) or is a known gap blocking promotion to default could not be determined from the code.
- The `packages/llm` package's own internal design notes describe a further, not-yet-built successor package with different semantics (e.g., redefining what a single "generate" call means, and adding cost/pricing computation that does not exist today) — it is unclear from the code alone whether that successor is an active near-term plan or a speculative proposal, and thus unclear whether a reimplementation should target today's `packages/llm` semantics or anticipate the proposed successor's.
- **Cost computation**: no component inspected actually computes a monetary cost from token usage and catalog pricing — that arithmetic, if it exists, lives outside the files examined for this dossier (plausibly in the adjacent Session & Conversation Runtime feature) and was not verified.
- Coverage gap: the per-vendor sampling-default and reasoning-effort/thinking-budget tables (very large, one hardcoded per-vendor/per-model-family table) were sampled rather than exhaustively enumerated here; a reimplementation should treat the live hosted catalog's own per-model metadata as the primary source of truth for numeric defaults where the catalog supplies them, and treat this dossier's examples as illustrative rather than a complete table.
