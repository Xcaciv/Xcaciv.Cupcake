# Feature: Auth, Credentials & Accounts

## Purpose
Gives OpenCode two related but distinct trust relationships it must manage locally:
1. **Provider credentials** — the secrets (API keys, OAuth tokens, delegated tokens) needed to call each LLM provider's API (Anthropic, OpenAI/ChatGPT, GitHub Copilot, xAI, Snowflake Cortex, Azure, arbitrary custom/"other" providers), obtained through a pluggable per-provider authentication contract.
2. **OpenCode's own cloud account** ("control plane" at opencode.ai/console, or a self-hosted equivalent) — a device-code OAuth login that lets the CLI act as a signed-in user/org, sync remote provider configuration, and support multiple local accounts with one "active" account+org at a time.

Both exist so a user can run `opencode auth login` / `opencode login` once per provider or account and have the CLI silently attach the right credential to every subsequent request, refreshing tokens as needed without further prompts.

## Behavior
- **Provider credential store ("Auth")**: a single JSON file (`auth.json`) under the app's per-user data directory, one entry per key (normally a provider id), each entry one of three shapes: `oauth` (access/refresh/expiry, optional account id / enterprise URL), `api` (a bare key plus optional string metadata), or `wellknown` (a token plus the name of the environment/header key it should be injected as, for delegated/SSO-style auth). Reads return `{}` if the file is absent; entries that fail schema validation are silently dropped rather than failing the whole read.
- **Provider auth methods are plugin-supplied**, not hardcoded: each provider plugin (or a "wellknown"-published remote server) declares one or more login methods of type `oauth` or `api`, each with an optional ordered list of prompts (text or single-select, with conditional `when` rules and per-field validators) collected interactively before the method runs.
- An `oauth` method's `authorize(inputs)` call returns a URL to open, human instructions, and one of two completion modes:
  - **`auto`** — the CLI/browser flow completes on its own (device-code polling, or a local loopback HTTP callback server); the caller just awaits `callback()`.
  - **`code`** — the user must copy/paste an authorization code back into the CLI, which is then passed to `callback(code)`.
  Either way `callback()` resolves to a tagged success (an `oauth` secret bundle, or an `api` key) or a `failed` result.
- A central per-instance **ProviderAuth** service exposes `methods()` (list of pluggable auth methods per provider, for UI), `authorize(providerID, method, inputs)` (runs the plugin's `authorize`, stashes the in-flight `AuthOAuthResult` in memory), and `callback(providerID, code?)` (looks up the stashed result, invokes its `callback`, and on success persists the returned secret into the Auth store). This is also exposed over HTTP as `GET /provider/auth`, `POST /provider/:id/oauth/authorize`, `POST /provider/:id/oauth/callback`, and raw credential set/remove as `PUT /auth/:providerID` / `DELETE /auth/:providerID`.
- A `loader(getAuth)` hook (also plugin-supplied) is invoked at actual LLM-request time to build the outbound request's auth: it re-reads the stored credential, refreshes an expired OAuth access token on demand (writing the new token back through the same set-credential path), and injects headers/`fetch` overrides (e.g. GitHub Copilot's loader classifies each outgoing request as vision/agent-initiated and sets custom headers; OpenAI's Codex loader rewrites the request URL to ChatGPT's backend Codex endpoint and adds an account-id header decoded from the OAuth id/access token's JWT claims — with no signature verification, since this is a same-process trust boundary). Several providers (OpenAI Codex, Azure, GitHub Copilot) put a fixed dummy string (`OAUTH_DUMMY_KEY`) in the AI-SDK-facing `apiKey` field solely to satisfy libraries that require a non-empty key, since the real credential is only ever attached via the custom `fetch`.
- **Control-plane account**: `opencode auth login [url]` (aliased as `console login`) starts an RFC-8628-style device-code flow against a normalized server URL (default `https://opencode.ai/console`): request a device/user code pair, open the browser to the verification URL, then poll for a token at the server-given interval (adding 5s each time the server replies `slow_down`) until success, denial, or the device code's own `expires_in` elapses (mapped to a client-enforced timeout). On success it fetches the user's profile and org list, auto-selects the first org (multi-org selection is a known TODO), and persists the account + active org.
- Multiple accounts can be stored at once (SQLite-backed); exactly one account+org pair is "active" at a time (a separate singleton state row), switchable via `opencode switch`/`console switch`, listable via `console orgs`, removable via `console logout [email]`.

## Business rules & edge cases
- Provider-credential keys are normalized on write/remove by stripping trailing slashes; setting a key also deletes any stale entry that differs only by a trailing slash, so `https://x/` and `https://x` can never coexist.
- `auth.json` is written with file mode `0600` (owner read/write only) — confidentiality at rest is filesystem-permission-based only; no encryption at rest.
- Setting the environment variable `OPENCODE_AUTH_CONTENT` makes credential reads return its parsed JSON instead of the file (malformed JSON silently falls back to the file); this is meant for ephemeral/sandboxed runs. Note: writes (`set`/`remove`) still read the current snapshot as a base and always persist to the real on-disk file, not to the override — see Open Questions.
- Corrupt or schema-invalid individual entries in the credential store are dropped silently rather than surfacing a read error (an unparseable single provider's entry does not break access to the others).
- Auth-method prompts support conditional visibility (`when: {key, op: eq|neq, value}`) evaluated against already-collected answers in the same flow (e.g., GitHub Copilot only asks for an Enterprise URL if the deployment-type prompt was answered "enterprise"), plus per-field synchronous validators that can reject an answer before the flow proceeds.
- Device-code polling is implemented independently per provider (GitHub Copilot, xAI "SuperGrok", the OpenCode console, and the newer DB-backed OpenCode integration) rather than through one shared helper; each retries on `authorization_pending` at the server's interval plus a fixed safety margin, and extends the interval by 5 seconds on `slow_down` per RFC 8628 §3.5 — the safety-margin constant (3000ms) and code are duplicated verbatim in several plugins.
- Browser PKCE flows (OpenAI/Codex, Snowflake) generate a local S256 PKCE verifier/challenge, start a loopback HTTP server to catch the redirect, and reject the callback if the returned `state` doesn't match the one that was sent (CSRF guard) before ever exchanging the code for tokens.
- Some "oauth" methods never expire in practice: GitHub Copilot's device-flow result stores the same raw GitHub token as both `refresh` and `access` with `expires: 0`, since GitHub's own device tokens are long-lived and Copilot's loader always forwards it as-is.
- Some "oauth" methods store no real secret at all: Azure's "Microsoft Entra ID (Azure CLI)" method requires the user to already be signed in via the external `az` CLI, stores a placeholder credential (dummy access/refresh token, ~1 year expiry, the Azure resource name as `accountId`) purely as a "this method is configured" marker, and fetches a real bearer token from the Azure CLI's own credential cache at request time.
- The generic "wellknown" method lets any HTTP(S) URL publish `{url}/.well-known/opencode` describing a local shell `command` to run and the header/env `name` its stdout token should be bound to; `opencode auth login <url>` runs that command as a subprocess and stores its stdout (trimmed) as the token — an extensibility escape hatch for auth schemes OpenCode doesn't know about natively.
- Removing the currently-active control-plane account automatically promotes the first remaining account's first org (if any) to active; removing the last account leaves no active account/org.
- Control-plane token refresh treats a token as still fresh if its expiry is more than 5 minutes away; refresh calls for the same account are deduplicated through a keyed cache so concurrent requests don't race multiple refreshes. The newer DB-backed integration/credential layer applies the identical 5-minute eager-refresh rule generically to any registered OAuth method.
- Only one control-plane org is auto-selected on login even when the account belongs to several (explicitly marked as a TODO in the code — no interactive org choice at login time, only afterward via `console switch`).

## Workflows & states
- **Provider API-key login**: select/enter provider id → (optional provider-specific hint text, e.g. Bedrock/Cloudflare/Vercel) → prompt for a secret string → store as `api`.
- **Provider OAuth login ("auto")**: select method → collect prompts → `authorize()` returns a URL + instructions → CLI opens the browser and shows a spinner "Waiting for authorization..." → `callback()` (device polling or loopback-server wait) resolves to success/failure → on success, persist `oauth` or `api` result.
- **Provider OAuth login ("code")**: same as above but instead of polling, the CLI prompts the user to paste a code, then calls `callback(code)`.
- **Wellknown delegated login**: fetch `.well-known/opencode` descriptor → run the described command → capture stdout as the token → store as `wellknown`.
- **Control-plane login**: request device/user code → open browser + show user code → poll with backoff → on success fetch profile+orgs, persist account, set it active with its first org.
- **Control-plane logout/switch**: `logout [email]` removes one (or interactively chosen) account, auto-reassigning "active" if it was the one removed; `switch` lets the user pick any (account, org) pair from all stored accounts as the new active one; `orgs` lists every org across every stored account with an active-marker; `open` launches the browser at the active account's server URL.
- **Per-request credential resolution (both systems)**: read stored credential → if OAuth and within the refresh window of expiry, refresh (provider-specific token endpoint or delegated CLI) and persist the new token → attach to the outbound HTTP request (bearer header, custom header, or endpoint rewrite as the specific provider's loader dictates).

## Data
- **`auth.json`** (flat file, one process-wide file, keyed by provider id / URL): `{type:"oauth", refresh, access, expires: non-negative int (ms epoch), accountId?, enterpriseUrl?}` | `{type:"api", key, metadata?: Record<string,string>}` | `{type:"wellknown", key, token}`.
- **Control-plane account (SQLite)**: `account` table — id, email, url, access_token, refresh_token, token_expiry, timestamps; `account_state` table — singleton row holding `active_account_id` (FK, `ON DELETE SET NULL`) and `active_org_id`; a `control_account` table exists but is explicitly marked **LEGACY** in the schema (single active boolean, composite email+url primary key) and appears superseded by the two tables above.
- **Newer DB-backed Credential (core, SQLite)**: `credential` table — id (`cred_<ascending-id>`), integration_id, label, JSON `value` (`{type:"oauth", methodID, refresh, access, expires, metadata?}` or `{type:"key", key, metadata?}`), plus `connector_id`, `method_id`, `active` columns not consumed by the service layer inspected (see Open Questions). `create` deletes any existing credential for the same `integration_id` before inserting — only one live credential per integration is retained (unlike `auth.json`, which can hold arbitrarily many independent provider entries).
- **Plugin auth contract** (canonical shape all provider plugins implement): `{provider: id, loader?, methods: [{type:"oauth", label, prompts?, authorize(inputs) → {url, instructions, method:"auto"|"code", callback(...)→ success|failed}} | {type:"api", label, prompts?, authorize?(inputs) → {type:"success", key, metadata?} | {type:"failed"}}]}`.

## Interfaces
- **Provider & LLM Integration** (not documented here): consumes resolved credentials through each provider's `loader`/`fetch` override to actually place outbound calls; owns model catalogs and request construction that the auth `loader` hooks plug into.
- **Config & Data Contracts** (not documented here): the "wellknown" remote-config mechanism (`/.well-known/opencode`) and per-provider `opencode.json` provider definitions are read/merged by the config subsystem; auth only supplies the resulting token.
- **Control Plane & Cloud Sync** (not documented here): the OpenCode account's access token is used to fetch remote provider/model configuration (`GET /api/config`) and drives the newer `opencode` integration plugin's catalog updates; account org/email drive that sync but the sync mechanics themselves are out of scope here.
- **Server/HTTP API** (not documented here): exposes provider-auth and raw-credential endpoints (`GET /provider/auth`, `POST /provider/:id/oauth/{authorize,callback}`, `PUT|DELETE /auth/:providerID`) that this feature implements; the server's own request authorization/session middleware is separate.
- **Permission System** (not documented here): not directly coupled to credential storage.

## Error handling
- Credential-store writes fail with a generic `AuthError{message, cause}`; reads never fail (a missing file yields an empty credential set, and individually invalid entries are dropped, not raised).
- `ProviderAuth` surfaces distinct tagged errors: `OauthMissing` (callback invoked with no prior `authorize` in this instance's memory), `OauthCodeMissing` (a "code"-mode method called back without a code), `OauthCallbackFailed` (the plugin's callback did not return success), and `ValidationFailed{field, message}` (a prompt's validator rejected input) — all mapped to HTTP error responses on the server API.
- Control-plane account errors are split into three distinct types with different user-facing framing: `AccountTransportError` (network never reached the server — message explicitly suggests checking network/proxy/VPN), `AccountServiceError` (server reached but request/decoding failed), and `AccountRepoError` (local database operation failed).
- OAuth loopback-callback servers render branded static HTML pages for success/error/pending states (shared templates), including a CSRF-style rejection page when the OAuth `state` doesn't match what was issued.
- Device-code polling loops treat `authorization_pending` and `slow_down` as retryable, `expired_token` and `access_denied` as terminal (mapped to distinct poll-result states), and any other error string as an opaque terminal failure.

## Non-functional observations
- Secrets at rest are plaintext JSON/SQLite rows protected only by OS file permissions (`0600` for the JSON file); there is no additional encryption layer.
- Device-code and PKCE flow implementations are duplicated per provider plugin rather than centralized, which is a maintenance/consistency risk for a reimplementation to consider consolidating (a single RFC 8628 helper and a single PKCE-authorization-code helper would cover nearly every provider observed).
- The in-memory "pending OAuth result" held by `ProviderAuth` between `authorize` and `callback` does not survive a process restart and is not namespaced beyond a single provider id — a second concurrent `authorize` call for the same provider silently replaces the first's pending state.
- Token refresh de-duplication (a single in-flight refresh shared by concurrent callers) is applied for both the control-plane account and the OpenAI/Codex plugin, but is not a universal guarantee across every provider plugin inspected.

## Acceptance criteria — 5-8 Given/When/Then statements
1. **Given** a provider credential is set for key `https://example.com/` (trailing slash), **when** the store is read back, **then** the entry appears under the normalized key `https://example.com` and no entry exists under the slashed key.
2. **Given** a provider OAuth method of type `auto`, **when** `authorize()` succeeds and returns a `callback`, but `callback()` (device poll) is invoked for a provider with no prior `authorize()` call recorded in the current process, **then** the operation fails with a "missing" error rather than proceeding.
3. **Given** a device-code login to the control-plane account, **when** the server keeps responding `authorization_pending` until the device code's `expires_in` elapses, **then** the CLI reports the login as expired rather than polling forever.
4. **Given** a device-code login where the server responds `slow_down`, **when** the client retries, **then** it waits at least 5 seconds longer than its previous interval before the next poll.
5. **Given** a browser-based PKCE OAuth callback whose `state` parameter does not match the value generated at `authorize()` time, **when** the callback server receives it, **then** the flow is rejected as a potential CSRF attempt and no token exchange is attempted.
6. **Given** a control-plane account's access token expires in under 5 minutes, **when** any operation needing that token runs, **then** the token is refreshed first and the refreshed token (and new expiry) is persisted before use.
7. **Given** the currently active control-plane account is removed while other accounts remain, **when** the removal completes, **then** the first org of one of the remaining accounts becomes the new active account/org automatically.
8. **Given** an `auth.json` file containing one entry that fails schema validation alongside other valid entries, **when** the credential store is read, **then** the valid entries are still returned and the invalid one is silently omitted (not a hard read failure).

## Confidence & open questions
- **Two parallel, seemingly unreconciled provider-credential stores exist**: the flat-file `auth.json` (`packages/opencode/src/auth`) that all current CLI commands (`opencode auth login/logout/list`) and provider plugins (`packages/opencode/src/plugin/**`) actually write to, versus a newer SQLite-backed `Credential`/`Integration` system in `packages/core` (methodID-keyed, "one live credential per integration", generic 5-minute refresh). Per the task's instruction to treat `core/` as authoritative on disagreement — but these two do not look like the same schema evolving; they look like two independent generations, and it is not visible in the code inspected whether/how data migrates from one to the other or which one wins when both hold a credential for the same provider. This should be confirmed with the maintainers before a from-scratch reimplementation commits to one shape.
- The `credential` SQL table carries `connector_id`, `method_id`, and `active` columns that are never read or written by the `Credential.Service` layer shown — likely forward-looking/in-progress schema; their intended semantics are unclear from the code alone.
- Behavior of `set`/`remove` when `OPENCODE_AUTH_CONTENT` is active was not covered by any test found: reads are redirected to the env var's JSON, but writes still target the real on-disk file — meaning a write could silently diverge from what subsequent reads (still preferring the env var) observe. Confirm whether this is intentional (e.g., env override is meant to be read-only/ephemeral) or a latent bug.
- GitHub Copilot's OAuth credential deliberately stores the same token as both `refresh` and `access` with `expires: 0`; this reads as an intentional "this token effectively never expires" encoding rather than a bug, but no comment in the source confirms the reasoning.
- Multi-org account selection at login time is an explicitly flagged TODO in the source (`// TODO: When there are multiple orgs, let the user choose`) — current behavior (auto-pick the first org) should be treated as provisional, not a settled design decision.
