# Feature: Permission System

## Purpose

Every tool call an agent makes (running a shell command, reading/writing a file, fetching a URL, searching the web, invoking a subagent, loading a skill, querying an LSP, etc.) is checked against a rule set before it runs. The rule set decides, per action and per concrete argument ("resource" — a file path, a glob, a shell command, a subagent name, a URL...), whether the call is silently **allow**ed, silently **deny**ied (blocked, tool returns an error to the model), or must **ask** a human for approval before proceeding. The system also lets a human's one-time answer be remembered ("always") so the same or similar future calls skip the prompt, and lets an agent definition (e.g. a read-only "plan" agent) carry its own baked-in policy that a session cannot escalate past. A secondary guard ("doom loop") forces a human check-in when the model repeats the exact same tool call three times in a row, to break stuck loops.

## Behavior

- Every tool execution first resolves an **effective rule set** = the calling agent's baked-in permission rules, merged with any session-specific rules (used to further restrict a spawned subagent's session), merged with rules from the user's config file, in that precedence order (later entries can add rules but cannot remove earlier hard denies — see Business rules).
- Rules are `(action, resource-pattern) -> effect` triples. `action` is a coarse category matching a permission key (`bash`, `edit`, `read`, `glob`, `grep`, `list`, `task`, `webfetch`, `websearch`, `question`, `skill`, `lsp`, `todowrite`, `external_directory`, `doom_loop`, plus mode-switch pseudo-actions `plan_enter`/`plan_exit`). `resource` is a free-text string specific to that action (a shell command string, a file path, a glob, a URL, a subagent name, a search query, a repeated-tool-name marker).
- To evaluate one call, every candidate resource string it touches (e.g. every parsed sub-command in a compound shell command, every directory a file operation reaches) is matched independently against the rule set with **last-matching-rule-wins** wildcard matching; the call's overall effect is the worst of the per-resource effects (`deny` beats `ask` beats `allow`). If nothing matches, the implicit default is `ask`.
- If the effect is `allow`, the tool runs immediately, no event is emitted.
- If the effect is `deny`, the tool call fails immediately with an error whose text (fed back to the model as the tool's error output) names the offending rule(s), and no prompt is ever shown.
- If the effect is `ask`, a pending permission request is created, a `permission.asked` event is broadcast, and the tool call blocks until a client answers it (or the session/process ends, which auto-declines all pending requests).
- A human (or an automated client) answers with one of:
  - **once** — approve just this call.
  - **always** — approve this call and remember a set of broader patterns (supplied by the tool that asked, e.g. a shell-command-prefix wildcard) so future matching calls in the same run/session are auto-allowed without asking again; any other currently-pending requests in the same session that now resolve to `allow` under the updated rules are also auto-approved and their askers unblocked.
  - **reject** — decline this call (optionally with a free-text message that is fed back to the model as corrective feedback instead of a bare rejection), and every other still-pending request in the same session is rejected too (rejecting one thing stops the whole turn).
- A shell command is parsed (via a bash/PowerShell grammar) into its individual piped/chained sub-commands before evaluation, so `permission` rules can allow `git *` while asking for everything else in the same command line. If any parsed sub-command touches a file path outside the current project directory, a separate `external_directory` check runs first for the containing directory (as `<dir>/*`), independent of the `bash` check on the command text itself.
- "Always allow" patterns for bash calls are generalized to a **command-prefix arity** (e.g. `git commit -m "x"` → remember `git commit *`, `npm run build` → remember `npm run *`) using a large built-in table of common CLI tools' subcommand depth, so one approval covers a whole family of invocations of that subcommand rather than only the exact command line.
- Built-in tools (bash, edit, read, ...) stay visible to the model even when denied — denial happens only at call time, returning an error the model must react to. Only MCP (external plugin) tools whose whole category is wildcard-denied are proactively hidden from the model's tool list, as is a subagent type whose `task` permission is denied (it is omitted from the "available agent types" the model is shown).

## Business rules & edge cases

- **Default policy** if the user configures nothing: every action defaults to `allow`, except: `doom_loop` and `external_directory` default to `ask`; `question` (subagent asking the user a question) defaults to `deny`, `plan_enter`/`plan_exit` (switching to/from the read-only planning agent) default to `deny`; reading a dotenv-like file (`*.env`, `*.env.*`, but not `*.env.example`) defaults to `ask` while other reads default to `allow`.
- **Plan (read-only) agent**: denies `edit` for everything except a plan document under `.opencode/plans/*.md` (and the app's own plans-data directory), denies spawning the `general` subagent (but allows other subagents such `explore`, or user-defined ones), allows exiting plan mode (`plan_exit`), and otherwise inherits the same defaults as the default "build" agent — **`bash` is not restricted by the plan agent and defaults to `allow`, the same as build.** (See Confidence & open questions — this contradicts the product's own README wording.)
- **Build (default) agent**: same defaults, plus `question` and `plan_enter` explicitly allowed.
- **Explore / research subagent**: denies everything (`*: deny`) except `read`, `glob`, `list`, `grep`, `bash`, `webfetch`, `websearch`, and read-only access to whitelisted external directories — cannot edit files at all.
- **General-purpose subagent**: same as build defaults but denies `todowrite` (can't manage the parent's todo list).
- **Internal system agents** (title generator, summarizer, context-compaction) deny every action outright — they run no tools.
- **Subagent spawn restriction (task tool)**: when an agent spawns a subagent via the task tool, the child session's permission set is built from the parent's own *deny* rules and the parent's `external_directory` rules (a parent cannot grant a child more directory access than it has, and a parent's explicit denials propagate down as a hard ceiling the child cannot lift even via its own config), plus a default deny of `todowrite` and `task` (spawning further subagents) unless the subagent's own definition explicitly allows them. The subagent's own permission rules for everything else fully apply and can be more permissive than the parent in areas the parent didn't explicitly deny (e.g., a subagent can still edit files even if its parent agent, like `plan`, cannot — the parent's *restriction on itself* is not automatically the subagent's restriction).
- **Doom loop guard**: if the same tool name is called with byte-identical input 3 times in a row within one assistant turn, an extra `doom_loop` permission check (default `ask`) is inserted before the (4th, repeated) call proceeds, regardless of that tool's own permission.
- **External directory allowlist**: a small built-in set of paths (system temp dir, skill directories, reference directories, and the app's own transcript/output glob) is always pre-allowed for external-directory access so routine internal file activity doesn't prompt; anything else outside the project root asks by default.
- **`~` / `$HOME` expansion**: only in `external_directory`-style path patterns written in config, expanded once at config-load time to an absolute path; it does not by itself grant access outside the project — an explicit `external_directory` allow rule is still required.
- **Wildcard syntax**: `*` = any run of characters (including empty), `?` = exactly one character; patterns are compiled to anchored regular expressions; a trailing "prefix `*`" pattern additionally matches the bare prefix with no trailing argument.
- **Legacy `tools: {name: boolean}` config** is converted to `permission` rules for backward compatibility (`write`/`edit`/`patch` all map to the single `edit` permission); the modern `permission` config, if also present, wins over the legacy conversion on a per-key basis.
- **`--auto` / auto-approve mode** (CLI flag or client-side toggle) does not change server-side rule evaluation — explicit `deny` rules still block silently. Instead, when a client is in auto mode, it simply answers every `permission.asked` event with `once` automatically instead of prompting the human; a non-interactive CLI run that is *not* in auto mode instead auto-**rejects** every ask (so headless/non-interactive runs never hang on a prompt).
- **Client-side auto-approve remembering** in the app/desktop client is scoped per session (and inherited down a subagent's session-parent chain) or per project directory, entirely independent of the server-side "always" saved-rule mechanism.

## Workflows & states

1. Tool call begins → its permission context computes the effective rule set (agent + session + config).
2. Rule evaluation → `allow` (proceed), `deny` (fail now with rule-explaining error), or `ask` (go to 3).
3. A pending request is recorded (in-memory, keyed by a generated request ID) and a `permission.asked` event fires; the tool call's fiber blocks.
4. A client (TUI, desktop app, ACP-connected editor, or the CLI's own non-interactive loop) receives the event, presents it (or auto-decides), and calls the reply endpoint with `once` / `always` / `reject` (+ optional message).
5. On `once`: the one request is unblocked, the tool proceeds; no state persists.
6. On `always`: the one request is unblocked, generalized patterns are added to a remembered allow-list (in the currently-implemented runtime, kept in memory for the life of the running process/instance, scoped to the project directory; the newer core rewrite persists it to a per-project database table instead — see Confidence), and every other still-pending request in the same session is re-evaluated against the updated rules and auto-resolved if it now allows.
7. On `reject`: the one request fails with a rejection (optionally carrying human feedback text); every other pending request in that session is force-rejected too.
8. If the whole process/session ends while requests are still pending (e.g., the user aborts), all pending requests are declined automatically so no fiber leaks blocked forever.
9. Answering an unknown/already-resolved request ID is an error (`NotFound`) rather than a silent no-op.

## Data

- **Rule** (in-memory / config-derived): `{ action|permission: string, resource|pattern: string, effect|action: "allow"|"ask"|"deny" }`. A rule set is an ordered array; evaluation is last-match-wins per `(action, resource)` pair via wildcard matching, defaulting to `ask` if no rule in the whole merged set matches.
- **Permission request**: id, owning session id, the action name, the list of resource strings needing a decision, the "save" pattern(s) that an `always` reply should remember, arbitrary tool-supplied metadata for display (command text, file diff, URL, directories...), and an optional back-reference to the originating tool call (message id + call id).
- **Reply**: request id, chosen outcome (`once`/`always`/`reject`), optional free-text message (only meaningful with `reject`, delivered to the model as corrective feedback).
- **Config schema** (`permission` key in project/user config): either a single action string applying to everything, or an object keyed by permission name where each value is either a single action or a nested object mapping resource-glob → action; unknown keys are permitted (open-ended) for forward compatibility with new tools.
- **Persisted "always" approvals** (core/DB-backed variant only): a durable row per project keyed by `(project, action, resource)`, uniquely constrained so re-adding the same approval is a no-op; deletable individually. Not currently how the shipped CLI runtime remembers "always" (see Confidence).
- **Agent definition** carries its own fixed `permission` rule set, computed once at startup by layering: engine defaults → agent-specific overrides → user's global config → (for user-defined custom agents) per-agent config overrides.

## Interfaces

- **Tool System** (adjacent, not documented here): every tool's execution context exposes an `ask(action, resources, save-patterns, metadata)` call that this feature answers with allow/ask(blocking)/deny; tools also decide what "always" patterns to suggest (e.g. bash's command-prefix generalization) and what human-readable summary/diff to attach as metadata for the prompt UI.
- **Agent/Subagent System** (adjacent): supplies each agent's static permission rule set and the "which subagent types are visible/allowed" filtering; this feature enforces it and derives a restricted session-level rule set when a subagent is spawned.
- **Session runtime** (adjacent): owns the per-session rule-set override field and the doom-loop repeated-call detector that triggers an extra ask.
- **HTTP/event API** (adjacent Server/HTTP surface): a "list pending permission requests" read endpoint and a "reply to a request" write endpoint, keyed by request id; a live event stream carries `permission.asked` (a new request appeared) and `permission.replied` (a request was resolved, and how) so any number of connected clients stay in sync.
- **TUI / desktop app / ACP (external-editor) client** (adjacent, not documented here): each independently subscribes to the ask/reply events and either prompts a human (rendering command text, file diffs, directory names, etc. from the request's metadata) or auto-decides per its own auto-approve setting; the ACP bridge additionally maps the three-choice reply model onto that protocol's own permission-option vocabulary and, for edit approvals, pushes the proposed file diff into the connected editor.
- **Config & Data Contracts** (adjacent): the `permission` block of the user/project config file and the legacy boolean `tools` block (which this feature translates into equivalent rules) are owned by that feature; this feature only consumes the parsed result.

## Error handling

- A `deny` outcome raises a typed error carrying the specific rule(s) that matched, rendered to the model as text explaining a human-configured rule is blocking this exact call (so the model can try a different approach rather than blindly retry).
- A `reject` reply (no message) raises a typed "user rejected this specific call" error with fixed model-facing wording.
- A `reject` reply with a message raises a distinct typed "corrected" error whose model-facing text embeds the human's feedback verbatim, so the model can adjust its next attempt instead of just seeing a bare refusal.
- Answering a request ID that is not currently pending (already answered, or the tool call was aborted/cancelled first) is a distinct "not found" error, not silently ignored.
- If the process/scope hosting pending requests shuts down (session end, abort), every still-blocked tool call is force-failed with the rejection error rather than hanging forever.
- A non-interactive CLI run with no one able to answer prompts auto-rejects every ask (with a warning printed) rather than deadlocking; only `--auto` mode auto-approves instead.
- If a client that only reads permission events (no bridge to a human, e.g. an ACP host with no permission UI wired up) receives an ask, it auto-rejects rather than leaving it pending indefinitely.

## Non-functional observations

- Rule evaluation is pure/synchronous per call (regex-based wildcard match over an in-memory array); the only asynchronous part is the wait for a human/client reply when the outcome is `ask`.
- Pending requests are held in memory keyed by generated ID; nothing about a pending (unanswered) request is durable, so restarting the server drops in-flight prompts (tool calls that were waiting fail as declined).
- The "always" remembered-approval store in the currently-shipped runtime is scoped to the lifetime of the running process/instance and to the project directory, not the individual chat session, and is lost on restart, despite the product's own docs describing it as scoped "for the rest of the current session" — a newer parallel implementation instead persists it durably per project in a database table (see Confidence).
- Every permission decision that reaches `ask` is observable externally via a broadcast event, enabling multiple simultaneous clients (TUI, app, ACP editor) to all see and race to answer the same prompt; the reply endpoint is idempotent against a second reply to the same ID only in the sense that the second reply returns "not found" once the first has resolved it.

## Acceptance criteria — 5-8 Given/When/Then statements

1. **Given** an agent's rule set has no rule matching a requested action/resource pair, **when** the tool call is evaluated, **then** the outcome is "ask" (safe default), not "allow" or "deny".
2. **Given** a rule set containing both a broad `deny` and a more specific `allow` for the same action, where the `allow` appears later in the merged/config order, **when** a resource matches both, **then** the later, more specific rule wins (last-match-wins), so the call is allowed.
3. **Given** a bash command that pipes together two sub-commands, one matching an `allow` rule and one matching no rule (default ask), **when** the command is evaluated, **then** the overall call requires approval (the worst per-sub-command outcome governs the whole call), and denial of any single sub-command blocks the whole command without ever prompting.
4. **Given** the plan (read-only) agent, **when** it attempts to edit any file other than an allowed plan document, **then** the edit is denied outright with no prompt; **when** it runs a shell command, **then** the command follows the same default (allow-unless-configured) as the default agent — plan mode does not itself force bash to ask.
5. **Given** a pending "ask" request, **when** the human replies "always" with a set of generalized patterns, **then** that specific request is approved, the patterns are remembered for future matching calls without prompting again, and any other currently-pending request in the same session that now evaluates to "allow" under the updated rules is also auto-approved.
6. **Given** a pending "ask" request, **when** the human replies "reject" (with or without a message), **then** that request fails (carrying the message as feedback if provided) and every other request still pending in the same session is also rejected.
7. **Given** an agent spawns a subagent whose own permission rules would allow editing files, but the parent agent's rules explicitly deny bash, **when** the subagent runs, **then** it can still edit files (subagent's own rules govern its own capabilities) but inherits the parent's bash denial as a hard ceiling it cannot override.
8. **Given** the same tool is called three times in a row with byte-identical arguments, **when** a fourth identical call is attempted, **then** an additional "doom loop" approval is required before it proceeds, independent of that tool's own permission rule.

## Confidence & open questions

- **Two coexisting implementations found, with unclear which is authoritative for the shipped product.** `packages/opencode/src/permission` (in-memory, "V1" schema under `packages/schema/src/permission-v1.ts` / `packages/core/src/v1/permission.ts`) is what the current CLI/TUI/session runtime actually calls (`ctx.ask`, agent definitions, shell tool, task tool all import this). A separate, more fully-featured implementation (`packages/core/src/permission.ts`, "PermissionV2", `packages/schema/src/permission.ts`, `packages/core/src/permission/saved.ts` with a SQLite-backed, project-scoped "always" allow-list, and per-agent-in-database permission rules) exists and is wired up in a different, newer server package (`packages/server`) that several packages depend on. Per the task's instruction to treat `core/` as authoritative, this dossier describes V2's richer semantics (durable saved rules, resource-array evaluation, agent lookup by ID from a session-attached agent registry) as the target behavior, but flags that **the actual running CLI today uses the simpler V1 in-memory version** (rules merged at agent-definition time, "always" approvals held only in per-process memory, no database persistence). A reimplementation team must confirm with the project owners which of these is the one to port, or whether V2 is a not-yet-released successor.
- **README/doc contradiction on the plan agent and bash.** The project's own top-level README states the plan agent "asks permission before running bash commands." Code (`packages/opencode/src/agent/agent.ts`, confirmed by a unit test asserting `evalPerm(plan, "bash") === "allow"`... actually the test found only confirms `build`'s bash is "allow"; the plan agent's own permission set contains no bash override at all, so it inherits the same `"*": "allow"` default as build) and the dedicated permissions doc page do not show any bash-specific rule for the plan agent — bash defaults to `allow` for every native agent unless the user configures otherwise. It's unresolved whether this is stale README wording, or whether some other layer (not found in this investigation) suppresses bash for plan mode at runtime; recommend the reimplementation team treat "bash defaults to allow, edit defaults to deny for plan agent" as the verified behavior and flag the README line to the product owner.
- **Scope/durability of "always" approvals is ambiguous even within the V1 docs.** The public permissions doc says an "always" approval lasts "for the rest of the current OpenCode session," but the V1 code scopes the remembered rule list to the whole running instance/project directory (all sessions in that instance), not to one chat session specifically. Confirm intended scope before reimplementing.
- **Where a hypothetical runtime bash-blocklist for destructive commands (e.g. `rm -rf`) would live** was not found as a built-in default; the arity table only helps generalize "always" patterns, it does not itself deny anything. If the target product wants safe-by-default denial of destructive shell commands, that would need to be added via user config (`bash: {"rm -rf *": "deny"}`), not something the engine does out of the box.
- Not exhaustively traced: the exact precedence/merge behavior when a user's config supplies a permission rule for a *custom* (non-native) agent versus the global `permission` block versus a per-agent `permission` override in config — code shows `Permission.merge(defaults, user)` then, separately, `Permission.merge(item.permission, Permission.fromConfig(value.permission))` for agents also declared under `cfg.agent`; a full precedence table across all four layers (engine defaults, global user config, per-agent config block, session-derived subagent restriction) would benefit from a dedicated code walk-through with the project maintainers before porting.
