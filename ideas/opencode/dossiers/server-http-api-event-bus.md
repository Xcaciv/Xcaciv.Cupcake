# Feature: Server, HTTP API & Event Bus

## Purpose

The local HTTP server is the single network-facing surface of the CLI: an embeddable HTTP+WebSocket server, started either in-process (the terminal UI boots one for itself) or standalone (`opencode serve`), that exposes the entire local agent state — projects, sessions/messages, tool permissions, clarifying questions, provider/model catalogue, configuration, filesystem/search, MCP servers, pseudo-terminals (PTYs), and cross-machine workspace sync — as a versioned, typed HTTP+SSE contract. It is the only way any external client (the bundled terminal UI, an editor/IDE integration, a companion app, or a generated SDK) talks to a running agent process, and it is what makes "one server, many simultaneous callers, live-updating state" possible: any number of HTTP clients and SSE subscribers can attach to the same running project and see the same conversation update in real time.

## Behavior

**Two coexisting API generations, one shipping surface.** At the pinned commit the codebase contains two structurally different HTTP API implementations that both build on the same typed-routing/schema library. Generation "v1" (root-level paths such as `/session`, `/config`, `/pty`, `/event`) is the one actually reached by the shipping CLI: tracing `opencode`'s `serve` subcommand and its in-process TUI server both lead to the same route-assembly function, and the adjacent Session/Provider dossiers independently confirm no shipped client ever calls anything else. Generation "v2" is a separate, more strictly-typed protocol/route package; its routes live under an `/api/...` prefix and it is compiled into the *same* server process and port as v1 (the two route tables are simply merged), but no shipped client (TUI, CLI, SDK) calls it by default — it is live and reachable, just unused by the product today. A wholly separate second CLI binary exists purely to run the v2 surface standalone as its own background daemon with its own auth/registration model (see Confidence & open questions). This dossier documents v1 as the primary, shipping contract and calls out v2 wherever it differs.

**Route organization.** Endpoints are grouped by domain (session, message-within-session, config, provider, permission, question, mcp, project, project-copy, pty, pty-connect, file, sync, tui, workspace, experimental, instance, control, control-plane, global, event) and mounted as one merged route table under a single listener. Three route families sit outside the common per-project pipeline: **global** routes (`/global/health`, `/global/event`, `/global/config`, `/global/dispose`, `/global/upgrade`) act server-wide, not per-project; **control** routes (`/auth/:providerID`, `/log`) are top-level auth/logging utilities; everything else is "instance-scoped" — resolved against one specific project directory (and optionally one named "workspace" within it) per request. A catch-all route serves the embedded web UI's static assets, and `GET /doc` serves a generated OpenAPI document describing the whole merged surface (v1 root paths plus the mounted `/api/*` v2 group), post-processed to stay byte-compatible with an existing hand-maintained SDK's expectations (stable component names, explicit SSE response docs, synthesized legacy error schemas).

**Multi-project / multi-workspace routing.** One server process serves many project directories concurrently. Every instance-scoped request resolves its target directory from, in priority order: a `directory` query parameter, an `x-opencode-directory` header, or the server process's own working directory. That directory is used to load-or-reuse an in-memory "instance" (config, tool registry, project state) via an instance store; the instance is torn down and optionally reloaded automatically after certain requests (e.g. config updates, explicit dispose), with the actual teardown deferred until *after* the HTTP response has already been sent so the client isn't blocked on it. An optional `workspace` query parameter (or a workspace already recorded on the addressed session) additionally selects a named "workspace" — a sandboxed or remote copy of the project. An `OPENCODE_WORKSPACE_ID` environment variable, when set, pins the workspace for the whole process and overrides anything a client requests. When the selected workspace's backing target is local, this only changes which directory is used; when it is remote (a different machine/process), the entire request — including a WebSocket upgrade — is transparently reverse-proxied end-to-end to that remote workspace's own server (stripping hop-by-hop and routing headers, forwarding cookies/auth as configured for that target), gated on the workspace's sync connection being active (otherwise a 503). A small hard-coded set of routes (workspace CRUD, the top-level session list) always stays local even when a workspace is selected, rather than being proxied. A companion mechanism ("fencing") lets a proxied response carry a per-aggregate sequence-number header so the caller can be blocked until the local read model has caught up to a client-visible point before the response is returned.

**Authentication.** The whole API is gated by a single optional server-wide password (`OPENCODE_SERVER_PASSWORD`; username `OPENCODE_SERVER_USERNAME`, default `opencode`). If the password is unset or empty, the server requires no credentials at all — this is the default, and the standalone `serve` command prints an explicit warning when it applies. When a password is set, standard HTTP Basic credentials are required on essentially every route, checked either via the `Authorization: Basic <base64>` header or, with equal validity and higher priority, a `?auth_token=<base64 username:password>` query parameter (needed because some browser-initiated request types, like an `EventSource` subscription or a WebSocket upgrade, cannot set custom headers). Failure returns 401 with a `WWW-Authenticate: Basic` challenge header. A small allowlist of static web-UI asset paths bypasses auth entirely so a password-protected server can still render its own login-adjacent UI shell. PTY WebSocket connections use a distinct short-lived, single-use, scope-bound ticket instead of (or in addition to) Basic auth, because a browser cannot attach an Authorization header to a WebSocket handshake (see PTY workflow below).

**CORS.** Cross-origin requests are allowed unconditionally from `localhost`/`127.0.0.1` (any port), the desktop app's custom URI schemes, any `*.opencode.ai` HTTPS origin, and any origin whose host matches the request's own `Host` header; anything else requires the origin to be explicitly present in an operator-supplied allowlist passed at server start. CORS headers (including on 401 responses) are added before/independent of authentication, and a dedicated correctness fix ensures cached preflight responses always vary on `Origin` so one origin's cached preflight is never served to a different one.

**Realtime event delivery.** All server-side state changes are published through one typed, versioned event system; a bridge attaches routing metadata (which directory/workspace/project produced the event) to every publish and fans it out to a process-wide, untyped in-memory bus that every SSE endpoint reads from. Three SSE endpoints exist:
- `GET /event` (v1, per-instance): scoped to one directory/workspace by server-side filtering. On connect it immediately emits a synthetic `server.connected` event, then live events for that instance only, plus a synthetic `server.heartbeat` event every 10 seconds; the stream self-terminates the moment that instance is disposed. Uses an unbounded per-connection queue (no drop policy).
- `GET /global/event` (v1, server-wide): identical envelope/heartbeat pattern but completely unfiltered — every event for every open project directory on the process, including install/upgrade events.
- `GET /api/event` (v2): reuses the same event catalogue but is **not** server-side filtered by directory at all — every event from every instance is delivered to every subscriber, each carrying its own `location` field so the client can filter; uses a bounded, dropping 256-entry queue (a slow consumer loses events rather than growing memory), a 15-second heartbeat sent as a raw SSE comment rather than a typed event, and no instance-disposal auto-close.
None of the three endpoints support replay/backfill by cursor or `Last-Event-ID` — a reconnecting client only sees events published after it reconnects; catching up on missed activity is the job of the separate, sequence-numbered sync/replay endpoints (an adjacent feature's transport, carried over this same server). A related but separate long-poll channel (`GET /tui/control/next` / `POST /tui/control/response`) exists purely for point-to-point request/response with the bundled terminal UI process, distinct from the broadcast event bus.

**PTY (terminal) sessions.** A client creates a PTY (`POST /pty`), lists/updates/removes it via ordinary JSON CRUD, then attaches to its live I/O over a WebSocket. Because a browser cannot set an Authorization header on a WebSocket handshake, attaching is a two-step dance: an already-authenticated client first mints a short-lived (60-second), single-use, scope-bound ticket (`POST /pty/:id/connect-token`, itself gated by a same-origin check and a custom header a cross-site request can't forge), then opens the WebSocket carrying that ticket as a query parameter; the upgrade handler validates PTY existence before decoding the ticket at all (to avoid leaking existence information through timing/response-shape differences), consumes the ticket atomically (single use, scope must match exactly), and only then completes the upgrade. A resumable output cursor lets a reconnecting client replay missed terminal output before switching to live streaming.

**Server lifecycle.** On start, the listener binds an explicit port if given, or tries port 4096 first and falls back to any free OS-assigned port. It can optionally advertise itself over mDNS/Bonjour for LAN discovery (skipped automatically if bound only to a loopback address). On shutdown, every open WebSocket (PTY or workspace-proxy) is sent a clean 1001 "server closing" close frame (bounded by a short per-socket grace period) via a small in-process connection tracker before the listener itself stops.

## Business rules & edge cases

- With no password configured, the server is fully open — this is a deliberate default (documented via a startup console warning), not an oversight; any local process on the machine can call the full API unauthenticated.
- Auth-token priority: if both a `?auth_token=` query value and an `Authorization: Basic` header are present, the query token wins.
- Static web-UI asset paths and the `/doc` OpenAPI document bypass typed-endpoint auth via a separate router-level check, but `/doc` itself still requires auth if a password is set (only a fixed handful of manifest/icon assets are truly public).
- The v1 surface returns an empty-bodied 401; the v2 (`/api/*`) surface returns a bodyful JSON `{ message: "Authentication required" }` alongside the same 401 status and challenge header — a real wire-contract inconsistency between the two generations on the same port.
- An invalid `workspace` query value is a 400 (structured validation error); a well-formed but unknown/unregistered workspace id is a 500 with a plain-text body — an inconsistency worth flagging (unknown-resource lookups are 404 everywhere else in this API).
- A small hard-coded allowlist of routes (workspace CRUD, the top-level session list) is never proxied to a remote workspace even when a `workspace` query targets one — they always answer from the local process.
- A remote workspace that isn't actively syncing responds 503 rather than attempting to proxy a request that would hang or fail confusingly.
- Compression (gzip/deflate, applied to responses ≥1KB of a compressible content-type) explicitly excludes both SSE endpoints and the session message/async-prompt POST endpoints, since those are streaming responses that must not be buffered.
- Validation-error response bodies truncate the underlying rejection reason to 1024 characters to avoid mirroring large or secret-bearing payloads back to the client or into logs.
- The v1 and v2 surfaces use different validation-error wire shapes on the same server (`{name:"BadRequest", data:{message,kind}}` vs. a tagged `{message, kind}` object) — a client must know which generation it's talking to.
- An uncaught server defect never leaks internal detail: it becomes a generic 500 with a random short correlation id that is also written to the server log, so an operator can locate the corresponding log line without exposing internals to the caller.
- `/event`'s per-connection queue is unbounded (a slow client can accumulate unbounded server-side memory); `/api/event`'s is bounded and drops on overflow — the two generations made different backpressure trade-offs for the same conceptual endpoint.
- The legacy `/pty` JSON listing only shows still-running sessions (an exited PTY vanishes immediately, matching old client expectations), while the same underlying PTY retains exited-session metadata for the newer surface until explicitly removed — a deliberate, documented behavior difference kept for compatibility.
- Two independently-versioned event catalogues exist: a small "public/server" set (used by the v2 SSE stream and its OpenAPI contract) is a strict subset of a larger internal manifest (used by the v1 stream) that also carries legacy/TUI/MCP/LSP/installer event types; at least one declared event type is deliberately excluded from both "latest" surfaces.

## Workflows & states

1. **Startup**: bind listener (explicit port, or 4096-then-any-free-port) → optionally publish mDNS → begin accepting connections; the in-process (TUI-embedded) and standalone (`opencode serve`) paths share this same startup logic.
2. **Per-request instance resolution**: parse `directory`/`workspace` inputs → load-or-reuse the matching project instance (or determine the target workspace is remote and switch to proxy mode) → run the matched handler inside that instance's scope → (if the handler marked the instance for disposal/reload) tear down or reload it after the response has been sent.
3. **SSE subscribe** (any of the three event endpoints): client connects → server sends a synthetic "connected" event → live matching events stream with periodic heartbeats → stream ends on an instance-disposal event (v1 per-instance endpoint only), client disconnect, or server shutdown.
4. **PTY attach**: create PTY → request a one-time connect ticket (requires existing auth + same-origin check) → open a WebSocket carrying the ticket (bypasses password auth) → optionally replay buffered output from a supplied cursor → bidirectional live terminal I/O → close (client-initiated, PTY exit, or server shutdown broadcast).
5. **Remote workspace proxying**: request targets a workspace resolved to a remote target → confirm the workspace is actively syncing → forward the HTTP request or WebSocket upgrade verbatim to the remote server → if the remote response carries a sync-sequence header, block locally until the local read model has caught up before returning to the caller.
6. **Config-driven instance disposal**: a global config update, or an explicit dispose call, tears down one or all loaded project instances and emits a disposal event; every open per-instance `/event` subscriber for an affected directory receives a terminal event and closes.
7. **Graceful shutdown**: stop accepting new connections → unpublish mDNS → send a clean close frame to every tracked open WebSocket (bounded grace period per socket) → close the underlying listener.

## Data

- **Event envelope** (v1 `/event`, `/global/event`): `{ id, type, properties }`; the global feed wraps this with routing metadata `{ directory, project?, workspace?, payload }`. A distinct "durable" wrapper (`{ type: "sync", syncEvent: { id, type(versioned), seq, aggregateID, data } }`) is emitted alongside the plain form for event types flagged as durable, feeding the adjacent sync/replay transport rather than ordinary SSE clients.
- **Event envelope** (v2 `/api/event`): a fuller, schema-validated union type carrying `{ id, type, data, durable?, location?, metadata? }` per event, rather than the simplified v1 shape.
- **Error envelope**: a closed family of ~18 tagged error types, each with a fixed HTTP status (400/401/403/404/409/500/502/503/504) and its own identifying fields (e.g. a not-found error for a session carries the session id; a validation error carries a `kind` indicating whether the params, query, headers, or body failed).
- **PTY connect ticket**: `{ ticket (opaque token), expires_in: 60 }`, internally scoped to one PTY id + directory + workspace and consumed exactly once.
- **CORS/auth configuration**: an optional operator-supplied list of extra allowed origins; a single username/password pair sourced from environment variables.
- **OpenAPI document**: a generated, legacy-normalized JSON Schema/OpenAPI 3 document describing every mounted route (both generations), served at `/doc`.

## Interfaces

- **Session & Conversation Runtime** (adjacent): session/message/prompt/fork/revert/interrupt/share endpoints are thin transport wrappers over that feature's service calls; this dossier documents only the HTTP verbs, paths, and status codes, not the underlying turn loop.
- **Tool System / Permission System** (adjacent): permission and question list/reply/reject endpoints expose that feature's pending-approval state over HTTP and the event bus; a reply is a side-effecting POST that unblocks a paused turn elsewhere in the system.
- **Provider & LLM Integration** (adjacent): provider/model listing and OAuth authorize/callback routes are a direct passthrough to that feature's catalogue and auth operations.
- **Auth/Credentials/Accounts** (adjacent): credential set/remove and MCP/integration OAuth routes delegate storage to that feature; this is a separate concern from the server's own Basic-auth gate over the whole API.
- **Storage/Sync/Share** (adjacent): the sync start/replay/steal/history endpoints and the durable "sync" event variant are this feature's transport for that feature's event-sourced replication protocol; a session "share" endpoint likewise hands off to it.
- **Control Plane & Cloud Sync** (adjacent): workspace listing/creation/status/warp endpoints, the remote-workspace HTTP/WebSocket proxy, and the sync-fence wait mechanism bridge a local request to a workspace that may live on a different machine; this feature implements only the proxy transport, not workspace orchestration.
- **Client SDKs** (adjacent): the generated OpenAPI document and the SDK packages that consume it are out of scope here; this dossier documents the served contract, not generated client code.
- **IDE Integration & ACP** (adjacent): editor/IDE integrations and the ACP bridge attach to this same HTTP surface (including its embedded static web UI); no IDE-specific endpoints exist beyond what's documented here.

## Error handling

- Request/response schema validation failures (bad params, query, headers, or body) are converted into structured 400 responses rather than raw framework exceptions, with the offending field/section identified and the rejection reason capped to a bounded length; the wire shape of this 400 differs between the two API generations sharing the port.
- A fixed catalogue of ~18 named, tagged domain errors covers not-found (404), conflict (409), forbidden (403), unauthorized (401), upstream-dependency failure (502), unavailable (503), and timeout (504) cases, each with its own stable status code and identifying fields.
- Any uncaught defect is converted to a generic 500 carrying only a short correlation reference; full detail (including the underlying cause) is logged server-side, never returned to the client.
- Remote-workspace proxying treats an upstream 5xx specially: the body is buffered, logged locally (so the failure is visible in the host's own log even though it originated in a remote sandbox), and forwarded to the client largely unchanged so a structured error (including its correlation reference) can still be parsed.
- A slow SSE consumer on the v2 event endpoint is dropped past a fixed buffer size rather than allowed to grow server memory without bound; the v1 endpoints make the opposite (unbounded) choice.
- WebSocket teardown always attempts a clean protocol-level close (with a distinct close code when a PTY has already exited/vanished) rather than an abrupt socket reset, both for ordinary disconnects and for server shutdown.

## Non-functional observations

- Authentication is fully optional and off by default on the primary shipping server — appropriate for a localhost developer tool, but it means any local user/process can reach the entire API surface (including credential and provider-auth endpoints) unless an operator explicitly opts into a password.
- Two structurally different, path-namespace-separated API generations are mounted on the very same server process and port; this is a real, currently-live dual wire-contract, not merely an internal code-organization detail — any reimplementation must decide whether to expose both, gate the second behind a flag, or converge on one.
- Every SSE endpoint is deliberately stateless across reconnects (no replay-by-cursor), pushing "catch up after a gap" onto a separate, sequence-numbered sync subsystem rather than the live feed itself.
- The two event-bus SSE implementations diverge in backpressure policy (unbounded vs. bounded-and-dropping) and in scoping policy (server-side directory filtering vs. client-side filtering of an unscoped global stream) for what is conceptually the same endpoint — a sign of an in-progress, not-yet-unified migration between the two generations.
- Considerable engineering effort goes into keeping the generated OpenAPI document byte-compatible with an older, hand-maintained SDK's expectations even as the underlying schema-generation library's output shape drifts — a strong signal that external tooling depends on wire-contract stability more than on the internal implementation being clean.

## Acceptance criteria — 6-8 Given/When/Then statements

1. **Given** no server password is configured, **when** any client calls any API route (including the event streams), **then** the request succeeds without credentials, while a standalone `serve` invocation still prints an explicit unsecured-server warning at startup.
2. **Given** a server password is configured, **when** a request supplies no credentials, wrong credentials, or a malformed `auth_token`, **then** the server responds 401 with a `WWW-Authenticate: Basic` challenge header, except for a small fixed set of public static asset paths which remain reachable unauthenticated.
3. **Given** an instance-scoped request carries a `directory` query parameter (or `x-opencode-directory` header) for a project not yet loaded, **when** the request is handled, **then** the server transparently loads that project's instance on first access and reuses the same loaded instance for later requests targeting the same directory.
4. **Given** a `workspace` query value resolves to a workspace whose backing target is remote and currently syncing, **when** any instance-scoped HTTP or WebSocket request carries that workspace, **then** the request is transparently proxied end-to-end to that remote workspace's own server rather than answered locally; if that workspace is not currently syncing, the request instead fails with a service-unavailable response.
5. **Given** a client is subscribed to the per-instance event stream for one project directory, **when** an event is published for a different directory, **then** the subscriber never receives it, while an event published for its own directory arrives promptly and a synthetic keep-alive event arrives at least every ten seconds even when idle.
6. **Given** a project instance is disposed (explicit dispose call or a global config change that changes effective settings), **when** disposal completes, **then** every open per-instance event subscriber for that directory receives a terminal disposal event and its connection closes cleanly.
7. **Given** a client wants to attach to a PTY's live terminal I/O over WebSocket, **when** it presents a valid, unexpired, correctly-scoped one-time connect ticket in the connection URL, **then** the upgrade succeeds without separate password credentials; an invalid, expired, reused, or missing ticket (when no valid password credentials are otherwise supplied) causes the upgrade to be rejected without ever revealing whether the addressed PTY exists.
8. **Given** the server process is shutting down while WebSocket connections (PTY sessions or workspace proxies) are open, **when** shutdown proceeds, **then** every open socket receives a clean "server closing" close frame, bounded by a short per-socket grace period, before the underlying listener stops accepting connections.

## Confidence & open questions

**High confidence:**
- The "v1" surface (root-level paths such as `/session`, `/config`, `/pty`, `/event`, `/global/*`) is the one actually reached by the shipping CLI and terminal UI — confirmed by tracing the `serve` subcommand's route assembly and independently corroborated by the adjacent Session & Conversation Runtime and Provider & LLM Integration dossiers, both of which found no shipped client code path reaching anything else.
- The "v2" protocol/route package (paths under `/api/...`) is genuinely mounted in the very same server process and port as v1 — its route layer is merged directly into the same route table the `opencode` binary serves — so it is live and network-reachable on the shipping server today, just not called by any default shipped client, and with authentication for this embedded mount unconditionally disabled regardless of the v1 password setting (see below).
- A wholly separate second CLI binary exists solely to run the v2 surface standalone as its own background daemon, with its own password-file-based credential (always required, independently generated and persisted), its own registration/discovery file, and a self-displacement lifecycle (a newer daemon registration causes an older one to terminate itself). This is architecturally distinct from the embedded `/api/*` mount inside the primary `opencode` binary — same route code, two different hosts and two different auth postures.
- The two realtime event endpoints for the same conceptual purpose (`/event` vs `/api/event`) were confirmed, by direct code reading, to differ in scoping (server-filtered vs. client-filtered), backpressure policy (unbounded vs. bounded-dropping), heartbeat representation, and disposal-driven auto-close — these are not assumptions but directly observed, and test-asserted, differences.

**Open questions (flagged, not silently resolved):**
- The embedded `/api/*` mount inside the primary `opencode` binary's own server unconditionally disables v2's own password requirement, meaning that generation's authentication becomes a pure no-op on that mount regardless of whatever password protects the v1 API on the same port — it is unclear from the code alone whether this is intentional (relying on the outer v1 gate covering the whole port) or an oversight; a reimplementation team should treat this as a decision point rather than copy it silently.
- The product intent behind having three parallel forms of essentially the same API (v1 embedded, v2 embedded-but-unused, v2 standalone-daemon) could not be determined from the code alone — whether the standalone daemon is a soon-to-be-promoted default, an internal tooling surface, or a paused experiment is unresolved.
- The exact PTY wire sub-protocol (binary control-frame layout for cursor resumption, close-code conventions) and the full ~85-entry internal event-type catalogue were sampled rather than exhaustively enumerated in this summary-depth dossier; a reimplementation should treat the live schema/manifest as the source of truth for exhaustive enumeration.
- The mDNS advertisement's actual consumer (which client discovers a server this way) was not traced and is assumed to be a companion app or LAN-discovery flow outside the files examined.
