# Feature: LSP Integration & Fast Search (ripgrep) Backend

## Purpose
Gives the coding agent live code intelligence for the project it is working in: syntax/type errors and warnings (diagnostics) surfaced automatically after the agent edits or reads a file, plus on-demand navigation (hover, go-to-definition, find-references, go-to-implementation, document/workspace symbol search, call hierarchy) exposed as an explicit tool. Underneath, a fast recursive file/content search backend (built on the `ripgrep` engine) provides file listing, glob matching, and grep-with-context used by the agent's search tools. Together these let the agent behave like an IDE-aware assistant without requiring the user to run or configure a language server themselves — servers are discovered per-language, auto-launched (and, where license/availability allows, auto-downloaded) on demand, and diagnostics are pushed back into tool output so the agent can self-correct.

## Behavior
- **Language server registry**: a fixed table of ~35 built-in language servers (TypeScript, ESLint, Oxlint, Biome, Vue, Svelte, Astro, Deno, Go (gopls), Python (Pyright or an experimental "ty"), Ruby (rubocop/ruby-lsp), Rust (rust-analyzer), C/C++ (clangd), C#/Razor/F# (Roslyn-based + fsautocomplete), Swift (sourcekit-lsp), Java (jdtls), Kotlin, YAML, Lua, PHP (Intelephense), Prisma, Dart, OCaml, Bash, Terraform, TeX (texlab), Dockerfile, Gleam, Clojure, Nix (nixd), Typst (tinymist), Haskell, Julia), each declaring: an id, the file extensions it should attach to, a "root finder" function, and a "spawn" function.
- **Root resolution**: each server's root finder walks upward from the touched file toward the project boundary looking for marker files (lockfiles, `go.mod`, `Cargo.toml`, `pom.xml`/`build.gradle`, `.sln`/`.csproj`, `Package.swift`, etc.); some also support exclusion markers (e.g. TypeScript's server is skipped when a `deno.json` is found in the same walk, ceding to the Deno server) and multi-root workspaces (e.g. Rust walks further up to find a Cargo workspace root; Java's finder tries Gradle wrapper, Gradle settings, single-project Gradle, then Maven POM `<modules>` chains, then Eclipse `.project`, in that priority order).
- **Auto-provisioning**: if a server binary is not already installed/on PATH, several server definitions download and install it themselves the first time it's needed — resolving an npm-distributed language server, fetching a GitHub release archive (zip/tar) for the current OS/architecture, extracting it into a shared binaries directory, and (Unix) marking it executable; some (ESLint, gopls, rubocop, Roslyn, fsautocomplete) instead run a package manager install (`npm`/`go install`/`gem install`/`dotnet tool install`) into that directory. Auto-download is skippable via a "disable LSP download" runtime flag, in which case the server is simply treated as unavailable.
- **Spawning and pooling**: language servers are spawned as child processes communicating over stdio using the Language Server Protocol's JSON-RPC framing. One process instance is pooled per (server id, resolved root) pair; concurrent requests for the same pair reuse an in-flight spawn rather than double-spawning. A server is marked "broken" (and not retried) once its spawn or initialization fails for a given root, for the remainder of the running instance.
- **Handshake**: on spawn, the client sends the LSP `initialize` request (declaring workspace-folder, configuration, watched-files, and diagnostic capabilities but explicitly not claiming diagnostic-refresh or push-diagnostic-version support it doesn't implement), waits up to a fixed timeout, then sends `initialized` and, if the server definition carries per-server initialization options, a `workspace/didChangeConfiguration` notification.
- **File sync**: the client tracks open documents with an internal version counter. First touch performs `textDocument/didOpen` (full text, version 0) plus a synthetic `workspace/didChangeWatchedFiles` "created" event. A later touch performs `didChange` (full-text or ranged/incremental replace, depending on what the server declared it supports) plus a "changed" watched-files event, without clearing previously known diagnostics (so servers that only re-diagnose on real content change don't have their errors wiped by a no-op touch).
- **Diagnostics — push and pull, merged**: the client both listens for server-initiated `textDocument/publishDiagnostics` pushes and, when a server dynamically registers pull-diagnostic support, actively polls `textDocument/diagnostic` (document-scoped) and `workspace/diagnostic` (project-scoped) — including multiple named "identifiers" a server can register (e.g. distinguishing a fast syntax pass from a slower semantic pass) which are requested in parallel. The two diagnostic sources are deduplicated and merged per-file when read. A caller can request diagnostics in "document" mode (wait until the current file's diagnostics are fresh, favoring a fast result once any parallel pull for the current file lands) or "full" mode (also wait for/merge workspace-wide pull results, e.g. for other files affected by an edit), each with its own timeout; a debounce absorbs jittery pushes before treating them as settled.
- **Code intelligence tool**: an agent-facing tool performs hover, go-to-definition, find-references, go-to-implementation, document-symbol, workspace-symbol (top 10 results, filtered to "interesting" kinds: classes, functions, methods, interfaces, variables, constants, structs, enums), and call-hierarchy (prepare + incoming/outgoing calls) queries, fanning a request out to every language server attached to the target file and flattening the results. It requires user/policy permission (`lsp` permission kind) before running, verifies the target file exists and that at least one LSP client can attach to it, and forces a fresh document sync before querying.
- **Automatic diagnostics on file mutation**: the file-write and file-edit tools notify the LSP layer after writing (document-scoped wait) and append a compact, human-readable error report to their own tool output — capped to a bounded number of errors for the touched file and a bounded number of other affected files — so the agent sees fresh compiler/linter errors inline with the result of its own edit, without a separate round-trip. The file-read tool also opportunistically "warms up" the relevant language server in the background (best-effort, failures ignored) so a subsequent LSP query is faster.
- **Status/inspection surface**: an HTTP endpoint and CLI debug subcommands expose currently connected servers (id, name, project-relative root, connection status), on-demand diagnostics for a file, and ad hoc symbol search — useful for support/debugging, not part of the agent's own tool surface.
- **Search backend (ripgrep)**: a small process-oriented adapter runs the `rg` binary for three operations — `find` (files whose relative path matches a glob, streamed with an optional per-entry callback for incremental UIs), `glob` (same idea, returning only strings), and `grep` (content search returning JSON match records: path, line number, absolute byte offset, matched text truncated to a size cap with surrogate-pair-safe truncation, and up to a bounded number of submatch spans per line). Every invocation disables ripgrep's own config-file loading, always excludes `.git`, and (for grep) always searches hidden files. Result and record sizes are hard-capped to bound memory; a limit+1 read lets the adapter detect truncation without buffering unbounded output.
- **ripgrep binary provisioning**: prefers a `rg`/`rg.exe` already on PATH, then a previously-downloaded copy in the shared binaries directory, else downloads a pinned ripgrep release for the current OS/architecture from GitHub, extracts it (native `tar` on Unix, PowerShell `Expand-Archive` on Windows), copies just the executable into the binaries directory, and marks it executable — cached for the life of the process.

## Business rules & edge cases
- LSP is **off by default**: it only activates when the project config's `lsp` setting is `true` (enable all built-ins) or an object (enable built-ins with per-server overrides/additions); when unset or `false`, no language server is ever spawned, `hasClients` returns false, and diagnostics/queries return empty results.
- A config object entry can: disable a named built-in server, add extra environment variables / initialization options / extensions to a built-in, or define an entirely custom server by command line — a custom (non-built-in) server id *must* declare its file extensions in config, since the runtime cannot infer them; this is enforced as a config-validation rule (an empty extensions array is accepted by the current validation, which is a known laxity).
- Requests are always scoped to the current project/instance: a file outside the instance's directory and worktree never triggers a spawn or attaches to a client, even when LSP is enabled (a non-git project's worktree can legitimately equal the filesystem root, which is special-cased so it doesn't accidentally match every absolute path).
- Python is the one language with two candidate servers (Pyright vs. an experimental "ty") gated by mutually exclusive selection: an experimental runtime flag switches from the Pyright default to "ty" and removes the other from the active registry, so only one Python server is ever active in the same run.
- Extension matching is inclusive-by-default: a server with an empty extensions list attaches to any file (used for project-wide servers like Bash, Dockerfile); one with a non-empty list only attaches to files whose extension is listed.
- Root resolution "exclusion" markers can short-circuit a server entirely for a file — the marker must not exist in the upward walk or the server is skipped for that file (e.g. TypeScript's server never attaches under a Deno project).
- Java root resolution has an explicit priority order (Gradle wrapper > Gradle settings > single-project Gradle build file > Maven POM chain validated via `<modules>` back-references > Eclipse native project) rather than "nearest marker wins."
- Diagnostics reported back to the agent are capped: a fixed maximum diagnostic lines per file in the pretty report, and a fixed maximum number of *other* (non-edited) files' diagnostics are surfaced per write/edit call, to keep tool output bounded.
- Only `severity === error` diagnostics are surfaced in the write/edit tool report text (warnings/info/hints exist in the data model and in `hover`/raw query results but are filtered out of the auto-report).
- Diagnostic dedup treats two diagnostics as the same if code, severity, message, source, and range all match — guards against a server re-publishing the same diagnostic via both push and pull.
- A first diagnostics push from the TypeScript server is seeded directly into the "known" state rather than waiting for the normal push/settle debounce, because that server pushes diagnostics unusually eagerly on open (an explicit special case for one server id).
- Failed spawn or failed client-initialization for a given (server, root) is remembered as "broken" so repeated touches don't repeatedly retry a known-bad combination in the same run; the underlying process is stopped/cleaned up when that happens.
- Auto-download is skipped, and the server treated as unavailable, when a runtime flag disabling LSP downloads is set — used for restricted/offline environments and exercised by tests to confirm the flag reaches every install path (npm, GitHub release, package-manager tool install).
- Ripgrep's `find`/`glob` always exclude `.git` regardless of `.gitignore` contents, but otherwise respect the project's own ignore files (a directory ignored via `.gitignore` is excluded from results); a dotfile/dot-directory outside `.git` (e.g. a tool's own config dir) is included unless explicitly hidden-filtered.
- Ripgrep match line-text is capped in length; when truncation would split a UTF-16 surrogate pair at the cut point, the trailing lone surrogate is dropped before appending the truncation marker, to avoid emitting invalid text.
- A ripgrep invalid-regex pattern is distinguished from a generic execution failure by matching known ripgrep stderr text against the process's regex-specific exit code, and surfaced as its own error type.

## Workflows & states
1. **Enablement**: instance boots → config's `lsp` value is read once per instance state → the built-in server table is filtered (disabled entries removed, custom entries merged/added, experimental Python variant chosen) → the resulting active-server map is retained for the life of the instance.
2. **Attach-on-touch**: a tool (read/write/edit) or the LSP tool calls "touch file" (or an equivalent internal `getClients` lookup) → for each active server whose extension filter matches and whose root can be resolved for that file → if no client exists yet for that (server, root), and no spawn is already in flight, spawn the process, run the initialize handshake, and register the client; otherwise reuse the existing or in-flight client → an "updated" event fires once per newly-created client so listeners (e.g. a UI) know the server roster changed.
3. **Document sync**: touch → open (first time) or change (subsequent) notification sent for that file to every attached client for that file → optionally (when a diagnostics mode is requested) block until diagnostics for that file are fresh, per the document/full wait logic described above, then return.
4. **Diagnostics-driven self-correction loop**: agent calls write or edit tool → file written to disk → touch with "document" mode → wait for diagnostics → diagnostics merged across all attached servers → error-only diagnostics for the edited file (and, capped, other affected files) rendered into the tool's returned text → agent sees the errors in the same turn and may issue a follow-up edit.
5. **Explicit code-intelligence query**: agent calls the LSP tool with an operation + file position (or a query string for workspace-symbol) → permission check → existence check → "has any client" check → forced document-mode touch/sync → the specific LSP request(s) fan out to every client attached to that file (or, for workspace-symbol, every connected client) → results flattened and returned as JSON, or a "no results" message if empty.
6. **Shutdown**: when the owning instance is torn down, every pooled client is asked to shut down (end/dispose the JSON-RPC connection, then terminate the child process).
7. **Search request**: a tool needs files or matches → the ripgrep service is asked for `find`/`glob`/`grep` with a working directory, pattern, and limit → the adapter spawns `rg` with fixed flags, streams and parses its stdout, stops once one more than the limit has been observed (marking the result truncated) → on clean exit, empty output is normalized to no results, a regex-syntax exit code is turned into a distinct pattern-error, and any other non-zero/one/two exit code becomes a generic failure carrying ripgrep's stderr.

## Data
- **Server definition**: id, extensions (list of dot-prefixed extensions or empty for "all"), optional "global" marker, root-resolution function, and an async spawn function that receives the resolved root, project instance context, and runtime flags, and returns either nothing (unavailable) or a process handle plus optional per-server initialization payload.
- **Client/connection state** (per server+root): JSON-RPC connection object; per-file open-document table (version counter + last-sent text); per-file push-diagnostics map and pull-diagnostics map (merged and deduplicated on read); a record of the server's dynamically registered diagnostic capabilities (document-scoped vs. workspace-scoped, each with optional named identifiers); a record of the most recent publish timestamp/version per file (used to decide when a push is "fresh" relative to a wait request); the negotiated text-sync kind (full vs. incremental).
- **Diagnostic** (VS Code / LSP diagnostic shape): a range (start/end line+character), message, numeric severity (1=Error, 2=Warning, 3=Info, 4=Hint), optional error code, optional source, optional related information.
- **Status record** (external-facing): server id, display name, project-relative root path, and a status literal (currently always "connected" once represented — a client that failed is simply absent, not represented as "error" in practice despite the type allowing it).
- **Symbol / DocumentSymbol** (external-facing, LSP-shaped): name, numeric symbol kind, and either a flat symbol's location (uri+range) or a hierarchical document symbol's own range/selection range/optional detail string.
- **Config schema (`lsp`)**: boolean, or a map from server id to either `{ disabled: true }` or `{ command: string[], extensions?: string[], env?: Record<string,string>, initialization?: object, disabled?: boolean }`.
- **Runtime flags relevant to this feature**: disable-LSP-auto-download; experimental switch to select the "ty" Python server instead of Pyright; experimental flag exposing an LSP tool in agent contexts where it might otherwise be withheld.
- **Ripgrep match record**: relative file path, line number, absolute byte offset, the (possibly truncated) matched line text, and a bounded list of submatches (each with matched text and start/end offsets within the line).
- **Ripgrep find/glob record**: a filesystem entry with a normalized (forward-slash, no leading `./`) relative path and a type marker.
- **Shared binaries directory**: a single global location where auto-downloaded/auto-installed tool binaries (per-language servers, ripgrep, ESLint's vendored server, jdtls, etc.) are cached across runs, keyed by tool name (and, for some, version/platform-qualified subdirectories).

## Interfaces
- **To the Tool System** (not documented here): the write and edit tools call "touch + wait for document diagnostics" and append the resulting error report to their own output; the read tool calls "touch" as a fire-and-forget warm-up; a dedicated LSP tool (gated by permission) exposes the full code-intelligence operation set to the agent; search/glob/grep-oriented tools are expected to consume the ripgrep service's `find`/`glob`/`grep` operations rather than shelling out themselves.
- **To Session & Conversation Runtime** (not documented here): the session prompt-construction path queries document symbols (e.g. to build a structural outline of an attached file) via the same LSP service interface used by tools.
- **To Platform Utilities** (not documented here): child-process spawning/lifecycle (start, stream stdio, signal/kill), a generic HTTP-download+archive-extraction helper, an npm-package "which" resolver, and a project-instance/workspace context (current directory, worktree root, "is this path inside the project" check) are all consumed rather than owned by this feature.
- **Outbound HTTP** (this feature's own use, not a documented adjacent feature): fetches to package registries/GitHub Releases APIs to resolve and download language-server and ripgrep binaries, and to a VS Code extension marketplace path convention (local `.razorExtension` files under an existing VS Code install) for one server's optional companion assets.
- **External surface**: an HTTP status endpoint reports connected LSP servers per project instance; CLI debug subcommands expose diagnostics-for-a-file, workspace-symbol-search, and document-symbol-listing outside the normal agent tool flow.

## Error handling
- A server's `spawn` returning "nothing" (binary unavailable, download disabled, install failed, unsupported OS/architecture) is treated as "this server is simply not available here" — not an error surfaced to the agent; the file is just left without that server attached.
- A spawn or initialize failure marks that (server, root) pair "broken" for the life of the instance so it is not retried on every subsequent touch of a matching file; any partially-started process is stopped.
- Individual LSP requests (hover, definition, references, etc.) that fail or time out are swallowed per-client and treated as "no results" for that client, so one misbehaving server doesn't fail a multi-client fan-out or the tool call as a whole.
- The initialize handshake has its own hard timeout, separate from and longer than per-request timeouts, distinguishing "server never came up" from "a single request was slow."
- Pull-diagnostic requests (document and workspace) use their own shorter timeouts and are treated as "not handled" on timeout/failure rather than raising, so the diagnostics-wait logic falls back to whatever push data is available instead of hanging indefinitely.
- A JSON line from ripgrep's `--json` grep output that exceeds a fixed byte size, or that fails to parse/decode, produces a typed error rather than being silently dropped or crashing the run.
- A ripgrep invocation that exits with a ripgrep-specific "regex parse error" is distinguished (via a dedicated error type carrying the offending pattern) from a general process failure, so callers can tell "your search pattern is invalid" apart from "the search tool itself broke."
- Exit code 1 from ripgrep (its convention for "no matches") is normalized to an empty successful result, not an error; only other non-zero/one/two codes become failures.
- File-write/edit tools treat a failure anywhere in the "touch + wait for diagnostics" step as non-fatal to the primary write/edit outcome — the write/edit itself is reported as having succeeded even if diagnostics could not be collected.
- The read tool's LSP warm-up explicitly ignores any failure so that a completely successful file read is never turned into an error by a background LSP hiccup.
- Archive downloads for auto-installed tools are defensively checked (HTTP status, non-empty body, presence of the expected extracted executable) before being wired up as usable, failing closed (server unavailable) rather than proceeding with a corrupt/partial install.

## Non-functional observations
- Per-file diagnostic waits are latency-tuned: document-scoped diagnostics use a shorter timeout than full/workspace-scoped ones, several parallel "identifier" pull requests race rather than sequence, and the code explicitly avoids adding any settle/debounce delay after the first useful result arrives for the current file — commented in the source as latency-critical and tied to a specific past regression, so a reimplementation should preserve "unblock as soon as the current file's diagnostics are available, let slower project-wide pulls keep merging in the background" rather than waiting for every source to finish.
- Client and process pooling by (server id, root) avoids redundant process spawns when many files under the same project root are touched in quick succession; concurrent lookups for the same not-yet-ready pair share one in-flight spawn rather than racing multiple spawns.
- All auto-downloaded/auto-installed tool binaries share one binaries directory, so the cost of installing a language server or ripgrep is paid once per machine, not once per project or per run.
- Search results (ripgrep) are bounded (byte caps per record, submatch caps, overall count limit with truncation signaling, capped line-text length) specifically to keep results usable when handed to a language model with a limited context window, and to bound memory when a match set is huge.
- The design explicitly separates "raw ripgrep-shaped rows" (this feature) from "presentation and permission behavior" (left to the Tool System) — the search adapter is described in its own source comments as deliberately not owning permission prompts or model-facing text formatting.

## Acceptance criteria — 5-8 Given/When/Then statements
1. Given a project with LSP support disabled in configuration (unset or `false`), when a file inside the project is opened, edited, or queried, then no language server process is spawned and code-intelligence/diagnostics operations return empty results without error.
2. Given LSP support enabled and a `.ts` file inside the project whose nearest ancestor (up to the project root) contains a recognized JS/TS lockfile, when that file is first touched, then a TypeScript language server process is spawned once with that ancestor directory as its root, and a subsequent touch of another file under the same root reuses the same server instance rather than spawning a second one.
3. Given an active language server attached to a file, when the agent writes or edits that file, then the tool re-syncs the file's contents with the server, waits (bounded by a timeout) for that file's diagnostics to become current, and appends a formatted list of any error-severity diagnostics (capped in count) to the tool's returned output.
4. Given a language server whose spawn function reports the binary is unavailable and automatic downloading is disabled by configuration, when a file matching that server's extensions is touched, then the touch completes without error, that server contributes no client, and the failure is not surfaced as a tool error.
5. Given the agent invokes the code-intelligence tool with a "go to definition" (or hover/references/implementation/call-hierarchy) operation on a file with no attached language server, when the tool executes, then it reports that no LSP server is available for that file type rather than attempting the query.
6. Given a project configuration that both disables one built-in server and defines a fully custom server entry with an explicit command and extensions, when the LSP layer initializes, then the disabled built-in never spawns, the custom entry is treated like any other server (root resolution, spawn, extension filtering), and a successful custom-server initialization emits an "updated" notification.
7. Given a directory tree containing a `.gitignore`-excluded folder and a `.git` folder, when a file-listing or content-search request is made over that tree, then results always exclude the `.git` folder's contents and exclude the gitignored folder's contents, while explicitly non-`.git` dotfiles/dot-directories remain included unless hidden-file matching is explicitly requested.
8. Given a content search whose pattern is not a valid regular expression, when the search runs, then the caller receives a distinct "invalid pattern" error identifying the offending pattern, distinguishable from a generic search-tool failure.

## Confidence & open questions
- **High confidence** on: the built-in server registry, root-resolution strategies, spawn/auto-install behavior, the initialize/didOpen/didChange/diagnostics protocol flow, diagnostics push+pull merge and dedup logic, the code-intelligence tool's operation set and permission gating, ripgrep's three operations and their flags/limits/error taxonomy, and the config schema's "custom servers need extensions" rule — all corroborated by direct source reading and by colocated tests asserting the exact behavior (e.g. `lsp/lifecycle.test.ts`, `lsp/index.test.ts`, `lsp/client.test.ts`, `config/lsp.test.ts`, `core/test/ripgrep.test.ts`).
- **Open question — core vs. opencode split is not a duplication here, it's a gap**: per repo convention, `packages/core/src/<domain>` is normally checked as the authoritative twin of `packages/opencode/src/<domain>`, but for LSP there is no core-side runtime at all — core only holds the **configuration schema** (`packages/core/src/config/lsp.ts`, and a `v1` variant), while the entire client/server/protocol implementation lives solely in `packages/opencode/src/lsp`. Explicit `TODO` comments in `packages/core/src/tool/edit.ts`, `packages/core/src/tool/write.ts`, and `packages/core/src/file-mutation.ts` state diagnostics integration is deferred "after V2 LSP runtime exists" — meaning core's own write/edit tool implementations currently do **not** wire up LSP diagnostics at all, unlike their `packages/opencode/src/tool/*` counterparts. It is unresolved whether a reimplementation should target the opencode-side behavior (fully functional, in active use) or anticipate an eventual core-side runtime that does not yet exist; this dossier documents the opencode-side (functional) behavior as authoritative for this feature.
- **Open question**: the `Status` record's status field is typed to allow "error" in addition to "connected," but no code path in the reviewed source ever constructs a status entry for a failed/broken client — broken clients are simply absent from the list. It's unclear whether an "error" status is planned/vestigial or produced by a path not covered in this pass.
- **Open question**: the empty-extensions-array validation gap (`Boolean([])` is truthy in the source language, so an explicitly empty extensions array satisfies "extensions must be present" even though it is not a meaningful set of extensions) is called out by the project's own test comments as documenting current, possibly-unintended behavior — worth an explicit product decision in a reimplementation rather than silently inheriting it.
- **Not deeply verified**: exact behavior of the "workspace warm pool" for very large monorepos with many roots (e.g. eviction, if any, of long-idle clients) — no eviction logic was found, suggesting clients live for the entire instance lifetime once spawned; treat as a design decision to confirm with the original maintainers if resource usage over long sessions is a concern.
