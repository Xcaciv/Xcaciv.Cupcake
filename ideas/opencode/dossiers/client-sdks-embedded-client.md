# Feature: Client SDKs & Embedded Client

## Purpose

OpenCode's core product runs an HTTP API describing everything a session/agent host can do (create and run coding sessions, list models/providers, manage permissions, browse files, run terminals, etc.). This feature is the set of client libraries that let other programs — and OpenCode's own front-end — call that API without hand-writing HTTP requests, plus a special "embedded" client that gives OpenCode's own application process the exact same call surface **in-process**, with no network socket, no serialization round trip, and no second process to manage.

Three concrete client generations coexist in the current codebase:

1. A **published, legacy REST SDK** — a resource-oriented client (`session.create`, `session.prompt`, …) generated from a live dump of the server's OpenAPI document. This is what external integrators and (today) OpenCode's own front-end app primarily use.
2. A **private, next-generation typed client pair** — a zero-dependency Promise/`fetch` client and a richer reactive client with pluggable transport, decoded domain values, and typed errors/streams — generated directly from the authoritative API contract (not from an OpenAPI dump).
3. An **embedded, in-process host** — a composition layer that assembles the real request-routing/handler stack used by a live server, wraps it as an in-memory request handler, and hands that handler to the typed client from (2), so callers get identical methods, payloads, and error types whether they call over HTTP or in-process.

## Behavior

**Endpoint coverage.** Both the legacy and next-generation clients cover the same functional groups: health, location (resolving a working directory/workspace/project context), agents, sessions (list/create/get/switch model or agent/prompt/compact/wait/interrupt/revert-stage/revert-clear/revert-commit/context/history/events/message), messages, models, providers, integrations (list/get/connect via API key or OAuth/connection-attempt status/complete/cancel), credentials, permissions (list pending requests, saved permissions, per-session request/get/reply), files (list/find), commands, skills, a global event stream, PTYs (pseudo-terminal sessions: list/create/get/update/remove, plus a separate connect flow), questions (list/reply/reject), references, and an experimental project-copy group. The next-generation Promise client alone defines 58 request methods across these groups (18 top-level groups).

**Two calling styles for the next-generation pair.**
- The **Promise client** takes a base URL, an optional custom fetch implementation, and default headers; every call returns a plain Promise, decoded from JSON with no extra runtime dependency, so it is safe to bundle into a browser page. Streaming endpoints (the global event feed, per-session event feed) return an async-iterable that parses Server-Sent-Events frames incrementally.
- The **reactive client** takes an environment-provided HTTP transport instead of a `fetch` function, decodes inputs/outputs into canonical typed domain values (e.g. a typed session ID, a typed absolute path, a typed model reference) instead of bare strings/objects, exposes streaming endpoints as a lazy event stream type instead of an async iterable, and represents every declared business error as a distinct typed failure value instead of a thrown exception.

**Legacy SDK.** Generated as grouped resource classes (`Session`, `Project`, `Pty`, `Config`, `Tool`, `Provider`, `Event`, …) from an OpenAPI document produced by actually starting a real server and asking it to dump its own spec. Each method takes a single `{ path, query, body }`-shaped input object and, depending on a per-call flag, either returns a `{ data, error }` result tuple or throws. The package additionally bundles convenience helpers to: spawn a real server as a subprocess and resolve its base URL once its startup banner appears on stdout; spawn the TUI as an interactive subprocess; and combine both into one call that returns a ready-to-use client plus a handle to stop the spawned server. Two API surfaces ship side by side inside the same package — an older route set and a newer ("v2") route set with slightly different pagination and header-driven default routing conventions — generated by the same pipeline pointed at the same live server, letting callers pick either generation.

**Embedded client.** Constructing the embedded host builds the same dependency graph of internal services a real server would build (session runtime, permissions, tool registries, credentials, PTY environment, etc.), then turns the fully wired HTTP router into a plain in-memory request handler (a function from a `Request` to a `Promise<Response>`) instead of binding a TCP listener. That handler is then plugged into the reactive client as a custom fetch implementation, so the resulting object exposes the identical method surface (`sessions.create`, `sessions.events`, …) as a networked reactive client. The embedded host additionally exposes a `tools.register(...)` call not present in the network API: it registers a tool at the application (host) level, visible by default to every open project/location, layered underneath any project-local tool registration of the same name. The host is exposed both as a plain constructor and as an injectable service for dependency-injection-style composition.

## Business rules & edge cases

- **Import boundary is load-bearing and enforced.** The plain/Promise client may depend only on the wire-contract/type layer, never on core business logic or the server implementation. The reactive client may additionally depend on the shared typed-schema and protocol layers, but likewise never on core or the server. Only the composition package that builds the embedded host is allowed to depend on the client, core, and server together. This is enforced by build-time tests that actually bundle each public entry point and inspect which source directories ended up compiled in, not just by convention.
- **Client and server contracts must generate identically.** A dedicated equivalence check compiles the client-side route/method definitions and the server's own definitions from the same underlying declarations and asserts their generated output is byte-identical, guarding against transport drift between what the server declares and what the client encodes.
- **Some endpoints are deliberately excluded from the generic client.** Raw file reads and the two PTY-connection endpoints (issuing a connect ticket, and the connect itself) are held out of the generated request/response client surface. PTY streaming instead uses a raw WebSocket upgrade: the caller first requests a short-lived, single-use connect ticket over the normal typed endpoint, then opens a WebSocket carrying that ticket as a query parameter (because a browser cannot attach custom headers to a WebSocket upgrade); the connect handler validates the ticket itself rather than going through the normal authorization layer.
- **Errors are contract-first, not ad hoc.** Every declared business error carries a fixed string tag (its discriminant) and a fixed HTTP status, declared once in the shared contract; both client generations derive their error types and boolean type-guards from that single declaration, so callers branch by tag rather than by parsing text or status codes.
- **Pagination style is endpoint-specific by design.** Listing sessions or messages returns an opaque cursor token for the next page; replaying session history or session events instead returns a numeric "after sequence" position for the next page, with a boolean flag telling the caller whether more data remains. Both conventions are exercised and asserted by tests, not accidental drift.
- **Legacy-SDK convenience header rewriting.** For GET/HEAD requests, the legacy client silently injects a "directory" query parameter (and, in its newer variant, also a "workspace" query parameter) taken from a request header if the URL doesn't already specify one, so a caller can set a default working context once when constructing the client instead of repeating it on every call.
- **Opt-in error normalization.** The legacy SDK's structured-error-to-`Error` conversion only runs when a caller opts into "throw on error" for a given call; callers using the default result-tuple convention keep receiving the parsed error body untouched, so existing field-level reads on it are unaffected.
- **Streaming has bounded memory and hard-fail semantics.** The SSE reader normalizes line endings, tolerates split lines across network reads, and treats an unresolved buffer beyond a fixed size limit, or any single malformed JSON payload, as a terminal stream failure rather than skipping the bad frame or growing memory unbounded.
- **Body draining on every exit path.** Whenever a response's body is not going to be read as the actual result (unexpected status, unsupported content type, empty/no-content success), the client explicitly drains/cancels it so the underlying connection isn't left hanging.
- **Tool registration lifetime differs by scope.** A tool registered through the embedded host's application-level registry lives for the process's lifetime with no automatic teardown; a tool registered inside a specific project/location's own registry is instead tied to that project's lifetime and is automatically removed when that project's context is torn down. A project can shadow an application-level tool locally by reusing the same name.
- **Embedded hosts are fully isolated from one another.** Two embedded hosts created independently in the same process share no state and no event traffic — an event raised inside one host's sessions is never observed by a subscriber attached to a different host.

## Workflows & states

- **Typical session lifecycle (identical in-process or over the network):** create a session (optionally pinning an id, starting agent, and starting model) → switch its active agent and/or model → submit a prompt, which returns an "admission" record decoupled from the prompt actually being processed → subscribe to the session's live event stream and/or replay its durable event history from a given sequence position → read back the session's reconstructed context/message list → fetch one specific message by id → interrupt an in-flight run. Both client generations, and the embedded host, walk this same sequence with the same method names and shapes.
- **Network server bootstrap (legacy SDK convenience helper):** spawn the OpenCode binary as a server subprocess with a chosen hostname/port, watch its combined stdout for a specific "server listening" banner line to learn the actual bound URL (falling back to a timeout that kills the subprocess if the banner never appears or the process exits first), then hand that URL to the client factory. Stopping mirrors this: a normal process kill on non-Windows, a forceful process-tree kill via a system utility on Windows, wired up to also fire on abort-signal cancellation.
- **Dual-generation health probe (observed in OpenCode's own front-end):** to check whether a configured server is reachable, the app first tries the next-generation client's health endpoint; on any failure that isn't a deliberate cancellation, it falls back to the legacy client's equivalent health call — letting one app build talk to servers running either API generation, with retry/backoff policy owned entirely by this caller, not by either client library.
- **PTY connect workflow:** request a one-time connect ticket over the ordinary request/response channel → open a WebSocket to the PTY connect route, passing that ticket (plus a resume cursor and location context) as query parameters → the connect handler consumes and validates the ticket itself before upgrading, independent of the normal authorization pipeline. This flow, and the WebSocket frame protocol itself, sits entirely outside the generated clients.
- **Contract regeneration:** when the authoritative API contract changes, a generation step re-derives both next-generation client sources from it, and a companion check re-runs generation and fails the build if committed generated sources don't match. The legacy SDK's regeneration instead starts a real server, dumps its live OpenAPI document, prunes unreachable schema definitions, feeds the pruned document through an OpenAPI-to-client generator, and then applies a few narrow, verified source patches (forcing certain pagination fields from string to numeric type, and correcting one generator type-parameter bug) before finalizing.

## Data

- **Client construction options:** a base URL; an optional custom fetch/transport implementation; optional default headers (used for auth headers, directory/workspace hints, etc.); per-call options for an abort signal and extra headers.
- **Session record:** id, owning project id, accumulated cost, token usage (input/output/reasoning/cache-read/cache-write), created/updated timestamps, title, and a location (directory, optional workspace id).
- **Prompt admission record:** an admitted sequence number, message id, session id, the original prompt payload, a delivery mode ("steer" or similar), and a creation timestamp — returned immediately on prompt submission, independent of whether/when the prompt is actually processed.
- **Session message:** id, message kind (e.g. a "model-switched" system message, user/assistant message types), creation time, and kind-specific fields (e.g. the model that was switched to).
- **Event envelope:** an id, a type string, a data payload specific to that type, and — for durable (replayable) event types — a `durable` stamp of `{ aggregateID, seq, version }` used to resume a stream from a specific point.
- **Pagination shapes:** cursor-style `{ data, cursor: { next } }` for session/message listing; sequence-style `{ data, hasMore }` for history/event replay, where the next page's "after" position is taken from the last returned item's durable sequence number.
- **Business error shape:** a discriminant field (a string tag on next-generation errors; a name field on at least one legacy-style error), a human-readable message, and a small number of identifying fields specific to the error (e.g. a session id on a "session not found" error, a request id on a "permission not found" error).
- **Transport-level error shape (Promise client):** a fixed small set of named failure reasons — a transport/network failure, an unexpected/undeclared HTTP status, an unsupported content type, or a malformed/undecodable response body — each optionally carrying the underlying cause.
- **Legacy SDK request shape:** each generated method takes one input object with up to three named sections — path parameters, query parameters, and a request body — plus an optional per-call client override and throw-on-error flag.

## Interfaces

- **Consumes (not documented here):** the Server/HTTP API & Event Bus feature owns the actual route definitions, request/response schemas, middleware placement, and error taxonomy. All three client generations compile or re-export bindings to that contract; they do not define or alter it. A contract-equivalence check ties the two together so this feature cannot silently drift from what the server actually serves.
- **Consumes (not documented here):** the Session & Conversation Runtime and its supporting services (tool registries, permissions, credentials, PTY handling) are what the embedded host's assembled handler stack actually calls into; this feature only wires that stack into an in-memory transport and does not redefine session/runtime behavior.
- **Exposed to OpenCode's own front-end/TUI application:** currently the primary consumer of the legacy REST SDK's newer ("v2") surface for all normal traffic, with the next-generation Promise client used today only as a secondary/fallback path for a server health check — evidence of an in-flight migration from the legacy generation toward the next-generation one.
- **Exposed to third-party integrators:** the legacy SDK is the publicly published npm package intended for external programs (Node/Bun/browser) that want to drive an OpenCode server; it also documents a spawn-a-server-and-drive-it workflow (see the bundled process/server helpers) as a first-class use case (e.g., batch-processing files through freshly created sessions).
- **Exposed to OpenCode's own process (in-process embedding):** the composition layer lets the desktop/CLI application host the entire router and business-logic stack, plus a client bound to it, inside a single process without ever opening a network port — avoiding a second process and a serialization round trip purely for the app's own use of its own API. This composition layer is explicitly transitional and, as of this snapshot, has no other in-repo consumer beyond its own tests.

## Error handling

- **Two clearly separated error families in the next-generation clients:** transport-level failures (network error, undeclared/unexpected HTTP status, wrong content type, undecodable body) versus declared business errors decoded from a response whose status matches one an endpoint documents. Both are represented as distinct, identifiable values rather than a single generic exception type.
- **Declared errors preserve identity end to end.** When a response's status is one an endpoint's contract lists as a possible error outcome, the body is decoded into the corresponding typed/tagged error and surfaced with all of its original fields (e.g. the session id on a not-found error) intact — including when the failure originates from request-pipeline middleware rather than the endpoint's own handler; there is no separate error shape for pipeline versus handler failures.
- **Streaming failures are terminal, not best-effort.** A single malformed data frame, or a stream buffer that grows past a fixed cap without ever completing a frame, ends the stream immediately with a distinct "malformed response" failure. Streams that never establish the expected content type fail immediately rather than attempting to parse a non-event response as events.
- **Response bodies are always accounted for.** On every code path that isn't going to consume a body as the actual result — unexpected status, wrong content type, empty/no-content success — the client actively drains or cancels the body so the connection isn't left in a half-read state.
- **Legacy SDK's opt-in Error normalization.** Only active when a caller requests throw-on-error behavior for a call. A structured (named/tagged) error body has a human message extracted from its message or name field (falling back to a synthesized "method + URL + status" description); a plain non-empty string body becomes an `Error` with that string as its message; an empty body, network failure, or empty object becomes an `Error` describing whether a response was received at all. In every case the original parsed body and HTTP status are preserved on the resulting error's cause field so structured callers can still recover them. Callers using the default result-tuple convention are entirely unaffected by this normalization.
- **Health/liveness checks classify errors instead of just failing.** The example front-end health-check workflow distinguishes retryable transport errors (aborted signal excluded, generic network/fetch-shaped errors included) from other errors, and only retries the former, with a small fixed retry count and increasing delay.

## Non-functional observations

- **Deliberately zero-dependency browser-safe entry point.** The Promise client is built to run with nothing beyond a standard fetch implementation, specifically so it can be bundled into a browser page without pulling in the effects runtime or any Node-only API.
- **Architecture boundaries are tested, not just documented.** Both client packages ship tests that actually invoke a bundler against each public entry point and assert which source directories appear in the resulting bundle, catching a forbidden-dependency regression (e.g. the plain client accidentally pulling in core/server code) at build time rather than relying on code review.
- **Reproducible, checked code generation.** Both the next-generation and legacy client sources are produced by scripted generation steps against a source of truth (a shared contract, or a live server's OpenAPI dump) rather than hand-maintained, with an automated check that fails if the generated output on disk has drifted from a fresh generation run.
- **Two API "shapes" for two audiences.** The reactive client keeps business errors and streaming values fully typed, favoring exhaustive handling by sophisticated callers; the Promise client instead folds everything into ordinary thrown exceptions for simple async/await ergonomics. This split is a deliberate, tested design choice rather than incidental duplication.
- **In-process embedding trades a coupling for a performance/operational win.** Running the exact HTTP stack in memory removes serialization and socket overhead, and the need to supervise a second process, for the application's own use of its own API — at the cost of the composition layer needing to depend on internals (core, server) that the client layer itself is forbidden from touching.
- **Acknowledged, intentional code duplication to avoid a dependency cycle.** The legacy SDK duplicates a small process-management helper (used for killing a spawned server) rather than importing it from the main application, because the main application already depends on the SDK package and importing back would create a cycle.
- **Transitional package with no external footprint yet.** The composition-layer package that builds the embedded host is marked in its own documentation as a transitional replacement for the legacy SDK once its consumers migrate, and — at the pinned commit — no other in-repo package imports it outside its own test suite.

## Acceptance criteria — 5-8 Given/When/Then statements

1. **Given** a reachable OpenCode server's base URL, **when** a caller constructs the Promise client and requests a known session by id, **then** it resolves with the decoded session record using nothing beyond a standard fetch implementation (no extra runtime required).
2. **Given** a caller subscribed to an event-stream endpoint, **when** the server emits a sequence of Server-Sent-Events frames — including heartbeat/comment lines and frames split across multiple network reads — **then** the client yields exactly one decoded event per logical data block, in order, silently skipping heartbeat/comment lines.
3. **Given** a successful-status response whose content type is not JSON (for a normal call) or not an event stream (for a streaming call), **when** the client processes it, **then** it fails with a distinct "unsupported content type" error rather than attempting to parse the body as the expected shape.
4. **Given** an embedded host created with no real network listener, **when** a caller runs the full session lifecycle (create, switch model/agent, submit a prompt, subscribe to events, fetch context/history, fetch one message, interrupt) through it, **then** every call succeeds with the same result shapes, and the same declared not-found error types, as the equivalent calls would produce against a real network server.
5. **Given** two embedded hosts created independently in the same process, **when** a session is created and modified through the first host while a subscriber listens on the second host's event stream, **then** the second host's subscriber never observes any event from the first host's session.
6. **Given** a tool registered through the embedded host's application-level registry, **when** any project/location subsequently looks up its available tools, **then** that tool is visible there by default; **and given** that same project registers its own tool under the identical name, **when** the lookup runs again, **then** the project-local tool is what's used, without needing to change the application-level registry, and the project-local registration disappears once that project's own context is torn down while the application-level one does not.
7. **Given** the shared API contract used to build both the server and the next-generation client, **when** the generation-equivalence check runs, **then** the client's generated route/method definitions match the server's own generated definitions exactly; a deliberate divergence (e.g. an endpoint's declared error list changing on one side only) must fail this check.
8. **Given** a legacy-SDK caller who opted into throw-on-error mode, **when** a request fails with a structured/tagged error body, **then** the thrown error's message is derived from that body's message or name field, and the original parsed body plus HTTP status are preserved under the thrown error's cause — while a caller who did not opt in receives the parsed error body completely unchanged from today's behavior.

## Confidence & open questions

**High confidence** (directly observed in source and exercised by colocated tests): Promise-client transport semantics (status handling, SSE parsing, content-type checks, body draining); reactive-client parity with the Promise client (same endpoints, decoded typed values, typed errors); embedded-host construction and behavior (session lifecycle, event isolation between hosts, application-level tool registration semantics); the Schema/Protocol-only dependency rule for client code and Client+Core+Server-only composition in the embedded package (stated in the repo's own contributor guide and enforced by dedicated bundle-boundary tests); legacy-SDK method/calling conventions, header-rewriting, subprocess-spawning helpers, and opt-in error normalization.

**Medium confidence / inference:** The exact current adoption state of the composition-layer package (embedded host) elsewhere in the codebase — a repository-wide search found no consumer besides its own tests, which matches its own documentation calling it "transitional," but a from-scratch reimplementation should confirm this is still accurate rather than an artifact of exactly this pinned commit.

**Open questions for a reimplementing team:**
- Whether the legacy SDK's two bundled API generations (older and "v2") are both meant to remain permanently supported side by side, or whether the older one is being phased out — no explicit deprecation marker was found in this codebase snapshot.
- The exact retry/backoff policy expected of a production integration: none of the three client generations implement automatic retries themselves; retry logic observed lives entirely in a calling application (e.g., a front-end health-check helper). Confirm this is an intentional "retries are the caller's job" design rather than a gap this dossier should have flagged as a defect.
- The full wire protocol used once a PTY WebSocket connection is established (frame types, resize/backpressure signaling) was identified as explicitly out of scope for every generated client and was not traced end to end in this pass; a team implementing PTY support needs a dedicated, separate investigation of that protocol.
- This dossier lists representative data shapes and endpoint groups rather than an exhaustive field-by-field schema (the underlying generated type definitions run to roughly 2,800 lines across ~58 next-generation methods, plus a ~160-route legacy OpenAPI document). Treat the checked-in generated sources and the OpenAPI document as the authoritative, exhaustive reference during reimplementation rather than this summary.
