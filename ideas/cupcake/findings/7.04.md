# Verification findings for 7.04-F3-plugin-discovery.md

10 finding(s). Apply every one.

## 1. [CRITICAL] §7.4 FR-4.25, FR-4.26, FR-4.27, FR-4.28, UC-4.B, AC-4.4, AC-4.5, AC-4.16, AC-4.17 (cites Crawler.cs:176-178)

**Problem:** The PRD states as fact that the scan "enumerates, recursively from the verified root, every file matching the pattern `*/bin/*.dll`" and that such binaries are opened and registered. Executed against a real filesystem, that enumeration finds nothing — it throws. Crawler.cs:176-178 builds `searchMask = Path.Combine("*", subDirectory, SearchPattern)` = `*/bin/*.dll` and calls `Directory.GetFiles(basePath, searchMask, SearchOption.AllDirectories)`. .NET splits a search pattern at its last separator and joins the directory portion to the root LITERALLY (no globbing on that portion), so it tries to enumerate `<root>/*/bin`. I ran this on .NET with a real fixture (`fsroot/Hello/bin/Hello.dll`, `fsroot/a/b/c/bin/Deep.dll`, `fsroot/bin/Root.dll`): result was `EX DirectoryNotFoundException: Could not find a part of the path '<root>/*/bin'` — zero files, on both platforms (Windows Path.GetDirectoryName("*\\bin\\*.dll") = "*\\bin" behaves identically). The framework's own passing walk test (CrawlerTests.cs:93-103) uses `MockFileSystem`, whose glob implementation DOES support a wildcard directory segment; its only real-`FileSystem` test (CrawlerTests.cs:106-110) deliberately passes `String.Empty` as the sub-directory so the segmented mask is never exercised for real. The shipping path uses the real filesystem: `new CommandController()` → CommandController.cs:104 → `new Crawler()` → Crawler.cs:36 `new FileSystem()`. Consequence: with the default `bin` filter no Plugin is ever discovered, and any Plugin Directory that passes the Verified Directory rule aborts start-up with `Error Unable to load commands.` / exit 1 regardless of its contents. US-4.4/US-4.5, UC-4.B in full, and AC-4.4/4.5/4.16/4.17 describe behaviour the source cannot produce.

**Required fix:** Re-verify Crawler.CrawlPackagePaths against a real `FileSystem` and rewrite the discovery requirements accordingly. State plainly that, as shipped, the segmented mask is only satisfiable by the framework's mock filesystem and that on a real filesystem the scan raises a directory-not-found condition naming `<root>/*/bin`; therefore no Plugin is ever loaded and every verified Plugin Directory is fatal. Recast FR-4.25–FR-4.28, UC-4.B and AC-4.4/4.5/4.16/4.17 as the *intended* layout the clone must implement with real glob semantics (an explicitly-flagged deviation), not as observed behaviour. Add the same correction to the §7.2 mirror (FR-2.13, UC-2.5) and to the Bug-for-bug decision list.

## 2. [MAJOR] §11.1 (OQ-1..OQ-25) and §11.2 Q-14, against §7.4 UC-4.D error flow E2 (assembled PRD line 2973)

**Problem:** F3's open question 4 — "**Does the containment check behave identically for a symbolic link, junction, or UNC path?** … Links and UNC paths remain open — the check canonicalises the textual path but does nothing to resolve links, so an in-bounds link pointing out of bounds is expected to be accepted, and a UNC path has a different location identifier shape whose base-of behaviour was not evaluated" — appears nowhere in §11.1, nowhere in the §11.2 quirk register, and not in §7.4's own thirteen-item "bug-for-bug decisions" list. Its single appearance in the whole 8,200-line document is one error-flow bullet inside UC-4.D. This is the document's most security-relevant undetermined item, and §11.2 Q-14's recommended disposition ("**Fix** — compare the candidate itself against a boundary normalised with a trailing separator") does **not** close it: a team that applies exactly that fix is still open to a symlink escape and has been given no signal that anything remains undecided. Phase 0 (§10) signs off the §11.2 register and named OQs, so this item is never put to the commissioning team at all.

**Required fix:** Add an OQ to §11.1 immediately after the containment material (e.g. OQ-7a): "**Does the Plugin Directory containment check hold against symbolic links, junctions and network-share paths?** Why it matters: the check canonicalises text only and resolves no links, so an in-bounds link pointing out of bounds is expected to be accepted — a direct bypass of the only boundary standing between the Plugin Directory and arbitrary code execution. Where we looked: the reference tag's directory-verification tests, which cover only plainly-inside and plainly-outside absolute paths with an explicitly set boundary; the subject repository's tests, which never touch directory verification. Not exercised by any test in either source; verify empirically for link, junction and network-share candidates." Also add a cross-reference to it from §11.2 Q-14's disposition column and from §7.4's decision list item 1, so the recommended fix is not read as complete.

## 3. [MAJOR] §7.4 (after AC-4.14) and §7.2 (after AC-2.8) — no acceptance criterion anywhere for FR-1.90 / FR-2.9 / FR-4.18+FR-4.57 / FR-5.45 / FR-6.29 / FR-10.48 / FR-11.11

**Problem:** The default Plugin Directory literal `.\packages` is flagged as a QUIRK with an observable consequence in seven of the eleven subsections, and named in the bug-for-bug list of §7.2 (item 4), §7.4 (item 10), §7.5 (item 13) and §7.11 (item 7) — but not one acceptance criterion in the whole of §7 pins it. Grepping all eleven files for an AC mentioning a backslash, POSIX or a non-Windows path yields nothing; AC-2.5, AC-4.1, AC-5.6, AC-6.1, AC-10.24 and AC-11.3 all pin the *absent-directory* case, never the mislocated-by-separator case. This is the single behaviour most likely to be silently "corrected" by a team rebuilding the product in another language on a POSIX host — which is the stated purpose of this document — and its symptom (silent Verified-Directory rejection, then the No Plugins Found guidance) is indistinguishable from a genuinely absent directory, so nothing will surface the divergence in testing.

**Required fix:** Add one acceptance criterion, wired to FR-4.57 and cross-referenced from FR-2.9, FR-5.45, FR-10.48 and FR-11.11: "AC-4.x — QUIRK, decide keep or fix. Given a POSIX host, a working directory containing a valid Plugin at ./packages/Hello/bin/Hello.<binary-ext>, and the Plugin Directory left at its compiled-in default, when the Shell starts, then `HELLO` is NOT registered, no diagnostic naming any path is produced on any channel, and the output is exactly the No Plugins Found guidance followed by a normal Prompt — because the literal `.\packages` names a single directory entry rather than a relative path. The clone team must consciously choose to reproduce the backslash literal or to use the platform separator." Reference it from open question Q-25, which currently records the decision with no executable criterion behind it.

## 4. [MAJOR] §11.2 — no row for verb displacement or for the non-executable group verb; body at §6 GR-53, §7.4 FR-4.9/FR-4.47/AC-4.9 ("decision 7: a supply-chain concern with no diagnostic"), §7.1 FR-1.18, §7.4 FR-4.15/AC-4.8, §7.9 FR-9.34/AC-9.17 ("QUIRK Q12")

**Problem:** Two distinct registration quirks have no row. (1) Registration is last-write-wins by name, so a Plugin declaring a verb already held by a Built-in or Host-linked Command "displaces it with no warning, no trace line and no user-visible notice" (GR-53) — §7.4 lists this as its seventh keep-or-fix decision and calls it a supply-chain concern. Q-15 covers only a Plugin that *fails* to load, not one that succeeds and silently takes over `SAY`. (2) A Command Group's synthesised entry carries no executable identity, so typing `PACKAGE` alone yields `Error executing PACKAGE (see trace for more info)` plus `**Error: Command type name is empty.` with nothing telling the user which members exist. Q-8 covers only that failure text names the group rather than the member; Q-13 covers namespacing and recommends "Keep".

**Required fix:** Add:
| Q-71 | Command registration is last-write-wins by name (with member-merging for Command Groups), so a Plugin that declares a verb already held by a Built-in or Host-linked Command displaces it with no warning, no trace line and no user-visible notice. | 6, 7.4 | S | **Fix** — surface the displacement; silently re-pointing an existing verb at Plugin code is a supply-chain gap. |
| Q-72 | A Command Group's synthesised entry carries no implementation identity, so the bare group verb — or a member word that matches no member — produces `Error executing PACKAGE (see trace for more info)` plus `**Error: Command type name is empty.`, never a member listing or a "missing sub-command" message. | 7.1, 7.4, 7.9 | U | **Fix** — print the member listing for a bare or unmatched group verb. |

## 5. [MAJOR] §6 GR-41 (contradicted by §7.2 FR-2.17, §7.4 FR-4.8, §7.5 FR-5.17, §7.6 UC-6.4/AC-6.26, §7.10 FR-10.60, §11.2 Q-17)

**Problem:** GR-41 states the startup-failure rule as "Any failure of the three guarded startup steps **other than No Plugins Available** shall be replaced by a Startup Load Failure whose summary is the fixed, cause-independent literal `Unable to load commands.` — **identical in both Session entry points**". Read as written, the No-Plugins-Available exemption holds in both entry points. Six other locations say the opposite: the asynchronous/background entry point has no tolerant branch and wraps No Plugins Available as fatal too (`Loop.cs:82-85` has only the generic catch). §6 also never records the two unrelated "nothing found" signals or which one is fatal, although §7.6's external-technology note calls collapsing them "the single most consequential substitution error available here" and §7.5's calls the two distinguishable signals "critical". §6 is the product-wide normative section a clone team will build the failure contract from.

**Required fix:** Split the clause: "In the blocking entry point, any failure other than No Plugins Available is replaced by a Startup Load Failure …; in the background entry point there is no tolerant branch, so **every** failure including No Plugins Available is wrapped. The summary literal is identical in both." Add a new §6.5 rule stating that the Command Service raises two unrelated sibling conditions — "no verified Plugin Directory" (caught, becomes the guidance line) and "Plugin Directory holds no plugin binaries" (uncaught, fatal, exit 1) — and that collapsing them inverts the first-run experience, cross-referencing §7.4 FR-4.42 and §7.6 FR-6.32.

## 6. [MAJOR] §7.4 FR-4.42 / UC-4.A E2 / UC-4.C E1 / AC-4.6 (cites Crawler.cs:180)

**Problem:** FR-4.42 states the empty-but-verified Plugin Directory case "raises a **different** condition, `No packages found in <absolute path>.`, which is a sibling of the No Plugins Available condition". On the shipping path that literal is unreachable: Crawler.cs:178 (`Directory.GetFiles` with the `*/bin/*.dll` mask) throws `DirectoryNotFoundException` before control ever reaches the `NoPackageDirectoryFoundException` throw at line 180 — verified by execution (see the critical finding). Line 180 is only reachable when the sub-directory filter is empty, which the Shell never does (Loop.cs:43 calls `LoadCommands()` with no argument, defaulting to `bin`). The user-visible outcome the PRD asserts (`Error Unable to load commands.`, exit 1) still holds, but the named condition, the quoted literal, and the whole "two unrelated sibling conditions" explanation of the quirk are wrong for the shipping configuration.

**Required fix:** Rewrite FR-4.42 to say the condition actually raised on the shipping path is a directory-not-found failure naming `<root>/*/bin` (Crawler.cs:178), that `No packages found in <absolute path>.` (Crawler.cs:180) is reachable only with an empty sub-directory filter, and that the quirk's true root cause is the unusable search mask rather than a sibling-exception hierarchy. Keep AC-4.6's observable outcome but restate its mechanism. Apply the same correction to UC-4.A E2, UC-4.C E1 and §7.2 UC-2.1 E2 / UC-2.5 E2.

## 8. [MINOR] §7.4 FR-4.25, UC-4.B precondition/step 1, AC-4.4, AC-4.5 (cites Crawler.cs:20)

**Problem:** The PRD repeatedly describes the file filter as "any file bearing the host platform's shared-library extension" and writes acceptance fixtures as `Hello.<binary-ext>`. Crawler.cs:20 is `private const string SearchPattern = "*.dll";` — a hard-coded, platform-independent literal (.NET assemblies are `.dll` on every OS). §7.4's own External technology entry gets it right ("with binary pattern `*.dll`"), so the section contradicts itself. A clone targeting Linux would read "host platform's shared-library extension" and scan for `*.so`, discovering nothing the original would.

**Required fix:** Replace "the host platform's shared-library extension" with "the fixed literal extension `.dll`, hard-coded regardless of host platform (Crawler.cs:20)" in FR-4.25, UC-4.B and the AC fixtures, and note that a clone on a runtime with a different module extension must choose its own constant deliberately.

## 9. [MINOR] §7.4 FR-4.30 (cites Crawler.cs:31, :54-58)

**Problem:** FR-4.30 says "The strictness is a mutable setting of the Command Service, not a constant, and the Shell never pins it." The policy field and its setter are on the Plugin Scanner, not the Command Service: Crawler.cs:31 `private AssemblySecurityPolicy _securityPolicy = AssemblySecurityPolicy.Strict;` and Crawler.cs:54 `public void SetSecurityPolicy(...)`. `CommandController` exposes no such member (grep for SetSecurityPolicy over the framework's non-test sources returns only Crawler.cs:54 and CommandFactory.cs:31), and because the Shell uses `new CommandController()` it never even holds a Crawler reference to configure. The PRD's own citation points at Crawler.cs, and the PRD calls that component the "Plugin Scanner" everywhere else (UC-4.B step 1).

**Required fix:** Reword FR-4.30 to "a mutable setting of the Plugin Scanner (Crawler.cs:31, :54-58), not of the Command Service; the Shell constructs the Command Service with its default Plugin Scanner and has no handle on which to change it". Note separately that a second, distinct security configuration exists on the command factory (CommandFactory.cs:31) if that is in scope.
