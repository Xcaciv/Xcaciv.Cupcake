## 3. [MAJOR] §6 GR-41 (contradicted by §7.2 FR-2.17, §7.4 FR-4.8, §7.5 FR-5.17, §7.6 UC-6.4/AC-6.26, §7.10 FR-10.60, §11.2 Q-17)

**Problem:** GR-41 states the startup-failure rule as "Any failure of the three guarded startup steps **other than No Plugins Available** shall be replaced by a Startup Load Failure whose summary is the fixed, cause-independent literal `Unable to load commands.` — **identical in both Session entry points**". Read as written, the No-Plugins-Available exemption holds in both entry points. Six other locations say the opposite: the asynchronous/background entry point has no tolerant branch and wraps No Plugins Available as fatal too (`Loop.cs:82-85` has only the generic catch). §6 also never records the two unrelated "nothing found" signals or which one is fatal, although §7.6's external-technology note calls collapsing them "the single most consequential substitution error available here" and §7.5's calls the two distinguishable signals "critical". §6 is the product-wide normative section a clone team will build the failure contract from.

**Required fix:** Split the clause: "In the blocking entry point, any failure other than No Plugins Available is replaced by a Startup Load Failure …; in the background entry point there is no tolerant branch, so **every** failure including No Plugins Available is wrapped. The summary literal is identical in both." Add a new §6.5 rule stating that the Command Service raises two unrelated sibling conditions — "no verified Plugin Directory" (caught, becomes the guidance line) and "Plugin Directory holds no plugin binaries" (uncaught, fatal, exit 1) — and that collapsing them inverts the first-run experience, cross-referencing §7.4 FR-4.42 and §7.6 FR-6.32.

## 4. [MAJOR] §7.5 FR-5.22 and UC-5.A alternate flow A3

**Problem:** Both state that when Status Visibility is off the Status lines `Loading Commands` and `Done` "go to the Diagnostic trace channel". The cited code (`src/Xcaciv.Cupcake.Core/ConsoleContext.cs:92-96`, verified at a05dc6f) writes them with `Debug.WriteLine(message)` — the *debug* sink. §7.3 FR-3.14/FR-3.15 and the External-technology list make the debug-sink-vs-trace-sink distinction load-bearing: `Debug.WriteLine` is stripped from optimized builds, while the Diagnostic trace sink (`Trace.WriteLine`, framework `AbstractTextIo.cs:174`) survives. As written, §7.5 tells a clone team the suppressed text is retrievable from the trace channel, which is the opposite of QUIRK-2.

**Required fix:** In FR-5.22 and UC-5.A/A3 replace "go to the Diagnostic trace channel" with "go to the debug diagnostic sink (`Debug.WriteLine`), which optimized builds strip entirely — see §7.3 FR-3.14, FR-3.15".

## 5. [MINOR] §7.5 FR-5.56

**Problem:** FR-5.56 describes `Loop.cs:49` as "a commented-out re-raise of the No Plugins Available condition". Line 49 is `// throw new Exceptions.LoadingException(ex.Message, ex);` — a commented-out *conversion* into the Session's own Startup Load Failure, not a re-raise of `NoPluginsFoundException`; and it references `ex`, which the catch clause at `:45` (`catch (Xcaciv.Command.Interface.Exceptions.NoPluginsFoundException)`) does not bind, so it would not even compile as written. The "deliberate and recent choice" gloss is also an inference stated as fact.

**Required fix:** Reword to "a commented-out conversion of the No Plugins Available condition into a Startup Load Failure (`// throw new Exceptions.LoadingException(ex.Message, ex);`), which would not compile as written because the catch clause binds no exception variable", and mark the intent gloss INFERRED.
