# Verification findings for S06-product-wide.md

9 finding(s). Apply every one.

## 1. [CRITICAL] §6 GR-26 (contradicted by §6 GR-27, §7.8 FR-8.16, §7.1 FR-1.68)

**Problem:** GR-26 states as a product-wide rule that the read-side-effect is observable: "a mere read can create an entry that a later variable dump lists — the first Package Search stores an empty value under the Registry Endpoint key — and the echo Built-in Command leaves an empty entry behind for every `%NAME%` it fails to resolve." The very next requirement, GR-27, gives the rule that disproves both examples: values flow back to the caller's scope only when the Command's registration record declares it environment-modifying. Package Search is registered with that flag off (§7.8 FR-8.4; `Lit/Program.cs:11` calls AddCommand with the default `modifiesEnvironment: false`), and SAY is not environment-modifying either (§7.1 FR-1.68 says so explicitly: "It is invisible for `SAY`"). Framework evidence confirms the gate: `CommandExecutor.cs` writes back only under `if (commandDescription.ModifiesEnvironment && childEnv.HasChanged)`. §7.8 FR-8.16 is the correct statement — the write lands in the discarded per-execution child scope and the Session store is unchanged.

**Required fix:** Rewrite GR-26's consequence clause to: "a read creates an entry **in the reading Command's own child scope**; whether it survives is decided by GR-27, so for a Command not declared environment-modifying — which includes Package Search and the echo Built-in — the entry is discarded with the child and no later variable dump lists it. The side effect is observable only inside an environment-modifying Command, or when a host invokes a Command directly against its own store with no child scoping." Keep the mutating-read rule itself; only the persistence claim is wrong.

## 2. [MAJOR] §11.2 — no rows for §7.1's binder and contract quirks; body at §7.1 FR-1.4, FR-1.14/1.67/1.68, FR-1.21, FR-1.23, FR-1.29, FR-1.44, FR-1.45, FR-1.48, FR-1.63, FR-1.64, FR-1.72, FR-1.77, FR-1.78, FR-1.103, FR-1.105 and their §6 twins GR-5, GR-6, GR-20, GR-21, GR-23, GR-27, GR-28

**Problem:** §7.1 tags 39 requirements QUIRK; the register covers 25 of them. Fourteen distinct §7.1 quirks have no row, including four that change what a typed command line does (`-taken` silently binding `take` and eating the next token; a trailing `-take` with no value crashing the binder; `-VERBOSITY quiet` binding nothing; the conditional-echo Built-in emitting the wrong token) and one security row (the dormant redaction policy). Phase 1 is "the largest and least negotiable phase" and is built from §7.1, so these are exactly the decisions the register exists to force.

**Required fix:** Add:
| Q-58 | Parameter-name matching is unanchored at the end: a token that merely begins with one or two dashes plus the declared name matches, so `-taken` binds a parameter declared `take` and swallows the following token as its value. First match in token order wins. | 6, 7.1, 7.8 | U | **Fix** — anchor the match. |
| Q-59 | A Named Parameter as the final token with no value after it reads past the end of the token list, so the user sees a raw index failure instead of a product message. | 6, 7.1, 7.8, 7.10 | U | **Fix** — diagnose a value-less Named Parameter explicitly. |
| Q-60 | Parameter *names* match case-sensitively and are lower-cased at declaration while parameter *values* do not, so `-VERBOSITY quiet` matches nothing and binds the default (or fails as missing), and a declaration whose name contains upper-case letters is unreachable in the form its author wrote it. | 6, 7.1 | U | **Fix** — match names case-insensitively. |
| Q-61 | Registering a Command by instance records only the Command's kind; the supplied object is discarded and a fresh instance is constructed for every execution. | 7.1 | D | **Keep** — but document it: state placed on a registered object does not survive. |
| Q-62 | The "may change Session Variables" flag is stamped on the Command Group's record, not the member: the first registration of a group decides write-back for every member, and a member joining later cannot change it. | 6, 7.1, 8 | D | **Decide** — per-member write-back is the defensible design. |
| Q-63 | A quoted or escaped pipe still routes the line into the Pipeline machinery (the delimiter search runs before quote handling), and the Pipeline splitter consumes quote characters before re-tokenising each stage — so quoting protects a dotted argument at the top level but not inside a pipeline: `say x \| package install "XCBatch.Core"` emits `Not installing x XCBatch,Core`. | 6, 7.1, 7.9 | U | **Fix** — quoting must behave identically in both positions. |
| Q-64 | A final Pipeline stage emitting more than 10,000 Outputs blocks forever: the final Stage Channel is bounded at 10,000 with a blocking full-buffer policy and has no reader until every stage has completed. | 7.1, 9 | U | **Fix** — this is a hang. |
| Q-65 | A `%NAME%` Session Variable reference is destroyed by tokenization unless double-quoted, and an unresolved reference comes back with doubled delimiters (`SAY "%NOPE%"` renders `%%NOPE%%`); the echo Built-in also prints the names it failed to resolve. | 6, 7.1 | U | **Fix** — the product's own help text tells users to double-quote for this reason. |
| Q-66 | The conditional-echo Built-in echoes the wrong token: it tests every token after the first but appends the token at position 1 once per match, so `REGIF a xa ba` emits `xa xa` rather than `xa ba`. | 7.1 | U | **Fix.** |
| Q-67 | A child variable scope is born already flagged "changed" (seeding runs through the write path that sets the flag) and never records its parent, though the contract requires the lineage field. | 6, 7.1, 8 | D | **Fix** — the change flag is meaningless as it stands. |
| Q-68 | The Command Service's own attribute-driven help generator is unreachable for any Command built on the shared Command base, and a synthesised usage line is written flush left while a declared prototype is indented two spaces. | 7.1 | D | **Fix** silently — but keep the non-empty-wins fallback. |
| Q-69 | The Shell's test stand-ins are not the published contract: they declare members the contract lacks, name the load-Commands argument as a configuration path rather than a binary sub-directory defaulting to `bin`, and read the third argument of a variable read as "raise if absent" rather than "store the fallback" — the opposite of the contract. | 7.1 | D | **Fix** — a reimplementer following the stand-ins builds the wrong load operation and the wrong read semantics. |
| Q-70 | The framework's audit redaction policy is dormant: masking is applied only to tokens shaped `-name=value` and the executor records the raw token list, so a secret typed as a Named Parameter reaches the audit record unmasked. | 7.1, 8 | S | **Fix** — apply the policy to the recorded parameters. |

## 3. [MAJOR] §11.2 — no row for verb displacement or for the non-executable group verb; body at §6 GR-53, §7.4 FR-4.9/FR-4.47/AC-4.9 ("decision 7: a supply-chain concern with no diagnostic"), §7.1 FR-1.18, §7.4 FR-4.15/AC-4.8, §7.9 FR-9.34/AC-9.17 ("QUIRK Q12")

**Problem:** Two distinct registration quirks have no row. (1) Registration is last-write-wins by name, so a Plugin declaring a verb already held by a Built-in or Host-linked Command "displaces it with no warning, no trace line and no user-visible notice" (GR-53) — §7.4 lists this as its seventh keep-or-fix decision and calls it a supply-chain concern. Q-15 covers only a Plugin that *fails* to load, not one that succeeds and silently takes over `SAY`. (2) A Command Group's synthesised entry carries no executable identity, so typing `PACKAGE` alone yields `Error executing PACKAGE (see trace for more info)` plus `**Error: Command type name is empty.` with nothing telling the user which members exist. Q-8 covers only that failure text names the group rather than the member; Q-13 covers namespacing and recommends "Keep".

**Required fix:** Add:
| Q-71 | Command registration is last-write-wins by name (with member-merging for Command Groups), so a Plugin that declares a verb already held by a Built-in or Host-linked Command displaces it with no warning, no trace line and no user-visible notice. | 6, 7.4 | S | **Fix** — surface the displacement; silently re-pointing an existing verb at Plugin code is a supply-chain gap. |
| Q-72 | A Command Group's synthesised entry carries no implementation identity, so the bare group verb — or a member word that matches no member — produces `Error executing PACKAGE (see trace for more info)` plus `**Error: Command type name is empty.`, never a member listing or a "missing sub-command" message. | 7.1, 7.4, 7.9 | U | **Fix** — print the member listing for a bare or unmatched group verb. |

## 4. [MAJOR] §11.2 — no rows for the product-wide reporting quirks; body at §6 GR-46 and GR-47, §7.6 FR-6.45/FR-6.48/FR-6.49, AC-6.22/AC-6.23/AC-6.25, §7.10 FR-10.24/AC-10.7/AC-10.11, §7.8 FR-8.48/FR-8.49/AC-8.22, §7.2 FR-2.52/FR-2.55/AC-2.6

**Problem:** Four product-wide QUIRK-tagged behaviours have no register row. §6 GR-46 ("The product shall silently correct invalid values rather than reporting them") and GR-47 ("Work the product does not perform… shall be announced as ordinary Output, never as failures") are stated as product-wide requirements with their own keep-or-fix framing, and §7.6 FR-6.49 says registry diagnostics are "discarded by construction" so "a Registry outage and a zero-result search are indistinguishable" — an availability defect Q-7 (zero results print nothing) does not cover. Q-7's disposition "emit an explicit no matches" is unimplementable without also deciding the outage case.

**Required fix:** Add:
| Q-73 | Invalid values are silently corrected rather than reported: a Result limit outside 1–100 is clamped, a search term over 200 characters is truncated to 200, and a blank search term returns empty Output and issues no query — none produces any message. | 6, 7.6, 7.8, 7.10 | U | **Decide** with Q-7 — reporting these is more helpful and less faithful. |
| Q-74 | Work the product does not perform is announced as ordinary Output, never as a failure, and never affects exit status: Package Install answers `Not installing ` plus its comma-joined arguments, and a piped Package Search answers `Unsupported search method for <chunk> (piped)` immediately followed by its comma-joined arguments with no separator, so they run into the closing parenthesis. | 6, 7.2, 7.6, 7.8 | U | **Fix** — route refusals to the failure channel and add the missing separator. |
| Q-75 | Registry-side diagnostics are discarded by construction: the Package Registry Client accepts a diagnostic sink at every entry point and every call site in the product passes the discard sink, so a Registry outage, a feed error and a genuine zero-result search are indistinguishable to the user. | 7.6, 7.7 | S | **Fix** — a supply-chain client that cannot report transport failure has no failure signal at all. |
| Q-76 | The No Plugins Available guidance travels on the Output channel rather than the Status channel, so a Shell started with Status Visibility off suppresses `Loading Commands` but still prints the guidance, and the guidance renders in Output colours. | 7.2, 7.3 | D | **Fix** — put narration on one channel. |

## 5. [MAJOR] §6 GR-41 (contradicted by §7.2 FR-2.17, §7.4 FR-4.8, §7.5 FR-5.17, §7.6 UC-6.4/AC-6.26, §7.10 FR-10.60, §11.2 Q-17)

**Problem:** GR-41 states the startup-failure rule as "Any failure of the three guarded startup steps **other than No Plugins Available** shall be replaced by a Startup Load Failure whose summary is the fixed, cause-independent literal `Unable to load commands.` — **identical in both Session entry points**". Read as written, the No-Plugins-Available exemption holds in both entry points. Six other locations say the opposite: the asynchronous/background entry point has no tolerant branch and wraps No Plugins Available as fatal too (`Loop.cs:82-85` has only the generic catch). §6 also never records the two unrelated "nothing found" signals or which one is fatal, although §7.6's external-technology note calls collapsing them "the single most consequential substitution error available here" and §7.5's calls the two distinguishable signals "critical". §6 is the product-wide normative section a clone team will build the failure contract from.

**Required fix:** Split the clause: "In the blocking entry point, any failure other than No Plugins Available is replaced by a Startup Load Failure …; in the background entry point there is no tolerant branch, so **every** failure including No Plugins Available is wrapped. The summary literal is identical in both." Add a new §6.5 rule stating that the Command Service raises two unrelated sibling conditions — "no verified Plugin Directory" (caught, becomes the guidance line) and "Plugin Directory holds no plugin binaries" (uncaught, fatal, exit 1) — and that collapsing them inverts the first-run experience, cross-referencing §7.4 FR-4.42 and §7.6 FR-6.32.

## 6. [MAJOR] §6 GR-11 (line 132) and GR-20 (line 216)

**Problem:** Both requirements point a reader at the wrong sibling requirement for the generic per-Command failure. GR-11 ends "...fails as a Command execution error (GR-41), not as an unknown Command", and GR-20 ends "...the user sees a generic Command execution error (GR-41) rather than a product message". GR-41 is the *startup* requirement — "Startup failures shall be fatal and uniform ... the fixed, cause-independent literal `Unable to load commands.`" — which ends the process with exit 1. The requirement that actually describes a generic Command execution error (`Error executing <NAME> (see trace for more info)` on Output, `**Error: <message>` on the Status line, Session survives) is GR-38, per CommandExecutor.cs:224-231. A clone team following the cross-reference would make an unknown Command-Group member and a trailing Named Parameter fatal to the Session, which is the opposite of the observed behaviour (and of §7.1 UC-2 E3, FR-1.18 and AC-1.12, which get it right).

**Required fix:** Change both "(GR-41)" references to "(GR-38)". Then re-check the rest of §6 for the same slip — GR-24, GR-32 and GR-37 already reference GR-38 correctly, so only lines 132 and 216 need the change.

## 7. [MINOR] §6 GR-61

**Problem:** "...only two of its six operations expose the parameter at all, with download and archive-metadata read hard-wiring it." The counts are right (six operations; `FindPackageAsync` NugetWrapper.cs:20/24 and `ResolveDependenciesAsync` :52/56 expose the parameter), but the second hard-wiring is mislabelled. The two cited hard-wired `CancellationToken.None` sites are NugetWrapper.cs:84 (`DownloadPackageAsync` — download, correct) and NugetWrapper.cs:46, which is inside `FindPackageVersionsAsync` — version enumeration, not archive-metadata read. The archive-metadata read, `GetNuspecData` (NugetWrapper.cs:103-109), is synchronous and takes no cancellation parameter of any kind, so it cannot be said to hard-wire one.

**Required fix:** Change "with download and archive-metadata read hard-wiring it" to "with download and version enumeration hard-wiring it to 'never cancelled', and the archive-metadata read taking no cancellation parameter at all", and extend the citation to `src/Xcaciv.Command.Packages/NugetWrapper.cs:24,46,56,84,103-109`.

## 8. [MINOR] §6 GR-50

**Problem:** "...and the binary pattern is every file with the platform's shared-library extension." The pattern is a hard-coded literal, not platform-derived: `Crawler.cs:20` reads `private const string SearchPattern = "*.dll";` and it is combined verbatim at `:176`. On a non-Windows host the platform shared-library extension is `.so`/`.dylib`, so a clone team reading GR-50 literally would build a platform-sensitive mask the product does not have. §7.1 FR-1.79 states the same rule correctly as `<Plugin Directory>/*/bin/*.dll`, so the two sections disagree.

**Required fix:** Change to "...and the binary pattern is the fixed literal `*.dll` — the managed-module extension on every platform, not a platform-derived shared-library extension", keeping the `Crawler.cs:20` citation and adding `:176`.

## 9. [MINOR] §6 GR-32

**Problem:** "...and because the Command Service reports every Command failure on the Status line (GR-38), turning Status Visibility off silently suppresses error reporting." This overstates the effect and contradicts GR-32's own opening sentence ("Status Visibility shall gate the Status line and nothing else") and GR-38. Per CommandExecutor.cs:228-229 the Command Service writes the Output line `Error executing <NAME> (see trace for more info)` first and only then the Status line `**Error: <message>`. Output is not gated by Status Visibility (ConsoleContext.cs:53-60 has no Verbose test), so a user with Status Visibility off still sees that a Command failed — what disappears is the failure's *message text*.

**Required fix:** Reword to: "...and because the Command Service puts the failure's actual message on the Status line (GR-38) while Output carries only the generic `Error executing <NAME> (see trace for more info)` line, turning Status Visibility off leaves the user knowing that a Command failed and nothing about why — with the detail recorded nowhere in a shipping build."
