## 1. [CRITICAL] §7.2 AC-2.15, §7.7 AC-7.26, §7.10 AC-10.5 (contradicted by §7.8 AC-8.27)

**Problem:** Four acceptance criteria make mutually exclusive claims about the same observable, so no implementation can satisfy the PRD's own QA suite. AC-2.15 ("a Session Variable dump afterwards shows an entry PACKAGESOURCEURL with an empty value"), AC-7.26 ("an empty value is left recorded under the uppercased key PACKAGESOURCEURL, visible in a subsequent variable dump") and AC-10.5 ("a subsequent Session Variable dump lists an entry under the upper-cased endpoint key") assert the pollution is visible; AC-8.27 asserts "the Session's store is unchanged and the endpoint key is not listed" and explicitly flags the conflict. The source settles it against the three: the Lit Shell registers the Command as `Controller.AddCommand("internal", new SearchCommand())` (src/Xcaciv.Cupcake.Lit/Program.cs:11) with `modifiesEnvironment` defaulting to false (OUT-OF-REPO CommandController.cs:190); the executor runs the Command against `environmentContext.GetChild(...)` — a fresh store seeded with a copy (EnvironmentContext.cs:45-55) — and merges back only under `if (commandDescription.ModifiesEnvironment && childEnv.HasChanged)` (CommandExecutor.cs:216). The store-on-read side effect therefore lands in the discarded child scope and never reaches the Session. A clone team following AC-2.15 would have to register the PACKAGE group as environment-modifying, which by §7.1 FR-1.21 stamps the flag on the whole group and also changes Package Install's write-back — a behavioural divergence introduced by the PRD itself.

**Required fix:** Rewrite AC-2.15, AC-7.26 and AC-10.5 to match AC-8.27: the read stores the empty default in the per-execution child scope only, and a subsequent variable dump does NOT list PACKAGESOURCEURL, because the Command is registered without the environment-modifying flag. Re-scope the supporting requirements the same way — FR-2.37, FR-7.69, FR-10.4 and UC-2.3 E3 and the UC-10.A postcondition must say "in the Command's own child scope, discarded on return", not "in every subsequent Session Variable dump". Delete the "the project quirk register predicts the opposite, and this criterion is the decision point" clause from AC-8.27 once the other three agree, and correct orchestrator-notes D7, which is the origin of the error.

## 3. [MAJOR] §7.7 FR-7.69 and AC-7.26 (also the §7.7 bug-for-bug list, item 10)

**Problem:** Both state as observed fact that the empty value written back under `PACKAGESOURCEURL` becomes visible in a subsequent variable dump ("after which a variable dump lists it" / "visible in a subsequent variable dump"). This is refuted by the very framework evidence §7.7 relies on: the write lands in the per-execution child scope (`ref-Xcaciv.Command-v2/src/Xcaciv.Command/CommandExecutor.cs:187`, `EnvironmentContext.cs:45-55` — the child is a *copy*), and the write-back to the Session store is gated at `CommandExecutor.cs:216-219` on `commandDescription.ModifiesEnvironment && childEnv.HasChanged`. Package Search is registered via `src/Xcaciv.Cupcake.Lit/Program.cs:11` `AddCommand("internal", new SearchCommand())`, and `CommandController.cs:190` defaults `modifiesEnvironment` to `false`, so the child scope is discarded and the Session store is unchanged. This also directly contradicts §7.8 FR-8.16 and AC-8.27, which assert the opposite outcome in the same PRD and explicitly flag the orchestrator quirk register (D7) as unreliable on this point.

**Required fix:** Rewrite FR-7.69 and AC-7.26 to match §7.8 FR-8.16/AC-8.27: the read does write an empty value into the *per-execution child* Session Variable scope, but because Package Search is registered as not modifying Session Variables that scope is discarded and a later variable dump does NOT list the key; the write is observable only on the direct-invocation path (US-7.7-style host embedding) where the host passes its own store with no child scoping. Cite `CommandExecutor.cs:216-219` and `CommandController.cs:190` alongside `IEnvironmentContext.cs:50`, and route the residual disagreement with quirk-register entry D7 to open questions as §7.8 does.

## 7. [MINOR] §7.7 FR-7.13 and AC-7.31

**Problem:** FR-7.13 states as observed behaviour that registry matching semantics "are observed to be case-insensitive and tolerant of the term being punctuated differently from the Plugin name", citing `Xcaciv.Command.PackagesTests/SearchCommandTests.cs:112-126`; AC-7.31 repeats "the registry matches it case-insensitively and punctuation-tolerantly". The cited test searches `cake.nuget` and asserts the output contains `Cake.NuGet`. The two strings have identical punctuation (one dot, same position); only casing differs. Nothing in the repository exercises a punctuation difference, so the punctuation-tolerance half is an unsupported inference stated as an observation.

**Required fix:** Drop the punctuation clause from FR-7.13 and AC-7.31, or restate it as INFERRED/untested. The cited evidence supports only case-insensitive matching.
