## 1. [CRITICAL] §7.2 AC-2.15, §7.7 AC-7.26, §7.10 AC-10.5 (contradicted by §7.8 AC-8.27)

**Problem:** Four acceptance criteria make mutually exclusive claims about the same observable, so no implementation can satisfy the PRD's own QA suite. AC-2.15 ("a Session Variable dump afterwards shows an entry PACKAGESOURCEURL with an empty value"), AC-7.26 ("an empty value is left recorded under the uppercased key PACKAGESOURCEURL, visible in a subsequent variable dump") and AC-10.5 ("a subsequent Session Variable dump lists an entry under the upper-cased endpoint key") assert the pollution is visible; AC-8.27 asserts "the Session's store is unchanged and the endpoint key is not listed" and explicitly flags the conflict. The source settles it against the three: the Lit Shell registers the Command as `Controller.AddCommand("internal", new SearchCommand())` (src/Xcaciv.Cupcake.Lit/Program.cs:11) with `modifiesEnvironment` defaulting to false (OUT-OF-REPO CommandController.cs:190); the executor runs the Command against `environmentContext.GetChild(...)` — a fresh store seeded with a copy (EnvironmentContext.cs:45-55) — and merges back only under `if (commandDescription.ModifiesEnvironment && childEnv.HasChanged)` (CommandExecutor.cs:216). The store-on-read side effect therefore lands in the discarded child scope and never reaches the Session. A clone team following AC-2.15 would have to register the PACKAGE group as environment-modifying, which by §7.1 FR-1.21 stamps the flag on the whole group and also changes Package Install's write-back — a behavioural divergence introduced by the PRD itself.

**Required fix:** Rewrite AC-2.15, AC-7.26 and AC-10.5 to match AC-8.27: the read stores the empty default in the per-execution child scope only, and a subsequent variable dump does NOT list PACKAGESOURCEURL, because the Command is registered without the environment-modifying flag. Re-scope the supporting requirements the same way — FR-2.37, FR-7.69, FR-10.4 and UC-2.3 E3 and the UC-10.A postcondition must say "in the Command's own child scope, discarded on return", not "in every subsequent Session Variable dump". Delete the "the project quirk register predicts the opposite, and this criterion is the decision point" clause from AC-8.27 once the other three agree, and correct orchestrator-notes D7, which is the origin of the error.

## 2. [CRITICAL] §7.2 FR-2.37 and AC-2.15 (also §7.2 UC-2.3 E3, §7.10 FR-10.4, §8 DM-3 Lifecycle, §11.2 Q-10) — contradicted by §7.8 FR-8.16

**Problem:** Five locations assert the disproved consequence as fact, and one of them is an executable acceptance criterion a clone would be tested against. §7.2 FR-2.37: "an entry `PACKAGESOURCEURL` with an empty value appears in every subsequent Session Variable dump"; §7.2 AC-2.15: "**and** a Session Variable dump afterwards shows an entry `PACKAGESOURCEURL` with an empty value"; §7.10 FR-10.4: "shall store an empty value under it as a side effect, after which a Session Variable dump lists it"; §8 DM-3: "the first Package Search **permanently** adds an empty `PACKAGESOURCEURL` entry that a subsequent variable dump then lists" — which the same paragraph then contradicts three sentences later with its own write-back rule; §11.2 Q-10 records it as a quirk of "the variable store" and attributes it to "6, 7.2" only. §7.8 FR-8.16 is correct: the child scope is discarded because Package Search is registered as not modifying Session Variables. A clone built to AC-2.15 must either wire write-back for a non-modifying Command or ship a test its faithful implementation fails.

**Required fix:** Correct all five. FR-2.37 and §7.10 FR-10.4: end at "...writes the default back into the Command's per-execution child scope, which is then discarded because Package Search is not registered as environment-modifying; the Session's store is unchanged." AC-2.15: replace the second clause with "**and** a Session Variable dump afterwards shows **no** `PACKAGESOURCEURL` entry — the write landed in the discarded child scope; the write is observable only when a host invokes the Command directly against its own store." §8 DM-3: delete "permanently" and the dump clause, and cross-reference the write-back sentence in the same paragraph. §11.2 Q-10: restate as "a read mutates the Command's child scope (invisible in the Session today, and visible the moment a Command is declared environment-modifying)" and add §7.8 to its § column.

## 3. [MAJOR] §7.4 (after AC-4.14) and §7.2 (after AC-2.8) — no acceptance criterion anywhere for FR-1.90 / FR-2.9 / FR-4.18+FR-4.57 / FR-5.45 / FR-6.29 / FR-10.48 / FR-11.11

**Problem:** The default Plugin Directory literal `.\packages` is flagged as a QUIRK with an observable consequence in seven of the eleven subsections, and named in the bug-for-bug list of §7.2 (item 4), §7.4 (item 10), §7.5 (item 13) and §7.11 (item 7) — but not one acceptance criterion in the whole of §7 pins it. Given a POSIX host, a working directory containing a valid Plugin at ./packages/Hello/bin/Hello.<binary-ext>, and the Plugin Directory left at its compiled-in default, when the Shell starts, then `HELLO` is NOT registered, no diagnostic naming any path is produced on any channel, and the output is exactly the No Plugins Found guidance followed by a normal Prompt — because the literal `.\packages` names a single directory entry rather than a relative path. The clone team must consciously choose to reproduce the backslash literal or to use the platform separator." Reference it from open question Q-25, which currently records the decision with no executable criterion behind it.

## 6. [MAJOR] §6 GR-41 (contradicted by §7.2 FR-2.17, §7.4 FR-4.8, §7.5 FR-5.17, §7.6 UC-6.4/AC-6.26, §7.10 FR-10.60, §11.2 Q-17)

**Problem:** GR-41 states the startup-failure rule as "Any failure of the three guarded startup steps **other than No Plugins Available** shall be replaced by a Startup Load Failure whose summary is the fixed, cause-independent literal `Unable to load commands.` — **identical in both Session entry points**". **Required fix:** Split the clause: "In the blocking entry point, any failure other than No Plugins Available is replaced by a Startup Load Failure …; in the background entry point there is no tolerant branch, so **every** failure including No Plugins Available is wrapped. The summary literal is identical in both." Add a new §6.5 rule stating that the Command Service raises two unrelated sibling conditions — "no verified Plugin Directory" (caught, becomes the guidance line) and "Plugin Directory holds no plugin binaries" (uncaught, fatal, exit 1) — and that collapsing them inverts the first-run experience, cross-referencing §7.4 FR-4.42 and §7.6 FR-6.32.

## 11. [MINOR] §7.2 UC-2.2 A2 (cites ConsoleContext.cs:38-47)

**Problem:** A2 states the child Interaction Context is constructed "with the parent's name plus the suffix `Child`, the child's own parameter list and the parent's identifier — and nothing else." ConsoleContext.cs:42-44 additionally forwards state to the child: `if (this.HasPipedInput && this.inputPipe != null) child.SetInputPipe(this.inputPipe);` and `if (this.outputPipe != null) child.SetOutputPipe(this.outputPipe);`. "And nothing else" is false, and a clone that took it literally would build Pipeline children with no input or output channel, breaking piping entirely.

**Required fix:** Amend UC-2.2 A2 to "…and the parent's identifier; the parent's input pipe (when piped input is present) and output pipe are also handed to the child (ConsoleContext.cs:42-44). What the child does NOT inherit is the template, the six colours and Status Visibility, which revert to compiled-in defaults." FR-2.30's enumeration should carry the same clarification.

## 12. [MINOR] §7.2 FR-2.56, AC-2.28 (cites InstallCommand.cs:19-27)

**Problem:** Both state that Package Install "every invocation, direct or per-chunk, returns `Not installing ` followed by the joined arguments". The two overloads differ: InstallCommand.cs:21 (direct) returns `"Not installing " + String.Join(',', parameters)`, but InstallCommand.cs:26 (per-chunk) returns `$"Not installing {pipedChunk} " + String.Join(',', parameters)` — the piped chunk is interposed between the prefix and the arguments, and the trailing space sits after the chunk, not after `installing`. A clone reproducing the quoted behaviour would emit the wrong text on the Pipeline path.

**Required fix:** Split the claim: direct invocation returns `Not installing ` + arguments joined with commas; per-chunk invocation returns `Not installing ` + the chunk + a space + arguments joined with commas. Update AC-2.28's third clause to assert the per-chunk shape separately.
