# Verification findings for 7.01-F10-extensibility-contract.md

13 finding(s). Apply every one.

## 1. [CRITICAL] §6 GR-26 (contradicted by §6 GR-27, §7.8 FR-8.16, §7.1 FR-1.68)

**Problem:** GR-26 states as a product-wide rule that the read-side-effect is observable: "a mere read can create an entry that a later variable dump lists — the first Package Search stores an empty value under the Registry Endpoint key — and the echo Built-in Command leaves an empty entry behind for every `%NAME%` it fails to resolve." The very next requirement, GR-27, gives the rule that disproves both examples: values flow back to the caller's scope only when the Command's registration record declares it environment-modifying. Package Search is registered with that flag off (§7.8 FR-8.4; `Lit/Program.cs:11` calls AddCommand with the default `modifiesEnvironment: false`), and SAY is not environment-modifying either (§7.1 FR-1.68 says so explicitly: "It is invisible for `SAY`"). Framework evidence confirms the gate: `CommandExecutor.cs` writes back only under `if (commandDescription.ModifiesEnvironment && childEnv.HasChanged)`. §7.8 FR-8.16 is the correct statement — the write lands in the discarded per-execution child scope and the Session store is unchanged.

**Required fix:** Rewrite GR-26's consequence clause to: "a read creates an entry **in the reading Command's own child scope**; whether it survives is decided by GR-27, so for a Command not declared environment-modifying — which includes Package Search and the echo Built-in — the entry is discarded with the child and no later variable dump lists it. The side effect is observable only inside an environment-modifying Command, or when a host invokes a Command directly against its own store with no child scoping." Keep the mutating-read rule itself; only the persistence claim is wrong.

## 2. [MAJOR] §11.2 — no rows for §7.1's binder and contract quirks; body at §7.1 FR-1.4, FR-1.14/1.67/1.68, FR-1.21, FR-1.23, FR-1.29, FR-1.44, FR-1.45, FR-1.48, FR-1.63, FR-1.64, FR-1.72, FR-1.77, FR-1.78, FR-1.103, FR-1.105 and their §6 twins GR-5, GR-6, GR-20, GR-21, GR-23, GR-27, GR-28

**Problem:** §7.1 tags 39 requirements QUIRK; the register covers 25 of them. Fourteen distinct §7.1 quirks have no row, including four that change what a typed command line does (`-taken` silently binding `take` and eating the next token; a trailing `-take` with no value crashing the binder; `-VERBOSITY quiet` binding nothing; the conditional-echo Built-in emitting the wrong token) and one security row (the dormant redaction policy). Phase 1 is "the largest and least negotiable phase" and is built from §7.1, so these are exactly the decisions the register exists to force.

**Required fix:** Add:
| Q-58 | Parameter-name matching is unanchored at the end: a token that merely begins with one or two dashes plus the declared name matches, so `-taken` binds a parameter declared `take` and swallows the following token as its value. First match in token order wins. | 6, 7.1, 7.8 | U | **Fix** — anchor the match. |
| Q-59 | A Named Parameter as the final token with no value after it reads past the end of the token list, so the user sees a raw index failure instead of a product message. | 6, 7.1, 7.8, 7.10 | U | **Fix** — diagnose a value-less Named Parameter explicitly. |
| Q-60 | Parameter *names* match case-sensitively and are lower-cased at declaration while parameter *values* do not, so `-VERBOSITY quiet` matches nothing and binds the default (or fails as missing), and a declaration whose name contains upper-case letters is unreachable in the form its author wrote it. | 6, 7.1 | U | **Fix** — match names case-insensitively. |
| Q-61 | Registering a Command by instance records only the Command's kind; the supplied object is discarded and a fresh instance is constructed for every execution. | 7.1 | D | **Keep** — but document it: state placed on a registered object does not survive. |
| Q-62 | The "may change Session Variables" flag is stamped on the Command Group's record, not the member: the first registration of a group decides write-back for every member, and a member joining later cannot change it. | 6, 7.1, 8 | D | **Decide** — per-member write-back is the defensible design. |
| Q-63 | A quoted or escaped pipe still routes the line into the Pipeline machinery (the delimiter search runs before quote handling), and the Pipeline splitter consumes quote characters before re-tokenising each stage — so quoting protects a dotted argument at the top level but not inside a pipeline: `say x \| package install "XCBatch.Core"` emits `Not installing x XCBatch,Core`. | 6, 7.1, 7.9 | U | **Fix** — quoting must behave identically in both positions. |
| Q-64 | A final Pipeline stage emitting more than 10,000 Outputs blocks forever: the final Stage Channel is bounded at 10,000 with a blocking full-buffer policy and has no reader until every stage has completed. | 7.1, 9 | U | **Fix** — this is a hang. |
| Q-65 | A `%NAME%` Session Variable reference is destroyed by tokenization unless double-quoted, and an unresolved reference comes back with doubled delimiters (`SAY "%NOPE%"` renders `%%NOPE%%`); the echo Built-in also prints the names it failed to resolve. | 6, 7.1 | U | **Fix** — the product's own help text tells users to double-quote for this reason. |
| Q-66 | The conditional-echo Built-in echoes the wrong token: it tests every token after the first but appends the token at position 1 once per match, so `REGIF a xa ba` emits `xa xa` rather than `xa ba`. | 7.1 | U | **Fix.** |
| Q-67 | A child variable scope is born already flagged "changed" (seeding runs through the write path that sets the flag) and never records its parent, though the contract requires the lineage field. | 6, 7.1, 8 | D | **Fix** — the change flag is meaningless as it stands. |
| Q-68 | The Command Service's own attribute-driven help generator is unreachable for any Command built on the shared Command base, and a synthesised usage line is written flush left while a declared prototype is indented two spaces. | 7.1 | D | **Fix** silently — but keep the non-empty-wins fallback. |
| Q-69 | The Shell's test stand-ins are not the published contract: they declare members the contract lacks, name the load-Commands argument as a configuration path rather than a binary sub-directory defaulting to `bin`, and read the third argument of a variable read as "raise if absent" rather than "store the fallback" — the opposite of the contract. | 7.1 | D | **Fix** — a reimplementer following the stand-ins builds the wrong load operation and the wrong read semantics. |
| Q-70 | The framework's audit redaction policy is dormant: masking is applied only to tokens shaped `-name=value` and the executor records the raw token list, so a secret typed as a Named Parameter reaches the audit record unmasked. | 7.1, 8 | S | **Fix** — apply the policy to the recorded parameters. |

## 3. [MAJOR] §11.2 — no row for verb displacement or for the non-executable group verb; body at §6 GR-53, §7.4 FR-4.9/FR-4.47/AC-4.9 ("decision 7: a supply-chain concern with no diagnostic"), §7.1 FR-1.18, §7.4 FR-4.15/AC-4.8, §7.9 FR-9.34/AC-9.17 ("QUIRK Q12")

(1) Registration is last-write-wins by name, so a Plugin declaring a verb already held by a Built-in or Host-linked Command "displaces it with no warning, no trace line and no user-visible notice" (GR-53) — §7.4 lists this as its seventh keep-or-fix decision and calls it a supply-chain concern. Q-15 covers only a Plugin that *fails* to load, not one that succeeds and silently takes over `SAY`. Q-8 covers only that failure text names the group rather than the member; Q-13 covers namespacing and recommends "Keep".

**Required fix:** Add:
| Q-71 | Command registration is last-write-wins by name (with member-merging for Command Groups), so a Plugin that declares a verb already held by a Built-in or Host-linked Command displaces it with no warning, no trace line and no user-visible notice. | 6, 7.4 | S | **Fix** — surface the displacement; silently re-pointing an existing verb at Plugin code is a supply-chain gap. |
| Q-72 | A Command Group's synthesised entry carries no implementation identity, so the bare group verb — or a member word that matches no member — produces `Error executing PACKAGE (see trace for more info)` plus `**Error: Command type name is empty.`, never a member listing or a "missing sub-command" message. | 7.1, 7.4, 7.9 | U | **Fix** — print the member listing for a bare or unmatched group verb. |

## 4. [MAJOR] §7.1 FR-1.51 and UC-4 error flow E4

**Problem:** Both claim the help check is confined to the non-piped path: FR-1.51 says "The check runs only on the non-piped path, so a Pipeline stage never renders help" and UC-4 E4 says "A stage with piped input never checks for a help request, so `--HELP` on a piped stage is passed to the Command as an ordinary argument." This is contradicted by the cited framework. `CommandExecutor.ExecuteAsync` runs `if (_helpService.IsHelpRequest(parameters))` at CommandExecutor.cs:57-58 unconditionally, before any Command is constructed, on a registry hit — and a Pipeline stage reaches exactly that method (PipelineExecutor.cs:136 `executeCommand(...)` -> CommandController.cs:278-281 `ExecuteCommandInternal` -> `_commandExecutor.ExecuteAsync`). So `SAY one | REGIF --HELP` renders REGIF's help into the stage's output channel; `--HELP` is never handed to the Command as an ordinary argument. The claim appears to have been read off the *second*, command-level help check inside `AbstractCommand.Main` (AbstractCommand.cs:154-172), which is indeed only on the else-branch of `io.HasPipedInput` — but that check is unreachable for a help request because the executor-level one pre-empts it.

**Required fix:** Rewrite FR-1.51's second sentence to: "The check runs on every dispatch path, Pipeline stages included, because it is performed by the executor before the Command is constructed (OUT-OF-REPO: `src/Xcaciv.Command/CommandExecutor.cs:57-58`, reached from `PipelineExecutor.cs:136` via `CommandController.cs:278-281`)." Add a note that the shared Command base carries a second, non-piped-only help check (`AbstractCommand.cs:154-172`) that the executor check makes unreachable — a clone must not implement only the base-level one. Replace UC-4 E4 with the corresponding alternate flow ("Help inside a Pipeline stage renders help into that stage's Stage Channel; for the last stage it reaches the user, for an intermediate stage it is fed to the next Command as input"), and revisit AC-1.17's neighbourhood for an acceptance criterion covering it.

## 5. [MAJOR] §7.1 UC-1 error flow E2

**Problem:** "E2 — Plugin Directory does not exist as a path at all. A directory-not-found failure naming the path; same fatal handling as E1." This is not what the code does and it contradicts three other statements in the same document. `VerifiedSourceDirectories.VerifyDirectory` (VerifiedSourceDirectories.cs:66-75) gates on `FileSystem.Directory.Exists(filePath)`, and `AddDirectory` (:82-89) returns false without adding when that fails; `CommandController.AddPackageDirectory` / `CommandLoader.AddPackageDirectory` (CommandLoader.cs:26-30) discard the return value. The Crawler's `DirectoryNotFoundException` (Crawler.cs:174) is therefore never reached for a missing Plugin Directory — the directory never gets into the list. `CommandLoader.LoadCommands` (:42-45) then throws `NoPluginsFoundException`, which Loop.cs:45-50 catches, so the user gets the friendly guidance and a working Session, not a fatal exit 1. The document says exactly this elsewhere: GR-49 ("fails verification — because it does not exist ... shall be silently dropped"), FR-1.84/FR-1.100 and AC-1.1.

**Required fix:** Merge E2 into E3: "E2 — Plugin Directory does not exist, is not a directory, or fails the Verified Directory rule. Silently ignored at the add step: no Output, no Status line, no Diagnostic trace; the eventual symptom is A1." Move the directory-not-found condition of FR-1.80 to a separate note stating it is reachable only if a directory passes verification and then disappears before the crawl (a race), and is not reachable on the Shell's own startup path.

## 7. [MINOR] §7.1 FR-1.29 (bug-for-bug decision 15) — no AC-1.x pins it

**Problem:** FR-1.29 states that a final Pipeline stage producing more than 10,000 Outputs stalls forever under the default Block back-pressure policy, and silently loses Output under a drop policy, because the last stage is given its own Stage Channel and the channel is drained only after every stage has completed. §7.1 lists this as a bug-for-bug decision the clone team must consciously keep or fix, but no acceptance criterion pins it: AC-1.17 covers a two-stage Pipeline and AC-1.19 a quoted pipe, and neither exercises the bound. The consequence is an unrecoverable hang of the Session, which is exactly the kind of behaviour a clone will "fix" by draining incrementally, changing observable ordering along with it.

**Required fix:** Add an acceptance criterion beside AC-1.17: "AC-1.x — QUIRK, decide keep or fix. Given a Pipeline whose final stage emits 10,001 Outputs and the Shell's stock Pipeline configuration (channel capacity 10,000, Block policy, all timeouts 0), when the line is submitted, then the Pipeline never completes, no Output reaches the terminal, and the Session cannot be recovered without killing the process; and given a drop policy configured by an embedder, then the run completes with Outputs silently missing. INFERRED — no test in either tree exercises it." Mark it INFERRED, as FR-1.29 is.

## 8. [MINOR] §7.1 FR-1.72 (bug-for-bug decision 22) — no AC-1.x pins it

**Problem:** FR-1.72 records that Direct invocation of the built-in pattern filter echoes the wrong token: it tests every token after the first against the expression but appends the token at position 1 once per match, so `REGIF a xa ba` emits `xa xa` rather than `xa ba`. This is a concrete, observable, trivially testable output defect in a Built-in Command that every clone must supply, and §7.1 lists it as a keep-or-fix decision — but no acceptance criterion covers it. AC-1.5 and AC-4.3 only assert that `REGIF` is registered; AC-1.17 exercises it only on the piped path, where the logic is different and correct. Its sibling quirk (FR-1.67, doubled delimiters on an unresolved variable reference) is pinned by AC-1.14, so the omission is inconsistent as well as material.

**Required fix:** Add, next to AC-1.14: "AC-1.x — QUIRK, decide keep or fix. Given the built-in pattern filter, when the user types `REGIF a xa ba` with no upstream Pipeline stage, then the Output is exactly `xa xa` — the token at position 1 repeated once per match — not `xa ba`; and when the same expression and subjects arrive as Pipeline chunks, then each matching chunk is echoed correctly. INFERRED: derived by evaluating the echoing logic by hand."

## 11. [MINOR] §7.1 FR-1.30

**Problem:** "Negative values, or a buffer size of 0 or less, are rejected as invalid configuration." is stated as active behaviour, but the validator is dormant. `PipelineConfiguration.Validate()` (PipelineConfiguration.cs:55-71) is never invoked anywhere in the framework: `CommandController.PipelineConfig`'s setter (CommandController.cs:150-154) only null-checks, and `PipelineExecutor.Configuration` (PipelineExecutor.cs:14) is a plain auto-property. A repo-wide grep for `.Validate()` in the framework tree returns exactly one call site, `CommandFactory.cs:34`, and that is for `AssemblySecurityConfiguration`, not for the pipeline configuration. A `MaxChannelQueueSize` of 0 would therefore surface as an `ArgumentOutOfRangeException` from `Channel.CreateBounded` (PipelineExecutor.cs:97), not as a configuration rejection.

**Required fix:** Reword to: "A validation routine exists that would reject negative values and a buffer size of 0 or less, but nothing calls it — neither the controller's configuration setter nor the executor — so an invalid value reaches the channel factory and fails there instead. OUT-OF-REPO only." Cite `PipelineConfiguration.cs:55-71` alongside `CommandController.cs:150-154` and `PipelineExecutor.cs:14,97`.

QUIRK — documentation-only promise." Cite the three reader methods plus the three attribute doc comments.
